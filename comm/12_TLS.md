# 12. TLS — 通信路を暗号化し、相手を確かめる

> **この章で扱う問い.**
> 11 章までで、機器はサーバと TCP の接続を張り、バイトの列を送受信できるようになった。しかし、そのバイトは経路の途中の機器から読めるし、書き換えることもできる。この章では、TCP の上に TLS を重ねて機器とサーバの間の通信を守る仕組みと、それをマイコンに組み込む方法を見る。
>
> この章では次の 3 つの問いに答える。
>
> 1. TLS は何を守り、何を守らないのか。守るために、データをどんな形にして送るのか。
> 2. 鍵を決めて相手を確かめる手順は、何をやり取りし、接続までにどれだけの時間がかかるのか。
> 3. RAM の少ないマイコンに TLS を載せるとき、RAM と時間をどう見積もり、ライブラリをどう呼ぶのか。
>
> 答えの道具は、レコードが足すバイト数の計算、往復の数と計算の時間を足し合わせる接続時間の式、そして証明書を 1 枚ずつたどる検証の手順である。

## 1. TLS が守るもの

07 章の温湿度センサが、測定値をサーバへ送る場面を考える。TCP の接続の上を流れるバイトは、そのままの形で、アクセスポイント・家庭のルータ・インターネットの中のいくつものルータを通る。経路の途中にいる者は、次の 3 つのことができる。

- **盗聴**: 流れるバイトを読む。測定値だけでなく、サーバにログインするためのパスワードも読まれる。
- **改ざん**: 流れるバイトを書き換える。サーバから機器への命令（「鍵を開ける」など）を書き換えられると、被害が大きい。CRC（03 章 5 節）は偶然の誤りに気づくためのもので、書き換えた者は CRC も計算し直せるので役に立たない。
- **なりすまし**: 相手のふりをする。DNS の答え（08 章 4 節）や ARP の応答（08 章 2 節）を偽れば、機器を本物のサーバではなく偽のサーバに接続させられる。

```fig
e12_threats
```

**TLS**（Transport Layer Security）は、トランスポート層の TCP とアプリケーション層の間に入り（07 章 1 節）、通信の両端の間をこの 3 つから守るプロトコルである。いま使われている版は TLS 1.2（RFC 5246）と TLS 1.3（RFC 8446）で、この章では主に TLS 1.3 を扱う。TLS が与える性質は次の 3 つである。

- **機密性**: 両端以外の者には中身が読めない（盗聴への対策）。
- **完全性**: 途中で書き換えられたら、受け手が必ず気づく（改ざんへの対策）。
- **認証**（相手の確認）: 通信の相手が、名乗っているとおりの相手であることを確かめる（なりすましへの対策）。ここでは一般的な意味で使う。09 章 3 節の、Wi-Fi の「認証」という名前の手続きとは別のものである。

Wi-Fi の WPA2（09 章 3 節）も暗号化するが、守るのは機器と AP の間の電波の区間だけで、AP から先は元の形に戻る。TLS は、機器の TLS からサーバの TLS までを、途中に何台のルータがあっても通して守る。HTTPS（ポート番号 443）や MQTT over TLS（8883。07 章 4 節）は、TLS の上で HTTP や MQTT を動かしたものである。

TLS が守らないものもある。

```fig
e12_scope
```

- 暗号化されるのは、TLS が送るバイトの中身だけである。IP と TCP のヘッダ（アドレス・ポート番号）と、送った時刻・バイト数は途中から読めるので、どの機器がどのサーバと、いつ、どれだけ通信したかは分かる。
- 接続の前の DNS の問い合わせと、ハンドシェイクの最初に送る接続先の名前（3 節の SNI）は暗号化されない。
- 両端の機器の中は守らない。機器のフラッシュメモリに置いた鍵（[IoT セキュリティシリーズ 06 章](../iotsec/06_鍵の保管.md#鍵はどこに置けるか)）やサーバの中のデータは、別の方法で守る。
- 通信を止めることは防げない。途中の者がパケットを捨てれば、TLS は届かないことや壊れていたことに気づけるだけである。

この章では、TLS の仕組みと、それを小さな機器に組み込む方法を扱う。TLS を正しく使うための確認の項目と、よくある失敗（検証を止めてしまうなど）は、[IoT セキュリティシリーズ 16 章](../iotsec/16_通信セキュリティ.md#tls-の正しい使い方) にまとめてある。

## 2. 2 段構え — ハンドシェイクとレコード

TLS の仕事は、2 つの段に分かれている。

1. **ハンドシェイク**: TCP の接続ができた直後に、両端が使う暗号の方式を決め、この接続だけで使う鍵を作り、クライアント（接続を始めた側。このシリーズでは多くの場合、機器）がサーバを確かめる。TCP の 3 ウェイハンドシェイク（10 章 1 節）とは別の、その後に行う TLS の手続きである。
2. **レコード**: ハンドシェイクの後は、送るデータを、ハンドシェイクで作った鍵で守り、レコードと呼ぶまとまりに包んで送る。

ハンドシェイクで作り、両端だけが持つ鍵を**共通鍵**（**セッション鍵**）という。暗号化と復号に同じ鍵を使うので、共通鍵と呼ぶ。2 段に分けるのは、計算の重さが違うからである。相手を確かめ、盗聴されても知られない鍵を作るには公開鍵暗号の計算が要り（3 節）、マイコンのソフトウェアでは 1 回に数十 ms〜数百 ms かかることがある（代表値）。これを接続の最初に数回だけ行い、その後のデータはすべて、ずっと速い共通鍵の暗号で守る。


### レコードの形

TCP が運ぶのは区切りのないバイトの列なので（07 章 4 節）、TLS は 03 章 4 節と同じく、長さを先に書いて区切る。レコードは 5 バイトのヘッダとペイロードからなる。ヘッダは、ペイロードの種類（1 バイト。22 はハンドシェイク、23 はアプリケーションのデータ、21 は**アラート**（誤りや終わりを相手に知らせる短いメッセージ））、版（2 バイト。互換のために残された欄で、TLS 1.3 でも TLS 1.2 を表す 0x0303 を入れる）、長さフィールド（2 バイト）である。1 つのレコードに入れられる平文（暗号化する前のデータ）は、最大 $`2^{14} = 16384`$ バイトである。

ペイロードは **AEAD**（Authenticated Encryption with Associated Data）で守る。AEAD は暗号化と改ざんの検出を 1 回の操作で行う方式で、TLS 1.3 では AES-GCM と ChaCha20-Poly1305 などを使う。送り手は、鍵・**ノンス**（同じ鍵で二度と使わない値）・追加のデータ（暗号化はしないが、書き換えられたら気づきたいもの）・平文から、暗号文と 16 バイトの**タグ**を作る。受け手は同じ計算をして、1 ビットでも違えばタグが合わないので、そのレコードを捨てて接続を切る（詳しくは [PSA シリーズ 08 章](../psa/08_AEAD.md#aead-とは何か)）。

TLS 1.3 は、ノンスをレコードに入れて送らない。両端がレコードを 0, 1, 2, … と数えた通し番号と、ハンドシェイクで作った値との XOR をノンスにするので、同じ鍵でノンスが重なることはない（[PSA シリーズ 08 章 4 節](../psa/08_AEAD.md#ノンスの管理-aead-で唯一難しいところ)の、カウンタをノンスにする方法）。追加のデータにはレコードのヘッダの 5 バイトを使うので、ヘッダの長さを書き換えてもタグが合わなくなる。

```fig
e12_record
```

1 つのレコードで TLS が足すバイト（オーバーヘッド。07 章 5 節）を数える。

**方針**: 線の上に出るレコードのバイト数から、送ったデータのバイト数を引く。

**導出**: TLS 1.3 では、暗号化する前にデータの後ろに本当の種類の 1 バイトを付ける（外のヘッダの種類はどのレコードでも 23 にして、中身の種類を隠す）。暗号化しても長さは変わらず、後ろに 16 バイトのタグが、前に 5 バイトのヘッダが付く。したがって、TLS 1.3 が 1 つのレコードに足すのは $`5 + 1 + 16 = 22`$ バイトである。TLS 1.2 で AES-GCM を使う場合は、種類の 1 バイトは付けないが、ノンスの一部の 8 バイトをレコードごとに送るので、$`5 + 8 + 16 = 29`$ バイトになる。n バイトを 1 回で送ると、16384 バイトずつのレコード $`k = \lceil n / 16384 \rceil`$ 個に分かれるので、TLS 1.3 で線の上に出るのは $`n + 22k`$ バイトである ∎

OpenSSL 同士で確かめると、1 バイトを書けば 23 バイト、16384 バイトなら 1 つのレコードで 16406 バイトになり、16385 バイトでは 2 つのレコードに分かれて 44 バイトが足された。07 章 5 節の例（20 バイトの測定値を MQTT・TCP・IPv4・Ethernet で送ると 112 バイト）に TLS 1.3 を足すと 134 バイト、効率は 14.9 % になる。なお TLS 1.3 は、長さを隠すために平文の後ろに 0 を詰めることも許しており、詰め方は実装によって違う。Mbed TLS 3.6 の既定の設定では、暗号化する前の長さを 16 の倍数にそろえるので、21 バイトを書くと線の上では 53 バイトになった（詰めなければ 43 バイト）。

受け手は、1 つのレコードを最後のタグまで受け取らないと、タグを確かめられず、中身を渡せない。満杯のレコードは線の上で 16406 バイトあり、MSS 1460 バイト（07 章 6 節）のセグメント 12 個に分かれて届くので、受け手はそれを全部ためておく領域を持たなければならない（6 節）。

送る側では、1 回の書き込みごとに少なくとも 1 つのレコードができる。小さなデータを何回にも分けて書くと、そのたびに 22 バイトと、TCP より下の層のヘッダ（07 章 6 節で数えた、1 つのセグメントあたり 78 バイト）が足される。

```fig
e12_writes
```

20 バイトずつ 5 回書くと線の上で 600 バイト（効率 16.7 %）、まとめて 100 バイトを 1 回で書くと 200 バイト（効率 50 %）になる。送るものは 1 つのメッセージに組み立ててから、1 回で書く。

## 3. TLS 1.3 のハンドシェイク — 1 往復で鍵を決める

ハンドシェイクは、暗号の 3 つの道具を組み合わせる。数学はほかのシリーズで扱っているので、ここでは役割だけを書く。

- **鍵交換（ECDHE）**: 両端がそれぞれ、その接続だけで使う一時的な鍵の組（秘密鍵と公開鍵）を作り、公開鍵を送り合う。自分の秘密鍵と相手の公開鍵から計算すると、両端で同じ値（共有の秘密）が得られるが、公開鍵だけを見た盗聴者には計算できない（[PSA シリーズ 11 章](../psa/11_鍵合意と公開鍵暗号.md#鍵合意とは何か)）。一時的な秘密鍵は使い終わったら捨てるので、サーバが長く使う鍵が後で漏れても、記録された過去の通信は読めない。この性質を前方秘匿性という（[PSA シリーズ 11 章 5 節](../psa/11_鍵合意と公開鍵暗号.md#一時鍵と前方秘匿性)）。
- **署名**: 秘密鍵で作り、公開鍵で確かめる値。確かめに成功すれば、その秘密鍵の持ち主がその内容に署名したと分かる（[PSA シリーズ 09 章](../psa/09_署名と検証.md#署名とは何か-mac-との違い)）。
- **ハッシュ**: 長いデータから作る短い値（SHA-256 なら 32 バイト）。ハンドシェイクでは、それまでのメッセージ全部のハッシュを、署名や確認の対象にする（[PSA シリーズ 05 章](../psa/05_乱数とハッシュ.md#この-2-つだけは鍵が要らない)）。

鍵交換だけでは、相手が本物かどうかは分からない。途中の者が両端に自分の公開鍵を送れば、両端それぞれと別々に鍵を共有できてしまう。このように、途中に割り込んで両端に相手のふりをする攻撃を**中間者攻撃**という（[暗号シリーズ 17 章 1 節](../crypto/17_DHと楕円曲線暗号.md#ディフィー-ヘルマン鍵交換-dh)）。そこでサーバは、自分の公開鍵を記した証明書（4 節）を送り、その公開鍵に対応する秘密鍵で、ハンドシェイクの内容に署名する。TLS 1.3 の手順を図に示す。

```fig
e12_hs13
```

1. **ClientHello**: クライアントの乱数、使える**暗号スイート**（AEAD とハッシュの組。例 TLS_AES_128_GCM_SHA256）の一覧、鍵交換の公開鍵（X25519 という方式なら 32 バイト）、受け付ける署名の方式、接続したいサーバの名前（**SNI**、Server Name Indication。RFC 6066）を送る。1 つのアドレスで複数の名前のサービスを動かすサーバは、SNI を見て返す証明書を選ぶ。ClientHello は暗号化されないので、SNI は途中から読める。
2. **ServerHello**: サーバが選んだ暗号スイートと、サーバの鍵交換の公開鍵を返す。ここで両端は共有の秘密を計算し、そこからハンドシェイク用の鍵を作る（鍵の作り方は [PSA シリーズ 11 章 3 節](../psa/11_鍵合意と公開鍵暗号.md#典型コード-ecdh-+-hkdf-でセッション鍵)）。これより後のメッセージは、すべて暗号化される（図の { } の中）。
3. サーバは続けて、**EncryptedExtensions**（そのほかの取り決め）、**Certificate**（証明書のチェーン。4 節）、**CertificateVerify**（ここまでのメッセージ全部のハッシュへの、証明書の秘密鍵による署名）、**Finished**（ここまでのメッセージ全部から、ハンドシェイク用の鍵で計算した確認の値）を、まとめて送る。
4. クライアントは、証明書を検証し、CertificateVerify の署名を証明書の公開鍵で確かめ、Finished を確かめる。署名が合えば、鍵交換の公開鍵を送ってきたのは証明書の持ち主で、途中ですり替えられていないと分かる。最後に自分の Finished を送り、続けてアプリケーションのデータを送れる。

OpenSSL 同士で、図と同じ楕円曲線（ECDSA）の証明書を使って測ると、ClientHello は 250 バイト、サーバがまとめて送ったのは 1314 バイト（うち Certificate のレコードが 978 バイト）、クライアントの Finished などが 80 バイトだった（サーバとクライアントの送信には、途中の機器との互換のために送る、中身のない ChangeCipherSpec のレコードが 1 つずつ含まれる。RFC 8446 付録 D.4）。サーバがクライアントの送った鍵交換の方式（曲線）を使えない場合は、別の方式で送り直すよう求め（HelloRetryRequest）、1 往復増える。機器は、つなぐサーバが使う方式の公開鍵を最初から送るようにしておく。

TLS 1.2 と比べる。

```fig
e12_hs12
```

TLS 1.2 では、サーバは鍵交換の公開鍵を証明書の後の ServerKeyExchange で送り、クライアントはそれを受け取ってから ClientKeyExchange で送る。クライアントの鍵交換の値がサーバに届くのは 2 回目の送信なので、アプリケーションのデータを送れるのは 2 往復の後になる。証明書も暗号化されずに流れる。

接続にかかる時間を求める。

**方針**: クライアントが TCP の接続を始めた時刻を 0 として、アプリケーションのデータを送れる時刻までを、往復の時間・計算の時間・送る時間に分けて足し合わせる。

**導出**: 往復時間を R、クライアントの公開鍵の計算の時間の合計を $`T_\mathrm{c}`$、ハンドシェイクのメッセージを送り出すのにかかる時間の合計（バイト数 × 8 ÷ ビットレート）を $`T_\mathrm{x}`$ とする。サーバの計算は速いとして無視する。TCP の 3 ウェイハンドシェイクで、クライアントは時刻 R に SYN+ACK を受け取り、すぐに ClientHello を送る。ClientHello は片道 R/2 でサーバに届き、サーバのまとめた送信は片道 R/2 で戻るので、計算と送る時間を除けば、受け取り終えるのは時刻 2R である。クライアントは検証と計算をして Finished を送り、続けてデータを送れる。計算と送る時間を足して

$$
T_{1.3} = 2R + T_\mathrm{c} + T_\mathrm{x}
$$

となる。TLS 1.2 では、ClientKeyExchange と Finished がサーバに届き、サーバの Finished が戻るまでもう 1 往復待つので、$`T_{1.2} = 3R + T_\mathrm{c} + T_\mathrm{x}`$ である ∎

クライアントの計算は、鍵交換 1 回（鍵の組を作り、共有の秘密を計算する）と、署名の確認（CertificateVerify の 1 回と、チェーンの証明書の数 d 回。4 節）である。鍵交換の時間を $`t_\mathrm{kx}`$、署名の確認 1 回の時間を $`t_\mathrm{v}`$ とすると、$`T_\mathrm{c} = t_\mathrm{kx} + (1 + d)\,t_\mathrm{v}`$ となる。PC で Mbed TLS 3.6.5 を測ると（曲線 P-256）、鍵交換が約 0.8 ms、署名の確認 1 回が約 0.9 ms で、ほぼ同じ重さだった。マイコンでは、クロック・実装・暗号の計算をする回路（**暗号エンジン**）の有無によって、1 回が数 ms から数百 ms まで変わる（代表値）。

**例**: R = 100 ms、d = 2（サーバの証明書と中間の CA の証明書）、ビットレート 1 Mbps とする。$`T_\mathrm{x}`$ は、測ったバイト数（ClientHello 250 + サーバ 1314）を送る時間で約 13 ms である。ソフトウェアで計算する遅いマイコンを仮定して $`t_\mathrm{kx}`$ = 400 ms、$`t_\mathrm{v}`$ = 450 ms とすると、$`T_\mathrm{c} = 400 + 3 \times 450 = 1750`$ ms で、$`T_{1.3} \approx 200 + 1750 + 13 = 1963`$ ms、つまり約 1.96 s、$`T_{1.2}`$ は約 2.06 s になる。暗号エンジンを仮定して $`t_\mathrm{kx}`$ = 10 ms、$`t_\mathrm{v}`$ = 12 ms とすると、$`T_\mathrm{c}`$ = 46 ms で、$`T_{1.3}`$ は約 0.26 s、$`T_{1.2}`$ は約 0.36 s になる。

```fig
e12_conntime
```

計算の遅いマイコンでは時間の大部分が計算で、TLS 1.3 で 1 往復減らしても 5 % ほどしか縮まない。計算が速ければ往復の時間が大部分になり、1 往復の差が効く。計算そのものを減らす方法は 6 節で扱う。

## 4. 証明書で相手を確かめる

**証明書**は、公開鍵と、その持ち主の名前などを組にして、**認証局**（**CA**、Certificate Authority）が署名したデータである。インターネットで使う証明書の形は X.509（RFC 5280）で決まっている。3 節の CertificateVerify の署名を確かめる公開鍵は、サーバの証明書に入っている。

```fig
e12_cert
```

発行者と主体は、署名した CA の名前と持ち主の名前である。有効期間（notBefore から notAfter まで）の外では使えない。拡張の subjectAltName（SAN）には、この証明書を使ってよいサーバの名前を並べ、basicConstraints が CA:TRUE の証明書は、ほかの証明書に署名してよい CA の証明書である。最後の署名は、それより前の内容に対する、発行者の秘密鍵による署名である。例として作った証明書は、楕円曲線 P-256 の鍵で 484 バイト、RSA-2048 の鍵で 880 バイトだった。公開の CA が発行する実際の証明書は拡張が多く、1 枚 1〜2 KB 程度のことが多い（代表値）。

CA も、自分の証明書に、さらに上の CA の署名をもらう。こうしてつながる証明書の列を**証明書チェーン**という。いちばん上の CA の証明書は、自分で自分に署名したもので、**ルート証明書**という。機器は、信じるルート証明書を前もってフラッシュメモリに入れておく。検証の出発点として信じるこの証明書を**トラストアンカー**という。サーバは、自分の証明書と中間の CA の証明書を送り、ルート証明書はふつう送らない。

クライアントが行う**証明書の検証**は、次の手順である。

```fig
e12_verify
```

1. **署名**: 各証明書の署名を、1 つ上の証明書の公開鍵で確かめる。いちばん上の中間の CA の証明書は、トラストアンカーの公開鍵で確かめる。
2. **有効期間**: いまの時刻が、各証明書の有効期間の中にあるかを確かめる。
3. **CA であること**: 署名した側の証明書が CA:TRUE かを確かめる。
4. **トラストアンカー**: チェーンの上端が、機器の持つトラストアンカーにつながるかを確かめる。
5. **ホスト名**: いちばん下のサーバの証明書の SAN に、接続しようとした名前があるかを確かめる。

これに 3 節の CertificateVerify の確認を合わせて、はじめて「接続した相手は、この名前の正しい持ち主である」と言える。図の右に示したように、どの段も別の攻撃を防ぐので、1 つでも省くと穴になる。とくにホスト名の確認を省くと、攻撃者が正規の CA から自分の名前で正しく受け取った証明書が通ってしまう。7 節の機器側のプログラム（Mbed TLS 3.6.5）で、ループバックの OpenSSL のサーバにわざと合わない証明書を出させて確かめると、どの場合も接続は失敗し、理由のビットとして、ホスト名の違いは 0x04、知らない CA と署名の不一致は 0x08、期限切れは 0x01、有効期間の開始前は 0x200 が得られた。

有効期間を確かめるには、機器がいまの日付を知っていなければならない。電池でバックアップした時計（RTC）を持たず、電源を入れるたびに 1970 年や 2000 年から時計が始まる機器では、すべての証明書が「有効期間の開始前」になり、接続できない。そこで TLS の前に、ネットワークの先の時刻のサーバに問い合わせる SNTP（[15 章 1 節](15_クラウドとつなぎ続ける.md#時刻を合わせる-sntp)）で時刻を合わせる。SNTP の答えそのものは守られていないので、時刻を偽られる危険とその対策（ファームウェアを作った日時を下限にするなど）は [IoT セキュリティシリーズ 16 章 2 節](../iotsec/16_通信セキュリティ.md#tls-の正しい使い方) を見よ。

有効期間の途中で秘密鍵が漏れた証明書は、CA が取り消す。これを**失効**という。失効した証明書の一覧（CRL）を取り寄せるか、問い合わせ用のサーバ（OCSP）に尋ねれば分かるが、機器には一覧を置く RAM や、もう 1 つ接続する余裕がないことが多い。サーバが OCSP の答えを添えて送る方法（OCSP stapling）もある。機器では、有効期間を短くする、サーバの側で拒否する一覧を持つ、などで補うことが多い（[IoT セキュリティシリーズ 12 章 4 節](../iotsec/12_プロビジョニング.md#デバイス-id-の設計)）。トラストアンカーには、自分のサーバが使う CA だけを入れる。入れるほど、攻撃者が利用できる CA が増えるからである。ただし、サーバの CA が変わる日に備えて、トラストアンカーを更新できるようにしておく。

## 5. 機器も名乗る — クライアント証明書と PSK

ここまでは、機器がサーバを確かめた。サーバの側も、つないできたのが正規の機器か、どの機器かを知る必要がある。正規の機器からのデータだけを受け付け、機器ごとに使えるトピック（13 章）などを決めるためである。方法は 3 つある。TLS の接続の上でパスワードやトークンを送る（13 章の MQTT の接続の要求など）、クライアント証明書を使う、PSK を使う、である。後の 2 つは TLS の中で行う。

機器が自分の証明書（**クライアント証明書**）と秘密鍵を持ち、サーバと同じ方法で名乗ることを**相互認証**という。TLS 1.3 では、サーバがまとめた送信に **CertificateRequest** を加え、機器は Finished の前に自分の Certificate と CertificateVerify を送る。

```fig
e12_mutual
```

往復は増えない。機器の仕事は、署名 1 回と、自分の証明書チェーンを送ることが増えるだけで、例の証明書では機器の送信が 80 バイトから 1139 バイトになった。サーバは機器の Finished を受け取ってから機器の証明書の判断を伝えるので、断られた機器の側では、ハンドシェイクは成功したように見え、最初の読み出しでアラートを受けて失敗が分かる（Mbed TLS で、証明書を出さずに接続して確かめた）。最初の応答を受け取るまでは、接続できたと判断しない。

機器の秘密鍵は、相互認証のかなめである。機器の中で作って外に出さないこと、読み出しから守ることは [IoT セキュリティシリーズ 06 章](../iotsec/06_鍵の保管.md#鍵はどこに置けるか) と [12 章](../iotsec/12_プロビジョニング.md#3-つの方式) が詳しい。全部の機器が同じ鍵を使うと、1 台から取り出された鍵で全部の機器になりすませるので、鍵と証明書は 1 台ずつ別にする（[IoT セキュリティシリーズ 12 章 6 節](../iotsec/12_プロビジョニング.md#全台共通鍵の何が問題か)）。

**PSK**（Pre-Shared Key）は、機器とサーバが前もって同じ秘密の値とその名前（ID）を持っておく方法である（09 章 3 節の WPA2-PSK と同じく、前もって分け合った鍵という意味）。機器は ClientHello で PSK の ID を知らせ、両端は PSK から鍵を作る。正しい PSK を持たない者は Finished の値を計算できないので、両端が互いを確かめたことになる。証明書の解析と署名の計算、証明書を運ぶバイトがいらない。TLS 1.3 には使い方が 2 つある（RFC 8446 4.2.9 節）。PSK だけで鍵を作る psk_ke は公開鍵の計算がまったくいらないが、PSK が後で漏れると、記録された過去の通信が読める（前方秘匿性がない）。PSK に鍵交換（ECDHE）を組み合わせる psk_dhe_ke は、鍵交換 1 回分の計算で前方秘匿性を保つ。Mbed TLS の機器と OpenSSL のサーバで psk_dhe_ke を試すと、ハンドシェイクで機器が送ったのは 333 バイト、サーバが送ったのは 225 バイトだった（証明書を使ったときは 532 バイトと 1298 バイト）。

```fig
e12_auth
```

その代わり、PSK ではサーバが全部の機器の PSK を持たなければならず、サーバから一覧が漏れれば、全部の機器になりすまされる。証明書なら、サーバが持つのは CA の証明書だけで、機器の公開鍵は漏れても困らない。どの方法でも、機器に資格情報を入れる手順（工場で入れるか、最初の起動で入れるか）が要る。これは [15 章 5 節](15_クラウドとつなぎ続ける.md#機器の名前と資格情報) と [IoT セキュリティシリーズ 12 章](../iotsec/12_プロビジョニング.md#何を入れるのか) で扱う。

## 6. RAM と時間を見積もる

TLS が使う RAM のうち、いちばん大きいのは、レコードを入れておく領域（バッファ）である。

**方針**: 受け手は、レコードを最後のタグまで受け取らないと確かめられないこと（2 節）から、受信のバッファの大きさの下限を求める。

**導出**: 受け手は、1 つのレコードを全部受け取ってはじめて、タグを確かめて中身を取り出せる。したがって受信のバッファには、相手が送りうる最大のレコードが入らなければならない。平文は最大 16384 バイトで、TLS 1.3 は暗号化した後のペイロードを 16384 + 256 バイトまで許すので（RFC 8446 5.2 節）、何も取り決めなければ、ヘッダを含めて $`5 + 16384 + 256 = 16645`$ バイトまで受けられるようにしておく。一方、送るレコードの大きさは自分で決められるので、送信のバッファには、自分が送る最大のレコード（ハンドシェイクのメッセージを含む）が入ればよい ∎

Mbed TLS では、受信と送信のバッファに入れる平文の大きさを、設定の MBEDTLS_SSL_IN_CONTENT_LEN と MBEDTLS_SSL_OUT_CONTENT_LEN で決める。既定はどちらも 16384 で、3.6.5 では 1 つのバッファが 16765 バイトになった（ヘッダや暗号の分の 381 バイトを足した大きさ）。7 節のプログラムで、TLS 1.3 のハンドシェイクの間に使ったヒープの最大を PC で測った。

```fig
e12_ram
```

既定の 58.1 KB に対して、送信を 2048 バイトにすると 34.9 KB、受信も 4096 バイトにすると 22.9 KB になった。その他には、鍵交換の計算や証明書の解析のように、ハンドシェイクの間だけ使う領域も含まれる。既定の設定でそれが大きいのは、鍵交換の値を作るときに、送信のバッファの空きと同じ大きさの一時的な領域を使うためである（3.6.5 の場合）。PC は 64 ビットなので、マイコンではバッファ以外の部分はもう少し小さくなる。ほかに、関数の中の変数を置くタスクのスタック（RAM の領域。プロトコルスタックとは別のもの）も要る（この試験のプログラム全体で約 12 KB だった。実機で測って決める）。

受信のバッファを小さくできるのは、相手に大きなレコードを送らせない取り決めができたときだけである。**max_fragment_length**（RFC 6066）は、クライアントが ClientHello で「レコードの平文を 512・1024・2048・4096 バイトのどれか以下にしてほしい」と求める拡張で、サーバが同じ値を返せば取り決めが成り立つ（Mbed TLS では、受信と送信のバッファの小さいほう以下の値しか設定できない）。受信を 4096 バイトにした Mbed TLS で確かめると、ハンドシェイク（いちばん大きいのはペイロード 973 バイトの Certificate）は通ったが、サーバが 10001 バイトを 1 つのレコードで返すと接続が切れた。TLS 1.2 で max_fragment_length を 2048 バイトに取り決めると、サーバは 2048 バイトずつのレコードで返し、受け取れた。試した Mbed TLS 3.6.5 では、TLS 1.3 の接続でこの拡張を使うと、サーバが応じた時点でハンドシェイクが失敗した。TLS 1.3 には、上限を 1 バイト単位で伝えられる record_size_limit（RFC 8449）という拡張もある（Mbed TLS 3.6 では TLS 1.3 だけで使え、既定では無効）。どの方法も、サーバが対応していることを確かめてから使う。

時間を減らすには、計算を速くする（暗号エンジン）か、計算と往復そのものを減らす。後者の仕組みが**セッションの再開**で、前の接続で作った秘密を覚えておき、次の接続で使って、証明書の送付と検証を省く。TLS 1.3 では、ハンドシェイクの後にサーバが NewSessionTicket（チケット）を送る。チケットはクライアントには中身の分からない値で、次の接続でクライアントはそれを ClientHello に入れ、前の接続から作った PSK（5 節）として使う。サーバは Certificate と CertificateVerify を送らないので、クライアントの署名の確認は 0 回になる。psk_dhe_ke なら鍵交換 1 回は残り、往復の数は 1 のままである。

```fig
e12_resume
```

OpenSSL 同士で測ると、再開したときのサーバのまとめた送信は 1314 バイトから 241 バイトに減った。チケットの寿命はサーバが決め、最長 7 日（604800 秒。RFC 8446 4.6.1 節）である。機器はチケットを RAM に覚えておく。眠る間に電源が切れる機器では、チケットとそれに対応する秘密を守れる場所に保存するかを決める（漏れれば、その期間はなりすましに使われうる）。TLS 1.3 には、再開の ClientHello と一緒にデータを送る 0-RTT もあるが、そのデータは途中の者に送り直される（リプレイ）おそれがあり、使い方に注意が要る（[IoT セキュリティシリーズ 16 章 3 節](../iotsec/16_通信セキュリティ.md#リソース制約への対応)）。TLS 1.2 では、セッション ID かセッションチケット（RFC 5077）で再開すると、鍵交換も署名もない 1 往復の手順になる（OpenSSL 同士で測ると、サーバの送信は 141 バイトだった）。

接続にかかる時間は、そのまま電荷（01 章 5 節）になる。データを送るたびに数秒かかる接続をし直すか、接続を保ったまま送るか（[13 章 5 節](13_MQTT.md#接続を見張る-キープアライブとウィルメッセージ)）、まとめて送るか（[15 章 7 節](15_クラウドとつなぎ続ける.md#送り方を設計する-まとめて送るか-すぐ送るか)）は、この見積もりで決める。

## 7. Mbed TLS で組み込む

**Mbed TLS** は、組み込み機器向けの TLS と暗号のライブラリである（オープンソースで、Trusted Firmware のプロジェクトとして開発されている）。この節の関数名は Mbed TLS 3.x のもので、版によって細部が異なる。コードは 3.6.5 で、ループバックの OpenSSL のサーバ（TLS 1.3 と 1.2）に対して動かして確かめた。

```fig
e12_mbed
```

Mbed TLS は、自分では送受信しない。アプリケーションが、ソケット（11 章 1 節）でバイトの列を送る関数と受ける関数を渡し、Mbed TLS はレコードを送るとき・受けるときにそれを呼ぶ。lwIP（11 章 6 節）のような組み込み向けの TCP/IP スタックのソケット API を使う場合も、同じ形で書ける。

```c
/* Mbed TLS がレコードを送る・受けるときに呼ぶ。ctx はソケット（ノンブロッキング）を指す */
static int bio_send(void *ctx, const unsigned char *buf, size_t len)
{
    ssize_t n = send(*(int *)ctx, buf, len, 0);
    if (n >= 0)
        return (int)n;                        /* 一部だけ送れたときも、その数を返す */
    if (errno == EAGAIN || errno == EWOULDBLOCK)
        return MBEDTLS_ERR_SSL_WANT_WRITE;    /* 送信の空きができたら、もう一度呼ばれる */
    return MBEDTLS_ERR_NET_SEND_FAILED;
}

static int bio_recv(void *ctx, unsigned char *buf, size_t len)
{
    ssize_t n = recv(*(int *)ctx, buf, len, 0);
    if (n >= 0)
        return (int)n;                        /* 0 は、相手が TCP の接続を閉じたこと */
    if (errno == EAGAIN || errno == EWOULDBLOCK)
        return MBEDTLS_ERR_SSL_WANT_READ;     /* まだ届いていない */
    return MBEDTLS_ERR_NET_RECV_FAILED;
}
```

ノンブロッキングソケット（11 章 3 節）で、まだ送れない・まだ届いていない（EAGAIN）ときは、MBEDTLS_ERR_SSL_WANT_WRITE・WANT_READ を返す。Mbed TLS はこの値を、呼ばれた関数の戻り値としてそのままアプリケーションに返すので、アプリケーションはソケットが書ける・読めるようになるのを待って、同じ関数をもう一度呼ぶ。設定からハンドシェイクまでは次のようになる。

```c
struct tls {                              /* 1 つの接続に要るもの */
    mbedtls_ssl_context      ssl;
    mbedtls_ssl_config       conf;
    mbedtls_x509_crt         ca;          /* トラストアンカー（ルート証明書） */
    mbedtls_entropy_context  ent;
    mbedtls_ctr_drbg_context drbg;        /* 乱数を作る */
};

/* 接続済みのソケット *fd の上で、host のサーバと TLS のハンドシェイクを行う。成功なら 0 */
int tls_open(struct tls *t, int *fd, const char *host, const unsigned char *ca_pem, size_t ca_len)
{
    int r;
    mbedtls_ssl_init(&t->ssl);
    mbedtls_ssl_config_init(&t->conf);
    mbedtls_x509_crt_init(&t->ca);
    mbedtls_entropy_init(&t->ent);
    mbedtls_ctr_drbg_init(&t->drbg);
    if (psa_crypto_init() != PSA_SUCCESS)                                  /* TLS 1.3 は PSA の暗号を使う */
        return -1;
    if ((r = mbedtls_ctr_drbg_seed(&t->drbg, mbedtls_entropy_func, &t->ent, NULL, 0)) != 0
        || (r = mbedtls_x509_crt_parse(&t->ca, ca_pem, ca_len)) != 0      /* PEM なら ca_len は末尾の '\0' を含む */
        || (r = mbedtls_ssl_config_defaults(&t->conf, MBEDTLS_SSL_IS_CLIENT,
                    MBEDTLS_SSL_TRANSPORT_STREAM, MBEDTLS_SSL_PRESET_DEFAULT)) != 0)
        return r;
    mbedtls_ssl_conf_authmode(&t->conf, MBEDTLS_SSL_VERIFY_REQUIRED);     /* 検証に失敗したら接続しない */
    mbedtls_ssl_conf_ca_chain(&t->conf, &t->ca, NULL);
    mbedtls_ssl_conf_rng(&t->conf, mbedtls_ctr_drbg_random, &t->drbg);
    if ((r = mbedtls_ssl_setup(&t->ssl, &t->conf)) != 0
        || (r = mbedtls_ssl_set_hostname(&t->ssl, host)) != 0)            /* SNI と、証明書の名前の確認 */
        return r;
    mbedtls_ssl_set_bio(&t->ssl, fd, bio_send, bio_recv, NULL);
    while ((r = mbedtls_ssl_handshake(&t->ssl)) != 0) {
        if (r != MBEDTLS_ERR_SSL_WANT_READ && r != MBEDTLS_ERR_SSL_WANT_WRITE)
            return r;                         /* 証明書の検証の失敗は MBEDTLS_ERR_X509_CERT_VERIFY_FAILED */
        if (wait_socket(*fd, r == MBEDTLS_ERR_SSL_WANT_READ, 10000) <= 0)
            return MBEDTLS_ERR_SSL_TIMEOUT;   /* 10 秒待っても進まなければやめる */
    }
    return 0;
}
```

`wait_socket` は、ソケットが読める（または書ける）ようになるまで最大 10 秒待つ、この章で置いた関数で、試験では poll（11 章 3 節）で書いた。要点は次のとおりである。

- 乱数は、鍵やノンスのもとになる。mbedtls_entropy_func が集める源（ハードウェアの乱数の回路など）は、移植ごとに用意する（[PSA シリーズ 05 章 2 節](../psa/05_乱数とハッシュ.md#psageneraterandom-乱数)）。3.6 では TLS 1.3 の計算に PSA の暗号の関数を使うので、psa_crypto_init() を先に呼んでおく。
- MBEDTLS_SSL_VERIFY_REQUIRED は、4 節の検証に失敗したらハンドシェイクを失敗させる設定である。mbedtls_ssl_set_hostname() は、SNI に入れる名前と、ホスト名の確認に使う名前を決める。3.6.3 より前の版では、これを呼び忘れるとホスト名を確かめないまま接続した。3.6.3 からは、呼び忘れるとハンドシェイクが失敗する（CVE-2025-27809）。
- ハンドシェイクはライブラリの中の状態機械（05 章 1 節）で、届いたメッセージに応じて少しずつ進む。待ちきれなければタイムアウト（05 章 1 節）として失敗にする。失敗したら、MBEDTLS_ERR_X509_CERT_VERIFY_FAILED のときは mbedtls_ssl_get_verify_result() で 4 節の理由のビットを読んでログに残し、時刻が原因なら合わせ直す。それ以外は指数バックオフ（05 章 5 節）で間をあけてやり直す（[15 章 2 節](15_クラウドとつなぎ続ける.md#つながるまで待つ-再接続の方針)）。

データは mbedtls_ssl_write() と mbedtls_ssl_read() で送受信する。どちらも WANT_READ / WANT_WRITE を返したら、同じ引数でもう一度呼ぶ決まりである。mbedtls_ssl_write() は 1 つのレコードに入らない分を残し、送れたバイト数を返すことがあるので、残りを送り直す（11 章 2 節の部分送信と同じ扱い）。mbedtls_ssl_read() は、相手が close_notify のアラートで終えたら MBEDTLS_ERR_SSL_PEER_CLOSE_NOTIFY を、TCP が閉じられたら 0 を返す。終えるときは mbedtls_ssl_close_notify() で close_notify を送ってから TCP を閉じる。TLS 1.3 の再開（6 節）を使うには、mbedtls_ssl_conf_tls13_enable_signal_new_session_tickets() でチケットの受け取りを有効にし、読み出しの関数が MBEDTLS_ERR_SSL_RECEIVED_NEW_SESSION_TICKET を返したら mbedtls_ssl_get_session() で取り出して、次の接続で mbedtls_ssl_set_session() に渡す（3.6.5 では、有効にしないとチケットを捨てた）。

設定（mbedtls_config.h）では、6 節のバッファの大きさを決め、使わない暗号スイートや機能を外してフラッシュメモリを減らす。ソフトウェアで数百 ms かかる楕円曲線の計算は、1 回の関数の呼び出しの中で続くので、RTOS を使わずにイベントループ（05 章 2 節）で動かす機器では、その間ほかの処理が止まる。MBEDTLS_ECP_RESTARTABLE を有効にして mbedtls_ecp_set_max_ops() で 1 回の計算量に上限を設けると、ハンドシェイクの関数が途中で MBEDTLS_ERR_SSL_CRYPTO_IN_PROGRESS を返すので、ほかの仕事やウォッチドッグタイマ（05 章 6 節）への知らせをしてから、もう一度呼べる（3.6 では TLS 1.2 のクライアントの ECDHE-ECDSA に限られる）。暗号エンジンを持つマイコンでは、メーカーが用意する、Mbed TLS の計算を暗号エンジンに回す部品を使うと、3 節の $`T_\mathrm{c}`$ が大きく縮む。06 章 1 節の構成 (b) のように、AT コマンドで操作する無線モジュールを使う場合は、TLS はモジュールの中で動き、ホストはモジュールにトラストアンカーと資格情報を書き込む（方法は製品ごとに違う）。

## 8. まとめ

| 項目 | 内容 |
|---|---|
| TLS が守るもの | TCP の上で、両端の間の機密性（盗聴）・完全性（改ざん）・認証（なりすまし）。IP・TCP のヘッダ、通信の量と時刻、SNI・DNS、機器の中の鍵は守らない |
| 2 段構え | ハンドシェイク（公開鍵の計算で共通鍵を作り、相手を確かめる。接続の最初だけ）と、レコード（共通鍵の AEAD で 1 まとまりずつ守る） |
| レコード | ヘッダ 5 バイト（種類・版・長さ）+ ペイロード。平文は最大 16384 バイト。足すバイトは TLS 1.3 で 5 + 1 + 16 = 22、TLS 1.2 の AES-GCM で 5 + 8 + 16 = 29。書き込みはまとめる |
| TLS 1.3 のハンドシェイク | ClientHello（鍵交換の公開鍵・SNI）→ ServerHello・{EncryptedExtensions・Certificate・CertificateVerify・Finished} → {Finished} とデータ。1 往復。TLS 1.2 は 2 往復 |
| 接続にかかる時間 | $`T_{1.3} = 2R + T_\mathrm{c} + T_\mathrm{x}`$、$`T_{1.2} = 3R + T_\mathrm{c} + T_\mathrm{x}`$、$`T_\mathrm{c} = t_\mathrm{kx} + (1 + d)\,t_\mathrm{v}`$。遅いマイコンでは計算、速ければ往復が大部分 |
| 証明書の検証 | 各証明書の署名・有効期間・CA であること・トラストアンカーへのつながり・ホスト名を確かめ、CertificateVerify で秘密鍵の持ち主であることを確かめる。時刻が要る（SNTP）。失効の確認は機器では難しい |
| 機器を確かめる | クライアント証明書（相互認証。往復は増えず、署名 1 回が増える）、または PSK（証明書が要らず軽い。サーバが全機器の秘密を持つ。psk_ke は前方秘匿性がない） |
| RAM | 受信のバッファは相手の最大のレコード（約 16 KB）が要る。送信は小さくできる。受信を小さくするのは max_fragment_length などで取り決めたときだけ。Mbed TLS 3.6.5 で測ると 58.1 KB → 34.9 KB → 22.9 KB |
| 時間を減らす | 暗号エンジン、セッションの再開（証明書の送付と検証を省く。TLS 1.3 は 1 往復のまま）、接続を保つ・まとめて送る |
| Mbed TLS | ソケットの送受信を関数で渡す。VERIFY_REQUIRED と set_hostname を必ず設定し、WANT_READ / WANT_WRITE の間は待って同じ関数を呼び直す |
