Chapter 23

通信コードを検証する — ホストでのテスト・故障注入・キャプチャ

この章で扱う問い. これまでの章では、メッセージの区切り、受信のバッファ、状態機械と再送、各層のプロトコルを、ファームウェアのコードとして組み立ててきた。これらのコードは、メッセージが失われた・壊れた・遅れて届いた・思いがけない形で届いた、という「まれな出来事」のときにこそ正しく動かなければならない。ところが、まれな出来事は実機の上ではめったに起きず、起きても同じようには起こし直せない。この章では、通信のコードの誤りを出荷の前に見つける方法と、出荷した後に起きたことを調べられるようにしておく方法を扱う。

この章では次の 3 つの問いに答える。

  1. 機器も電波もない所で、通信のコードをどう動かして確かめるのか。
  2. 喪失・重複・壊れた入力のような、めったに起きない出来事を、どうやってわざと、何度でも同じように起こすのか。
  3. 実機の上で起きていることを、どう外から見て、後から調べられるように記録しておくのか。

答えの道具は、ハードウェアに触る関数を差し替えて PC で動かすテスト、乱数の種で再現できる故障注入とファジング、パケットのキャプチャ、そして番号付きのログとカウンタである。

この章で使う既出の用語（定義は各リンク先）. 機器・サーバ（01 章 1 節）、遅延（01 章 3 節）、RAM・フラッシュメモリ・ファームウェア（01 章 4 節）、UART（02 章 1 節）、メッセージ・フレーム（03 章 1 節）、CRC（03 章 5 節）、TLV（03 章 7 節）、割り込みハンドラ（ISR）（04 章 1 節）、リングバッファ（04 章 3 節）、SPSC・クリティカルセクション（04 章 4 節）、状態機械・タイムアウト（05 章 1 節）、通信タスク（05 章 2 節）、ティック（05 章 3 節）、確認応答（ACK）・再送・ストップアンドウェイト・シーケンス番号・重複（05 章 4 節）、ウォッチドッグタイマ（05 章 6 節）、ホスト・コントローラ（06 章 1 節）、HCI・H4・HCI コマンド・HCI イベント・ACL データ・Command Complete（06 章 5 節）、IP アドレス・パケット（07 章 3 節）、TCP・UDP・セグメント（07 章 4 節）、DHCP（08 章 3 節）、DNS（08 章 4 節）、アクセスポイント（AP）（09 章 1 節）、RSSI（09 章 2 節）、SYN・FIN・RST（10 章 1 節）、遅延 ACK（10 章 6 節）、MSL（10 章 7 節）、errno（11 章 1 節）、部分受信（11 章 2 節）、TLS（12 章 1 節）、ハンドシェイク（12 章 2 節）、ClientHello（12 章 3 節）、Mbed TLS（12 章 7 節）、MQTT（13 章 1 節）、残りの長さ・CONNECT・CONNACK・PUBLISH・SUBACK（13 章 3 節）、PUBACK（13 章 4 節）、キープアライブ・PINGREQ・PINGRESP（13 章 5 節）、チャンク形式（14 章 2 節）、RTC（15 章 1 節）、再接続の方針（15 章 2 節）、ストアアンドフォワード・送信待ちの列・通し番号（15 章 3 節）、BLE（16 章 1 節）、周波数ホッピング（16 章 6 節）、接続イベント（18 章 1 節）、空パケット（19 章 1 節）、LTK（20 章 3 節）

1. 層を分けて、ホストで動かす

通信のコードを実機の上だけで試すと、3 つのことが難しい。

  • 起こしたい出来事を起こせない: 05 章 1 節の状態機械の「3 回とも応答がない」場面や、04 章 4 節の「受信のバッファが満杯のときに、取り出しの途中で割り込みが入る」場面は、普段の通信ではめったに起きない。
  • 同じことを起こし直せない: 電波の具合や処理のタイミングで結果が変わるので、一度見た誤りをもう一度起こして、直ったかどうかを確かめられない。
  • 時間がかかる: 1 ms のティックのカウンタが一周する（05 章 3 節。約 49.7 日）のを待って試すことはできない。

そこで、ファームウェアのうち、ハードウェアに直接触らない部分を、開発に使う PC でコンパイルして動かす。これをホストでのテストという。組み込みの開発では、プログラムを書いて機器に書き込む側の PC をホスト、書き込まれる側の機器をターゲットと呼ぶことが多い。この章のホストはこの意味で、06 章 1 節のホスト（無線のチップに命令を送る側のマイコン）や、BLE のホスト（16 章 5 節）とは別のものである。

図の真ん中の段の部品は、入ってきたバイトや出来事から、出すものと次の状態を計算するだけのコードである。これまでの章で作ったものでは、03 章の slip_rx_byte と tlv_next、06 章の at_feed と h4_feed、13 章の mqtt_rx_feed、14 章の chunk_feed などの解析器、05 章の fsm_handle と saw_send などの状態機械、04 章のリングバッファ、15 章の reconn_fail がこれにあたる。これらの部品は、ハードウェアに触る所を、tick_now()・link_send_data()・uart_hw_read()・flash_write() のような「この章で仮に置く関数」を通して呼ぶように書いてきた。仮に置いた関数の並びが、部品とハードウェアの境目になっている。

部品が使う下の層の関数を、テストのときだけ、テストのために作った偽物に替えることを依存の差し替えという。偽物は、本物と同じ名前と引数を持ち、中身だけが違う。時刻を返す関数は、テストが決めた値を返す。このように、テストが値を決める時計を偽物の時計という。送る関数は、送ったものを配列に書き留めるだけにし、受け取る関数は、前もって用意したバイトの列を返す。フラッシュメモリは、配列で作った模型にする（15 章 3 節で、書き込みの途中で電源を切る試験に使った）。

差し替え方は 2 つある。1 つは、リンクのときに替える方法である。テスト用のファイルに同じ名前の関数を書き、機器用のファイルの代わりにリンクする。下の層の関数を名前で呼んでいる 05 章のコードは、1 行も変えずにテストできる。もう 1 つは、関数へのポインタを構造体に入れて渡す方法である。06 章の at_rx の on_event や、14 章の chunk_rx の on_data がこの形で、1 つのプログラムの中で、部品ごとに違う偽物を渡せる。

偽物の時計で、再送と一周を確かめる

1 つの部品（関数や状態機械）だけを取り出し、決めた入力を与えて、出力や呼ばれた関数が期待どおりかを確かめるテストを単体テストという。05 章 4 節のストップアンドウェイトの送り手を、リンクのときの差し替えで単体テストする。05 章のコード（saw_send・saw_on_ack・saw_poll）は変えずに、下の層の関数をテストのファイルに書く（受け手の側の関数と main は省略した）。

/* test_saw.c — 05 章 4 節の送り手を、偽物の時計と書き留める送信で試す */
static uint32_t fake_now;                          /* 偽物の時計: 値はテストが決める */
uint32_t tick_now(void) { return fake_now; }

static int sent, sent_seq[16], failed;             /* 下の層の代わりに、呼ばれたことを書き留める */
void link_send_data(uint8_t seq, const uint8_t *p, size_t n) { (void)p; (void)n; sent_seq[sent++] = seq; }
void link_failed(void) { failed = 1; }

static void test_retry_across_wrap(void)
{
    struct saw_tx t = {0};
    sent = failed = 0;
    fake_now = 0xFFFFFFF0u;                        /* カウンタが一周する直前から始める */
    assert(saw_send(&t, (const uint8_t *)"A", 1) == 0 && sent == 1);
    for (uint32_t k = 0; k < T_ACK; k++) {         /* 期限の手前の各ティックでは */
        saw_poll(&t);
        assert(sent == 1);                         /* まだ送り直さない */
        fake_now++;
    }
    saw_poll(&t);                                  /* 期限ちょうど（一周の後）には */
    assert(sent == 2 && sent_seq[1] == sent_seq[0]);   /* 同じ番号で送り直す */
    for (int k = 2; k < MAX_TRIES; k++) { fake_now += T_ACK; saw_poll(&t); }
    assert(sent == MAX_TRIES && !failed);
    fake_now += T_ACK; saw_poll(&t);
    assert(failed && !t.busy);                     /* MAX_TRIES 回送っても来ないので諦める */
}

assert は、条件が成り立たなければ、ファイルと行を示してプログラムを止める C の標準の仕組み（<assert.h>）である。テストは、カウンタが一周する 16 ティック前から始める。期限は \(\mathtt{0xFFFFFFF0} + 20\) の下位 32 ビットの 0x00000004 で、一周の後にある。期限の手前の 20 ティックのそれぞれで saw_poll を呼んで送り直さないことを、期限ちょうどで同じ番号で送り直すことを、MAX_TRIES（5）回送った後の期限で諦めることを確かめる。実機なら約 49.7 日待つ一周を、このテストは PC の上で数 ms で通る。1 つ前の番号の ACK を取り違えないことも、saw_on_ack を呼ぶ同じ形のテストで確かめた。

テストが誤りを見つけられるかを確かめる

テストが通っても、テストが弱いだけかもしれない。そこで、コードにわざと誤りを入れて、テストが落ちることを確かめる。05 章 3 節の期限の比較 (int32_t)(now - deadline) >= 0 を、一周に弱い now >= deadline に書き換えて同じテストを動かした結果を図に示す。

誤った比較では、送った直後の 1 回目の saw_poll で、0xFFFFFFF0 ≥ 0x00000004 が成り立ってしまい、期限の前に送り直す。テストはそこで止まり、誤りを知らせる。実は、このテストの最初の版は、期限の 1 ティック前と期限ちょうどの 2 か所でしか saw_poll を呼んでおらず、誤った比較のままでも通ってしまった。誤った比較が誤るのは、今がまだ一周する前（0xFFFFFFF0〜0xFFFFFFFF）にある間だけで、最初の版はその間に一度も呼んでいなかったからである。誤りが現れる時刻や入力でテストを呼ばなければ、テストは誤りを見逃す。わざと誤りを入れて確かめると、こうした弱いテストに気づける。

分け方を変えても同じ結果になるか

06 章の at_feed、13 章の mqtt_rx_feed、14 章の chunk_feed は、どれも「届いたバイトの列がどこで分かれて届いても、同じ結果になる」ように作った（11 章 2 節の部分受信に備えるため）。これは、期待する結果を 1 つずつ書かなくても確かめられる性質である。同じ列を、1 回で渡した場合と、いろいろな位置で分けて渡した場合とで、知らせの列を比べればよい。各章のテストは、この方法で数万〜十万通りの分け方を試した。3 節のファジングでも、この性質を使う。

ホストでのテストでは分からないこと

PC と機器のマイコンとでは、int の大きさ・エンディアン・番地のそろえ方（03 章 6 節）が違うことがある。大きさの決まった型（uint32_t など）を使い、警告を多めに出す設定（gcc の -Wall -Wextra）で、機器用と PC 用の両方でコンパイルする。割り込みが入るタイミング、本物の TCP/IP や BLE のスタックの動き、電波の様子は、ホストでのテストでは確かめられない。これらは、実機の上での試験と、4 節のキャプチャ、5 節のログで補う。

2. 壊れる通信路を作る — 故障注入

1 節の偽物の送受信は、送ったものをそのまま相手に渡した。現実の通信路は、メッセージを失い、遅らせ、壊す。テストのために、こうした故障をわざと起こすことを故障注入という。通信路の故障は、次の 5 つに分けられる。

  • 喪失: メッセージが届かない。
  • 遅延（01 章 3 節）が延びる・揺れる: 届くまでの時間が、いつもより長くなったり、メッセージごとに違ったりする。
  • 重複（05 章 4 節）: 同じメッセージが 2 回以上届く。
  • 順番の入れ替え: 後から送ったメッセージが、前に送ったものより先に届く。
  • 破損: メッセージの中のビットが変わって届く。

UART の線の上では主に破損が、無線では主に喪失が起き、インターネットの上ではこの 5 つのすべてが起きうる。どの故障をどれだけ起こすかを確率で決め、乱数で起こす模擬の通信路を C で書く。

struct fault_cfg {
    double   loss, dup, corrupt, reorder;    /* それぞれが起きる確率 */
    uint32_t delay, jitter, hold;            /* 遅延 = delay + [0, jitter]、入れ替えではさらに hold */
};
struct ch_msg { uint32_t at; uint16_t len; uint8_t b[CH_MAXB]; };
struct chan {
    struct fault_cfg cfg;
    uint32_t rng;                            /* 乱数の状態。種（0 以外）を入れて始める */
    struct ch_msg q[CH_QMAX];                /* 通信路の中にあるメッセージ */
    int n;
};
static uint32_t rnd(struct chan *c)          /* xorshift32: 同じ種なら同じ列 */
{
    uint32_t x = c->rng;
    x ^= x << 13; x ^= x >> 17; x ^= x << 5;
    return c->rng = x;
}
static int chance(struct chan *c, double p) { return rnd(c) < p * 4294967296.0; }

/* 1 つのメッセージを通信路に入れる。故障は乱数で決める */
void chan_send(struct chan *c, uint32_t now, const uint8_t *p, size_t len)
{
    if (chance(c, c->cfg.loss)) return;                      /* 喪失 */
    int copies = chance(c, c->cfg.dup) ? 2 : 1;              /* 重複 */
    for (int k = 0; k < copies && c->n < CH_QMAX; k++) {
        struct ch_msg *m = &c->q[c->n++];
        memcpy(m->b, p, len); m->len = (uint16_t)len;
        m->at = now + c->cfg.delay + rnd(c) % (c->cfg.jitter + 1);   /* 遅延 */
        if (chance(c, c->cfg.reorder)) m->at += c->cfg.hold;  /* 入れ替え: 後のものに追い越させる */
        if (chance(c, c->cfg.corrupt))                        /* 破損: 1 ビットを反転 */
            m->b[rnd(c) % len] ^= (uint8_t)(1u << (rnd(c) % 8));
    }
}
/* chan_recv(c, now, out): 時刻 now までに届くもののうち、最も早いものを 1 つ取り出す（省略） */

chan_send は、送られたメッセージごとに乱数で故障を決め、届く時刻を付けて通信路の中に置く。chan_recv は、届く時刻が now を過ぎたもののうち最も早いものを返す（時刻の比較は 05 章 3 節の形）。入れ替えは、一部のメッセージだけをさらに hold ティック遅らせ、後から送ったものに追い越させて起こす。乱数は xorshift32（シフトと XOR を 3 回行って次の値を作る、簡単な擬似乱数）で作る。行きと帰りに 1 つずつ通信路を置き、別々の種を入れる。

3 つの方式を比べる

この通信路の上で、3 つの方式を比べる。

  • (A) 素朴な方式: 10 ティックごとにメッセージを 1 つ送るだけ。番号も CRC も確認応答もない。
  • (B) 05 章のストップアンドウェイト + CRC: 05 章 4 節の方式で、データと ACK に 03 章 5 節の CRC-16/CCITT-FALSE を付け、合わないものは捨てる。シーケンス番号は 1 ビット。
  • (C) (B) の番号を 16 ビットにしたもの。

遅延は 2〜4 ティック、ACK を待つ時間は 20 ティック、入れ替えるメッセージはさらに 50 ティック遅らせた。1 回の試験で 1000 個のメッセージを送り、種を変えて 200 回試した平均を示す。

(A) は、失われた分を失い、重複した分を 2 回渡し、壊れた分を壊れたまま渡し、入れ替わった分を順番を違えて渡す。どれにも気づかない。(B) は、喪失・重複・破損をすべて扱えた。壊れたものは CRC が合わないので捨て、届かなかったものとして送り直す。その分、送った回数は 1000 から約 1236 に増える。データと ACK がそれぞれ 10 % 失われると、1 回で往復できる確率は \(0.9 \times 0.9 = 0.81\) なので、1 つのメッセージを平均 \(1/0.81 \approx 1.235\) 回送ることになり（05 章 4 節）、試験の値と合う。

ところが (B) は、入れ替えに弱い。10 % を入れ替えると、平均で約 56 個を 2 回渡し、別の約 55 個を失った。どう起きたかを、試験の記録から図にする。

05 章 4 節で、1 ビットの番号で足りることを導いたとき、前提 (1) として「通信路はメッセージの順番を入れ替えない」と置いた。入れ替えのある通信路では、送り直した後に、遅れていた最初の写しが届く。そのとき受け手が待っている番号が、たまたまその写しと同じ偶奇なら、受け手は古い写しを新しいメッセージとして渡し、本物の新しいメッセージを重複として捨てる。番号を 16 ビットにした (C) では、古い写しの番号は待っている番号と違うので、重複として捨てられる。ただし、何ビットの番号でも、写しがいくらでも遅れて届くなら、いつかは番号が一周して取り違える。TCP が 32 ビットの番号と、パケットがネットワークの中に残りうる最長の時間（MSL）を組み合わせているのは、このためである（10 章 7 節）。

故障注入は、コードの誤りだけでなく、設計の前提が崩れたときに何が起きるかも見せる。1 本の UART なら順番は入れ替わらないので (B) で足りるが、同じコードを UDP（11 章 5 節）の上で使い回すと、このように壊れる。

再現性 — 乱数の種を残す

同じ条件で試せば同じ結果になることを、再現性という。故障を乱数で起こすテストに再現性を持たせるには、乱数の種（乱数の列を決める最初の値）を記録しておく。上の通信路は、同じ種を入れれば同じ故障の列を起こすので、テストの結果も同じになる。たとえば (B) で入れ替えを 10 % にした試験は、種の番号 1 では、171 ティック目に、すでに 17 番まで受け取った受け手が、14 番のメッセージを 2 回目に渡した。何度動かしても、同じ時刻に同じことが起きる。

そこで、テストは種を変えながら繰り返し、失敗したら種を表示するように書く。失敗した種でテストを動かし直せば、デバッガで止めて調べたり、直した後に同じ場面で通ることを確かめたりできる。乱数に頼らず、「3 番目のデータと 5 番目の ACK を失う」のように故障の並びを決めたテストも作っておくと、直した誤りがまた入ったときに必ず気づける。

netem — OS の通信路を壊す

11 章のソケットを使うコードは、Linux の netem を使えば、コードを変えずに壊れた通信路の上で試せる。netem は、ネットワークの口から出ていくパケットに、遅延・喪失・重複・破損・順番の入れ替えを加える Linux のカーネルの機能で、tc コマンドで設定する（管理者の権限が要る）。

sudo tc qdisc add dev lo root netem delay 100ms loss 5%     # 遅延と喪失を加える
sudo tc qdisc change dev lo root netem delay 100ms 20ms duplicate 1% corrupt 0.1%
tc qdisc show dev lo                                        # いまの設定を見る
sudo tc qdisc del dev lo root                               # 元に戻す

lo は、自分自身あての通信を運ぶ仮のネットワークの口（ループバック）である。netem は口から出ていく向きにかかり、ループバックでは行きも帰りも同じ口から出るので、delay 100ms で往復時間は約 200 ms 延びる。delay 100ms 20ms は、遅延を 100 ms ± 20 ms の範囲で揺らす指定である。口を使うすべてのプログラムが影響を受けるので、試験のための口や Linux のネットワークの名前空間（ip netns）の中で使い、終わったら元に戻す。netem はカーネルの機能なので、カーネルの設定によっては使えない（そのとき tc は Specified qdisc kind is unknown と答える）。指定の細かな意味は man tc-netem で確かめる。機器の Wi-Fi の通信を壊したいときは、4 節のように PC をアクセスポイントにし、機器へ向かう向きは PC の無線の口に、機器から出ていく向きは PC の上流の口に netem をかける。

3. 入力を乱して確かめる — ファジング

解析器は、外から届くバイトを読む。線の雑音、相手の誤り、悪意によって、どんな形のバイトの列も届きうる。03 章 7 節では、長さを確かめない TLV の解析が、壊れた長さで配列の外を読むことを見た。単体テストは、書いた人が思いついた入力しか試さない。そこで、思いつかない入力を機械に作らせる。乱数で作った入力や、正しい入力を少しずつ変えた入力を大量に与えて、プログラムが止まる・配列の外を読み書きする・決めた性質に合わない答えを出す、といった入力を探すテストをファジングという。この章のファジングは、自分の書いたコードを PC の上で確かめるためのものである。

乱数の入力と、変異させた入力

わざと誤りを入れた小さな解析器で、入力の作り方を比べる。メッセージは、印の 1 バイト 0xA5、残りの長さの 1 バイト、その後に 03 章 7 節の TLV が並ぶ形とする。誤りは、型 0x09（名前）の値を 8 バイトの配列に写すときに、長さが 8 以下かどうかを確かめていないことである。

長さ 1〜32 バイトの乱数で作った 200 万個の入力では、99.6 % が最初の印で捨てられた。印が合う確率は 1/256、残りの長さも合う確率は \(1/256^2 = 1/65536\) で、誤りのある所まで届いた入力は 1 つも無かった。そこで、正しい入力を集めておき（これをコーパスという）、1 つを選んで、ビットを 1 つ反転する・1 バイトを書き換える・1 バイトを足す・1 バイトを消す、といった小さな変更を 1〜4 回加える。この変更を変異という。変異させた 20 万個の入力では、31 % が残りの長さの検査を通り、0.31 % が誤りのある所に届いた。正しい入力の形をほとんど保ったまま一部だけを変えるので、検査を通って奥まで届く。

サニタイザ — 配列の外に触れたその場で止める

配列の外に書いても、プログラムがすぐに止まるとは限らない。隣の変数を黙って書き換え、ずっと後に別の所でおかしな動きとして現れることが多い。ファジングで見つけるには、外に触れたその場で止まってほしい。

コンパイラが実行ファイルに検査のコードを足し、配列の外の読み書きや C で未定義の動作が起きたその場でプログラムを止めて、場所を知らせる仕組みをサニタイザという。gcc と clang には、配列の外の読み書きや解放した後のメモリの使用を見つける AddressSanitizer と、符号付きの整数のあふれや範囲を超えたシフトなどの未定義の動作を見つける UndefinedBehaviorSanitizer がある。コンパイルのときに -fsanitize=address,undefined を付けるだけで使え、このシリーズのテストもこれを付けて動かした（03・06・13・14 章）。その代わり、AddressSanitizer では実行がおよそ 2 倍遅くなり（説明書にある目安）、メモリも多く使うので、主に PC の上のテストで使う。上の解析器で、変異させた入力を与えて誤りを見つけるまでの回数を数えると、サニタイザありでは中央値 198 回、なしでは中央値約 1500 回だった（なしの場合は、名前の後ろの 8 バイトを越えて書いたときにだけ落ちる、という模型で数えた）。

libFuzzer で 13 章の解析器を試す

clang には、ファジングを行う libFuzzer という仕組みが付いている。libFuzzer は、入力を変異させて試すだけでなく、試した入力がプログラムのどの分岐を通ったかを数え、新しい分岐を通った入力をコーパスに加えていく。こうして、少しずつ奥の分岐まで届く入力が増えていく。

使う人は、入力を受け取って試す相手を呼ぶ関数を、決まった名前 LLVMFuzzerTestOneInput で書くだけでよい。13 章 6 節の mqtt_rx_feed を試す関数を示す。この関数は、サニタイザに加えて、1 節の「分け方を変えても同じ結果になる」性質も確かめる。

static uint32_t count[2], digest[2];          /* [0]: 1 回で渡した結果、[1]: 分けて渡した結果 */
static int which;
static void on_packet(uint8_t first, const uint8_t *body, uint32_t len)
{
    count[which]++;
    digest[which] = digest[which] * 31 + first + len;     /* 受け取ったものを 1 つの数にまとめる */
    for (uint32_t i = 0; i < len; i++) digest[which] = digest[which] * 31 + body[i];
}

/* libFuzzer が、作った入力ごとに呼ぶ入口の関数 */
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)
{
    static struct mqtt_rx r;
    int ret[2];
    if (size < 1) return 0;
    size_t step = data[0] % 16 + 1;            /* 先頭の 1 バイトで、分ける大きさを決める */
    data++; size--;
    which = 0; count[0] = digest[0] = 0; memset(&r, 0, sizeof r);
    ret[0] = mqtt_rx_feed(&r, data, size, on_packet);          /* 全部を 1 回で渡す */
    which = 1; count[1] = digest[1] = 0; memset(&r, 0, sizeof r);
    ret[1] = 0;
    for (size_t i = 0; i < size && ret[1] == 0; i += step)       /* step バイトずつ渡す */
        ret[1] = mqtt_rx_feed(&r, data + i, size - i < step ? size - i : step, on_packet);
    if (ret[0] != ret[1] || count[0] != count[1] || digest[0] != digest[1])
        abort();                               /* 渡し方で結果が変わった: 誤り */
    return 0;
}
clang -g -O1 -fsanitize=fuzzer,address,undefined fuzz_mqtt.c mqtt_rx.c -o fuzz_mqtt
./fuzz_mqtt -max_total_time=60 corpus/      # corpus/ には正しいパケットを 1 つずつファイルにして置く
./fuzz_mqtt crash-…                          # 見つかった入力で、もう一度動かす

コーパスには、CONNACK・PUBLISH・SUBACK・PUBACK・PINGRESP の正しいバイトの列を置いた。この章の PC（clang 18）で、13 章のコードのままでは、60 秒・約 1400 万回の試行で何も見つからなかった。そこで、2 種類の誤りをわざと入れて試した。

  • 長さの上限の検査を外す（13 章の rem > RX_MAX で -1 を返す行を消す）: 種を変えた 8 回とも 0.6〜3.1 秒（12 万〜67 万回）で AddressSanitizer が止め、body の外に 1 バイト書いた行を示した。見つかった入力を libFuzzer の -minimize_crash=1 で短くすると 517 バイトになり、残りの長さを FF 10（\(127 + 16 \times 128 = 2175\)）と読んで、513 バイト目を body に書いた所で止まっていた。
  • 呼ばれるたびに状態を初めに戻す（「1 回の受信 = 1 つのパケット」と思い込んだ誤り。11 章 2 節）: 配列の外には触れないのでサニタイザでは見つからないが、分けて渡した結果が 1 回で渡した結果と違うので、コーパスを読み込んだ直後に abort で止まった。

見つかった入力は crash- で始まるファイルに保存されるので、それを単体テストの入力として残しておけば、同じ誤りがまた入ったときに気づける。libFuzzer を使うには、clang と、ファジングのための部品（clang の版や OS によっては別に入れる）が要る。gcc しか無いときは、LLVMFuzzerTestOneInput を乱数や変異させた入力で繰り返し呼ぶ main を自分で書いても、分岐を数える働きは無いが、同じ確かめ方ができる。

CRC や署名で守られた入力は、変異させるとほぼすべてが最初の検査で捨てられる。そのため、ファジングのときだけ検査を外した版を作って試すことが多い（libFuzzer の説明では、そうした版を作るための印として FUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION という名前のマクロを使うことを勧めている）。この版は、決して機器に入れない。完成した機器を外から乱した入力で試す方法は、組み込みテストシリーズ 16 章 が扱っている。

下の図で、入力の作り方（乱数・変異）とサニタイザの有無を選んで試すと、この節の小さな解析器が誤りを起こす入力を見つけるまでの試行の数と、見つかった入力のバイトが表示される。

4. パケットを見る — キャプチャ

実機をつなぐと、ホストでのテストでは見えなかったことが起きる。何が起きているかを知る最も確かな方法は、通信路を流れるものを、そのまま見ることである。通信路を流れるパケットやフレームを、そのままの形で写し取って記録することをパケットキャプチャという。

どこで写し取るか

機器とサーバの間の Wi-Fi・IP の通信は、次のどこかで写し取る。

  • PC をアクセスポイントにする: 機器を、AP として動かした PC につなぐ。機器のすべてのパケットが PC を通るので、そこで写し取れる。2 節の netem もここでかけられる。
  • スイッチのミラーポート: 有線なら、ほかの口を流れるパケットの写しを出す口（ミラーポート）を持つスイッチを使う。
  • サーバの側: サーバが自分のものなら、そこで写し取る。届いたものしか見えないことに注意する。

Wi-Fi の電波を直接受けて写し取る方法もあるが、中身は Wi-Fi の暗号化（09 章 3 節）で守られているので、読むにはさらに手間がかかる。

写し取る道具には、Linux などの tcpdump がある。写し取ったものは、pcap というファイルの形式で保存することが多い。pcap のファイルを読み、各層のヘッダを解読して並べて見せるソフトウェアが Wireshark である（文字の画面で使う tshark も付いている）。

sudo tcpdump -i wlan0 -w dev.pcap host 192.168.4.20     # 機器のアドレスに関わるパケットを dev.pcap に書く

Wireshark では、表示する条件を ip.addr == 192.168.4.20（このアドレスに関わるもの）、tcp.analysis.retransmission（再送と判断したセグメント）、tcp.flags.reset == 1（RST）、dns、dhcp、mqtt のように書いて絞り込む。これまでの章の仕組みは、次の所で見える。

見たいこと見る所章
つながるまでの時間の内訳DHCP・DNS・SYN・ClientHello・CONNECT の時刻08・10・12・13 章
再送同じシーケンス番号のセグメントと、その間隔10 章 4 節
接続が切れた理由RST・FIN と、その前のやり取り10 章 7 節
小さな書き込みの待ち書き込みの間が、遅延 ACK の時間だけ空く10 章 6 節
キープアライブPINGREQ と PINGRESP の間隔13 章 5 節

pcap のファイルは、24 バイトのファイルの頭と、パケットごとの 16 バイトの頭（写し取った時刻、写した長さ、もとの長さ）とパケットの中身の並びである。tcpdump で写し取ったファイルの先頭を図に示す。

形が簡単なので、自分のテストの記録を pcap で書き出して、Wireshark で時刻の順に眺めることもできる。

TLS の中身を読む

TLS は中身を暗号化するので、キャプチャには暗号文しか写らない（12 章 1 節）。開発のときに限り、TLS のライブラリに、ハンドシェイクで決めた鍵の元になる値をファイルに書き出させ、それを Wireshark に渡すと、中身を復号して表示できる。

書き出す形は、NSS の鍵のログと呼ばれる文字の形式である。OpenSSL の試験用のクライアント openssl s_client は -keylogfile でこの形を書き出し、PC の多くのブラウザは環境変数 SSLKEYLOGFILE で書き出す。Wireshark では、設定の tls.keylog_file（tshark なら -o tls.keylog_file:keys.log）にそのファイルを指定する。図はこの手順を PC の上で確かめた結果である。Mbed TLS（12 章 7 節）のような組み込み向けのライブラリにも、鍵を取り出す関数を登録する仕組みがある（名前と形は版によって違う）。このファイルを持つ人は誰でも通信を読めるので、書き出す機能はデバッグのための版（6 節）だけに入れ、出荷する機器には決して入れない。

BLE — スニファと HCI のログ

BLE のリンク層のパケットは、2 つの機器の無線の回路の間でやり取りされ、機器の外に出てこない。BLE の電波を受信して、ほかの機器どうしのリンク層のパケットを記録する装置を BLE スニファという。開発用のボードに専用のファームウェアを入れ、PC の Wireshark で見る形が多い。接続中は接続イベントごとにチャネルを変える（16 章 6 節の周波数ホッピング）ので、スニファは、接続を始めるときのパケットから、どのチャネルをどの順に使うかの設定（18 章 1 節）を読み取って追いかける。多くのスニファは、そのパケットを受け損なうと、その接続を追えない。暗号化された接続の中身を読むには、鍵（20 章 3 節の LTK）をスニファに渡す必要がある。スニファには、接続イベントごとのすべてのパケット（空パケットや送り直しも含む）が写るので、1 回のイベントに何往復しているか（19 章 3 節）が分かる。

BLE のホストとコントローラの間を流れる HCI のパケット（06 章 5 節）を記録したものを HCI のログという。リンク層の暗号化はコントローラの中で行われるので、HCI のログには、接続した相手とやり取りしたデータ（ACL データ）が平文で写る。その代わり、リンク層のパケットそのもの（空パケットや送り直し）は写らず、コントローラが送り終えたパケットの数の知らせ（06 章 5 節の Number Of Completed Packets）だけが分かる。Android のスマートフォンでは開発者向けの設定で、Linux では BlueZ の btmon などで HCI のログをとれる。保存の形式としては btsnoop がよく使われ、Wireshark で読める。06 章 5 節の (d) の構成なら、ホストのマイコンの H4 のドライバで、送ったパケットと受け取ったパケットを btsnoop の形で書き出せる。

static void be32(uint8_t *p, uint32_t v) { for (int i = 0; i < 4; i++) p[i] = (uint8_t)(v >> (24 - 8 * i)); }

int btsnoop_open(FILE *f)                       /* ファイルの頭 16 バイト（数値はビッグエンディアン） */
{
    uint8_t h[16];
    memcpy(h, "btsnoop\0", 8);                 /* 識別の 8 バイト */
    be32(h + 8, 1);                            /* 版 = 1 */
    be32(h + 12, 1002);                        /* データリンク = 1002（H4: 先頭に種類の 1 バイト） */
    return fwrite(h, 1, 16, f) == 16 ? 0 : -1;
}

/* p は H4 の 1 パケット（種類の 1 バイトを含む）。received: コントローラから届いたら 1 */
int btsnoop_write(FILE *f, const uint8_t *p, uint32_t n, int received, uint64_t usec_since_1970)
{
    uint8_t h[24];
    int cmd_evt = (p[0] == 0x01 || p[0] == 0x04);       /* HCI コマンドかイベントか */
    uint64_t ts = usec_since_1970 + 0x00DCDDB30F2F8000ull;   /* btsnoop の時刻の起点に合わせる */
    be32(h, n);                                /* もとの長さ */
    be32(h + 4, n);                            /* 記録した長さ */
    be32(h + 8, (uint32_t)(received ? 1 : 0) | (uint32_t)(cmd_evt ? 2 : 0));   /* 向きと種類の印 */
    be32(h + 12, 0);                           /* それまでに取りこぼした数 */
    be32(h + 16, (uint32_t)(ts >> 32)); be32(h + 20, (uint32_t)ts);
    return (fwrite(h, 1, 24, f) == 24 && fwrite(p, 1, n, f) == n) ? 0 : -1;
}

btsnoop の時刻は、1970 年より前の決まった起点から数えた µs なので、1970 年からの µs に決まった値を足して書く。印のビット 0 は向き（0 = ホストが送った、1 = ホストが受け取った）、ビット 1 は種類（0 = データ、1 = コマンドかイベント）である。06 章 5 節の HCI_Reset（01 03 0C 00）と Command Complete（04 0E 04 01 03 0C 00）をこの関数で書いたファイルは、Wireshark（tshark 4.2）で「host → controller HCI_CMD Reset」「controller → host HCI_EVT Command Complete (Reset)」と読め、書いた時刻もそのまま表示された。

マイコンの上ではファイルの代わりに、5 節のリングバッファや UART に同じバイトを書き、PC で集めてファイルにする。

UART

UART のやり取り（06 章の AT コマンドなど）は、線の信号をロジックアナライザで写し取って読むか（組み込みテストシリーズ 04 章）、USB とシリアルの変換器の RX と GND だけを線につないで、流れるバイトを PC で記録する。向きごとに 1 つずつ、2 つの変換器を使えば両方向を記録できる。電圧の形（02 章 5 節）がそろっていることを確かめてからつなぐ。

5. ログと計測を仕込む

キャプチャは、手元で試すときの道具である。出荷した機器が現場で切れる・遅れる・リセットするとき、そこに PC は無い。機器が自分で記録を残し、つながったときにサーバへ送る必要がある（05 章 6 節のリセットの理由もこの形で送る）。

何を残すか

1 件ごとに、決まった欄を決まった形で並べたログを構造化ログという。人が読む文章として書くのではなく、サーバの側のプログラムが並べ替え・数え・絞り込みをできるようにする。欄は次のものにする。

  • いつ: ティック（05 章 3 節）。RTC が合っていれば日付と時刻（15 章 1 節）も。
  • どの接続で: つなぎ直すたびに 1 増やす接続の番号。どの記録が同じ接続のものかが分かる。
  • 何が: 出来事の番号。状態機械の遷移（遷移の前と後の状態）、エラー（11 章 4 節の errno、TLS のライブラリの誤りの番号、MQTT の CONNACK の結果、BLE の切断の理由など）、再送と時間切れ、リセットとその理由。
  • 値: 出来事ごとの値。
  • 記録の通し番号: 記録が抜けたことに気づくため。

パスワードや鍵のような秘密は、ログに書かない。

文字で書いた 1 行は、同じ内容をバイナリで書いた記録の 4 倍の大きさになる。機器の中では出来事の番号だけを持ち、番号から文字の説明を引く表はサーバの側に置く（バイナリ解析シリーズ 12 章 3 節）。

RAM のリングバッファにためる

記録は、RAM のリングバッファ（04 章 3 節）にためる。受信のバッファと違い、満杯なら最も古い記録を上書きする（新しい記録のほうが、いまの不具合を調べるのに役立つことが多い）。

struct log_rec {                    /* 1 件 12 バイト */
    uint32_t seq;                   /* 記録の通し番号（抜けに気づくため） */
    uint32_t tick;                  /* いつ（05 章 3 節のティック） */
    uint8_t  event;                 /* 何が（出来事の番号。文字の説明は PC の側の表で引く） */
    uint8_t  conn;                  /* どの接続で（つなぎ直すたびに 1 増やす番号） */
    uint16_t arg;                   /* 出来事ごとの値（エラーの番号、遷移の前後の状態など） */
};
#define LOG_N 256u                  /* 件数。2 のべき乗にする（04 章 3 節） */
static struct log_rec log_buf[LOG_N];
uint32_t log_head;                  /* これまでに書いた件数 = 次の通し番号 */

/* どのタスクや ISR からも呼べる。満杯なら最も古い記録を上書きする */
void log_event(uint8_t event, uint8_t conn, uint16_t arg)
{
    uint32_t s = irq_save();        /* 書き手が複数なので、短い間だけ割り込みを禁止する */
    struct log_rec *r = &log_buf[log_head & (LOG_N - 1)];
    r->seq = log_head++;
    r->tick = tick_now(); r->event = event; r->conn = conn; r->arg = arg;
    irq_restore(s);
}

/* 通し番号 seq の記録を写す。1 = 写した、0 = まだ書かれていない、-1 = 上書きされて無い */
int log_copy(uint32_t seq, struct log_rec *out)
{
    uint32_t s = irq_save();
    uint32_t behind = log_head - seq;    /* seq が何件前の記録か（04 章 3 節の差） */
    int ret = (behind == 0) ? 0 : (behind > LOG_N) ? -1 : 1;
    if (ret == 1) *out = log_buf[seq & (LOG_N - 1)];
    irq_restore(s);
    return ret;
}

irq_save・irq_restore は 04 章 4 節で仮に置いた、割り込みを禁止して元に戻す関数である。log_event は、どのタスクからも、ISR からも呼ばれるので、04 章 4 節の SPSC の方式は使えず、短いクリティカルセクションにする。中では写すだけで、待つことも、時間のかかる処理もしない。送る係のタスクは、log_copy で通し番号の順に記録を写してまとめ、サーバに送る。送ったまとまりは、MQTT の PUBACK（13 章 4 節）などで受け取ったことが分かってから、次の通し番号へ進む（15 章 3 節のストアアンドフォワード）。log_copy が -1 を返したら、その記録は上書きされて無いので、log_head - LOG_N まで飛ばし、飛ばした件数も報告する。サーバは、通し番号の抜けで、記録が失われたことを知る。このコードは、ときどき 300 件まとめて書かれ、読む側がそれより遅い場合を、通し番号を一周する直前から 40 万件以上試し、読んだ件数と上書きされた件数の和が書いた件数に等しく、読んだ記録の通し番号が抜けなく続くことを確かめた。

記録はどれだけの時間残るか

方針: リングバッファに入る件数と、1 秒あたりに書かれる件数から、いちばん古い記録が上書きされるまでの時間を求める。

導出: 入る件数を \(N\)、1 秒あたりに書かれる件数を \(r\) とする。上書きされずに残るのは、新しい方から \(N\) 件なので、残っている記録の範囲は、\(N\) 件が書かれる時間 \(N / r\) 秒である ∎

\(N\) = 256（3 KB）で、ふだんは 1 時間に 30 件なら、\(256 / (30/3600) = 30720\) 秒、約 8.5 時間分が残る。ところが、同じエラーが 1 秒に 10 件ずつ続くと、\(256 / 10 = 25.6\) 秒で全部が入れ替わり、不具合が始まる前の記録が消える。そこで、同じ出来事が続くときは 1 件目だけを記録し、続いた回数を数えておいて、止んだときに「n 回続いた」を 1 件記録する。リセットの理由のような大事な記録は、別のリングバッファや、起動時に 0 にしない RAM の領域（05 章 6 節）に分けて残す。

数えておくもの — カウンタ

出来事の回数や量を、起動してから数え続ける変数を計測値（カウンタ）という。ログが「何が、いつ起きたか」を残すのに対し、カウンタは「どれだけ起きているか」を、決まった小さな RAM で表す。

カウンタ何が分かるか章
送ったメッセージの数と、そのうちの再送の数通信路の喪失の割合05 章 4 節
層ごとのつなぎ直しの数どの層で切れやすいか15 章 2 節
受信のバッファで捨てたバイトの数受け取りが間に合っているか04 章 2 節
CRC が合わずに捨てたフレームの数線や電波の質03 章 5 節
送信待ちの列の最大の量つながらない時間の長さ15 章 3 節
前の報告からの RSSI の最小電波の弱い時間帯09 章 1 節

機器は、カウンタの値を決まった間隔で（たとえば 1 時間ごとのまとめて送る記録と一緒に）報告する。サーバは、続いた 2 つの報告の差を時間の差で割って、1 時間あたりの再送の数のような割合を求める。32 ビットの符号なしのカウンタなら、2 つの報告の間に \(2^{32}\) 回より少なくしか増えない限り、符号なしの引き算で、一周をまたいでも正しい増え方が求まる（04 章 3 節の head − tail と同じ理由）。カウンタはリセットで 0 に戻るので、起動からの時間や起動の回数を一緒に送り、サーバが一周とリセットを見分けられるようにする。

6. 試験のための機能

2 節の故障注入を、ホストではなく実機の上で行いたいときや、つなぎ直しの手順を製品と同じ機器で確かめたいときのために、ファームウェアに試験のための機能を入れておく。

  • 強制切断: TCP の接続を閉じる、Wi-Fi の接続を切る、BLE の接続を切る命令。15 章 2 節の再接続の方針を、実機の上で層ごとに試せる。
  • 故障注入のスイッチ: 送る・受け取るフレームを決めた割合で捨てる、CRC をわざと壊す、ACK を遅らせる。乱数の種を命令で決められるようにし、その種をログに残す（2 節の再現性）。
  • 時計を進める: ティックのカウンタの初めの値を、一周する少し前にして起動する。5 分で一周するので、05 章 3 節の比較の誤りが、49.7 日待たずに現れる。Linux のカーネルも、32 ビットの時刻のカウンタ（jiffies）が起動の 5 分後に一周するように、初めの値を決めている。
  • 通信の質の報告: 5 節のカウンタ・状態機械の状態・RSSI を、その場で返す命令。

命令は、UART のコンソール（組み込みテストシリーズ 05 章）などから送る。開発と試験のための機能を入れてビルドしたファームウェアをデバッグ版、製品として機器に入れるファームウェアを出荷版という。試験のための機能は、デバッグ版だけに入れる。

#if TEST_HOOKS                                  /* デバッグ版だけに入れる */
static uint16_t fi_drop_tx_permille;            /* 故障注入のスイッチ: 送るフレームを捨てる割合 [‰] */
static uint32_t fi_rng = 1;                     /* 種はコマンドで決め、ログに残す */
static int fi_drop_tx(void)
{
    fi_rng ^= fi_rng << 13; fi_rng ^= fi_rng >> 17; fi_rng ^= fi_rng << 5;
    return fi_rng % 1000u < fi_drop_tx_permille;
}
void test_cmd_fault(uint16_t permille, uint32_t seed)   /* 試験用のコマンドから呼ぶ */
{
    fi_drop_tx_permille = permille; fi_rng = seed ? seed : 1;
}
void tick_init(void) { g_tick = 0u - 5u * 60u * 1000u; }   /* 起動の 5 分後に一周する */
#else                                           /* 出荷版: スイッチそのものが無い */
#define fi_drop_tx() 0
void tick_init(void) { g_tick = 0; }
#endif

int link_send_frame(const uint8_t *p, uint32_t n)
{
    if (fi_drop_tx()) { stats.fi_dropped++; return 0; }    /* 送ったことにして捨てる */
    stats.tx_frames++;
    return uart_write(p, n) == n ? 0 : -1;
}

TEST_HOOKS は、ビルドのときに決めるマクロである。出荷版（TEST_HOOKS が 0）では fi_drop_tx() が 0 に置き換わり、コンパイラは捨てる分岐ごと消す。g_tick は 05 章 3 節のティックのカウンタ、0u - 5u * 60u * 1000u は 1 ms のティックで 5 分前の値（0xFFFB6C20）、stats は 5 節のカウンタ、uart_write は 04 章 7 節の関数である。

試験のための機能には、2 つの危うさがある。1 つは、出荷版に残ると、誰でも機器を切断させたり故障を起こさせたりできる穴になることである。ビルドした出荷版のファイルの中に、試験のための関数や変数の名前が無いことを、nm などの道具で確かめる（上のコードを PC の gcc でビルドすると、出荷版には fi_ で始まる名前と test_cmd_fault が無い）。もう 1 つは、デバッグ版で試験して出荷版を出すと、試験した物と出す物が違うことである。違いを、スイッチの有無のような小さな所にとどめ、最後の試験は出荷版で、2 節の netem や電波を弱めるなど、機器の外から起こす故障で行う。

機能デバッグ版出荷版理由
