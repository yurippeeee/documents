Chapter 22

大きなデータを運ぶ — ファームウェア更新の転送と書き込み

この章で扱う問い. 21 章までは、測定値や命令のような小さなデータを、どの方式でどう運ぶかを見てきた。この章では、機器が受け取るデータのうちで最も大きなもの、つまり新しいファームウェアを取り上げる。大きさは数百 KB〜数 MB で、機器の RAM（数十 KB〜数百 KB。01 章 4 節）よりずっと大きい。

この章では次の 3 つの問いに答える。

  1. RAM に収まらないデータを、途中で切れるかもしれない通信路で、どう運ぶのか。
  2. 受け取ったデータを、消してからでないと書けないフラッシュメモリに、受信を止めずにどう書くのか。
  3. 書き終えたファームウェアをどう確かめて切り替え、新しい版が動かなかったときにどう元に戻すのか。

答えの道具は、どこまで書いたかを覚えて続きから運ぶこと、2 つのバッファで受信と書き込みを重ねること、試しに起動してから確定することである。

1. 更新の全体の流れ

機器を出荷した後で、不具合が見つかったり、機能を足したくなったりすることがある。機器を回収したり、人が出向いて配線をつないだりせずに、通信で新しいファームウェアを届けて書き換えることを、ファームウェアの無線更新（OTA、over-the-air）という。届けるのは、新しいファームウェアを、フラッシュメモリにそのまま書ける形にしたバイトの列で、これをイメージという。機器から見ると、イメージは下りのデータであり、その中で最も大きい。

いま動いているファームウェアの上に、新しいイメージを直接書くことはしない。書いている途中で通信や電源が切れると、機器には起動できるファームウェアが残らないからである。そこで、フラッシュメモリを次のように分けて使う。

イメージを 1 つ置くためのフラッシュメモリの領域をスロットという。新しいイメージは、いま動いているイメージとは別のスロットに書く。リセットの後に最初に動き、どのスロットのイメージを起動するかを決めて、そこへ処理を移す小さなプログラムを、ブートローダという。ブートローダは、自分自身を書き換えている途中で電源が切れると機器が起動できなくなるので、多くの場合、更新しない（IoT セキュリティシリーズ 13 章 6 節）。

更新は、次の 5 つの段で進む。

  1. 新しい版があるかを知る: 機器がサーバに定期的に問い合わせる（14 章 3 節の GET）、MQTT のメッセージで知らせを受ける、デバイスシャドウの desired に新しい版の番号が書かれる（15 章 6 節）、などの方法がある。BLE の機器では、スマートフォンのアプリが新しいイメージを持っていて、接続したときに機器の版を読んで判断することが多い。知らせには、新しい版の番号・イメージの大きさ・イメージのハッシュ・取り込む場所（URL）などを書いた小さなデータが付く。これをマニフェストという（形を決めた規格もある。IoT セキュリティシリーズ 13 章 8 節）。
  2. 取り込む（2〜4 節）: イメージを少しずつ受け取り、もう一方のスロットに書く。この間も、いまのファームウェアは動き続け、測定や通信を止めなくてよい。
  3. 確かめる（5 節）: 書いたイメージが、マニフェストに書かれたものと同じかを確かめる。
  4. 切り替えて起動する（6 節）: 再起動し、ブートローダが新しいイメージを起動する。再起動の間は機器の働きが止まるので、利用者が使っていない時間や、電池の残りが十分なときを選ぶ。
  5. 確定する（6 節）: 新しいイメージが正しく動き、サーバとつながることを確かめてから、以後もそれを起動すると決める。確かめられなければ、元のイメージに戻す。

Wi-Fi や LTE-M の機器は、自分でサーバからイメージを取りに行く。BLE の機器には、スマートフォンがイメージを送り込む。どちらでも 5 つの段は同じで、違うのは 2 段目の運び方である。

署名でイメージの作り手を確かめること、古い版に戻させないこと（ロールバック防止と呼ばれる）、イメージの暗号化といった、更新の安全の面は IoT セキュリティシリーズ 13 章 が詳しい。この章では、イメージを運ぶ・書く・確かめて切り替える仕組みに集中する。Matter の機器の更新の手順は Matter シリーズ 18 章、広く使われるブートローダ MCUboot のイメージとスロットの形は バイナリ解析シリーズ 08 章 にある。

2. 分けて運ぶ — チャンクと再開

例として、500 KB（512,000 バイト）のイメージを運ぶ（10 章 3 節の例と同じ大きさ）。機器の RAM には、イメージ全体を置く場所は無い。しかも、運んでいる間に通信が切れることがある。BLE ではスマートフォンが離れれば切れ、Wi-Fi や LTE-M でも電波が弱まれば切れる（15 章 2 節）。機器の電源が切れることもある。

チャンク・オフセット・再開

イメージを決まった大きさに分けた 1 つ 1 つを、この章ではチャンクという（14 章 2 節のチャンク形式は HTTP の本文の区切り方で、ここでのチャンクとは別のものである）。この章の例では、チャンクを 4 KB（4096 バイト）とする。15 章 3 節で見たとおり、フラッシュメモリは数 KB のまとまりごとに消してから書くので、チャンクの大きさをこのまとまりにそろえておくと、1 つのチャンクを「消して書く」の 1 回で扱える（3 節）。500 KB のイメージは、ちょうど 125 個のチャンクになる。

イメージの先頭から数えたバイトの位置をオフセットという。チャンク \(k\)（0 から数える）は、オフセット \(4096k\) から \(4096k + 4095\) までである。機器は、チャンクを 1 つ受け取るたびに、それをもう一方のスロットの同じオフセットに書き、続けて「書き終えたチャンクの数」をフラッシュメモリに記録する。

通信や電源が切れた後、記録した位置から続きを運ぶことを再開という。記録が \(m\) なら、オフセット \(4096m\) から頼み直せばよい。記録は、チャンクを書き終えた後に書く。この順番なら、2 つの間で電源が切れても、記録は 1 つ前の値のままで、そのチャンクをもう一度書くだけで済む。逆の順番では、記録だけが進み、書かれていないチャンクを書いたことにしてしまう（04 章 4 節で、データを書いてから head を進めたのと同じ考え方である）。記録は、15 章 3 節の列と同じく、同じ場所を書き直さずに順に書き足す。1 つの記録は、チャンクの数と、そのビットを反転した値の 8 バイトで、両者が合わない記録（書いている途中で電源が切れたもの）は読み飛ばす。新しい版の取り込みを始めるときに、記録の領域を消す。

HTTP — Range 要求で続きを頼む

Wi-Fi や LTE-M の機器は、マニフェストの URL に、HTTPS の GET でイメージを取りに行く。続きから頼むときは、要求のヘッダに Range: bytes=262144- のように欲しいバイトの範囲を書く（この例は「オフセット 262144 から最後まで」）。本文の一部だけを頼むこの要求を Range 要求という（RFC 9110）。対応しているサーバは、ステータスコード 206 Partial Content と、送る範囲を書いた Content-Range の欄を返す。

機器は、本文を書き始める前に 3 つを確かめる。206 であること（Range に対応しないサーバは、要求の Range を無視して、200 で先頭から全部を返す）、Content-Range の始まりが頼んだオフセットであること、全体の大きさがマニフェストの大きさと同じであること（違えば別のファイルである）。同じ URL の中身が、途中で別の版に替わらないようにもしておく。版の番号を URL に入れる（/fw/1.4.0.bin など）か、If-Range の欄に、最初の応答で受け取った ETag（サーバが中身ごとに付ける札）を書いて送る。If-Range を付けると、中身が替わっていれば、サーバは 206 ではなく 200 で全体を返す。

/* 10 進の数字の並びを読み、32 ビットに収まらなければ -1 */
static int read_u32(const char **s, uint32_t *v)
{
    const char *p = *s;
    uint32_t x = 0;
    if (*p < '0' || *p > '9') return -1;
    for (; *p >= '0' && *p <= '9'; p++) {
        if (x > (UINT32_MAX - (uint32_t)(*p - '0')) / 10) return -1;
        x = x * 10 + (uint32_t)(*p - '0');
    }
    *s = p; *v = x;
    return 0;
}

/* 続きを頼んだ応答を使ってよいかを確かめる。off: 書き終えたバイト数、size: イメージの大きさ。
   crange は Content-Range の値（例 "bytes 262144-511999/512000"。無ければ NULL） */
int resume_ok(int status, const char *crange, uint32_t off, uint32_t size)
{
    uint32_t first, last, total;
    const char *s = crange;
    if (status == 200) return off == 0 ? 0 : -1;  /* Range が無視された: 先頭から全部が来る */
    if (status != 206 || s == NULL || strncmp(s, "bytes ", 6) != 0) return -1;
    s += 6;
    if (read_u32(&s, &first) || *s++ != '-' || read_u32(&s, &last) ||
        *s++ != '/' || read_u32(&s, &total) || *s != '\0') return -1;
    if (first != off || total != size || last != size - 1) return -1;  /* 頼んだ所・同じ大きさか */
    return 0;
}

resume_ok が誤りを返したら、記録を消して最初から取り込み直すか、時間をおいて頼み直す。このコードは、正しい応答・始まりや大きさの違う応答・Range を無視した 200 の応答・形の壊れた応答（32 ビットを超える数を含む）の 18 通りで期待どおりに判定し、乱数で作った 20 万個の文字列でも配列の外を読まないことを AddressSanitizer で確かめた。

残りを 1 回の GET で頼めば、サーバは続けて送ってくるので、届いた分ずつ書けばよい（受け手が追いつかないときの止め方は 4 節）。1 チャンクずつ Range: bytes=262144-266239 のように頼む作り方もあるが、持続的接続を使っても、1 チャンクごとに 1 往復待つことになり、05 章 4 節のストップアンドウェイトと同じく、RTT が長いと遅くなる（7 節で数える）。CoAP では、ブロック転送の Block2 にブロックの番号を入れて頼む。ブロックの大きさが 1024 バイトなら、オフセットは番号 × 1024 で、4 つのブロックが 1 つのチャンクになる。

BLE — アプリケーションの確認を挟む

BLE の機器では、スマートフォンのアプリが GATT でイメージを書き込む。速く送るために、値は応答の無い Write Command（18 章 4 節）で送る。ATT_MTU を 247 にすれば、1 回に 244 バイトを書けるので、4096 バイトのチャンクは 17 回の書き込み（244 バイトが 16 回と、残りの 192 バイト）になる。

機器は、チャンクをフラッシュメモリに書き終えるたびに、書き終えたチャンクの数を通知で知らせる。スマートフォンは、最後に知らされたチャンクより先へは、決めた数（図では 2 つ）までしか送らない。10 章 3 節のスライディングウィンドウを、チャンクを単位として、アプリケーションの層で行うものである。BLE のリンク層も確認応答を取っている（18 章 4 節）が、それは機器のコントローラに届いたことしか示さない。アプリケーションの確認は、(1) フラッシュメモリに書き終えたことを示し、(2) 接続が切れたときに、どこまで届いていたかをスマートフォンに伝え、(3) 書き込みが遅いときにスマートフォンを待たせる（4 節）。始める・やめる・どこまで書いたかを聞く、といった命令は、コントロールポイントで受ける。接続し直したら、スマートフォンは、まず書き終えたチャンクの数を聞き、そこから送り直す。

最初からやり直すと、どれだけ遅くなるか

再開ができなければ、切れるたびに最初からやり直すことになる。2 つの場合で、終わるまでの時間の期待値を比べる。

方針: 1 つのチャンクを送るのに \(t_\mathrm{c}\) かかり、各チャンクを送る間に、ほかのチャンクとは独立に確率 \(q\) で接続が切れるとする（\(s = 1 - q\) を、そのチャンクが届く確率とする）。切れたときは、送っていたチャンクの時間 \(t_\mathrm{c}\) をまるごと失い（実際にはチャンクの途中で切れるので、多めの見積もりである）、つなぎ直すのに \(R\) かかる。最初から \(n\) 個のチャンクを全部届けるまでの時間の期待値 \(E_n\) を、最初の 1 回の試み（先頭から送り始め、切れるか最後まで届くまで）と、その後に分けて求める。

導出: 1 回の試みで、チャンク \(i\)（0 から数える）を送るのは、それより前の \(i\) 個がすべて届いたとき、つまり確率 \(s^i\) のときである。したがって、1 回の試みで送るチャンクの数の期待値は

\[ \sum_{i=0}^{n-1} s^i = \frac{1 - s^n}{1 - s} \]

である（等比数列の和）。試みが最後まで届く確率は \(s^n\) である。届かなければ（確率 \(1 - s^n\)）、つなぎ直す \(R\) の後に最初からの状態に戻り、その後にかかる時間の期待値は、また \(E_n\) である。よって

\[ E_n = t_\mathrm{c}\,\frac{1 - s^n}{1 - s} + (1 - s^n)\,(R + E_n) \]

が成り立つ。右辺の \((1 - s^n) E_n\) を左辺に移すと \(s^n E_n = t_\mathrm{c}(1 - s^n)/(1 - s) + (1 - s^n) R\) となり、両辺を \(s^n\) で割って

\[ E_n = \frac{t_\mathrm{c}\,(1 - s^n)}{(1 - s)\,s^n} + \left(\frac{1}{s^n} - 1\right) R \]

を得る。続きから運べる場合は、チャンクごとに、この式の \(n = 1\) の場合を繰り返すことになる。\(n = 1\) では \((1 - s)/(1 - s) = 1\) なので \(E_1 = t_\mathrm{c}/s + (1/s - 1) R\) で、\(n\) 個では \(n E_1\) である ∎

\(n E_1\) は \(n\) に比例して増えるだけだが、\(E_n\) には \(1/s^n\) が掛かる。\(s^n\) は一度も切れずに最後まで届く確率で、\(n\) が大きくなると急に小さくなる。

例: 19 章 3 節の (b) の BLE（スループットの実効値 20.3 kbps）で 500 KB を運ぶ。\(t_\mathrm{c} = 4096 \times 8 / 20300 \approx 1.614\) s で、切れなければ \(125 \times 1.614 \approx 201.8\) s である。つなぎ直しに \(R\) = 10 s かかるとする。

3. フラッシュに書く

15 章 3 節で見たとおり、フラッシュメモリ（以下フラッシュ）は、消すと全部のビットが 1 になり、書き込みでは 1 を 0 にしかできず、消すのは数 KB のまとまりごとである。イメージを書くときには、このまとまりの大きさと、消す・書くのにかかる時間が効いてくる。

一度に消せる最小のまとまりを消去単位という（15 章 3 節で「消すまとまり」と呼んだもの。製品によってセクタ・ページ・ブロックと呼ぶ）。一度に書く最小のまとまりを書き込み単位という。消去単位 1 つを消すのにかかる時間を消去時間、書き込み単位 1 つ（または 1 回の書き込みの命令）にかかる時間を書き込み時間という。

図の下段のように、書いてある所にもう一度書くと、1 を 0 にする分しか効かず、結果は 2 つの値のビットごとの AND になる。書き直すには、消去単位ごと消すしかない。さらに、書き込み単位ごとに誤り訂正の符号を付けているフラッシュでは、同じ書き込み単位に 2 回書くこと自体が許されないことが多い（製品による）。

表の値は代表値で、製品・温度・書き換えた回数で変わる。データシートには標準の値と最大の値があり、最大は標準の数倍のことが多い。この章の計算では、次の値を例として使う。消去単位 4 KB・消去時間 30 ms、書き込み単位 8 バイト・書き込み時間 40 µs である。4 KB のチャンクを書くには、消去に 30 ms、書き込みに 512 × 40 µs = 20.48 ms、合わせて 50.48 ms かかり、書く速さは 4096 ÷ 0.05048 s ≈ 81,141 B/s（約 79.2 KB/s、649.1 kbps）になる。

チャンクを書く

チャンクの大きさを消去単位にそろえてあるので、チャンクを書く前に、その消去単位を 1 回消せばよい。

#define CHUNK 4096u                   /* チャンク = 消去単位の大きさ（この例） */
#define WUNIT 8u                      /* 書き込み単位（この例） */

/* チャンク k（len バイト。最後のチャンクだけ CHUNK より短い）を、スロットの先頭 base からの位置に書く。
   buf は CHUNK バイトの RAM のバッファで、端数を埋めるのに使う */
int chunk_store(uint32_t base, uint32_t k, uint8_t *buf, uint32_t len)
{
    uint32_t a = base + k * CHUNK;
    uint32_t n = (len + WUNIT - 1) / WUNIT * WUNIT;    /* 書き込み単位の倍数に切り上げる */
    uint8_t  r[256];
    memset(buf + len, 0xFF, n - len);                  /* 端数は消した状態と同じ 0xFF で埋める */
    if (flash_erase(a) != 0) return -1;                /* 書きかけが残っていても、消してから書く */
    for (uint32_t i = 0; i < n; i += WUNIT)
        if (flash_write(a + i, buf + i, WUNIT) != 0) return -1;
    for (uint32_t i = 0; i < n; i += sizeof r) {       /* 読み直して、書いたとおりかを確かめる */
        uint32_t m = (n - i < sizeof r) ? n - i : (uint32_t)sizeof r;
        flash_read(a + i, r, m);
        if (memcmp(r, buf + i, m) != 0) return -1;
    }
    return 0;
}

flash_erase（消去単位を消す）・flash_write・flash_read は、15 章 3 節と同じく、この章で仮に置く関数で、実際のマイコンではフラッシュの回路を操作する。書く前に必ず消すのは、電源が切れて書きかけで残ったチャンクを、再開のときに書き直せるようにするためである。最後のチャンクの端数は、書き込み単位の倍数まで、消した状態と同じ 0xFF で埋める。書いた後に読み直して比べ、書き込みの失敗をその場で見つける。2 節の記録と合わせて、このコードを、消すと 0xFF になり、1 を 0 にしかできず、消していない書き込み単位への書き込みを誤りとして止める模型のフラッシュの上で確かめた。大きさの違う 400 個のイメージを、消去や書き込みの途中でわざと電源を切りながら（合わせて 6000 回）書き、再開を繰り返して、どれも元のイメージと一致した。

スロット全体を最初にまとめて消しておく作り方もある。例の値では 125 × 30 ms = 3.75 s かかり、その間は受信を止めておくことになる。チャンクを書く直前にその消去単位だけを消せば、消去時間が取り込みの間に分散し、4 節のように受信と重ねられる。

書き込み回数の上限（15 章 3 節）は、更新では問題になりにくい。1 回の更新では、スロットの各消去単位を 1 回ずつ消すだけなので、上限が 1 万回でも、更新の回数がそれに届くことはまず無い。2 節の記録は 1 チャンクごとに 8 バイトを書き足すので、125 個で 1000 バイトになり、4 KB の消去単位 1 つに収まる（消すのは更新 1 回につき 1 回）。

消している間、CPU が止まることがある

マイコンの内蔵のフラッシュは、プログラムを置く場所でもある。フラッシュの中で、ほかと独立に読み書きできるまとまりをバンクという。多くのマイコンでは、あるバンクを消したり書いたりしている間、同じバンクからは読み出せない。プログラムをそこから実行していると、命令を読めずに CPU が止まり、例の値では 1 回の消去で 30 ms 止まる。

その間は割り込みも処理されない。115200 bps の UART からは 86.8 µs ごとに 1 バイトが届く（02 章 2 節）ので、30 ms の間に約 345 バイトが届き、受信の回路があふれてオーバーランになる。無線の回路を内蔵した SoC では、無線のスタックが決まった時刻に送受信できなくなる。そこで、次のどれかを取る。

  • フラッシュが 2 つのバンクに分かれていて、一方を消し書きしている間も他方から読めるマイコンでは、新しいイメージを書くスロットを、プログラムを実行しているのとは別のバンクに置く。
  • フラッシュを操作する関数と、その間に動く割り込みハンドラを RAM に置いて実行する。
  • 新しいイメージを外付けの SPI のフラッシュに書く。内蔵のフラッシュには触らないので、CPU は止まらない。
  • 無線のスタックを同じチップで動かす SoC では、スタックが用意する手順でフラッシュを操作する。スタックが、無線の送受信の予定の合間に消し書きを割り当てる（仕組みと名前は製品による）。

4. 受信と書き込みを重ねる

チャンクを受信する速さを \(v_\mathrm{r}\)（バイト/秒）、フラッシュに書く速さ（消去を含む）を \(v_\mathrm{w}\) とする。チャンクの大きさを \(c\) とすると、1 つのチャンクを受信する時間は \(t_\mathrm{r} = c/v_\mathrm{r}\)、書く時間は \(t_\mathrm{w} = c/v_\mathrm{w}\) である。

RAM のバッファが 1 つだけなら、受信したチャンクを書き終えるまで、次のチャンクを受け取る場所が無い。1 つのチャンクに \(t_\mathrm{r} + t_\mathrm{w}\) かかり、受信と書き込みのどちらかが、いつも休んでいる。

同じ大きさのバッファを 2 つ用意し、一方に受信している間に、もう一方をフラッシュに書く使い方を、ダブルバッファという。このように、処理をいくつかの段に分け、ある段が次のデータを扱っている間に、別の段が前のデータを扱うように重ねることを、パイプラインという（ここでは受信と書き込みの 2 段である）。

方針: チャンク \(k\)（1 から数える）の受信が終わる時刻を \(A_k\)、書き込みが終わる時刻を \(B_k\) とする。それぞれの段がいつ始められるかの条件から漸化式を立てて、\(n\) 個のチャンクを書き終える時刻 \(B_n\) を求める。

導出: 受信の段は 1 つなので、チャンク \(k\) の受信は、チャンク \(k-1\) の受信が終わってから始まる。さらに、チャンク \(k\) は 2 つ前のチャンク \(k-2\) と同じバッファを使うので、チャンク \(k-2\) を書き終えてからでないと始まらない。書き込みの段も 1 つなので、チャンク \(k\) の書き込みは、その受信が終わり、かつチャンク \(k-1\) を書き終えてから始まる。\(A_0 = B_0 = B_{-1} = 0\) として

\[ A_k = \max(A_{k-1},\, B_{k-2}) + t_\mathrm{r}, \qquad B_k = \max(A_k,\, B_{k-1}) + t_\mathrm{w} \]

である。2 つの場合に分ける。

  • \(t_\mathrm{r} \ge t_\mathrm{w}\) のとき、\(A_k = k t_\mathrm{r}\)、\(B_k = k t_\mathrm{r} + t_\mathrm{w}\) となる。\(k = 1\) では \(A_1 = t_\mathrm{r}\)、\(B_1 = t_\mathrm{r} + t_\mathrm{w}\) で成り立つ。\(k - 1\) まで成り立つとすると、\(B_{k-2} = (k-2)t_\mathrm{r} + t_\mathrm{w} \le (k-1) t_\mathrm{r} = A_{k-1}\) なので \(A_k = (k-1)t_\mathrm{r} + t_\mathrm{r} = k t_\mathrm{r}\) となる。また \(B_{k-1} = (k-1)t_\mathrm{r} + t_\mathrm{w} \le k t_\mathrm{r} = A_k\) なので \(B_k = k t_\mathrm{r} + t_\mathrm{w}\) となり、\(k\) でも成り立つ。
  • \(t_\mathrm{r} < t_\mathrm{w}\) のとき、\(B_k = t_\mathrm{r} + k t_\mathrm{w}\) となる（書き込みが休みなく続く）。\(A_1 = t_\mathrm{r}\)、\(A_2 = 2t_\mathrm{r}\) で、\(k \ge 3\) では \(A_k = B_{k-2} + t_\mathrm{r} = 2 t_\mathrm{r} + (k-2) t_\mathrm{w}\) である（\(A_{k-1} \le B_{k-2}\) を確かめると、差は \(t_\mathrm{w} - t_\mathrm{r} \ge 0\) になる）。\(k \ge 2\) では \(A_k \le B_{k-1}\)（差はやはり \(t_\mathrm{w} - t_\mathrm{r}\)）なので \(B_k = B_{k-1} + t_\mathrm{w}\) となり、\(B_1 = t_\mathrm{r} + t_\mathrm{w}\) から \(B_k = t_\mathrm{r} + k t_\mathrm{w}\) を得る。

どちらの場合も

\[ B_n = t_\mathrm{r} + t_\mathrm{w} + (n - 1)\max(t_\mathrm{r},\, t_\mathrm{w}) \]

と書ける。\(n\) が大きいとき、1 つのチャンクにかかる時間は \(\max(t_\mathrm{r}, t_\mathrm{w})\) に近づくので、平均の速さは \(c / \max(t_\mathrm{r}, t_\mathrm{w}) = \min(v_\mathrm{r}, v_\mathrm{w})\) になる ∎

例: 19 章 3 節の (a) の BLE（スループットの実効値 865.4 kbps、\(v_\mathrm{r}\) = 108,175 B/s）で受け取り、3 節の例の値（\(v_\mathrm{w}\) = 81,141 B/s）で書く。\(t_\mathrm{r}\) = 37.9 ms、\(t_\mathrm{w}\) = 50.5 ms である。バッファが 1 つなら、125 個のチャンクに \(125 \times (37.9 + 50.5)\) ms ≈ 11.0 s かかる。ダブルバッファなら \(B_{125} = 37.9 + 50.5 + 124 \times 50.5\) ms ≈ 6.35 s で、速さは書く速さの 79.2 KB/s で決まる。BLE の回線だけなら 4.7 s で運べるが、書くほうが遅いので、それより速くはならない。

バッファを 3 つ以上にしても、平均の速さは \(\min(v_\mathrm{r}, v_\mathrm{w})\) を超えない。それでも増やす意味があるのは、速さが揺れるときである。消去がときどき長くかかる（3 節の表の最大の値）とき、受信がまとまって届くときに、余分なバッファが揺れを吸収し、受信を止める時間を減らす。

書くのが遅いときは、送り手を止める

\(v_\mathrm{r} > v_\mathrm{w}\) なら、やがて 2 つのバッファが両方とも書き込み待ちになり、それ以上は受け取れない。その後に届いたデータは置く場所が無いので、送り手のほうを止める。

  • TCP（HTTP）: 空いたバッファができるまで、ソケットから読まない。スタックの受信バッファが埋まると受信ウィンドウが 0 になり、サーバは送るのを止める（10 章 3 節）。lwIP の raw API では、受け取った分を tcp_recved で知らせるのを、そのデータをバッファに入れられてからにする（11 章 7 節）。
  • BLE: 2 節のとおり、機器はチャンクを書き終えてから確認を返し、スマートフォンは確認されていないチャンクを決めた数までしか送らない。決めた数を、機器のバッファの数に合わせる。
  • CoAP: 空いたバッファができてから、次のブロックを頼む。

02 章 6 節のフロー制御と同じく、受け手の空きを送り手に伝える仕組みは、どの層にもある。

ダブルバッファの受け渡しの部分を示す。受信側（ネットワークの受信のコールバック）と書き込み側（書き込みのタスク）が、バッファを 1 つずつ受け渡す。

#define NBUF 2
struct dbuf {
    uint8_t  data[NBUF][CHUNK];
    uint32_t len[NBUF];
    volatile uint8_t full[NBUF];    /* 0 → 1 は受信側だけ、1 → 0 は書き込み側だけが変える */
    uint32_t rx_i, rx_fill, rx_left; /* 受信側: 埋めているバッファ・その中のバイト数・イメージの残り */
    uint32_t wr_i, wr_k;            /* 書き込み側: 次に書くバッファ・そのチャンクの番号 */
};

/* 受信側: 届いた p[0..n-1] を入れ、受け取ったバイト数を返す。n より少なければ、残りは後で渡し直す */
size_t dbuf_put(struct dbuf *d, const uint8_t *p, size_t n)
{
    size_t used = 0;
    while (used < n && d->rx_left > 0) {
        uint32_t i = d->rx_i;
        if (d->full[i]) break;                     /* 空いたバッファが無い: ここで受け取りを止める */
        uint32_t k = CHUNK - d->rx_fill;
        if (k > d->rx_left) k = d->rx_left;
        if (k > n - used) k = (uint32_t)(n - used);
        memcpy(d->data[i] + d->rx_fill, p + used, k);
        d->rx_fill += k; d->rx_left -= k; used += k;
        if (d->rx_fill == CHUNK || d->rx_left == 0) {
            d->len[i] = d->rx_fill;                /* データと長さを置いてから、印を変えて渡す */
            d->full[i] = 1;
            d->rx_i = (i + 1) % NBUF; d->rx_fill = 0;
        }
    }
    return used;
}

/* 書き込み側: 渡されたバッファがあれば 1 つ書いて返す。書けば 1、無ければ 0、失敗は -1 */
int dbuf_write_one(struct dbuf *d, uint32_t base)
{
    uint32_t i = d->wr_i;
    if (!d->full[i]) return 0;
    if (chunk_store(base, d->wr_k, d->data[i], d->len[i]) != 0) return -1;
    prog_append(++d->wr_k);                        /* 書き終えたチャンクの数を記録する（2 節） */
    d->wr_i = (i + 1) % NBUF;
    d->full[i] = 0;                                /* 書き終えてから、受信側に返す */
    return 1;
}

full[i] は、0 から 1 へは受信側だけが、1 から 0 へは書き込み側だけが変える。受信側はデータと長さを置いてから full[i] を 1 にし、書き込み側はフラッシュに書き終えてから 0 に戻すので、04 章 4 節の SPSC のリングバッファと同じ理由で、割り込みを止めずに受け渡せる。prog_append は 2 節の記録を書き足す関数（省略）である。dbuf_put が、渡したバイト数より小さい値を返したら、受信側は残りを手元に置いて、ソケットから読むのをやめる（BLE なら、確認が返るまでスマートフォンが待つ）。このコードを、届く区切り（1〜3000 バイト）と、受信側と書き込み側が動く順番を乱数で変えながら、大きさの違う 300 個のイメージで確かめた。受け取りを止めた 15,516 回を含めて、どれもフラッシュの中身が元のイメージと一致し、記録したチャンクの数も合った。

5. 届いたイメージを確かめる

書き終えたイメージを起動する前に、それが正しいものかを確かめる。何が起こりうるかと、それぞれを何で見つけるかを図に並べる。

  1. 大きさ: 受け取ったバイト数が、マニフェストの大きさと同じか。
  2. ハッシュ: 書いたイメージ全体のハッシュ（SHA-256 なら 32 バイト）が、マニフェストのハッシュと一致するか。通信の途中での化け、フラッシュの書き込みの失敗、再開の位置の誤り（同じチャンクを 2 回書いた、1 つ飛ばした）、別のファイルを受け取ったこと、のどれでも一致しなくなる。CRC でも偶然の誤りには気づけるが、わざと作り替えたデータを、同じ CRC になるように直すのは易しい（暗号と誤り訂正シリーズ 09 章 7 節）。
  3. 署名: ハッシュが一致しても、イメージとマニフェストの両方を差し替えられていれば意味が無い。そこで、マニフェストに作り手の秘密鍵で署名しておき、機器は、持っている公開鍵でそれを確かめる。TLS は、サーバとの間の通信路を守るが、サーバに置かれたイメージが正しい作り手のものかは示さない。スマートフォンを通す BLE の経路では、TLS も使わない。手順は IoT セキュリティシリーズ 05 章 と PSA シリーズ 09 章 4 節 にある。
  4. 版: この機器（ハードウェアの種類）向けで、いまの版より新しいか。わざと古い版を入れて、直したはずの弱点を戻す攻撃への備え（ロールバック防止）は、IoT セキュリティシリーズ 13 章 4 節 にある。

受信しながらハッシュを計算する

ハッシュは、データを少しずつ入れながら計算できる（PSA シリーズ 05 章 4 節）。dbuf_put が受け取ったバイトを、そのままハッシュの計算に入れていけば、書き終えたときにはハッシュもでき上がっていて、イメージ全体を読み直す必要が無い。

ただし、ハッシュの計算の途中の状態は RAM にあるので、電源が切れて再開するときには失われている。そこで再開のときは、書き終えた先頭の部分をフラッシュから読み直して、ハッシュの計算を作り直してから、続きを受け取る。

/* 再開するとき: 書き終えた先頭 off バイトをフラッシュから読み直して、ハッシュの計算を作り直す */
psa_status_t hash_rebuild(psa_hash_operation_t *op, uint32_t base, uint32_t off)
{
    uint8_t b[256];
    psa_status_t st = psa_hash_setup(op, PSA_ALG_SHA_256);
    for (uint32_t i = 0; st == PSA_SUCCESS && i < off; i += sizeof b) {
        uint32_t m = (off - i < sizeof b) ? off - i : (uint32_t)sizeof b;
        flash_read(base + i, b, m);
        st = psa_hash_update(op, b, m);
    }
    return st;
}

psa_hash_setup・psa_hash_update は、PSA Crypto API の関数である。受信側は、dbuf_put が受け取ったバイトを psa_hash_update に入れる。最後のチャンクまで受け取ったら、psa_hash_verify(op, expected, 32) でマニフェストのハッシュと比べる（一致すれば PSA_SUCCESS）。比べるのに専用の関数を使う理由は、PSA シリーズ 05 章 3 節 にある。読み直しにかかる時間の多くはハッシュの計算で、ソフトウェアで計算する SHA-256 は 1 秒に 1 MB 程度（代表値。暗号の計算をする回路があればもっと速い）なので、500 KB を全部読み直しても 0.5 s 程度である。このコードを Mbed TLS 3.6.7 の PSA Crypto API で動かし、取り込みの途中で 0〜5 回、RAM の中身を失う再起動をはさんだ 60 回の取り込みのすべてで、ハッシュが期待値（Python の hashlib で計算した値と同じ）と一致し、フラッシュの 1 ビットを反転させると一致しなくなることを確かめた。

機器が確かめた後も、ブートローダは起動のたびにイメージを確かめ直す（IoT セキュリティシリーズ 13 章 2 節）。確かめてから起動するまでの間に、フラッシュの中身が書き換えられる場合に備えるためである。

6. 切り替えと確定

確かめたイメージに、どう切り替えるか。スロットの使い方には、主に 3 つの形がある。

  • (a) A/B: 2 つのスロットのどちらからでも、イメージをその場所のまま実行できるようにしておく。ブートローダが起動するスロットを替えるだけで切り替わり、元のイメージもそのまま残る。ただし、イメージはふつう、置かれる番地を決めて作るので、スロットごとに別のイメージを用意する（または、番地を読み替える回路を持つマイコンを使う）必要がある。
  • (b) スワップ: イメージは、いつも 1 つ目のスロットで実行する。新しいイメージは 2 つ目のスロットに書き、ブートローダが、2 つのスロットの中身を消去単位ごとに入れ替える。この入れ替えをスワップという。中身を一時的に置く予備の消去単位を使い、どこまで入れ替えたかをフラッシュに記録しながら進めるので、途中で電源が切れても続きから進められる。入れ替えた後は、元のイメージが 2 つ目のスロットに残るので、もう一度入れ替えれば戻せる。消去単位 1 つにつき、消して書くことを 3 回（2 つのスロットと予備）行うとすると、例の値では 125 × 3 × 50.48 ms ≈ 19 s かかる（方式による）。
  • (c) 上書き: 2 つ目のスロットの新しいイメージを、1 つ目のスロットに写す。簡単だが、元のイメージは消えるので、新しいイメージが動かなかったときに戻れない。写している途中で電源が切れても、新しいイメージは 2 つ目のスロットに残っているので、写し直せばよい。

MCUboot は、これらのいくつかを選べるようにしている（IoT セキュリティシリーズ 13 章 3 節。スロットの状態の記録は バイナリ解析シリーズ 08 章 5 節）。以下では、元のイメージが残る (a) で考える。(b) でも考え方は同じである。

試しの起動と確定

新しいイメージは、ハッシュと署名が正しくても、動くとは限らない。起動の途中で止まる、ある周辺回路でだけ固まる、Wi-Fi やサーバにつながらない、といった不具合は、動かしてみるまで分からない。とくに、つながらないイメージは致命的である。一度それに切り替わると次の更新を受け取れないので、遠くからは二度と直せない。

そこで、新しいイメージを、まだ確定していない状態で起動する。これを試しの起動という。新しいイメージは自己診断を行い、通ったら、以後もそれを起動すると決める。これを確定という。確定しないまま再起動したら、ブートローダは元のイメージを起動する。これをロールバックという（1 節で名前を挙げた、古い版を入れさせない「ロールバック防止」とは別のものである）。

ブートローダが、試しの起動の途中で再起動したことを知れるように、フラッシュに印を残す。各スロットに 3 つの印を置き、どれも、消した状態（0xFF）から 0x00 に 1 回だけ書く。

  • 試してほしい（PENDING）: 取り込んで確かめ終えたとき、いまのファームウェアが書く。
  • 試し始めた（TRIED）: 試しの起動に入る直前に、ブートローダが書く。
  • 確定した（OK）: 自己診断に通ったとき、新しいイメージが書く。
enum { F_PENDING, F_TRIED, F_OK };  /* 試してほしい・試し始めた・確定した */
static int is_set(int s, int f)   { return flag_read(s, f) == 0x00; }
static int is_clear(int s, int f) { return flag_read(s, f) == 0xFF; }  /* 書きかけは、どちらでもない */

/* ブートローダ: 起動するスロットの番号を返す（-1 は、起動できるものが無い） */
int boot_select(void)
{
    for (int s = 0; s < 2; s++)       /* 試しの起動を待つスロットがあれば、印を書いてから起動する */
        if (is_set(s, F_PENDING) && is_clear(s, F_TRIED) && is_clear(s, F_OK) && image_valid(s)) {
            flag_set(s, F_TRIED);
            return s;
        }
    int best = -1;                    /* それ以外は、確定したスロットのうち版の新しいほう */
    for (int s = 0; s < 2; s++)
        if (is_set(s, F_OK) && image_valid(s) && (best < 0 || image_ver(s) > image_ver(best)))
            best = s;
    return best;
}

/* 新しいイメージの側: 試しの起動中なら、自己診断に通ったときだけ確定する */
void confirm_if_trial(int me, int self_test_passed)
{
    if (is_set(me, F_TRIED) && is_clear(me, F_OK) && self_test_passed)
        flag_set(me, F_OK);
}

flag_read・flag_set（印を読む・書く。印は 1 つずつ別の書き込み単位に置く）・image_valid（5 節のハッシュと署名を確かめる）・image_ver（イメージの版の番号を読む）は、この章で仮に置く関数である。印は書き足すだけで書き直さないので、消去単位を消す必要が無い。印を書いている途中で電源が切れると、0xFF でも 0x00 でもない値が残ることがある。is_set と is_clear はその値をどちらとも見なさないので、書きかけの印は、新しいイメージを起動しない側に働く。

起こりうる流れを追う。

  • 取り込みの途中で電源が切れた: 新しいスロットには PENDING が無いので、元のイメージを起動する。2 節の記録から再開する。
  • PENDING を書いて再起動した: ブートローダは TRIED を書いてから、新しいイメージを起動する。
  • 新しいイメージが自己診断に通った: OK を書く。以後は、確定したスロットのうち版の新しいほうとして、新しいイメージが起動する。
  • 新しいイメージが固まった、自己診断に通らなかった、試しの起動の途中で電源が切れた: OK が書かれないまま再起動する。新しいスロットには TRIED があるので試しは繰り返されず、確定した元のイメージが起動する（ロールバック）。

固まったときに再起動させるのは、ウォッチドッグタイマである。自己診断に通らないことが分かったときは、新しいイメージが自分で再起動すればよい。このコードを、模型のフラッシュの上で、印を書く途中を含むあらゆる位置でわざと電源を切りながら（7305 回）、取り込み・試しの起動・自己診断の成功と失敗を乱数で選んで 3000 通り（起動 119,999 回）動かした。いつも完全なイメージを起動すること、確定していないイメージを起動するのは試しの最初の 1 回だけであること、試しが失敗した後は、いつも確定済みの最も新しい版に戻ることを確かめた。

自己診断には、少なくとも次を含める。起動を終え、すべてのタスクが動いていること（05 章 6 節の監視タスクへのチェックイン）。Wi-Fi・IP・DNS・TLS・MQTT と順につながり（15 章 2 節）、更新を配るサーバに届くこと。時間の上限も決めておき（例 10 分）、その間に確定できなければ、自分で再起動する。確定した版は、デバイスシャドウの reported などでサーバに知らせる。サーバは、どの機器が更新に成功し、どの機器が元に戻ったかを知ることができる。BLE の機器では、更新で GATT の表が変わることがあるので、18 章 6 節の Service Changed で知らせる。

確定をどの時点で行うかは、安全の面からも決める。古い版に戻させない仕組みのカウンタを、どこで進めるかと関係するからである（IoT セキュリティシリーズ 13 章 4 節）。

下の図で、ボタンを押して更新の各段を進めると、2 つのスロットの印と、ブートローダがどちらを起動するかが表示される。試しの起動で固まらせたり、印を書く途中で電源を切ったりして、ロールバックの様子を確かめられる。

7. 転送時間を見積もる

ここまでの結果を合わせると、イメージを取り込む時間を見積もれる。

方針: 4 節のとおり、受信と書き込みを重ねれば、取り込みの速さは、途中の段の速さのうち最も小さいものになる。受信の速さには、回線の実効の速さのほかに、10 章 3 節の「スループット ≤ ウィンドウ ÷ RTT」と、1 往復に 1 ブロックしか運ばない方式の上限が効く。それぞれの上限を求め、最も小さいものでイメージの大きさを割る。

導出: 回線の実効の速さを \(v_\mathrm{link}\)、TCP の受信ウィンドウを \(W\)、往復時間を RTT、フラッシュに書く速さを \(v_\mathrm{w}\) とする。TCP では、受信の速さは \(W/\mathrm{RTT}\) を超えないので、取り込みの速さは

\[ v_\mathrm{TCP} = \min\left(v_\mathrm{link},\ \frac{W}{\mathrm{RTT}},\ v_\mathrm{w}\right) \]

である。1 往復に \(b\) バイトのブロックを 1 つずつ運ぶ方式（CoAP のブロック転送、1 チャンクずつの Range 要求）では、1 つのブロックに、送る時間 \(b/v_\mathrm{link}\) と RTT がかかるので

\[ v_\mathrm{blk} = \min\left(\frac{b}{b/v_\mathrm{link} + \mathrm{RTT}},\ v_\mathrm{w}\right) \]

である（1 つ目は、05 章 4 節の効率に \(v_\mathrm{link}\) を掛けたもの）。大きさ \(S\) のイメージの取り込みには \(S/v\) かかる ∎

500 KB の取り込みの時間を、次の仮定で計算する。TCP の受信ウィンドウは 11 章 7 節の例の 5840 バイト、書く速さは 3 節の例の 81,141 B/s（649.1 kbps）とする。回線の速さと RTT は代表値で、場所と条件で大きく変わる。

表と図から、次のことが分かる。

  • 速い経路では、フラッシュに書く速さが上限になる。BLE の (a) でも Wi-Fi の LAN でも 6.3 s で、回線を速くしても縮まない。
  • クラウドのサーバからの TCP の取り込みは、機器の受信ウィンドウで決まる。ウィンドウを 2 倍にすれば（そのための RAM が要る。11 章 7 節）、書く速さに届くまでは速さも 2 倍になる。
  • 1 往復に 1 ブロックの方式は、RTT の長い LTE-M では、TCP より大幅に遅い。
  • DLE などがそろわない BLE は、回線そのもので決まる。2 節のとおり、時間が長いほど切れる回数も増える。

取り込みのほかにも時間がかかる。接続（Wi-Fi への接続・DNS・TCP と TLS のハンドシェイク）、5 節の確認（読み直すなら 0.5 s 程度）、6 節の切り替え（A/B なら再起動だけ、スワップなら例の値で約 19 s）である。速い経路では、スワップの時間のほうが取り込みより長くなる。

LoRaWAN では現実的でない

LoRaWAN で同じ 500 KB を運ぶとどうなるかを見積もる。1 回に送れるデータは、EU868 では SF7 で 242 バイト、SF12 で 51 バイトまでである（21 章 5 節）。毎回これだけ載せるとする。21 章 3 節の空中時間の式で（帯域幅 125 kHz、符号化率 4/5、プリアンブル 8、明示ヘッダと CRC あり、SF12 では LDRO あり）、242 バイトのデータ（LoRaWAN のヘッダなど 13 バイトを足して 255 バイト）を SF7 で送ると、空中時間は 399.6 ms である。51 バイト（64 バイト）を SF12 で送ると 2793.5 ms になる。デューティサイクル 1 %（21 章 4 節の欧州の例）なら、送った後は空中時間の 99 倍の時間は送れないので、送り始めの間隔は空中時間の 100 倍になる。500 KB を運ぶには、SF7 では 2116 回 × 40.0 s ≈ 23.5 時間、SF12 では 10,040 回 × 279.3 s ≈ 32.5 日かかる。

これは、1 台の機器が、規則の上限まで休まず受け取り続けた場合の値である。実際には、イメージは下りなので、送るのはゲートウェイで、ゲートウェイの送信の時間も同じ規則に従い、多くの機器で分け合う（21 章 4 節）。クラス A の機器は、上りを送った後の受信窓でしか下りを受け取れない（21 章 5 節）。日本の 920 MHz 帯にも、送信時間と休む時間の規則がある（21 章 4 節）。したがって、LoRaWAN の機器では、イメージ全体を送る更新は現実的でない。変わった部分だけを送る、設定の値で振る舞いを変えられるように作っておく、近くから BLE などで更新する、といった別の手段を考える。
