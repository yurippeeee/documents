Chapter 11

ソケットと組み込みの TCP/IP スタック — UDP と lwIP

この章で扱う問い. 07 章では TCP と UDP のヘッダを、10 章では TCP がバイトに番号を付け、失われた分を送り直して順番どおりに届ける仕組みを見た。この章では、それを使う側に回る。機器のアプリケーションは、どんな関数を呼んで接続し、送り、受け取るのか。その関数を受け持つマイコンの TCP/IP スタックは、どんな作りで、どれだけの RAM を使うのか。

この章では次の 3 つの問いに答える。

  1. 接続・送信・受信の関数は、それぞれどのパケットとつながっていて、戻り値で何を約束し、何を約束しないのか。
  2. 待たずに送受信するには、どうすればよいのか。失敗したときは、その理由をどう見分けて、どう立て直すのか。UDP では何が違うのか。
  3. マイコン向けの TCP/IP スタック lwIP は、どんな部品でできていて、RAM の量と速さの上限は何で決まるのか。

答えの道具は、関数の戻り値を確かめて足りない分を繰り返す書き方と、ウィンドウの大きさと RTT から RAM と速さを見積もる計算である。

この章で使う既出の用語（定義は各リンク先）. 機器・ゲートウェイ・サーバ・クラウド（01 章 1 節）、プロトコルスタック（スタック）（01 章 2 節）、RAM・KB・ドライバ・RTOS（01 章 4 節）、受信バッファ（02 章 6 節）、メッセージ（03 章 1 節）、長さフィールド（03 章 4 節）、ネットワークバイトオーダ（03 章 6 節）、割り込みハンドラ（ISR）・DMA（04 章 1 節）、ブロッキング・ノンブロッキング・イベント駆動・イベントループ・コールバック・通信タスク（05 章 2 節）、ティック（05 章 3 節）、確認応答（ACK）・ARQ・シーケンス番号・往復時間（RTT）（05 章 4 節）、指数バックオフ・ジッタ（05 章 5 節）、Ethernet フレーム（07 章 2 節）、IP・パケット（07 章 3 節）、ポート番号・UDP・TCP・セグメント（07 章 4 節）、カプセル化（07 章 5 節）、MTU・MSS・フラグメンテーション（07 章 6 節）、DHCP・リース（08 章 3 節）、DNS・名前解決（08 章 4 節）、NAT（08 章 5 節）、コネクション・SYN・FIN・RST・3 ウェイハンドシェイク（10 章 1 節）、帯域幅遅延積・受信ウィンドウ（10 章 3 節）、Nagle アルゴリズム・遅延 ACK・TCP の送信バッファ・制御ブロック（10 章 6 節）、ハーフオープン・TCP キープアライブ（10 章 7 節）

1. ソケット API — 接続して送って受ける

アプリケーションは、TCP や UDP の処理を自分では書かない。IP・TCP・UDP と、ARP・DHCP・DNS（08 章）などをまとめて実装したプロトコルスタックを TCP/IP スタックという。PC やスマートフォンでは OS の一部として、マイコンでは 6 節で見る lwIP のようなライブラリとして動く。アプリケーションは、TCP/IP スタックの関数を呼んで通信する。

その関数の組として最も広く使われているのが、BSD UNIX で作られ、POSIX（UNIX 系の OS に共通の規格）で決められた BSD ソケット API（以下、ソケット API）である。Linux や macOS のほか、多くのマイコン向けの TCP/IP スタックも同じ形の関数を持つ。ソケット API では、アプリケーションから見た通信の端点をソケットという。アプリケーションはソケットを作り、それを指定して送受信する。

TCP のソケットは、1 つのコネクション（以下、接続と書く）に対応し、スタックの中に 10 章で見た 2 つのバッファを持つ。送信バッファには、アプリケーションから受け取ったが、まだ確認応答の来ていないデータが入る（再送に備えて持ち続ける）。受信バッファには、届いたがアプリケーションがまだ取り出していないデータが入り、その空きが受信ウィンドウとして相手に知らされる。アプリケーションが呼ぶ関数は、このバッファとの間でデータを写すだけで、パケットの送受信はスタックが受け持つ。

TCP で接続し、送って受け取る関数を、Linux で書く。

/* host の port 番に TCP で接続し、ソケットのファイル記述子を返す。失敗なら -1 */
int tcp_open(const char *host, const char *port)
{
    struct addrinfo hints, *res, *ai;
    memset(&hints, 0, sizeof hints);
    hints.ai_family = AF_UNSPEC;              /* IPv4 でも IPv6 でもよい */
    hints.ai_socktype = SOCK_STREAM;          /* TCP */
    if (getaddrinfo(host, port, &hints, &res) != 0)
        return -1;                            /* 名前解決の失敗（4 節） */
    int fd = -1;
    for (ai = res; ai != NULL; ai = ai->ai_next) {   /* 得たアドレスを順に試す */
        fd = socket(ai->ai_family, ai->ai_socktype, ai->ai_protocol);
        if (fd < 0)
            continue;
        if (connect(fd, ai->ai_addr, ai->ai_addrlen) == 0)
            break;                            /* 3 ウェイハンドシェイクが終わった */
        int e = errno;
        close(fd);                            /* このアドレスでは失敗: 次を試す */
        errno = e;
        fd = -1;
    }
    freeaddrinfo(res);
    return fd;
}

/* 使い方: 7 バイトを送り、応答を受け取って閉じる（戻り値の扱いは 2・4 節で補う） */
int fd = tcp_open("server.example.com", "5000");
if (fd >= 0) {
    ssize_t s = send(fd, "T=23.5\n", 7, 0);   /* 送信バッファに写したバイト数 */
    char buf[64];
    ssize_t n = recv(fd, buf, sizeof buf, 0); /* 届いた分のバイト数、0（FIN）、-1 */
    close(fd);                                /* FIN を送る */
}
  • getaddrinfo(名前, ポート, 条件, &結果) は、名前解決（08 章 4 節）をして、接続に使えるアドレスの一覧を struct addrinfo のリストで返す。IPv4 と IPv6 のアドレスが両方返ることもあるので、順に試す。使い終わったら freeaddrinfo で返す。
  • socket(アドレスの種類, ソケットの種類, プロトコル) は、ソケットを作り、その番号を返す。この番号は、POSIX の OS がファイルや通信の口を表すのに使う 0 以上の小さな整数で、ファイル記述子という。種類が SOCK_STREAM なら TCP、SOCK_DGRAM なら UDP（5 節）のソケットになる。
  • connect(fd, アドレス, 長さ) は、TCP では 3 ウェイハンドシェイクを行い、終わったら 0 を返す。
  • send(fd, データ, 長さ, フラグ) は、データを送信バッファに写し、写したバイト数を返す。
  • recv(fd, 配列, 大きさ, フラグ) は、受信バッファにあるデータを配列に取り出し、そのバイト数を返す。相手の FIN が届いていて、もう何も届かないときは 0 を返す。
  • close(fd) は、ソケットを閉じる。TCP では FIN を送って終わりの手順（10 章 7 節）を始める。

失敗した関数は −1 を返し、理由を表す番号を errno という変数（スレッドごとに 1 つ）に入れる。tcp_open が errno を取っておいてから close を呼ぶのは、close に errno を書き換えさせないためである。番号の読み分けは 4 節で扱う。関数の呼び出しとパケットの対応を図に示す。

send が戻った時点では、データはまだ機器から送り出されていないかもしれない。戻り値が約束するのは「送信バッファに入れた」ことだけで、相手のアプリケーションが受け取ったかどうかは、相手の応答で確かめるしかない。recv は、受信バッファにデータが 1 バイトも無ければ、届くまで待つ（ブロックする）。サーバの側は、bind で自分のポート番号を決め、listen で待ち受けを始め、accept で接続を 1 つずつ受け取る。機器はふつう、クライアントとして外へ接続する（08 章 5 節の NAT のため）。この章の試験では、同じ Linux の上に試験用のサーバを置き、ループバック（自分自身を指すアドレス。IPv4 では 127.0.0.1、名前は localhost）で接続して確かめた。

2. send と recv は全部を約束しない

1 節の使い方には、見落としが 2 つある。

1 つ目は send の戻り値である。send は、渡した長さのうち、送信バッファに入った分しか受け付けない。空きが足りないとき、ブロッキングのソケットでは空くまで待つのがふつうである。しかし、待つ時間に上限を付けた場合（3 節）、シグナル（Linux などの OS がプログラムに送る知らせ）で待ちが中断された場合、ノンブロッキングのソケット（3 節）では、入った分だけを受け付けて、そのバイト数を返す。send が渡した長さより少ないバイト数を返すことを部分送信という。

2 つ目は recv の区切りである。TCP が運ぶのはバイトの列で、送り手の 1 回の send の区切りは運ばれない（07 章 4 節）。送り手が何回かに分けて渡したデータは、TCP の中で MSS ごとに分けられたり、Nagle アルゴリズムでまとめられたりしてセグメントになる。受け手の recv は、呼んだ時点で受信バッファにたまっていた分を返す。1 回の recv が、1 つのメッセージの一部だけを返したり、いくつかのメッセージをまとめて返したりすることを部分受信という。長さを先に置いた形（03 章 4 節）のメッセージを 3 つ送ったときの例を図に示す。

「1 回の recv が 1 つのメッセージ」と思い込んだ受け手（図の赤い列）は、1 回目に A を正しく読むが、一緒に届いた B の長さの 2 バイトを捨ててしまう。2 回目は B の本体の H= を長さと読み、その後は区切りを誤り続ける。この思い込みは、LAN の中で小さなメッセージを間を空けて送る試験では、たまたま当たることが多い。そのため、遅い回線や大きなメッセージで初めて誤りが現れる。

したがって、送る側は全部を送り終えるまで send を繰り返し、受ける側は欲しいバイト数がそろうまで recv を繰り返す。区切りは、03 章 4 節の長さフィールドで自分で付ける。長さを 2 バイトにした場合のコードを示す。

/* len バイトをすべて送る。成功なら 0、失敗なら -1（errno に理由） */
int send_all(int fd, const void *buf, size_t len)
{
    const uint8_t *p = buf;
    while (len > 0) {
        ssize_t n = send(fd, p, len, 0);
        if (n < 0 && errno == EINTR)
            continue;                         /* シグナルで中断された: もう一度 */
        if (n < 0)
            return -1;
        p += n;                               /* 受け付けられた分だけ進める */
        len -= (size_t)n;
    }
    return 0;
}

/* ちょうど len バイトを受け取る。成功なら 0、途中で相手が閉じたら -2、失敗なら -1 */
int recv_exact(int fd, void *buf, size_t len)
{
    uint8_t *p = buf;
    while (len > 0) {
        ssize_t n = recv(fd, p, len, 0);      /* 届いている分（len 以下）が返る */
        if (n == 0)
            return -2;                        /* 相手の FIN: もう届かない */
        if (n < 0 && errno == EINTR)
            continue;
        if (n < 0)
            return -1;
        p += n;
        len -= (size_t)n;
    }
    return 0;
}

/* 長さ 2 バイト（ネットワークバイトオーダ）+ 本体 のメッセージを 1 つ受け取り、
   本体の長さを返す。本体が cap バイトを超えるなら -3、ほかは recv_exact と同じ */
int recv_msg(int fd, uint8_t *body, size_t cap)
{
    uint8_t h[2];
    int r = recv_exact(fd, h, 2);
    if (r != 0)
        return r;
    size_t len = (size_t)h[0] << 8 | h[1];
    if (len > cap)
        return -3;                            /* 長さの上限を確かめる（03 章 4 節） */
    r = recv_exact(fd, body, len);
    return r != 0 ? r : (int)len;
}

EINTR は、待っている間にシグナルで中断されたことを表す errno の値で、そのまま呼び直せばよい。recv_exact は、0 が返ったら（相手の FIN が届いたら）それ以上は届かないので、メッセージの途中で終わったことを −2 で知らせる。テストでは、本体が 0〜199 バイトのメッセージ 2000 個を、1 バイトずつ、または 1〜91 バイトの乱数の長さに区切って送り、socketpair（同じプログラムの中でつながった 2 つのソケットを作る関数）と TCP のループバックの両方で、すべてのメッセージが順に正しく取り出されることを確かめた。同じ形のメッセージ 200 個を 1〜40 バイトに区切って送り、「1 回の recv が 1 つのメッセージ」として読むと、正しく読めたのは 0 個だった。

下の図で、メッセージの数と長さ、受け手の recv への届き方を変えると、バイトの列の区切りと、2 つの読み方の結果が並んで表示される。

3. 待たないソケット — ノンブロッキングと select

05 章 2 節の通信タスクは、依頼・受信・時間切れをイベントループで 1 つずつ扱った。そのループの中でソケットの recv をブロッキングのまま呼ぶと、データが届くまで通信タスクが止まり、その間の依頼にも期限にも応じられない。そこで、ソケットを待たない形にする。

呼んだ関数が、できることだけをして、すぐに戻るソケットをノンブロッキングソケットという。POSIX では、ファイル記述子の性質を変える関数 fcntl で O_NONBLOCK の印を立てると、ノンブロッキングになる（下の connect_timeout の初め）。ノンブロッキングソケットの関数は、次のように戻る。

  • send は、送信バッファの空きの分だけを受け付ける（部分送信）。空きが無ければ −1 を返し、errno は EAGAIN（いまはできないので、後でもう一度呼ぶように、という意味。同じ意味の EWOULDBLOCK のこともある）になる。
  • recv は、受信バッファにある分を返す。何も無ければ −1 を返し、errno は EAGAIN になる。
  • connect は、3 ウェイハンドシェイクの終わりを待たずに −1 を返し、errno は EINPROGRESS（始めたが、まだ終わっていない）になる。

Linux のループバックで、送信バッファを小さく（8192 バイトに）したノンブロッキングのソケットに、相手が読まない状態で 100000 バイトずつ send すると、6144・2048・2048 バイトを受け付けた後、4 回目は −1 を返して EAGAIN になった。

EAGAIN の後に、いつもう一度呼べばよいかを知らせるのが select と poll である。select は、いくつかのファイル記述子について、「読める」か「書ける」状態になるか、決めた時間がたつまで待つ関数である。poll も同じ働きの関数で、待つものを構造体の配列で渡す（数が多いときに向く）。

  • 読める: recv がすぐに戻る状態。データがある、相手の FIN が届いている（recv は 0 を返す）、エラーがある（−1 を返す）のどれかである。
  • 書ける: send が少なくとも一部を受け付ける状態（送信バッファに空きがある）。ノンブロッキングの connect の結果が出たときも、書けるになる。

通信タスクは、ソケットが読めるとき（recv して、2 節の長さによる切り出しに渡す）、送り残しがあって書けるとき（残りを send する）、期限が来たとき（05 章 3 節）を、1 回の select でまとめて待つ。select はファイル記述子しか待てないので、ほかのタスクからの依頼（05 章 2 節のキュー）は、select の待ち時間を短く区切って戻るたびにキューを確かめるか、依頼のたびに自分自身へ UDP で短いデータを送って select を起こす（その UDP のソケットも一緒に待つ）、などの工夫で受け取る。

接続に期限を付ける

ブロッキングの connect は、相手が答えないと、TCP が SYN を送り直し続ける間、戻らない。Linux の既定の設定では、待つ時間を倍々に延ばしながら SYN を 6 回まで送り直すので、あきらめるまでに 2 分あまりかかる（試験の環境では 134 秒だった）。機器が自分で決めた期限で打ち切るには、ノンブロッキングの connect と select を組み合わせる。

/* fd が読める（want_write が 1 なら書ける）ようになるまで最大 ms ミリ秒待つ。
   なったら 1、時間切れなら 0、失敗なら -1 */
int wait_fd(int fd, int want_write, int ms)
{
    fd_set set;
    FD_ZERO(&set);
    FD_SET(fd, &set);
    struct timeval tv = { ms / 1000, (ms % 1000) * 1000 };
    return select(fd + 1, want_write ? NULL : &set, want_write ? &set : NULL, NULL, &tv);
}

/* sa へ接続する。ms ミリ秒たっても結果が出なければ、あきらめる。
   成功なら 0、失敗なら -1（errno に理由。時間切れは ETIMEDOUT） */
int connect_timeout(int fd, const struct sockaddr *sa, socklen_t salen, int ms)
{
    int fl = fcntl(fd, F_GETFL, 0);
    if (fl < 0 || fcntl(fd, F_SETFL, fl | O_NONBLOCK) < 0)
        return -1;
    if (connect(fd, sa, salen) == 0)
        return 0;                             /* すぐにつながった */
    if (errno != EINPROGRESS)
        return -1;                            /* すぐに失敗した */
    int r = wait_fd(fd, 1, ms);               /* 結果が出る（書ける）まで待つ */
    if (r == 0)
        errno = ETIMEDOUT;                    /* 期限までに結果が出なかった */
    if (r <= 0)
        return -1;
    int err = 0;
    socklen_t elen = sizeof err;
    if (getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &elen) < 0)
        return -1;
    if (err != 0) {
        errno = err;                          /* ECONNREFUSED など */
        return -1;
    }
    return 0;
}

fd_set は select に渡すファイル記述子の集まりで、FD_ZERO で空にし、FD_SET で加える。select の第 1 引数は、いちばん大きなファイル記述子 + 1 である。書けるようになっただけでは、つながったのか失敗したのかは分からない。getsockopt（ソケットの設定や状態を読む関数）で SO_ERROR を読むと、つながったなら 0、失敗したならその理由の errno の値が得られる。テストでは、待ち受けているポートには 0 を、待ち受けていないポートには ECONNREFUSED（接続を拒まれた。4 節）を返した。受け付けの列を満杯にして SYN が捨てられるようにしたサーバには、700 ms の期限で、701 ms 後に ETIMEDOUT（時間切れ。4 節）を返した。戻った後もソケットはノンブロッキングのままなので、以後の send と recv も select と組み合わせて使う。

ブロッキングのまま、待つ時間にだけ上限を付ける方法もある。setsockopt（ソケットの設定を変える関数）で SO_RCVTIMEO を設定すると、その時間のうちに何も届かなければ、recv は −1 を返し、errno は EAGAIN になる（200 ms に設定したテストでは 204 ms 後に戻った）。送信の SO_SNDTIMEO も同じで、2 節の部分送信はこのときにも起きる（送信バッファを小さくし、相手が読まない接続に 8 MB を send すると、10240 バイトだけを受け付けて 206 ms 後に戻った）。

下の図で、送信バッファの大きさ、スタックが送り出せる速さ、アプリケーションが書く量と間隔、send の呼び方を変えると、送信バッファの中の量と、各回の send の戻り値が表示される。

4. エラーを読み分ける

ここまでの関数は、失敗すると −1 を返して errno に理由を入れた。理由によって、次にすべきことが違う。通信でよく見る errno の値が、どのパケットの出来事から生じるかを図に示す。

  • ECONNREFUSED: 接続を拒まれた。SYN に RST が返ってきた（そのポートで待ち受けているプログラムがいない）。
  • ETIMEDOUT: 時間切れ。SYN やデータを送り直しても応答が無いまま、送り直しの回数の上限に達した。相手の電源が切れた、経路が切れた、NAT の変換表の行が消えた（08 章 5 節）などで起きる。3 節の connect_timeout のように、自分で決めた期限で打ち切ったときにも使う。
  • ECONNRESET: 接続を相手に切られた。接続の途中で RST が届いた。相手のプログラムが止まって再起動した場合のほか、相手が受け取ったデータを読まないまま close した場合にも RST が送られる（テストでも、こうして ECONNRESET が返った）。
  • EPIPE: 送れなくなった接続に send した。RST を受け取った後や、自分で送信の向きを閉じた後に送ると返る。

recv の 0 はエラーではなく、相手が FIN で普通に送り終えたことを表す。errno の番号の値は OS やスタックによって違うので、必ず名前（定数）で比べる。同じ出来事を別の名前で知らせるスタックもある（再送をあきらめたときに ECONNABORTED を返すものなど）ので、使うスタックで実際に起こして確かめる。

結果ごとに、次にすることを表にまとめる。「間をおいて」の待ち時間は 05 章 5 節の指数バックオフとジッタで決め、どこからやり直すかは 08 章 7 節の参加の手順に戻って決める（層ごとのやり直しの全体は 15 章 2 節）。

返ってきたもの次にすること
EINTR（シグナルで中断された）すぐに呼び直す
EAGAIN（ノンブロッキング、SO_RCVTIMEO の時間切れ）select で待って呼び直す。期限を過ぎていれば時間切れとして扱う
recv が 0（相手の FIN）こちらも閉じる。続けるなら接続し直す

ETIMEDOUT閉じて、間をおいて名前解決からやり直す（サーバのアドレスが変わったかもしれない）
ECONNRESET・EPIPE閉じて、間をおいて接続し直す。届いたか分からないメッセージは送り直す（重複に備える。15 章 4 節）
EHOSTUNREACH・ENETUNREACH（宛先への経路が無い）リンクの状態と DHCP のリースを確かめる（08 章 7 節）

getaddrinfo は errno を使わず、失敗の理由を戻り値（EAI_ で始まる番号）で返す。1 節の tcp_open は −1 しか返さないので、この表のとおりに分けるには、getaddrinfo の戻り値も呼び出し元に返すように変える。

SIGPIPE — 送っただけでプログラムが終わる

POSIX の OS では、EPIPE になる send は、同時にシグナル SIGPIPE をプログラムに送る。SIGPIPE の既定の動作はプログラムを終わらせることなので、接続が 1 つ壊れただけで、Linux で動くゲートウェイのプログラムが黙って終わってしまう。テストでも、相手に RST で切られた接続に 2 回 send すると（1 回目は、先に届いていた RST を ECONNRESET として受け取る）、プログラムは SIGPIPE で終わった。Linux では、send の最後の引数（フラグ）に MSG_NOSIGNAL を渡すと、シグナルを送らずに −1 と EPIPE を返すだけになる。2 節の send_all の send(fd, p, len, 0) は、Linux では send(fd, p, len, MSG_NOSIGNAL) にする（signal(SIGPIPE, SIG_IGN) でプログラム全体として無視する方法もある）。マイコンの lwIP にはシグナルが無い。

何も返ってこない失敗

相手が電源ごと消え、RST も返らないと、こちらが何も送らない限り、どの関数もエラーを返さない（ハーフオープン）。ブロッキングの recv は永久に待ち続ける。受け取るだけの接続でも、SO_RCVTIMEO や select の期限で「決めた時間に何も届かない」ことを失敗として扱い、TCP キープアライブや、アプリケーション層のキープアライブ（13 章 5 節）で、ときどき相手に応答を求める。

5. UDP — 1 回の送信が 1 つのデータグラム

UDP のソケットは、socket(…, SOCK_DGRAM, 0) で作る。UDP で 1 回に送るまとまり（UDP のヘッダとデータ）をデータグラムという。送るときは sendto に宛先のアドレスを渡し、受け取るときは recvfrom で、データと一緒に送り手のアドレスを受け取る。接続の手続きは無い。TCP とは、届き方が次の点で違う。

  • 区切りが保たれる。1 回の sendto が 1 つのデータグラムになり、受け手の 1 回の recvfrom は、ちょうど 1 つのデータグラムを返す（2 節のような長さの欄は要らない）。受け取る配列がデータグラムより小さいと、入りきらない分は捨てられるので、配列は最大のデータグラムより大きくする。
  • 届く保証はない。失われても誰も送り直さず、順番が入れ替わることも、同じものが 2 回届くこともある。受け手のソケットの受信バッファが満杯なら、届いたデータグラムは黙って捨てられる。
  • 大きさは、IP のパケットが MTU に収まるようにする。Ethernet の IPv4 なら、データは 1472 バイト以下にする（07 章 6 節。フラグメンテーションを避けるため）。

届けたいなら、アプリケーションが 05 章 4 節の ARQ を組み立てる。ただし、IP の上ではデータグラムが遅れて届いたり、順番が入れ替わったりするので、05 章 4 節の 1 ビットのシーケンス番号では足りない。そこで、要求ごとに 16 ビットの番号を付け、応答にも同じ番号を入れてもらう（08 章 4 節の DNS の ID と同じ考え方）。

/* 要求に 2 バイトの番号を付けて送り、同じ番号の応答を待つ。来なければ待ち時間を
   2 倍にして送り直す。fd は connect で相手を決めた UDP のソケット。
   応答の長さを返す。4 回送っても来なければ -1 */
int udp_request(int fd, const uint8_t *req, size_t qlen, uint8_t *resp, size_t cap)
{
    static uint16_t last_id;
    uint8_t pkt[2 + REQ_MAX];
    if (qlen > REQ_MAX)
        return -1;
    uint16_t id = ++last_id;
    pkt[0] = (uint8_t)(id >> 8);              /* 番号はネットワークバイトオーダ */
    pkt[1] = (uint8_t)id;
    memcpy(pkt + 2, req, qlen);
    int wait_ms = 250;
    for (int tries = 0; tries < 4; tries++, wait_ms *= 2) {
        send(fd, pkt, 2 + qlen, 0);           /* 1 回の送信が 1 つのデータグラム */
        uint32_t deadline = now_ms() + (uint32_t)wait_ms;
        for (;;) {
            int32_t left = (int32_t)(deadline - now_ms());     /* 05 章 3 節 */
            if (left <= 0 || wait_fd(fd, 0, (int)left) <= 0)
                break;                        /* 時間切れ: 送り直す */
            ssize_t n = recv(fd, resp, cap, 0);   /* 1 回で 1 つのデータグラム */
            if (n >= 2 && resp[0] == pkt[0] && resp[1] == pkt[1])
                return (int)n;                /* この要求への応答 */
        }                                     /* 番号の違う応答（遅れて届いた前の応答）は捨てた */
    }
    return -1;
}

相手が 1 つなら、UDP のソケットにも connect で相手を決めておける。こうすると send・recv で送受信でき、ほかの相手からのデータグラムは届かなくなる。now_ms はミリ秒の時計を返す、この章で仮に置く関数である（Linux では clock_gettime で作る。マイコンでは 05 章 3 節のティック）。待ち時間は 250・500・1000・2000 ms と倍にするので、あきらめるまでに合わせて 3.75 秒待つ。番号の違う応答を捨てた後も、同じ期限まで待ち続ける。サーバの側は recvfrom で要求と送り手のアドレスを受け取り、同じ番号を付けた応答を sendto でそのアドレスへ返す。

応答が失われたり遅れたりすると、クライアントは同じ番号の要求を送り直すので、サーバには同じ要求が 2 回以上届く。値を読むだけの要求なら、そのまま答え直せばよい。「弁を開ける」のように 2 回行うと困る要求なら、サーバはクライアントごとに最後の番号と応答を覚えておき、同じ番号には覚えた応答を返す（15 章 4 節）。テストでは、要求と応答をそれぞれ 20 % の確率で捨て、番号が奇数の応答を 300 ms 遅らせる試験用のサーバに 120 回要求した。取り違え（違う要求への応答を受け取ること）は 0 回、4 回送っても届かなかったのは 2 回（1 回の送信で往復が成り立つ確率 \(0.8^2 = 0.64\) から見込む \(120 \times 0.36^4 \approx 2.0\) 回と合う）で、サーバが同じ番号の要求を 2 回以上処理したのは 56 回だった。

6. lwIP の構成 — 3 つの API と tcpip スレッド

ここからは、マイコンの上で動く TCP/IP スタックを見る。例として、マイコン向けに作られたオープンソースの TCP/IP スタック lwIP（lightweight IP）を取り上げる。IPv4・IPv6・TCP・UDP・ARP・DHCP・DNS などを持ち、多くのマイコンの開発環境に入っている。以下の関数名と設定名は lwIP 2.x のもので、版によって細部が異なる。

lwIP は、アプリケーションに 3 つの API を用意している。

  • raw API: スタックの関数を直接呼び、データが届いた・送ったデータの確認応答が来た・接続が切れた、といった出来事をコールバックで受け取る。RTOS が無くても使える（RTOS を使わない設定 NO_SYS = 1 では、使えるのは raw API だけである）。
  • netconn API: lwIP 独自の、順に書ける API である。netconn_connect・netconn_write・netconn_recv などの関数が、終わるまでブロックする。RTOS が要る。
  • ソケット API: 1〜5 節と同じ形の関数（socket・connect・send・recv・select など）で、netconn API の上に作られている。RTOS が要る。

RTOS を使う場合、lwIP はスタックの処理を 1 つのタスクにまとめる。lwIP の説明書は RTOS のタスクをスレッドと呼ぶので、このタスクを tcpip スレッドという（tcpip_init で作られる）。tcpip スレッドは、メールボックス（移植の層が RTOS のキューで作る。OS シリーズ 11 章）に届く仕事（ドライバが渡す受信したフレームや、ほかのタスクからの依頼）を 1 つずつ処理し、その合間に、決まった時刻に動くタイマ（再送のタイマなど）を処理する。

スタックの中身（接続ごとの状態やバッファの列）は、tcpip スレッドだけが読み書きする前提で作られていて、同時に触られるのを防ぐ鍵を持たない。そのため、raw API の関数は、tcpip スレッドの中（raw API のコールバックの中を含む）からだけ呼ぶ。ほかのタスクから raw API を使いたいときは、tcpip_callback(関数, 引数) で、その関数を tcpip スレッドで実行してもらう。割り込みハンドラからはスタックの関数を呼ばず、受信したフレームは、割り込みハンドラに起こされたドライバのタスクなどが tcpip スレッドに渡す。スタックの持ち主を 1 つのタスクに決め、ほかのタスクは依頼を送るこの形は、05 章 2 節の通信タスクと同じ考え方である。

netconn とソケットの関数は、どのタスクから呼んでもよい。中の動きは、設定 LWIP_TCPIP_CORE_LOCKING によって 2 通りある。

0 なら、依頼をメールボックスに入れ、tcpip スレッドが処理を終えるまで待つ。1 なら、スタック全体の鍵（ミューテックス。OS シリーズ 12 章）を取り、自分のタスクの中でスタックの関数を呼ぶ。この鍵は LOCK_TCPIP_CORE() と UNLOCK_TCPIP_CORE() で取ったり返したりでき、ほかのタスクから raw API を呼ぶときにも使える。どちらのやり方でも、スタックの中身を同時に触るのは 1 つだけになる。

3 つの API を比べる。ソケット API は、関数を呼ぶたびに依頼の受け渡しか鍵の取り合いがあり、netconn の層も通り、受け取ったデータをアプリケーションの配列に写すので、時間と RAM を最も多く使う。

RAM と速さに余裕があり、Linux で試したコードをそのまま使いたいならソケット API、RAM が少ない、または RTOS を使わないなら raw API を選ぶ。

7. pbuf とメモリプール — RAM を見積もる

lwIP は、パケットを pbuf（packet buffer）という構造体で扱う。1 つの pbuf は、データの先頭を指す payload、その長さ len、次の pbuf を指す next、自分から連結の最後までのデータの合計 tot_len を持つ（ほかに、確保のしかたや、この pbuf を指しているものの数などの欄がある）。大きなパケットは、next でつないだ何個かの pbuf で表す。連結の中では、どの pbuf でも tot_len = len + (次の pbuf の tot_len)（最後の pbuf では tot_len = len）が成り立ち、先頭の tot_len がパケット全体の長さになる。

受け取ったフレームの pbuf は、層を上がるときに写されない。各層は自分のヘッダを読んだら、payload をヘッダの分だけ後ろへずらし、len と tot_len を同じだけ減らして、同じ pbuf を上の層に渡す。送るときも、各層のヘッダの分の空きを先頭に取っておき、payload を前にずらしてヘッダを書き込む。

07 章 5 節のカプセル化を、データを写さずに行っているわけである。このように、データを写さずに、置き場所を指すものだけを受け渡すことをゼロコピーという。

受信用の pbuf や制御ブロックのように、大きさの決まったものは、メモリプール（MEMP）から取る。メモリプールは、決まった大きさの領域を決まった数だけ並べたもので、種類ごとに別々に持つ。取るのも返すのも一定の短い時間で済み、取ったり返したりを繰り返しても、空きが細切れになって大きな領域が取れなくなる（断片化）ことがない。数を使い切ると、取れずに失敗する（多くの関数がエラー ERR_MEM を返す）。大きさが一定でないもの（送るデータの写しなど）は、決まった大きさのヒープ（malloc のように使う領域）から取る。

受信は、次のように進む。ドライバは、受け取ったフレームを受信用のプール（PBUF_POOL）の pbuf に入れて tcpip スレッドに渡す（DMA で pbuf に直接書き込むドライバもある）。raw API では、接続を、その制御ブロックである struct tcp_pcb（PCB、protocol control block）で指定し、TCP のデータは pbuf のまま、受信のコールバックで受け取る。

/* raw API の受信のコールバック（tcpip スレッドの中で呼ばれる） */
static err_t on_recv(void *arg, struct tcp_pcb *pcb, struct pbuf *p, err_t err)
{
    (void)err;
    if (p == NULL) {                          /* 相手の FIN が届いた */
        tcp_close(pcb);
        return ERR_OK;
    }
    for (struct pbuf *q = p; q != NULL; q = q->next)
        msg_feed(arg, q->payload, q->len);    /* 連結を順にたどる（写さずに読む） */
    tcp_recved(pcb, p->tot_len);              /* 読んだ分だけ受信ウィンドウを開ける */
    pbuf_free(p);                             /* pbuf をプールに返す */
    return ERR_OK;
}

msg_feed は、2 節のように長さでメッセージを切り出す、この章で仮に置く関数である。tcp_recved を呼ぶまで、受け取ったデータの分だけ受信ウィンドウは閉じたままになる。アプリケーションが pbuf を持っている間は、その分の RAM と受信ウィンドウが使われている。

主な設定と RAM の見積もり

lwIP の設定は、lwipopts.h というファイルに書く。書かなかった設定は opt.h の既定値になる。lwIP 2.x の opt.h では、TCP_MSS が 536、TCP_WND が 4 × TCP_MSS = 2144、TCP_SND_BUF が 2 × TCP_MSS = 1072 である（10 章 3 節の例）が、移植ごとの設定で変わる。RAM に効く主な設定を、例の値とともに示す。例は、Ethernet か Wi-Fi で TCP の接続を同時に 2 つまで使い、どちらも速く受け取れるようにする場合である。

設定意味例の値

TCP_WND自分の受信ウィンドウの大きさ4 × 1460 = 5840
TCP_SND_BUF1 つの接続が、確認応答を待つ分を含めて持てる送信のデータの量4 × 1460 = 5840

PBUF_POOL_BUFSIZEその pbuf 1 つのデータの大きさ（1 つのフレームが入るように）1516

PBUF_POOL_BUFSIZE の 1516 は、1460 バイトのデータに Ethernet・IPv4・TCP のヘッダ 14 + 20 + 20 = 54 バイトを足した 1514 を、4 の倍数に切り上げた値である。

受信に要る RAM と、受け取れる速さの関係を求める。

方針: 相手は、受信ウィンドウの分（TCP_WND バイト）までを、確認応答を待たずに送ってくる。アプリケーションが読むまで、そのデータは受信用のプールの pbuf に入っている。そのために要る pbuf の数を数え、10 章 3 節の「速さ ≤ ウィンドウ ÷ RTT」と組み合わせる。

導出: 相手が MSS いっぱいのセグメントで送るとき、1 つのセグメントは 1 つのフレームになり、1 つの pbuf に入る（PBUF_POOL_BUFSIZE をそう決めた）。1 つの接続のウィンドウの分には \(\lceil \mathrm{TCP\_WND} / \mathrm{TCP\_MSS} \rceil\) 個の pbuf が要る。同時に受け取る接続が \(n\) 個で、ほかのパケット（ARP・DHCP など）のために \(k\) 個の余裕を見ると

\[ \mathrm{PBUF\_POOL\_SIZE} \ge n \left\lceil \frac{\mathrm{TCP\_WND}}{\mathrm{TCP\_MSS}} \right\rceil + k \]

で、プールの RAM は \(\mathrm{PBUF\_POOL\_SIZE} \times (\mathrm{PBUF\_POOL\_BUFSIZE} + h)\) である（\(h\) は pbuf の構造体の大きさで、32 ビットのマイコンでは多くの設定で 16 バイト）。一方、1 つの接続で受け取れる速さ \(v\) は、10 章 3 節のとおり \(v \le \mathrm{TCP\_WND} / \mathrm{RTT}\) である。速さ \(v\) が欲しければ \(\mathrm{TCP\_WND} \ge v \cdot \mathrm{RTT}\) が要るので、1 つの接続あたり

\[ \left\lceil \frac{v \cdot \mathrm{RTT}}{\mathrm{TCP\_MSS}} \right\rceil \times (\mathrm{PBUF\_POOL\_BUFSIZE} + h) \]

バイトの RAM が要る ∎

受信に要る RAM は、欲しい速さと RTT の積（10 章 3 節の帯域幅遅延積と同じ形）におよそ比例する。例の値では、1 つの接続に \(\lceil 5840 / 1460 \rceil = 4\) 個、2 つの接続と余裕 4 個で 12 個の pbuf が要り、プールの RAM は \(12 \times (1516 + 16) = 18384\) バイト（約 18.0 KB）になる。RTT が 100 ms のクラウドのサーバからは、1 つの接続で多くとも \(5840 / 0.1 = 58400\) B/s（約 467 kbps）、RTT が 20 ms の LAN の中なら 292000 B/s（約 2.34 Mbps）で受け取れる。

送信の側では、tcp_write（raw API の送信の関数）やソケットの send に渡したデータの写しが、確認応答が来るまでヒープに置かれる。2 つの接続がそれぞれ TCP_SND_BUF まで持つと \(2 \times 5840 = 11680\) バイト（約 11.4 KB）で、セグメントごとのヘッダの空きや管理の構造体の分を足して、MEM_SIZE を 16 KB にした。送る速さも、\(\mathrm{TCP\_SND\_BUF} / \mathrm{RTT}\) で上限が決まる（10 章 6 節）。lwIP のソケットで部分送信や EAGAIN が起きるのは、主に、この TCP_SND_BUF の残りやヒープが足りないときである。

このほかに、PCB などの接続ごとの構造体（1 つあたり数百バイトの代表値）、tcpip スレッドとアプリケーションのタスクのスタック、ドライバの DMA の領域が要る。lwIP 2.x は、TCP_WND がプールに入りきらない設定や、TCP_SND_BUF が 2 × TCP_MSS より小さい設定（10 章 6 節の遅延 ACK とぶつかる）を、コンパイルのときにエラーとして知らせる（検査の内容は版によって細部が異なる）。相手が小さなセグメントで送ってくると、1 つの pbuf に少しのデータしか入らないので、ウィンドウを使い切る前にプールが尽きる（5840 バイトを 100 バイトずつ送られると 59 個要る）。プールが尽きると、ドライバは届いたフレームを捨て、TCP の再送で速さが大きく落ちる。

下の図で、MSS・ウィンドウ・送信バッファ・接続の数・プールの大きさ・RTT を変えると、RAM の見積もりの内訳と、受け取れる速さ・送れる速さの上限が表示される。

8. まとめ

項目内容
ソケット APIgetaddrinfo で名前を解決し、socket でソケット（ファイル記述子）を作り、connect（3 ウェイハンドシェイク）・send・recv・close（FIN）で使う。関数はソケットの送信・受信バッファとの間で写すだけ
send の戻り値送信バッファに入れたバイト数。相手に届いたことは意味しない。少ないこともある（部分送信）ので、send_all のように残りを渡し直す
recv と区切り受信バッファにある分を返す（部分受信）。TCP は区切りを運ばないので、長さの欄で区切り、recv_exact で足りない分を繰り返す。0 は相手の FIN
ノンブロッキングと selectすぐに戻り、できなければ EAGAIN。select・poll で、読める・書ける・期限を 1 回で待つ。connect の期限は EINPROGRESS → 書ける → SO_ERROR
エラーの読み分けECONNREFUSED（SYN に RST）、ETIMEDOUT（応答が無く再送をあきらめた）、ECONNRESET（接続中の RST）、EPIPE（壊れた接続に送った）。間をおいて接続し直すか、名前解決からやり直す。Linux では MSG_NOSIGNAL で SIGPIPE を止める
UDP1 回の sendto が 1 つのデータグラムで、区切りは保たれるが届く保証はない。16 ビットの番号と指数バックオフで送り直し、番号の違う応答は捨てる。サーバには重複が届く
lwIP の 3 つの APIraw API（コールバック、RTOS が無くてもよい）・netconn API（順に書く）・ソケット API（BSD と同じ形）。後ろほど書きやすく、RAM と時間を多く使う
tcpip スレッドスタックの処理は 1 つのスレッドが行う。raw API はその中からだけ呼ぶ（ほかからは tcpip_callback か、鍵で囲む）
pbuf とメモリプールpbuf は連結できるパケットのバッファで、層の間を写さずに渡す（ゼロコピー）。大きさの決まったものはメモリプール、決まらないものはヒープから取る
RAM と速さ受信の pbuf は 1 つの接続あたり \(\lceil \mathrm{TCP\_WND}/\mathrm{TCP\_MSS} \rceil\) 個、速さは \(\mathrm{TCP\_WND}/\mathrm{RTT}\) 以下。欲しい速さ × RTT にほぼ比例する RAM が要る
