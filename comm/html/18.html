Chapter 18

接続と GATT — 属性を読み書きする

この章で扱う問い. 17 章では、ペリフェラルになる機器がアドバタイズで存在を知らせ、セントラルになる機器がそれを見つけるまでを見た。この章では、見つけた 2 台が接続し、決まった間隔でパケットをやり取りしながら、機器のデータを読み書きする仕組みを見る。

この章では次の 3 つの問いに答える。

  1. 接続した 2 台は、いつ、どのチャネルでパケットをやり取りするのか。相手が消えたことは、どう判断するのか。
  2. 機器のデータは、どんな表として表され、どんなバイトの列で読み書き・通知されるのか。
  3. 機器のデータの表をどう設計し、BLE のスタックの上でどう実装するのか。

答えの道具は、接続イベントの時間軸と、番号（ハンドル）を付けた属性の表、そしてそれを読み書きする、1 バイトの番号で始まる短いメッセージである。

この章で使う既出の用語（定義は各リンク先）. 機器・サーバ（01 章 1 節）、プロトコル・ヘッダ（01 章 2 節）、遅延（01 章 3 節）、ファームウェア（01 章 4 節）、平均電流（01 章 5 節）、ペイロード（03 章 1 節）、CRC（03 章 5 節）、リトルエンディアン・固定小数点（03 章 6 節）、TLV（03 章 7 節）、リングバッファ（04 章 3 節）、状態機械・イベント・タイムアウト（05 章 1 節）、イベントループ・コールバック・通信タスク（05 章 2 節）、確認応答（ACK）・再送・ストップアンドウェイト・シーケンス番号（05 章 4 節）、ホスト・コントローラ（06 章 1 節）、HCI・ACL データ（06 章 5 節）、ポート番号（07 章 4 節）、MTU（07 章 6 節）、アクセスポイント（AP）・SSID（09 章 1 節）、プロビジョニング（09 章 6 節）、BLE（16 章 1 節）、データチャネル（16 章 2 節）、アドバタイザ・イニシエータ・セントラル・ペリフェラル（16 章 4 節）、リンク層・L2CAP・ATT・GATT・SMP（16 章 5 節）、チャネルマップ・チャネル選択アルゴリズム（16 章 6 節）、アドバタイズ（17 章 1 節）、PDU・アクセスアドレス・接続可能（17 章 2 節）、UUID（17 章 3 節）

1. 接続の確立と接続イベント

アドバタイズは、相手を決めずに送るだけで、届いたかどうかも分からない。決まった相手と、両方向に、届いたことを確かめながらデータをやり取りし続けるには、接続する。BLE の接続とは、2 台が、決めた間隔ごとに、決めたデータチャネルでパケットをやり取りし続ける状態である。接続を始めるのはイニシエータで、接続した後はセントラルになり、アドバタイズしていた側はペリフェラルになる。

CONNECT_IND — 接続の設定を 1 つのパケットで渡す

イニシエータは、接続可能なアドバタイズ（ADV_IND など）を受け取ると、その 150 µs 後に、同じチャネルで CONNECT_IND を送る（17 章 2 節）。CONNECT_IND のペイロードは、イニシエータのアドレス 6 バイト、アドバタイザのアドレス 6 バイト、接続の設定 22 バイトからなる。この 22 バイトに、接続のやり方がすべて入っている。

  • アクセスアドレス: この接続のパケットに付ける値。アドバタイズの 0x8E89BED6 ではなく、イニシエータが接続ごとに乱数で選ぶ。受け手は、これが合わないパケットを、ほかの接続のものとして捨てる。
  • CRCInit: この接続で使う CRC の初期値。
  • WinSize・WinOffset: 最初のパケットを送る時刻の範囲（送信窓）。どちらも 1.25 ms 単位。
  • Interval・Latency・Timeout: 以下で定義する接続間隔・ペリフェラルレイテンシ・監視タイムアウト。
  • ChM・Hop: 使うデータチャネルの一覧（チャネルマップ）と、チャネル選択アルゴリズムで使うホップ量（16 章 6 節）。
  • SCA: セントラルの時計の精度の区分（例の 5 は 31〜50 ppm）。

CONNECT_IND を送り終えてから 1.25 ms + WinOffset × 1.25 ms の後に、長さ WinSize × 1.25 ms の送信窓が開き、セントラルはその中で最初のパケットを送る。

それから後、2 台は決まった間隔ごとに 1 本のデータチャネルに集まり、パケットをやり取りしては、また眠る。この 1 回の集まりを接続イベント、接続イベントの始まり（セントラルが最初のパケットを送り始める時刻）をアンカーポイント、アンカーポイントの間隔を接続間隔という（接続イベントは、05 章 1 節の状態機械のイベントとは別のものである）。接続間隔は Interval × 1.25 ms で、Interval は 6〜3200 なので 7.5 ms〜4 s である。1 つの接続イベントは同じチャネルで行い、次の接続イベントでは別のチャネルに移る。チャネル選択アルゴリズム #1 なら、前のチャネルにホップ量を足して 37 で割った余りのチャネルで、例の Hop = 7 では 7、14、21、28、35、5、… となる。接続を始めてから 6 回の接続イベントのうちに相手のパケットを 1 つも受け取れなければ、接続はできなかったとして終える。

接続イベントの中 — セントラルが先に送り、ペリフェラルが答える

接続イベントは、必ずセントラルの送信で始まる。ペリフェラルは、アンカーポイントの少し前から受信して待ち、セントラルのパケットを受け終えてから 150 µs 後に答える。送るデータが無くても、データの無いパケット（空パケット。19 章 1 節）で答える。どちらかに送るものが残っていれば、同じ接続イベントの中でやり取りを続け、無ければ 2 台とも次のアンカーポイントまで眠る。ペリフェラルが少し前に起きるのは、2 台の時計がわずかにずれる（02 章 4 節と同じ）からである。前のアンカーポイントから時間がたつほどずれうる幅が広がるので、そのぶん早く起きる。SCA は、この幅を見積もるのに使う。

リンク層は、ここで届いたことを確かめている。データのパケットのヘッダには、05 章 4 節の 1 ビットのシーケンス番号にあたる SN と、次に受け取りたい番号を表す NESN の 2 つのビットがある。送り手は、相手から次に届いたパケットの NESN を見て、前に送ったパケットが届いたかを知り、届いていなければ同じパケットを送り直す（再送）。

CRC が合わないパケットは捨てられ、次の機会に送り直される。同じパケットが 2 回届いても、受け手は SN で見分けて捨てる。そのため、接続が続いている限り、上の層が渡したデータは、順番どおりに 1 回ずつ届く（4 節でこの性質を使う）。

ペリフェラルレイテンシ — ペリフェラルが休める回数

セントラルは、すべての接続イベントで送る。ペリフェラルは、送るものが無ければ、続けて L 回までの接続イベントで受信を休んでよい。この L をペリフェラルレイテンシという（CONNECT_IND の Latency。0〜499。古い版の規格での呼び名は slave latency）。L = 4 なら、ペリフェラルは 5 回に 1 回だけ起きればよく、平均電流が下がる（19 章 5 節）。その代わり、セントラルから送るデータは、ペリフェラルが次に起きるまで届かない。

方針: データができてから、それを運ぶ接続イベントまで待つ時間の最大を、向きごとに求める。接続間隔を \(I\) とする。

導出: ペリフェラルが受信した接続イベントを k 番目とすると、休めるのは続けて L 回までなので、次に必ず受信するのは k + L + 1 番目である。セントラルのデータが k 番目のアンカーポイントの直後にできると、それを運べる最初の接続イベントは k + L + 1 番目で、待ちは最大でほぼ \((1 + L) I\) である。逆向きでは、ペリフェラルは送るものがあれば次の接続イベントで起きて送れるので、待ちは最大でほぼ \(I\) である ∎

\(I\) = 30 ms、L = 4 なら、セントラルからペリフェラルへは最大 150 ms、ペリフェラルからセントラルへは最大 30 ms 待つ。測定値を送るのが主な仕事の機器なら、L を大きくしても、送る向きの遅延は増えない。

監視タイムアウト — 相手が消えたと判断する

相手の電池が切れたり、電波の届かない所へ持ち去られたりしても、相手は切断を知らせてこない。そこで 2 台は、相手のパケットを正しく受け取るたびに計り直すタイマを持ち、決めた時間のあいだ何も受け取れなければ、接続が失われたと判断する（05 章 1 節のタイムアウト）。この時間を監視タイムアウトという。CONNECT_IND の Timeout × 10 ms で、100 ms〜32 s である。Bluetooth Core Specification は、監視タイムアウトを \(2(1 + L) I\) より長くすることを求めている。この条件の意味を確かめる。

方針: やり取りが起きうる接続イベントだけを時刻の順に並べ、最後にやり取りできた時刻から、次の機会が監視タイムアウトより前に来るかを調べる。

導出: やり取りは、ペリフェラルが受信する接続イベントでしか起きない（ペリフェラルが答えなければ、セントラルも何も受け取らない）。ペリフェラルが最も少なく受信する場合、受信は (1 + L) 回に 1 回なので、最後にやり取りできた時刻を 0 とすると、次の機会は \((1 + L) I\)、その次は \(2(1 + L) I\)、… に来る。最初の機会でやり取りできれば、タイマは計り直される。最初の機会のパケットが雑音などで失われても、2 番目の機会 \(2(1 + L) I\) が監視タイムアウトより前に来れば、接続は保たれる。したがって、監視タイムアウト \(> 2(1 + L) I\) は、1 回の機会を失っても切断と判断しないための条件である。同じように、続けて k 回の機会を失っても保つには、監視タイムアウトを \((k + 1)(1 + L) I\) より長くする ∎

\(I\) = 50 ms、L = 3 では、\(2(1 + L) I\) = 400 ms である。監視タイムアウトを 300 ms にすると、1 回の機会を失っただけで切断になる。1 s にすれば、続けて 3 回まで失っても接続は保たれる。一方、監視タイムアウトを長くするほど、相手が本当に消えたことに気づくのが遅れ、その間は接続し直しも始められない。

接続パラメータを変える

接続間隔・ペリフェラルレイテンシ・監視タイムアウトを合わせて、接続パラメータという。接続パラメータは、接続の途中でも変えられる。これを接続パラメータの更新という。決めるのはセントラルで、新しい値と、切り替える接続イベントの番号（2 台が接続イベントごとに数えている通し番号）をペリフェラルに送り、2 台はその接続イベントから新しい値を使う。ペリフェラルは、希望する値の範囲を送って頼むことしかできない（2 節の L2CAP の LE シグナリングのチャネルか、リンク層の制御用のパケットで送る）。スマートフォンがセントラルのときは、受け入れる値の範囲を OS が決めていることが多く、希望どおりになるとは限らない。大きなデータを送る間だけ接続間隔を短くし、終わったら長くする、といった使い方をする（19 章 6 節）。

下の図で、接続間隔・ペリフェラルレイテンシ・監視タイムアウトと、1 回の機会のやり取りが失われる確率を変えると、接続イベントの時間軸、条件を満たすか、向きごとの最大の待ち、模擬した 1 時間の接続で切断と判断した回数が表示される。

2. L2CAP と ATT

接続ができると、2 台のリンク層は、接続イベントごとにデータのパケットを運べるようになる。リンク層のパケットのペイロードは、既定では最大 27 バイトである（広げる方法は 19 章 1 節）。この節では、その中身の形を見る。

L2CAP — 行き先を表す 4 バイト

リンク層が運ぶペイロードの中身は、L2CAP のパケットである。ホストとコントローラを分けた構成では、HCI の ACL データがこれを運ぶ。L2CAP のヘッダは 4 バイトで、その後ろのデータの長さ（2 バイト）と、データの行き先を表すチャネル ID（2 バイト）からなる。どちらもリトルエンディアンで並べる。チャネル ID が表す行き先を、L2CAP のチャネルという（07 章 4 節のポート番号が機器の中のプログラムを選ぶのと同じ考え方である）。BLE では、0x0004 が ATT（この章）、0x0005 が LE シグナリング（L2CAP 自身の制御。1 節の接続パラメータの更新の希望など）、0x0006 が SMP（ペアリング。20 章）と、固定で決まっている。L2CAP は、1 つのリンク層のパケットに入らない長いデータを、いくつかのパケットに分けて送り、受け手で組み立て直すこともする（5 節）。

ATT — 属性を読み書きする約束

ATT（Attribute Protocol）は、一方の機器が持つデータを、もう一方の機器が読み書きするためのプロトコルである。データを持つ側を ATT のサーバ、読み書きする側を ATT のクライアントという（01 章のインターネットのサーバと区別するため、この章では「ATT のサーバ」「GATT のサーバ」と書く）。サーバが持つデータの 1 つ 1 つを属性といい、属性は次の 4 つを持つ。

  • ハンドル: 属性を区別する 16 ビットの番号（0x0001〜0xFFFF）。クライアントは、ハンドルで読み書きする属性を指定する（06 章 5 節で HCI が接続ごとに付ける番号とは別物である）。
  • 属性の型: その属性が何であるかを表す UUID。
  • 属性の値: 0〜512 バイトのバイトの列。
  • パーミッション: その属性を読めるか・書けるか、そのために暗号化や認証が要るか（20 章 7 節）。サーバの中だけで使う決まりで、PDU では送らない。

ATT のクライアントとサーバは、セントラルとペリフェラルとは別の軸である。多くの場合、スマートフォン（セントラル）が機器（ペリフェラル）の値を読み書きするので、機器が ATT のサーバになる。しかし、機器がスマートフォンの持つ時刻を読むときは機器がクライアントになり、1 台が両方の役を同時に持つこともある。

ATT の PDU

ATT がやり取りする PDU を ATT の PDU という。先頭の 1 バイトは PDU の種類を表す番号で、これをオペコードという。その後ろに、種類ごとに決まったパラメータが続く。PDU は、次の組み合わせで使う。

  • クライアントがサーバに送る要求と、サーバがそれに答える応答。応答できないときは、応答の代わりに Error Response を返す。
  • クライアントがサーバに送り、何も返してもらわないコマンド。
  • サーバがクライアントに値を送る、通知と指示（4 節）。指示には、クライアントが確認を返す。

主な PDU を示す（名前は Bluetooth Core Specification のもの。新しい版では ATT_READ_REQ のような名前で書かれている）。

誤りの番号には、0x01 Invalid Handle（そのハンドルの属性が無い）、0x02 Read Not Permitted、0x03 Write Not Permitted、0x05 Insufficient Authentication・0x0F Insufficient Encryption（認証・暗号化が足りない。20 章 7 節）、0x06 Request Not Supported（知らない要求）、0x0A Attribute Not Found（範囲の中に無い。4 節）などがある。

ATT には、05 章 4 節のストップアンドウェイトと同じ決まりがある。クライアントは、要求を 1 つ送ったら、その応答（か Error Response）が届くまで次の要求を送らない。サーバも、指示を 1 つ送ったら、確認が届くまで次の指示を送らない。応答も確認も無いコマンドと通知は、続けていくつでも送れる。要求を送ってから 30 s たっても応答が無ければ、そのやり取りは失敗とし、その接続ではもう ATT の PDU を送らない（接続し直す）。

3. GATT — サービス・キャラクタリスティック・記述子

ATT は属性を読み書きする方法を決めているが、どんな属性をどう並べるかは決めていない。それを決めるのが GATT である。GATT は、属性を、サービス・キャラクタリスティック・記述子の 3 段に組み立てる。GATT のクライアントとサーバは、ATT のクライアントとサーバと同じである。

  • サービス: 1 つの機能のまとまり（電池の残り、温度の測定など）。型 0x2800 のプライマリサービス宣言の属性で始まり、その値はサービスの UUID である。次のサービス宣言の手前までの属性が、そのサービスに属する。
  • キャラクタリスティック: サービスの中の 1 つの値（電池の残り、温度など）。型 0x2803 のキャラクタリスティック宣言の属性で始まり、その値は、プロパティ（1 バイト。下で説明する）・値のハンドル（2 バイト）・キャラクタリスティックの UUID（2 か 16 バイト）である。宣言のすぐ次の属性が値そのもので、その型はキャラクタリスティックの UUID である。この属性のハンドルを値のハンドルという。
  • 記述子: キャラクタリスティックの値の後ろに置く、その値についての補足の属性。最もよく使うのは、クライアントが通知や指示を受けるかを書き込む CCCD（Client Characteristic Configuration Descriptor、型 0x2902。4 節）である。ほかに、値を説明する文字列（0x2901）、値の形と単位（0x2904）などがある。

17 章 3 節の温湿度センサ TH-01 を GATT のサーバにした例の表を示す。

0x0004 から 0x0007 までが Battery Service（0x180F）で、その中に電池の残り（Battery Level、0x2A19）のキャラクタリスティックが 1 つある。0x0005 の宣言の値 12 06 00 19 2A は、プロパティ 0x12、値のハンドル 0x0006、UUID 0x2A19 を表し、0x0006 の値 0x57 = 87 は 87 % である。0x0008 からは独自のサービスで、温度と測定の間隔の 2 つのキャラクタリスティックを持つ。温度の値 29 09 は、03 章 6 節と同じ 0.01 °C 単位の符号付き 16 ビットの固定小数点（0x0929 = 2345 で 23.45 °C）である。先頭の 0x0001〜0x0003 は、機器の名前（Device Name、0x2A00）を持つ Generic Access のサービス（0x1800）で、多くのスタックが用意する。

プロパティは、そのキャラクタリスティックの値にクライアントが何をできるかを、ビットで知らせる 1 バイトである。

プロパティはクライアントへの案内で、実際に許すかどうかはパーミッションで決まる。たとえば、Read のプロパティを持っていても、パーミッションが暗号化を求めていれば、暗号化していない接続での読み出しには Error Response（0x05 か 0x0F。20 章 7 節）が返る。

16 ビットの UUID と基準 UUID

UUID は本来 128 ビットである。Bluetooth SIG が割り当てた 16 ビットの UUID xxxx は、基準 UUID 0000xxxx-0000-1000-8000-00805F9B34FB の xxxx の位置にその番号を入れた 128 ビットの UUID を、短く書いたものである。宣言の型（0x2800・0x2803）、記述子（0x2902）、標準のサービス（0x180F）とキャラクタリスティック（0x2A19）は、どれも 16 ビットで書ける。独自のサービスやキャラクタリスティックには、自分で作った 128 ビットの UUID（乱数で作る版 4 の UUID など）を使い、割り当てを受けていない 16 ビットの番号を使ってはいけない。表の独自のサービスの UUID 5C3A0001-8E2F-4B7D-A1C6-3F9E0D27B845 は、この章の例として乱数で作ったものである。1 つの製品の独自の UUID は、1 つの UUID の一部（ここでは 3〜4 バイト目の 0001・0002・0003）だけを変えて作ると、まとめて扱いやすい。PDU の中では、UUID も 16 バイトの整数としてリトルエンディアンで並べるので、文字で書いた順とはバイトの順が逆になる。

4. 読む・書く・通知する

探索 — クライアントが表を知る

クライアントは、初めて接続したサーバの表を知らない。そこで、ハンドルの範囲と型を指定して探す要求を繰り返し、ハンドルを集める。これを探索という。

  1. サービスの探索: Read By Group Type Request に、範囲 0x0001〜0xFFFF と型 0x2800 を入れて送る。応答は、サービスごとの最初と最後のハンドルと UUID の組の列である。受け取った最後のハンドルの次から送り直し、Error Response（0x0A Attribute Not Found）が返ったら終わる。
  2. キャラクタリスティックの探索: サービスの範囲で、Read By Type Request に型 0x2803 を入れて送り、宣言のハンドルと値（プロパティ・値のハンドル・UUID）の組を集める。
  3. 記述子の探索: 値のハンドルの次から次の宣言の手前までを Find Information Request で調べ、ハンドルと型の組（CCCD なら 0x2902）を得る。

1 つの応答には同じ長さの組しか入らないので、16 ビットの UUID のサービスと 128 ビットの UUID のサービスは、別の応答で返る。128 ビットの UUID のキャラクタリスティック宣言は、1 つで 21 バイトの組になり、ATT の PDU の長さの上限（既定で 23 バイト。5 節）の中に 1 つしか入らないので、図のように 1 往復で 1 つずつ集める。クライアントは集めたハンドルを覚え、以後は UUID ではなくハンドルで読み書きする。

読む・書く

  • Read: Read Request（0x0A、ハンドル）に、サーバは Read Response（0x0B、値）を返す。
  • Write: Write Request（0x12、ハンドル・値）に、サーバは書けたら Write Response（0x13）を、書けなければ Error Response を返す。クライアントは結果を知ってから次へ進める。
  • Write Command（Write Without Response とも呼ぶ）: Write Command（0x52、ハンドル・値）には何も返さない。書けなかったときも何も返らないので、クライアントは結果を知らない。その代わり、応答を待たずに続けて送れる。

通知と指示

サーバの値が変わったことを、クライアントが繰り返し読みに来なくても伝えられるように、サーバから値を送る PDU が 2 つある。

  • 通知（Handle Value Notification、0x1B）: サーバがハンドルと値を送るだけで、クライアントは何も返さない。
  • 指示（Handle Value Indication、0x1D）: クライアントは、受け取ったら確認（Handle Value Confirmation、0x1E）を返す。サーバは、確認が届くまで次の指示を送らない。

サーバは、クライアントが頼んだときだけ送る。頼み方は、そのキャラクタリスティックの CCCD に 2 バイトの値を書くことで、0x0001 なら通知を、0x0002 なら指示を始め、0x0000 で止める（リトルエンディアンなので、通知なら 01 00 を書く）。CCCD の値はクライアントごとに別で、2 台のスマートフォンがつながっていれば、それぞれが自分の値を持つ。ボンディング（20 章 5 節）した相手の CCCD の値は、切断の後も覚えておき、次の接続でそのまま使う。

05 章 4 節の確認応答と比べる。通知には ATT の確認は無いが、1 節で見たとおり、リンク層が 1 つずつ確認応答を取って送り直すので、接続が続いている限り、通知が電波の上で失われることはない。通知が相手に届かないのは、届く前に接続が切れたときと、送る側のスタックの送信の列がいっぱいで、そもそも送れなかったとき（7 節）である。指示の確認は、相手のリンク層ではなく、相手の ATT（ホストの層）まで届いたことを示す。その代わり、確認を待つ間は次の指示を送れないので、続けて多くの値を送るのには向かない（どれだけ遅くなるかは 19 章）。

機器（ATT のサーバ）の側で、届いた要求を処理する部分を示す。tbl は 3 節の表の属性の配列、put_le16・get_le16 は 03 章 6 節の関数、mtu は 1 つの PDU の長さの上限（5 節の ATT_MTU）である。

enum { P_READ = 0x01, P_WRITE = 0x02 };          /* パーミッション（この例では 2 つだけ） */
struct attr {           /* ハンドル・型（16 ビット。128 ビットの型なら uuid128 に 16 バイト）・パーミッション・値・長さ */
    uint16_t handle, type; const uint8_t *uuid128; uint8_t perm, *val; uint16_t len, max;
};
static size_t att_err(uint8_t *rsp, uint8_t op, uint16_t h, uint8_t code)
{
    rsp[0] = 0x01; rsp[1] = op; put_le16(&rsp[2], h); rsp[4] = code;   /* Error Response */
    return 5;
}
/* 届いた PDU を 1 つ処理し、返す PDU を rsp に作って長さを返す（返さないなら 0） */
size_t att_server(const uint8_t *req, size_t n, uint8_t *rsp, uint16_t mtu)
{
    if (n == 0) return 0;
    uint8_t op = req[0];
    int cmd = op & 0x40;                         /* ビット 6 が 1 ならコマンド（何も返さない） */
    switch (op) {
    case 0x0A: case 0x12: case 0x52: {          /* Read Request・Write Request・Write Command */
        if (n < 3) return cmd ? 0 : att_err(rsp, op, 0x0000, 0x04);          /* Invalid PDU */
        uint16_t h = get_le16(&req[1]);
        struct attr *a = attr_find(h);           /* tbl からハンドルで探す（省略） */
        if (a == NULL) return cmd ? 0 : att_err(rsp, op, h, 0x01);           /* Invalid Handle */
        if (op == 0x0A) {
            if (n != 3) return att_err(rsp, op, 0x0000, 0x04);
            if (!(a->perm & P_READ)) return att_err(rsp, op, h, 0x02);        /* Read Not Permitted */
            size_t k = a->len < mtu - 1u ? a->len : mtu - 1u;                 /* 入るのは mtu − 1 まで */
            rsp[0] = 0x0B; memcpy(&rsp[1], a->val, k);                        /* Read Response */
            return 1 + k;
        }
        size_t vl = n - 3;
        if (!(a->perm & P_WRITE)) return cmd ? 0 : att_err(rsp, op, h, 0x03); /* Write Not Permitted */
        if (vl > a->max) return cmd ? 0 : att_err(rsp, op, h, 0x0D);          /* 値の長さが不正 */
        memcpy(a->val, &req[3], vl); a->len = (uint16_t)vl;
        on_write(a);                  /* アプリケーションに知らせる（CCCD なら通知の可否を覚える） */
        if (cmd) return 0;
        rsp[0] = 0x13;                                                        /* Write Response */
        return 1;
    }
    /* … 0x02 MTU の交換・0x04/0x08/0x10 の探索・0x0C Read Blob・0x1E 確認（省略） … */
    default:
        return cmd ? 0 : att_err(rsp, op, 0x0000, 0x06);                      /* Request Not Supported */
    }
}

コマンドには、誤りがあっても何も返さない。知らないコマンドも黙って捨て、知らない要求には 0x06 を返す。応答が mtu を超えないように、Read Response に入れる値を mtu − 1 バイトで切っている（残りの読み方は 5 節）。省いた探索の処理も含めて、図の探索・読み書き・誤りのバイトの列と一致することを確かめ、さらに乱数で作った 30 万個の PDU（長さや中身の壊れたものを含む）を与えて、応答が mtu を超えないこと、配列の外を読み書きしないことを AddressSanitizer で確かめた。

5. MTU — 1 回に運べる大きさ

07 章 6 節の MTU が IP のパケットの大きさの上限だったのと同じく、1 つの ATT の PDU の長さ（オペコードを含む）の上限を ATT_MTU という。既定は 23 バイトである。1 つの PDU で運べる値の長さは、ATT_MTU から、オペコードと値の前のパラメータの長さを引いたものになる。

  • 通知・指示・Write Request・Write Command: オペコード 1 とハンドル 2 を引いて、ATT_MTU − 3 = 20 バイト
  • Read Response: オペコード 1 だけを引いて、ATT_MTU − 1 = 22 バイト

既定が 23 なのは、L2CAP のヘッダ 4 バイトを足すと 27 バイトになり、既定のリンク層のペイロードの上限（2 節）にちょうど収まるからである。

MTU の交換

20 バイトでは足りないとき、ATT_MTU を大きくできる。これを MTU の交換という。クライアントは Exchange MTU Request（0x02）で自分が受け取れる大きさを知らせ、サーバは Exchange MTU Response（0x03）で自分が受け取れる大きさを返す。2 台は、2 つのうち小さいほう（23 より小さくはしない）を、その接続の ATT_MTU として使う。交換は 1 つの接続で 1 回だけで、クライアントが始める。

247 がよく使われるのは、L2CAP の 4 バイトを足すと 251 バイトになり、リンク層のペイロードを広げたとき（19 章 1 節）の上限にちょうど収まるからである。リンク層のペイロードが 27 バイトのままなら、L2CAP が 251 バイトを 10 個のパケットに分けて運ぶ。

長い値を読む・書く

ATT_MTU に入らない値（最大 512 バイト）は、何回かに分けて読み書きする。

  • Read Blob: Read Blob Request（0x0C）でハンドルとオフセット（値の何バイト目から読むか）を送り、Read Blob Response（0x0D）でそこから ATT_MTU − 1 バイトまでを受け取る。クライアントは、まず Read Request で読み、応答がちょうど ATT_MTU − 1 バイトなら続きがあるかもしれないので、それまでに受け取った長さをオフセットにして Read Blob Request を送る。これを、応答が ATT_MTU − 1 バイトより短くなるまで繰り返す。
  • Prepare Write・Execute Write: Prepare Write Request（0x16）で、値の一部（ATT_MTU − 5 バイトまで）をオフセットとともに送る。サーバはそれをすぐには書かずに預かり、受け取った内容をそのまま Prepare Write Response（0x17）で返す。クライアントは、返ってきた内容で正しく届いたかを確かめる。全部を送ったら、Execute Write Request（0x18）にフラグ 0x01 を入れて送り、サーバは預かった部分を一度に書いて Execute Write Response（0x19）を返す（フラグが 0x00 なら取り消す）。

要求は 1 つずつしか送れないので、往復の数が、長い値を読み書きする時間を決める。長い値を読むのに何往復かかるかを求める。

方針: 「応答がちょうど ATT_MTU − 1 バイトなら次を読む」という規則から、値の長さ n を ATT_MTU − 1 で割った商と余りで数える。

導出: \(c\) = ATT_MTU − 1 とし、\(n = qc + r\)（\(q\) は商、\(0 \le r < c\)）と書く。最初の \(q\) 回の応答はどれもちょうど \(c\) バイトなので、クライアントは毎回次を読む。\(q + 1\) 回目の応答は残りの \(r\) バイトで、\(r < c\) なので、そこで終わる。したがって、往復の数は \(q + 1 = \lfloor n / c \rfloor + 1\) である。\(r = 0\)（\(n\) が \(c\) で割り切れる）なら、最後の応答は 0 バイトになる ∎

50 バイトの値なら、ATT_MTU 23（\(c\) = 22）で \(\lfloor 50/22 \rfloor + 1 = 3\) 往復（22・22・6 バイト）である。512 バイトなら 24 往復かかるが、ATT_MTU 247（\(c\) = 246）にすれば 3 往復で済む（1 往復にかかる時間は 19 章）。通知には分けて送る仕組みが無く、ATT_MTU − 3 バイトを超える部分は送られない。長い値を通知で送るには、MTU を交換するか、アプリケーションで分けて番号を付ける。

6. GATT を設計する

GATT の表は、機器とスマートフォンのアプリケーションの間の約束になる。一度出荷すると、アプリケーションの古い版も新しい版もつながってくるので、後から変えにくい。設計の指針を挙げる。

  1. 機能ごとにサービスを分ける. 測定・設定・電池・機器の情報を別のサービスにすると、アプリケーションは使うサービスだけを探せばよく、機能を足しても、ほかのサービスのハンドルや形は変わらない。
  2. 標準のサービスがあれば使う. Battery Service（0x180F。Battery Level 0x2A19 は 0〜100 % の 1 バイト）と Device Information（0x180A。製造者名 0x2A29、型番 0x2A24、ファームウェアの版 0x2A26 などの文字列）は、汎用のアプリケーションや OS がそのまま読める。環境の測定には Environmental Sensing Service（0x181A。温度 0x2A6E は 0.01 °C 単位の符号付き 16 ビット）もある。標準のサービスを使うときは、必須のキャラクタリスティックやプロパティを、そのサービスの仕様書で確かめる。標準に無い機能は、128 ビットの UUID の独自のサービスにする。
  3. 値の形を決める. 03 章 6 節と同じく、エンディアン（リトルエンディアン）・単位・倍率を決めて、固定小数点の整数で送る。文字の "23.45" や JSON は長く、桁数で長さも変わる。JSON にすると、温度と湿度だけで ATT_MTU 23 の通知の 20 バイトを超える（下の図）。
  4. 読み出し・通知・書き込みを使い分ける. 変わったらすぐ知らせたい値は Read と Notify、確かに届いたことを知りたい知らせ（警報や、命令の結果）は Indicate、設定の値は Read と Write（Write Request で結果を受け取る）、速く大量に流すデータは Notify と Write Command にする。
  5. 命令はコントロールポイントで受ける. 命令を書き込みで受け取り、結果を指示で返すキャラクタリスティック（Write と Indicate）を、コントロールポイントという。値は、命令の番号 1 バイトとパラメータの形（03 章 7 節の TLV に近い）にし、結果には命令の番号と状態を入れて、どの命令の結果かを分かるようにする。
  6. 版の情報を読めるようにする. ファームウェアの版と、独自のサービスの形の版を読めるようにしておくと、アプリケーションが機器に合わせて動きを変えられる。ファームウェアの更新（22 章）で表が変わると、ハンドルを覚えていたクライアントは別の属性を読み書きしてしまう。Generic Attribute のサービス（0x1801）の Service Changed（0x2A05）の指示で、表が変わったハンドルの範囲を知らせる。
  7. パーミッションで守る. 設定や命令の属性には、暗号化や認証を求めるパーミッションを付ける（20 章 7 節）。

指針に沿って TH-01 の GATT を設計した例と、値の形の良い例・悪い例を示す。

09 章 6 節のプロビジョニングで、BLE で Wi-Fi の設定を渡す場合も、コントロールポイントで作れる。スマートフォンが SSID とパスフレーズを書いて「接続を試す」命令を送り、機器は AP につなげたかどうかを指示で返す。結果を返すので、パスフレーズの打ち間違いを利用者に知らせられる。パスフレーズは最大 63 文字なので、MTU を交換するか、長い書き込み（5 節）が要る。

パスフレーズを書く属性には、認証された暗号化を求める（20 章 7 節）。暗号化していない接続で書こうとすると Error Response（0x05 か 0x0F）が返り、スマートフォンはペアリングしてからやり直す。

7. スタックの API で実装する

機器のファームウェアでは、ATT の PDU の組み立てと解析、探索への応答、MTU の交換、リンク層の再送は、BLE のスタックが受け持つ。アプリケーションは、属性の表をスタックのマクロや構造体で静的に定義して起動時に登録し（ハンドルはスタックが順に付ける）、読まれたとき・書かれたときに呼ばれるコールバックで値を渡し、受け取った値を確かめて使う。接続・切断・CCCD の書き込み・MTU の変更・送信の完了も、コールバックで知らされる。値が変わったら、通知を送る。コールバックは、スタックのタスクや割り込みの中から呼ばれることが多い（05 章 2 節）ので、コールバックの中では長い処理をせず、イベントを通信タスクのキューに入れるだけにする。

通知は、すぐには空中に出ない。スタックは、通知の PDU を送信の列に置き、接続イベントごとに送り出す。列に置ける数は数個〜十数個（代表値。スタックと設定による）なので、接続イベントの間に多くの値を送ろうとすると、列がいっぱいになる。そのとき、エラーをすぐに返すスタックと、空くまで呼んだタスクを止めるスタックがある。エラーで返る場合に、値を捨てたり、空くまで呼び続けて CPU を使い切ったりしないように、「送り終えた」の知らせを待って続きを送る。

スタックに依存しない形で書く。ble_notify と on_notify_sent は、この章で仮に置くスタックの関数とコールバックで、temp_queue_get は、測定タスクが値を入れるリングバッファ（2 バイトの値の列）から 1 つ取り出す関数、post_event は通信タスクのキューにイベントを入れる関数、H_TEMP は温度の値のハンドル（3 節の表の 0x000A）である。

#define BLE_BUSY (-1)
/* 通知を送信の列に置けたら 0、置く場所が無ければ待たずに BLE_BUSY を返す（この章で仮に置く関数） */
int ble_notify(uint16_t conn, uint16_t handle, const uint8_t *v, uint16_t len);

static bool subscribed;      /* CCCD に通知の有効（0x0001）が書かれている */
static bool waiting;         /* 送信の列の空きを待っている */
static bool has_pend;        /* 取り出したが、まだ列に置いていない値がある */
static int16_t pend;

/* 通信タスクの中で呼ぶ。送れるだけ送り、送信の列がいっぱいになったら止まる */
static void notify_pump(uint16_t conn)
{
    while (subscribed && !waiting) {
        if (!has_pend && !temp_queue_get(&pend)) return;   /* 送る値が無い */
        has_pend = true;
        uint8_t v[2];
        put_le16(v, (uint16_t)pend);                        /* 0.01 °C 単位の符号付き 16 ビット */
        if (ble_notify(conn, H_TEMP, v, 2) == BLE_BUSY) {
            waiting = true;                                 /* 送り終えた知らせを待つ */
            return;
        }
        has_pend = false;                                   /* 送信の列に置けた */
    }
}
/* 通信タスクのイベントループ（05 章 2 節）から、イベントを 1 つずつ渡す */
void comm_event(const struct event *ev)
{
    switch (ev->type) {
    case EV_TEMP_READY:                                     /* 測定タスクが値を入れた */
        notify_pump(ev->conn); break;
    case EV_NOTIFY_SENT:                                    /* スタックが通知を 1 つ送り終えた */
        waiting = false; notify_pump(ev->conn); break;
    case EV_CCCD_WRITTEN:                                   /* クライアントが CCCD を書いた */
        subscribed = (ev->value & 0x0001) != 0; notify_pump(ev->conn); break;
    case EV_DISCONNECTED:
        subscribed = false; waiting = false; break;
    }
}
/* スタックが呼ぶコールバックは、キューに入れるだけにする */
void on_notify_sent(uint16_t conn) { post_event(EV_NOTIFY_SENT, conn, 0); }

列に置けなかった値は pend に残し、送り終えた知らせが来たときに、同じ値から送り直す。そのため、値は順番どおりに、抜けも重複もなく列に置かれる。模擬のスタック（列に 3 つ、1 回の接続イベントで最大 4 つ送る）と測定タスクを組み合わせて、送り終えた知らせのたびにだけ続きを送ること、値が順番どおりに届くことを確かめた。測定の速さが接続イベントで運べる速さを超えると、測定タスクとの間のリングバッファがあふれる。そのときは、送る間隔を延ばすか、値をまとめて 1 つの通知に入れる（6 節の値の形）。
