Chapter 10

TCP — 順番どおり確実に届ける仕組み

この章で扱う問い. 08・09 章で、機器はアドレスを借り、Wi-Fi のアクセスポイントにつながって、サーバへ IP のパケットを送れるようになった。しかし IP は、パケットを失うことも、順番を入れ替えることも、同じパケットを 2 回届けることもある。07 章 4 節では、その上で TCP が、送ったバイトの列を失わず、重ねず、送った順に届けると述べ、仕組みはこの章に回した。

この章では次の 3 つの問いに答える。

  1. TCP は、どのように相手と手続きをして、送ったバイトのどこまでが届いたかを知るのか。
  2. 確認応答を待たずに続けて送るとき、どれだけの速さで送れるのか。失われたことにいつ気づいて、送り直すのか。
  3. RAM の少ない機器で TCP を使うと、どんな遅れとメモリの問題が起きるのか。コネクションはどう終わり、相手が黙って消えたことにはどう気づくのか。

答えの道具は、バイトに付けた番号と累積の確認応答、ウィンドウとスループットの上限 \(W/\mathrm{RTT}\)、RFC 6298 の RTO の式、そしてセグメントのやり取りを時間軸に並べて遅れを数えることである。

1. コネクション — 3 ウェイハンドシェイク

TCP の送り手は、どのバイトまでを送り、そのうちどこまでが相手に届いたかを覚えている。受け手は、どこまでを受け取り、次にどのバイトを待っているかを覚えている。07 章 4 節で見たとおり、TCP は送るバイトに番号を付けてこれらを覚える（番号の付け方は 2 節）。そのため、データを送り始める前に、両端は番号の始まりを伝え合い、それが相手に伝わったことを確かめておく必要がある。この手続きを済ませ、通信する 2 つのプログラムが、番号などの送受信の状態を両端で持ち合っている関係を、コネクションという。TCP のコネクションは、両端の IP アドレスとポート番号の 4 つの値で区別される（07 章 4 節の 5 つの値のうち、プロトコルは TCP に決まっている）。

セグメントの役割を表すフラグ

手続きに使うセグメントは、TCP のヘッダのフラグの欄（07 章 4 節の図）で見分ける。フラグは 8 ビットで、1 ビットが 1 つの印である。

  • SYN（synchronize）: コネクションを始め、自分の番号の始まりを知らせる。
  • ACK フラグ: ヘッダの確認応答番号の欄（次に受け取りたいバイトの番号。2 節）が有効であることを表す。接続を始める最初の SYN には無く、コネクションができた後のセグメントには必ず立てる。
  • FIN（finish）: こちらからはもう送らないことを知らせる（7 節）。
  • RST（reset）: コネクションを直ちに打ち切る（7 節）。

残りの 4 つのうち、CWR と ECE は混雑の通知に使い（5 節）、URG はほとんど使われない。PSH は、受け手に早くアプリケーションへ渡すよう求める印で、多くの実装が自動で付ける。以下、SYN と ACK フラグを両方立てたセグメントを SYN+ACK、データを運ばず ACK フラグだけを立てたセグメントを単に ACK と書く。

初期シーケンス番号

番号は、コネクションごとに決めた値から始める。この最初の値を初期シーケンス番号（ISN、Initial Sequence Number）という。ISN を毎回 0 にしない理由は 2 つある。1 つは、同じ 4 つの値のコネクションを閉じてすぐに作り直したとき、前のコネクションのセグメントがネットワークの中で遅れて届き、新しいコネクションの番号の範囲に入って受け取られてしまうおそれがあることである。もう 1 つは、番号を予測できると、通信路の外の第三者が、番号を合わせた偽のセグメント（RST など）を差し込めることである。そこで ISN は、コネクションごとに予測しにくい値に選ぶ（RFC 9293 は、時刻とともに増える値に、4 つの値と秘密の値から計算したハッシュを足す方法を示している）。

なぜ 3 回のやり取りか

両端がそれぞれ、(1) 自分の ISN を相手に知らせ、(2) 相手がそれを受け取ったことを確かめるには、いくつのセグメントが要るかを数える。

方針: 接続を始める機器の ISN を \(x\)、サーバの ISN を \(y\) として、(1) と (2) を両方の向きで行うセグメントを並べ、1 つにまとめられるものをまとめる。

導出: 機器の ISN については、① 機器が SYN で \(x\) を知らせ、② サーバが確認応答番号 \(x + 1\) を返す（SYN は番号を 1 つ使うので、次に欲しいのは \(x + 1\) になる）。サーバの ISN については、③ サーバが SYN で \(y\) を知らせ、④ 機器が確認応答番号 \(y + 1\) を返す。② と ③ は、どちらもサーバから機器へ、① を受け取った時点で送れるので、1 つのセグメント（SYN+ACK）にまとめられる。① は最初に要り、④ は ③ を受け取った後でなければ送れないので、これ以上はまとめられない。したがって 3 つのセグメントで足り、3 つより少なくはできない ∎

この 3 つのやり取りを 3 ウェイハンドシェイクという。値を入れた例を示す。

TCP の両端は、コネクションの段階を状態として持つ状態機械（05 章 1 節）である。サーバのプログラムは、あらかじめ決まったポートで SYN を待つ状態 LISTEN にしておく。機器は SYN を送ると SYN_SENT に、サーバは SYN を受け取って SYN+ACK を返すと SYN_RECEIVED に移り、それぞれ自分の SYN への確認を受け取った所で、データを送り合える状態 ESTABLISHED に移る（RFC 9293 は SYN-SENT のように「-」でつなぐが、この章は多くの実装に合わせて「_」でつなぐ。7 節の TIME_WAIT も同じ）。

SYN には、ヘッダのオプション（07 章 4 節の図）で、自分が受け取れるセグメントの最大の大きさ（MSS。07 章 6 節）を書く。相手は、これより大きいセグメントを送らない。知らせが無ければ、IPv4 では 536 バイトとみなす。RAM の少ない機器は、受け取るためのバッファを小さくするために、小さな MSS を知らせることもある。

機器が最初のデータを送れるのは、SYN+ACK を受け取った後、つまり SYN を送ってから 1 RTT 後である（3 つ目の ACK と同じセグメントにデータを載せてもよい）。要求への応答が届くのは、さらに 1 RTT 後になる。送るたびにコネクションを作ると 1 回のやり取りに 2 RTT かかり、作ってあるコネクションで送れば 1 RTT で済む。09 章 4 節の「送るときだけつなぐ」作り方では、このハンドシェイクも送るたびにかかる。TLS（12 章）を使うと、さらに往復が加わる。SYN が失われれば、機器は時間切れで SYN を送り直す（その間隔は 4 節）。サーバのそのポートで待っているプログラムが無ければ、サーバは RST を返し、接続は断られる（7 節）。

2. バイトに番号を付ける — シーケンス番号と確認応答番号

05 章 4 節のストップアンドウェイトでは、メッセージに 1 ビットのシーケンス番号を付けた。TCP は、メッセージではなく、送るバイトの 1 つ 1 つに 32 ビットの番号を付ける。アプリケーションが書いたバイトの列は、ISN + 1 から始まる連続した番号を持つ（ISN の番号は SYN が使っている）。セグメントのヘッダのシーケンス番号の欄には、そのセグメントが運ぶデータの最初のバイトの番号を入れる。この番号を、05 章のシーケンス番号と区別して、TCP のシーケンス番号という。

メッセージではなくバイトに番号を付けるのは、TCP がアプリケーションの書き込みの区切りを保たない（07 章 4 節）からである。送り手は、書き込まれたバイトを MSS 以下の好きな大きさに区切って送ってよく、送り直すときに区切り方を変えてもよい（図の下の段）。どの区切りで届いても、受け手は番号から、各バイトを列のどこに置けばよいかが分かる。

受け手は、ACK フラグを立てたセグメントの確認応答番号の欄に、次に受け取りたいバイトの番号を入れる。この番号を確認応答番号という。確認応答番号が \(a\) なら、\(a\) より前の番号のバイトはすべて受け取った、という意味になる。1 つ 1 つのセグメントではなく、それまでの全部をまとめて確かめるので、この確かめ方を累積の確認応答という。

受け手が返す番号を決める

受け手が何を返せばよいかを、届いたセグメントの番号から導く。

方針: 受け手は、次に受け取りたい番号を 1 つ覚えている（以下 rcv_nxt と書く）。番号 \(s\) から \(n\) バイトのセグメントが届いたとき、そのバイトの範囲（\(s\)〜\(s + n - 1\)）と rcv_nxt の関係を、すべての場合に分けて扱いを決める。

導出: 範囲と rcv_nxt の関係は、次の 3 通りのどれかである。

  1. \(s \le \text{rcv\_nxt} < s + n\)（次に欲しいバイトを含む）: 先頭の \(\text{rcv\_nxt} - s\) バイトは受け取り済みなので除き、残りを受け取って rcv_nxt を \(s + n\) に進める（受信バッファに入る分だけ。3 節）。
  2. \(s + n \le \text{rcv\_nxt}\)（全部受け取り済み）: 再送された写しなどの重複なので捨てる。
  3. \(\text{rcv\_nxt} < s\)（間が抜けている）: 前のセグメントが失われたか、遅れている。rcv_nxt は進められないので、捨てるか、抜けた所が届くまで取っておく。

どの場合も、処理した後の rcv_nxt が「次に受け取りたい番号」なので、確認応答番号として rcv_nxt を返す ∎ この規則で 3 つの場面を追う。

  • (a) ACK が 1 つ失われても、後の ACK がそれまでの分をまとめて確かめるので、送り手は送り直さなくてよい（05 章 4 節のストップアンドウェイトでは、ACK が失われると再送が起きた）。
  • (b) 順番が入れ替わって 1201 が先に届くと、場合 3 なので、受け手は同じ確認応答番号 1101 をもう一度返す。前と同じ確認応答番号を持つ、データの無い ACK を重複 ACK という。1101 が届くと、取っておいた 1201〜1300 まで受け取り済みになり、確認応答番号は 1301 に飛ぶ。
  • (c) 1101 が失われると、後に届くセグメントのたびに重複 ACK が返る。送り直した 1101 が届くと、確認応答番号は 1501 に飛ぶ。

送り手から見ると、(b) と (c) は重複 ACK の数でしか区別できない。入れ替わりなら重複 ACK は少数で止まり、喪失なら後のセグメントの数だけ続く。4 節では、これを手がかりに失われたことに早く気づく。確認応答番号だけでは「1201〜1400 は受け取ったが 1101〜1200 が無い」とは伝えられないので、受け取った範囲を知らせるオプション（SACK、RFC 2018）もある。RAM の少ないスタックには、場合 3 のセグメントを取っておかずに捨てるものもある（組み込み向けの TCP/IP スタックの 1 つである lwIP（11 章）では、TCP_QUEUE_OOSEQ という設定で選べる。版によって細部が異なる）。捨てた場合は、送り手がそのセグメントも送り直すことになる。

番号の一周と比較

シーケンス番号の欄は 32 ビットなので、番号は \(2^{32}\) で一周して 0 に戻る。ISN は予測しにくい値に選ぶので、コネクションを作ってすぐに一周することもある。そのため、番号の前後は、05 章 3 節の期限の比較と同じく、差を符号付きで読んで比べる。05 章 3 節の導出から、比べる 2 つの番号が \(2^{31}\) 未満しか離れていなければ、この比べ方は正しい。TCP で比べる番号はウィンドウ（3 節）の範囲に収まり、ウィンドウは \(2^{31}\) バイトよりずっと小さいので、この条件は満たされる。

受け手の処理を C で書くと次のようになる。データを運ぶ部分だけを示し、SYN・FIN と、ウィンドウの外のセグメントの検査は省いた。場合 3 のセグメントは捨てる、RAM の少ない形である。

/* TCP のシーケンス番号の比較（2^32 を法とする。05 章 3 節の期限の比較と同じ） */
static int seq_lt(uint32_t a, uint32_t b) { return (int32_t)(a - b) < 0; }   /* a が b より前 */
static int seq_le(uint32_t a, uint32_t b) { return (int32_t)(a - b) <= 0; }

/* 届いたセグメント（先頭の番号 seq、データ p、長さ n）を処理し、返す確認応答番号を返す。
   *rcv_nxt は次に欲しいバイトの番号（これより前は全部受け取った） */
uint32_t rx_segment(uint32_t *rcv_nxt, uint32_t seq, const uint8_t *p, uint32_t n)
{
    if (seq_le(seq, *rcv_nxt) && seq_lt(*rcv_nxt, seq + n)) {    /* 次に欲しいバイトを含む */
        uint32_t skip = *rcv_nxt - seq;        /* そのうち受け取り済みの先頭の部分 */
        uint32_t take = n - skip;
        if (take > rx_space())
            take = rx_space();                 /* 受信バッファに入る分だけ受け取る */
        rx_store(p + skip, take);
        *rcv_nxt += take;
    }
    /* 間が抜けた先のセグメントと、古い重複は捨てる */
    return *rcv_nxt;                           /* どの場合も、次に欲しい番号を返す */
}

rx_space（受信バッファの空きを返す）と rx_store（受信バッファへ入れる）は、この章で仮に置く関数で、受信バッファは 04 章 3 節のリングバッファで作れる。rx_segment の if の条件が場合 1 で、それ以外が場合 2 と 3 である。このコードは、2 割を失い、1 割を重複させ、順番を入れ替える模擬の通信路で、番号が送り始めてすぐに一周する 300 通りの転送を行い、アプリケーションが読んだバイトの列が送った列と一致すること、確認応答番号が一度も戻らないことを確かめてある。

3. スライディングウィンドウ — 応答を待たずに続けて送る

05 章 4 節のストップアンドウェイトは、1 つ送ると、その ACK が届くまで次を送らなかった。RTT が送る時間より長いと、ほとんどの時間を待つことに使い、05 章 4 節の例 2（1 Mbps の回線で 100 バイトを送り、RTT 100 ms）では、1 秒に約 990 バイトしか送れなかった。TCP は、確認されていないバイトが決めた量に達するまでは、ACK を待たずに続けて送る。

送り手が、確認応答を受け取らないまま送ってよいバイト数の上限をウィンドウという。ウィンドウを \(W\) バイトとし、確認されていない最初のバイトの番号を snd_una、次に送るバイトの番号を snd_nxt と書く。送り手は、送ったが確認されていないバイト数 snd_nxt − snd_una を \(W\) 以下に保つ。

ACK が届いて snd_una が進むと、送ってよい範囲の右端 snd_una + \(W\) も同じだけ進む。バイトの列の上を窓が滑っていくように見えるので、この送り方をスライディングウィンドウという。ストップアンドウェイトは、\(W\) をメッセージ 1 つ分にしたスライディングウィンドウにあたる。

スループットの上限 W/RTT

\(W\) を決めると、送れる速さの上限が決まる。1 つのセグメントを送る時間（長さ ÷ 回線の速さ）を \(T_\mathrm{s}\) とする。

方針: あるセグメントを送り始めてから、その ACK が届くまでの間に、送り手が送れるバイト数の上限を求める。

導出: セグメント \(j\) を送り始める時刻を \(t_j\)、その最初のバイトの番号を \(b_j\) とする。セグメント \(j\) の ACK が届くのは、送り終える \(t_j + T_\mathrm{s}\) から RTT 後、すなわち \(t_j + T_\mathrm{s} + \mathrm{RTT}\) である（RTT は 05 章 4 節のとおり、送り終えてから ACK を受け取り終えるまでの時間）。それまでセグメント \(j\) は確認されないので、snd_una は \(b_j\) を越えない。送り手は snd_nxt − snd_una ≤ \(W\) を保つので、この間に送るバイトの番号は \(b_j + W\) より小さい。一方、時刻 \(t_j\) 以後に送るバイトの番号は \(b_j\) 以上である。したがって、\(t_j\) から長さ \(T_\mathrm{s} + \mathrm{RTT}\) の間に送れるのは多くとも \(W\) バイトである。送り続ける間は、どのセグメントから測っても同じことが言えるので、平均の速さについて

\[ \text{スループット} \le \frac{W}{T_\mathrm{s} + \mathrm{RTT}} < \frac{W}{\mathrm{RTT}} \]

が成り立つ ∎

何も失われなければ、送り手はウィンドウ分を送って最初の ACK を待ち、ACK が 1 つ届くたびに次のセグメントを 1 つ送るので、上限 \(W/(T_\mathrm{s} + \mathrm{RTT})\) に届く（図の (a)）。\(W\) をメッセージ 1 つ分にすると、この上限は 05 章 4 節の効率 \(T_\mathrm{f}/(T_\mathrm{f} + \mathrm{RTT})\) に回線の速さを掛けたものと一致する。回線の速さを \(C\)（バイト/秒）として \(W \ge C\,(T_\mathrm{s} + \mathrm{RTT})\) なら、最初の ACK が戻る前に次を送る番が来るので、送り手は休まず送り続け、スループットは回線の速さ \(C\) で頭打ちになる（図の (b)）。回線を使い切るのに要る \(C \times \mathrm{RTT}\) 程度のバイト数を帯域幅遅延積という。10 Mbps（\(1.25 \times 10^6\) バイト/秒）で RTT 100 ms なら 125,000 バイトである。

例: RAM の少ない機器の TCP/IP スタックは、ウィンドウを MSS の数倍にすることが多い。たとえば lwIP の既定の設定は、MSS を 536 バイト、ウィンドウをその 4 倍の 2144 バイトとしている（11 章 7 節。版や設定による）。RTT 100 ms なら、スループットは 2144 ÷ 0.1 s = 21,440 バイト/秒（約 171.5 kbps）を超えず、回線を速くしても上がらない。ストップアンドウェイトの約 990 バイト/秒の 20 倍を超えるが、10 Mbps の回線の 1/58 にすぎない。

受信ウィンドウ — 受け手が速さを決める

\(W\) は、まず受け手の都合で決まる。受け手のスタックは、届いたバイトを、アプリケーションが読むまで RAM の受信バッファ（02 章 6 節）に置く。受信バッファがいっぱいなら、それ以上届いても置けない。そこで受け手は、送るすべてのセグメントのウィンドウの欄（07 章 4 節の図）に、受信バッファの空き、つまりあと何バイト受け取れるかを書く。この値を受信ウィンドウという。送り手は、確認応答番号に受信ウィンドウを足した番号より前までしか送らない。アプリケーションが読むのが遅れると、受信バッファが埋まって受信ウィンドウが小さくなり、送り手は遅くなる。受け手が送り手に「待って」と伝える 02 章 6 節のフロー制御を、TCP はこの欄で行っている。

受信バッファが満杯になると、受け手は受信ウィンドウ 0 を知らせ、送り手は止まる。アプリケーションが読んで空きができると、受け手は新しい受信ウィンドウを書いた ACK を送る。この ACK が失われると、送り手は待ち続け、受け手も送るものが無いので、両方が止まったままになる。そこで送り手は、受信ウィンドウが 0 の間も、ときどき 1 バイトだけのセグメントを送って受信ウィンドウを確かめる（RFC 9293 が求めている）。なお、ウィンドウの欄は 16 ビットなので、そのままでは 65535 バイトまでしか書けず、RTT 100 ms では 655,350 バイト/秒（約 5.24 Mbps）が上限になる。それより大きな値は、SYN で倍率を決めておくオプション（ウィンドウスケール、RFC 7323）で表す。RAM の少ない機器では、65535 バイトで足りることが多い。

機器が受け手になるときは、機器の受信ウィンドウ、つまり受信バッファに割り当てた RAM が速さの上限を決める。22 章のファームウェアの更新で、機器が 500 KB（512,000 バイト）を受け取るとき、受信ウィンドウが 2144 バイト、RTT が 100 ms なら、少なくとも 512,000 ÷ 21,440 ≈ 23.9 秒かかる。

4. 失われたら — 再送タイマと RTO の計算

失われたセグメントには、05 章 4 節と同じく、時間切れで気づく。TCP の送り手は、確認されていないデータがある間、時計を 1 つ動かしておく。この時計を再送タイマ、時間切れまでの時間を RTO（Retransmission TimeOut、再送タイムアウト）という。動かし方は次のとおりである（RFC 6298）。

  • データを送るとき、再送タイマが止まっていれば動かす。
  • 新しいデータを確かめる ACK が届いたら、動かし直す。確認されていないデータが無くなったら止める。
  • 時間切れになったら、確認されていない最初のセグメントを送り直し、RTO を 2 倍にして動かし直す。

RTO は、05 章 4 節のタイムアウトと同じく RTT より長くなければならず、長すぎると、失われたときの回復が遅れる。ところがインターネットの RTT は、近くのサーバなら数 ms、遠くのサーバなら 100 ms 以上、携帯電話の網（21 章）では 1 秒を超えることもあり（代表値）、同じ経路でも、途中のルータの混み具合で刻々と変わる。そこで TCP は RTT を測り続け、その平均と揺らぎから RTO を決める。手順は RFC 6298 に定められている。

RFC 6298 の計算

送り手は、セグメントを送った時刻を覚えておき、それを確かめる ACK が届いた時刻との差を、RTT の測定値とする（05 章 4 節の RTT に、セグメントを送る時間を足したものにあたる）。最初の測定値を \(R\) として \(\mathrm{SRTT} \leftarrow R\)、\(\mathrm{RTTVAR} \leftarrow R/2\) とし、2 回目からは、新しい測定値 \(R'\) で次の順に更新する（RTTVAR の式の SRTT には、更新する前の値を使う）。

\[ \begin{aligned} \mathrm{RTTVAR} &\leftarrow (1 - \beta)\,\mathrm{RTTVAR} + \beta\,\lvert \mathrm{SRTT} - R' \rvert \\ \mathrm{SRTT} &\leftarrow (1 - \alpha)\,\mathrm{SRTT} + \alpha R' \end{aligned} \]

ここで \(\alpha = 1/8\)、\(\beta = 1/4\) である。SRTT（smoothed RTT）は RTT の平均を滑らかにした値、RTTVAR は測定値の平均からの外れ（揺らぎ）の大きさの平均である。更新のたびに

\[ \mathrm{RTO} \leftarrow \mathrm{SRTT} + \max(G,\ 4\,\mathrm{RTTVAR}) \]

とする。\(G\) はタイマの時計の細かさ（05 章 3 節のティックの長さ）である。RFC 6298 はさらに、最初の測定の前は RTO を 1 秒とすること、RTO が 1 秒未満なら 1 秒に切り上げること（推奨）、上限を置くなら 60 秒以上にすることを定めている。SRTT の式が、過去の測定値をどう混ぜているかを確かめる。

方針: SRTT の更新の式に、1 つ前の SRTT の式を繰り返し代入し、各測定値に掛かる重みを求める。

導出: \(k\) 回目の測定値を \(R_k\)、その後の SRTT を \(S_k\) とすると、\(S_k = \tfrac{7}{8} S_{k-1} + \tfrac{1}{8} R_k\) である。これに \(S_{k-1} = \tfrac{7}{8} S_{k-2} + \tfrac{1}{8} R_{k-1}\) を代入すると

\[ S_k = \tfrac{1}{8} R_k + \tfrac{1}{8} \cdot \tfrac{7}{8} R_{k-1} + \left(\tfrac{7}{8}\right)^2 S_{k-2} \]

となる。これを繰り返すと、\(j\) 回前の測定値 \(R_{k-j}\) の重みは \(\tfrac{1}{8}\left(\tfrac{7}{8}\right)^j\) である。重みは 1 回さかのぼるごとに 7/8 倍になり、\((7/8)^5 \approx 0.51\)、\((7/8)^{16} \approx 0.12\) なので、5 回前の測定値の重みは最新の約半分、16 回前では約 1/8 になる ∎

SRTT は、最近の十数回の測定値に重みを付けた平均で、1 回だけ外れた値には振り回されず、RTT が本当に変わったときは数回で追いつく。RTTVAR は、平均からの外れ \(\lvert \mathrm{SRTT} - R' \rvert\) を、同じ形（重み 1/4）で平均したものである。RTO を SRTT に 4 × RTTVAR を足した値にするのは、揺らぎの大きな経路ほど、RTO を平均から大きく離しておくためである。

再送したセグメントの RTT は測らない

再送したセグメントの ACK が届いても、それが最初に送った分への ACK か、再送した分への ACK かは、送り手には分からない。最初の分への ACK だったのに再送からの時間を測ると（図の (a)）、RTT を短く見積もって RTO が下がり、さらに不要な再送を招く。再送した分への ACK だったのに最初からの時間を測ると（図の (b)）、長く見積もる。そこで、再送したセグメントの測定値は使わない。これを Karn のアルゴリズムといい、RFC 6298 は使うことを求めている。時間切れで RTO を 2 倍にした後は、再送していないセグメントで新しい測定値が得られるまで、2 倍にした RTO を使い続ける。

時間切れが続くとき

時間切れのたびに RTO を 2 倍にするのは、05 章 5 節の指数バックオフである。経路が混んでいて失われているのなら、送る量を減らさなければならないからである（5 節）。RFC 6298 の再送タイマには、乱数によるずらし（ジッタ）は入っていない。最初の測定の前の RTO は 1 秒なので、SYN が失われ続けると、機器は 0、1、3、7、15 秒…に SYN を送る。

08 章 7 節の参加の手順では、接続の期限を 10 秒にしていたので、SYN を 4 回送ったところで諦めて、待ってからやり直す。Linux の既定の設定では、SYN を 6 回送り直し（合わせて 7 回）、127 秒で諦める。機器では、接続の期限をアプリケーションの側で決めておくほうがよい。

実装

RTO の計算を C で書くと次のようになる。時間はミリ秒の整数で持つ。SRTT を 8 倍、RTTVAR を 4 倍した値で覚えると、\(\alpha = 1/8\) と \(\beta = 1/4\) の掛け算が、足し算と、8 と 4 での割り算になり、浮動小数点を使わずに済む。

#define RTO_MIN  1000     /* [ms] 1 秒未満なら 1 秒に切り上げる (2.4) */
#define RTO_MAX  60000    /* [ms] 上限（60 秒以上なら置いてよい (2.5)） */
#define CLOCK_G  10       /* [ms] 時計の細かさ G（ティックが 10 ms の例） */

struct rto_est { int32_t srtt8, rttvar4, rto; int have; };  /* 8 × SRTT、4 × RTTVAR、RTO、測ったか */

static int32_t rto_clamp(int32_t v) { return v < RTO_MIN ? RTO_MIN : v > RTO_MAX ? RTO_MAX : v; }
void rto_init(struct rto_est *e)    { e->have = 0; e->rto = 1000; }           /* 測る前は 1 秒 (2.1) */
void rto_backoff(struct rto_est *e) { e->rto = rto_clamp(2 * e->rto); }   /* 時間切れのたびに (5.5) */

/* RTT の測定値 r で更新する。再送したセグメントの測定値は渡さない（Karn のアルゴリズム） */
void rto_sample(struct rto_est *e, int32_t r)
{
    if (!e->have) {                         /* 最初の測定 (2.2): SRTT = R、RTTVAR = R/2 */
        e->srtt8 = 8 * r;
        e->rttvar4 = 2 * r;
        e->have = 1;
    } else {                                /* 2 回目から (2.3) */
        int32_t err = r - e->srtt8 / 8;     /* R' − SRTT（更新する前の SRTT） */
        e->srtt8 += err;                    /* SRTT ← SRTT + (R' − SRTT)/8 */
        if (err < 0)
            err = -err;
        e->rttvar4 += err - e->rttvar4 / 4; /* RTTVAR ← RTTVAR + (|R' − SRTT| − RTTVAR)/4 */
    }
    int32_t k = e->rttvar4 > CLOCK_G ? e->rttvar4 : CLOCK_G;   /* max(G, 4 × RTTVAR) */
    e->rto = rto_clamp(e->srtt8 / 8 + k);
}

括弧の中の (2.1) などは、RFC 6298 の規則の番号である。送り手は、確認されていないセグメントのうち 1 つについて、送った時刻と番号を覚えておき、それを確かめる ACK が届いたら、その差を rto_sample に渡す。そのセグメントを再送したら、覚えた時刻を捨てる（Karn のアルゴリズム）。再送タイマが時間切れになったら rto_backoff を呼ぶ。上の表の例では、このコードの RTO は表の値と 1 ms 未満しか違わない。乱数で作った 40 万個の測定値の列でも、浮動小数点で計算した RFC 6298 の式との差は 5 ms 未満だった（整数の割り算で切り捨てる分）。

高速再送

RTO は 1 秒以上なので、RTT が 50 ms の経路で時間切れを待つと、20 RTT 分の時間が止まる。2 節で見たとおり、セグメントが 1 つ失われると、後に届くセグメントのたびに重複 ACK が返る。ただし重複 ACK は、順番の入れ替わりでも返る。そこで、同じ確認応答番号の重複 ACK を 3 つ受け取ったら、そのセグメントは失われたと判断し、時間切れを待たずに送り直す。これを高速再送という（RFC 5681）。重複 ACK が 3 つ返るには、失われたセグメントの後に、3 つ以上のセグメントが送られて届かなければならない。それがいつ成り立つかを数える。

方針: ウィンドウをセグメント \(k\) 個分とし、セグメント \(j\) が失われたとき、\(j\) の後に送られるセグメントの数を数える（後のセグメントが失われなければ、それぞれが届くたびに重複 ACK が 1 つ返る）。

導出: \(j\) を送った時点で確認されていないセグメントは、\(j\) を含めて多くとも \(k\) 個なので、そのうち最も古いものは \(j - k + 1\) 番以降である。\(j\) が失われると、確認応答番号は \(j\) の先頭より先に進まないので、送り手は \(j - k + 1\) 番から \(k\) 個分、つまり \(j + k - 1\) 番までしか送れない。したがって \(j\) の後に送られるのは多くとも \(k - 1\) 個で、\(j\) の後に送るデータがセグメント \(m\) 個分しか残っていなければ \(\min(k - 1, m)\) 個である。高速再送には \(\min(k - 1, m) \ge 3\)、すなわち \(k \ge 4\) かつ \(m \ge 3\) が要る ∎

ウィンドウが MSS の 4 倍の機器でも、大きなデータを送り続けている途中なら、重複 ACK はちょうど 3 つ届き、高速再送できる（図の (a)）。しかし、測定値やコマンドのように 1 つのセグメントに収まるメッセージを送る機器では \(m = 0\) なので、失われると必ず時間切れを待つ（図の (b)）。ウィンドウが 3 セグメント分以下の場合や、データの最後の 3 つのセグメントのどれかが失われた場合も同じである。小さな機器では、失われるたびに RTO（1 秒以上）止まることが多い。

5. 輻輳制御 — ネットワークの混雑に合わせる

受信ウィンドウは、受け手があふれないように送り手を抑える。しかし、あふれるのは受け手だけではない。インターネットでは、多くの送り手のパケットが、同じルータの同じ出口を通る。ルータは、出口の回線が送り出せる速さを超えて届いたパケットを待ち行列に並べ、行列がいっぱいになると捨てる。送り手たちが速く送りすぎると、行列が延びて RTT が増え、捨てられたパケットの再送がさらに混雑を増やす。このように、ネットワークの途中が運べる以上のパケットで混み合った状態を輻輳という。1980 年代の後半には、輻輳でインターネットのスループットが大きく落ちる事態が実際に起き、それをきっかけに TCP に輻輳制御が加えられた。

送り手は、途中の経路がどれだけのデータを抱えられるかを知らない。そこで、自分で見積もった値を持ち、それを超えて送らないようにする。この値を輻輳ウィンドウ（cwnd、congestion window）という。確認されていないまま送ってよいバイト数は

\[ \text{実効のウィンドウ} = \min(\text{受信ウィンドウ},\ \mathrm{cwnd}) \]

で、受け手の都合と経路の都合の小さい方になる。3 節の \(W\) は、この値である。cwnd の増やし方と減らし方は RFC 5681 に定められている。

スロースタートと輻輳回避

コネクションの始めは、経路の空きが分からないので、cwnd を MSS の数倍の小さな値から始め（RFC 5681 では 2〜4 セグメント分。10 セグメント分から始める実装も多い）、新しいデータを確かめる ACK が 1 つ届くたびに、cwnd を 1 MSS 増やす。これをスロースタートという。

方針: 1 RTT の間に届く ACK の数を数え、1 RTT の間の cwnd の増え方を求める。

導出: cwnd がセグメント \(n\) 個分のとき、送り手は \(n\) 個のセグメントを送り、およそ 1 RTT 後に \(n\) 個の ACK を受け取る（受け手がセグメントごとに ACK を返すとする）。ACK 1 つで 1 MSS 増えるので、1 RTT 後の cwnd は \(n + n = 2n\) 個分になる ∎

名前に反して、cwnd は RTT ごとに 2 倍に増える。始めの値を IW（initial window）、目標の大きさを \(W\) とすると、\(\mathrm{IW} \cdot 2^m \ge W\) となる \(m\)、すなわち \(\log_2 (W / \mathrm{IW})\) RTT ほどで \(W\) に届く。IW = 4 × 1460 = 5840 バイトから、3 節の 10 Mbps・RTT 100 ms の帯域幅遅延積 125,000 バイトまでは、\(\log_2 (125000 / 5840) \approx 4.4\) なので 5 RTT（0.5 秒）かかる。

cwnd がスロースタートしきい値（ssthresh）に達したら、増やし方を 1 RTT に 1 MSS に落とす（ACK 1 つごとに MSS × MSS ÷ cwnd ずつ増やす）。これを輻輳回避という。ssthresh の始めの値は十分大きくしておき、失われたときに決め直す。

失われたら減らす

失われたことに気づいたら、経路が混んでいるとみなして cwnd を減らす。

  • 重複 ACK 3 つで気づいたとき（高速再送）: 後のセグメントは届いているので、混雑は軽いとみなす。ssthresh を、そのとき送って確認されていない量の半分にし、cwnd もほぼその値に下げて、輻輳回避を続ける。
  • 時間切れで気づいたとき: ssthresh を同じく半分にし、cwnd を 1 MSS に戻して、スロースタートからやり直す。

こうして cwnd は、輻輳回避の間は 1 RTT に 1 MSS ずつ増え、失われると半分になる、のこぎりの歯の形を描く。

図の (b) は、RAM の少ない機器が受け手のときである。受信ウィンドウが 2144 バイト（MSS 536 の 4 倍）なら、始めの cwnd（MSS が 1095 バイト以下なら 4 セグメント分、つまり 2144 バイト）と同じ大きさなので、実効のウィンドウは最初から受信ウィンドウで決まる。機器が送り手のときも、送信バッファ（6 節）の大きさが同じように上限になる。小さな機器の TCP の速さの上限は、多くの場合、輻輳制御ではなく、受信ウィンドウと RAM で決まる。輻輳制御が効いてくるのは失われたときで、時間切れのたびに cwnd が 1 MSS に戻り、スロースタートをやり直す。なお、サーバや PC の OS では、cwnd の増やし方を変えた方式（CUBIC など）が使われることが多い。ルータがパケットを捨てる代わりに印を付けて混雑を知らせる仕組み（ECN、RFC 3168。1 節のフラグの CWR と ECE を使う）もある。

6. 小さな機器で起きること — Nagle・遅延 ACK・メモリ

機器は、測定値やコマンドのような小さなデータを、小さな書き込みで送ることが多い。1 バイトのデータでも、TCP の 20 バイトと IPv4 の 20 バイトのヘッダが付いて 41 バイトの IP パケットになり、Ethernet では最小のフレームまで詰め物をして、線の上では 84 バイト分になる（07 章 5 節）。効率は 1/84 ≈ 1.2 % である。書き込むたびにセグメントを 1 つ送ると、ネットワークを小さなセグメントで埋めてしまう。TCP には、セグメントの数を減らす工夫が、送り手と受け手の両方にある。

Nagle アルゴリズム（RFC 896）は、送り手の工夫である。送ったが確認されていないデータがある間は、MSS に満たない小さなデータを送らずにためておき、ACK が届くか、MSS 分たまったら、まとめて送る。確認されていないデータが無ければ、すぐに送る。これで、MSS に満たない小さなセグメントは、1 RTT に 1 つまでになる（図の (b)）。

遅延 ACK は、受け手の工夫である。受け手は、データを受け取っても、すぐには ACK を返さずに少し待つ。待つ間に受け手のアプリケーションが応答を書けば、ACK を応答のセグメントに載せて 1 つで済ませられ（図の (a)）、次のセグメントが届けば、2 つ分を 1 つの ACK で確かめられる（図の (b)）。RFC 1122（とそれを引き継いだ RFC 9293）は、遅らせる時間を 0.5 秒未満とし、満杯のセグメントが続くときは、少なくとも 2 つに 1 つは ACK を返すよう求めている。実際に待つ時間は実装によって違い、数十 ms〜200 ms 程度が多い（代表値）。

書く・書く・読む で止まる

2 つの工夫は、それぞれ単独では役に立つが、組み合わさると止まることがある。機器がサーバに要求を送って応答を待つとき、要求を「ヘッダを書く」「本体を書く」の 2 回の書き込みで送る場合を考える。サーバのアプリケーションは、要求の全体がそろってから応答を書くとする。

方針: 片道の時間を RTT/2 とし（送る時間と処理の時間は無視する）、遅延 ACK の待ち時間を \(D\) として、要求を書き始めてから応答を受け取るまでのセグメントを、1 つずつ時刻を付けて追う。

導出:

  1. 時刻 0: 機器がヘッダを書く。確認されていないデータは無いので、ヘッダはすぐ送られる。続けて本体を書くが、ヘッダがまだ確認されていないので、Nagle アルゴリズムにより本体はためておかれる。
  2. 時刻 RTT/2: サーバにヘッダが届く。アプリケーションは本体を待っていて応答を書かないので、ACK を載せるセグメントが無く、サーバの TCP は ACK を \(D\) だけ遅らせる。
  3. 時刻 RTT/2 + \(D\): サーバが ACK を送る。
  4. 時刻 RTT + \(D\): 機器に ACK が届き、ためていた本体が送られる。
  5. 時刻 3RTT/2 + \(D\): サーバに本体が届き、アプリケーションが応答を書く。応答のセグメントには、本体への ACK も載る。
  6. 時刻 2RTT + \(D\): 機器に応答が届く。

したがって 1 回の要求に 2RTT + \(D\) かかる。ヘッダと本体が続けて送られていれば、どちらも RTT/2 にサーバに届き、応答は RTT に届くので、\(D\) + RTT だけ余分にかかっている ∎

RTT 40 ms、\(D\) = 200 ms なら、1 回に 280 ms かかり、続けて送れた場合の 40 ms の 7 倍になる。1 秒に送れる要求は 25 回から約 3.6 回に減る。この環境の Linux のループバック（RTT は 0.1 ms 未満）で、10 バイトと 20 バイトを書いて 30 バイトの応答を読むことを繰り返すと、1 回に平均 44 ms かかった。本体をためないようにすると 0.04 ms 未満だったので、遅延 ACK の待ち時間（この環境では 40 ms 程度）が、1 回ごとにそのまま加わっていることが分かる。対策は 2 つある。

  • 要求の全体をアプリケーションのバッファで組み立て、1 回で書く。セグメントの数も減るので、まずこれを考える。
  • Nagle アルゴリズムを止める。ソケット（11 章）では、TCP_NODELAY という設定で止められる。
int one = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof one);   /* Nagle アルゴリズムを止める */

Nagle アルゴリズムを止めると、小さな書き込みのたびにセグメントが出るので、書き込みの回数を減らすことと組み合わせる。上の測定で本体をためないようにしたのは、この設定である。

確認されるまで持ち続けるメモリ

TCP の送り手は、送ったバイトを、確認されるまで捨てられない。失われたら送り直すためで、05 章 4 節の送り手がメッセージの写しを持ち続けたのと同じである。アプリケーションが書いたバイトは、まだ送っていない分も、送ったが確認されていない分も、スタックの中の RAM の領域に置かれる。この領域を TCP の送信バッファという（以下、単に送信バッファと書く）。送信バッファの大きさを \(B\) とすると、確認されていないバイトは \(B\) を超えられないので、3 節と同じ考え方で、スループットは \(B/\mathrm{RTT}\) を超えない。ソケットの送信の関数が戻ったことは、データが送信バッファに入ったことを意味するだけで、相手に届いたことは意味しない（11 章 2 節）。送信バッファが小さすぎると、遅延 ACK とぶつかる。

方針: 送信バッファが MSS 1 つ分しかない送り手が、大きなデータを満杯のセグメントで送り続けるとき、1 つのセグメントにかかる時間を求める（送る時間は無視する）。

導出: 送り手はセグメントを 1 つ送ると送信バッファがいっぱいになり、ACK を待つ。受け手には満杯のセグメントが 1 つずつしか届かないので、「2 つに 1 つは ACK を返す」決まりは働かず、受け手は ACK を \(D\) だけ遅らせる。セグメントは送ってから RTT/2 後に届き、ACK はその \(D\) 後に送られ、さらに RTT/2 後に届く。ACK が届いて送信バッファが空いてから次のセグメントを送るので、1 つのセグメントに RTT + \(D\) かかり、スループットは MSS/(RTT + \(D\)) である ∎

MSS 536 バイト、RTT 40 ms、\(D\) = 200 ms なら、536 ÷ 0.24 s ≈ 2233 バイト/秒である。送信バッファを MSS の 2 倍にすると、受け手は 2 つ目の満杯のセグメントで ACK をすぐ返すので、2 × 536 ÷ 0.04 s = 26,800 バイト/秒まで上がる（送る時間を無視した値）。lwIP の設定の説明でも、送信バッファを MSS の 2 倍以上にすることが勧められている（版によって細部が異なる）。

1 つのコネクションには、送信バッファと受信バッファのほかに、2〜5 節の番号・ウィンドウ・タイマなどを覚える構造体が要る。これを制御ブロックという。同時に張るコネクションの数だけ RAM が要るので、張れる数も RAM で決まる。lwIP での見積もりは 11 章 7 節で行う。

7. 終わり方 — FIN・RST・TIME_WAIT とキープアライブ

送るデータが無くなった側は、FIN を立てたセグメントを送る。FIN は「こちらからはもう送らない」という意味で、SYN と同じく番号を 1 つ使い、相手は ACK を返す。TCP の 2 つの向きは別々に閉じるので、FIN を受け取った側は、まだデータを送ってよく、送り終えたら自分も FIN を送る。こうして、ふつうは 4 つのセグメントでコネクションが終わる（相手が ACK と FIN を同時に出せるときは 3 つになる）。

先に FIN を送った側（図では機器）は、FIN_WAIT_1（自分の FIN への ACK を待つ）、FIN_WAIT_2（相手の FIN を待つ）と進み、相手の FIN に ACK を返した後も、すぐにはコネクションの情報を消さずに待つ。この待つ状態を TIME_WAIT という。後から FIN を受け取った側は、CLOSE_WAIT（自分のアプリケーションが閉じるのを待つ）、LAST_ACK（自分の FIN への ACK を待つ）と進んで終わる。TIME_WAIT で待つ時間は 2MSL である。MSL（Maximum Segment Lifetime）は、セグメントがネットワークの中に残りうる最長の時間として決めた値で、RFC 9293 では 2 分としている（したがって 2MSL は 4 分）。実装はもっと短くすることが多い（Linux の TIME_WAIT は 60 秒）。待つ理由は 2 つある。

  • 最後の ACK が失われると、相手は FIN を送り直してくる（図の右）。コネクションの情報が残っていれば、ACK を送り直せる。消してしまっていると、知らないコネクションへのセグメントとして RST を返すことになり、相手はエラーで終わる。
  • 同じ 4 つの値で新しいコネクションをすぐに作ると、前のコネクションのセグメントが遅れて届き、新しいコネクションのものとして受け取られるおそれがある。2MSL 待てば、両方向のセグメントがネットワークから消える。

TIME_WAIT の間も、制御ブロックは RAM に残る。機器が先に閉じる側になり、接続と切断を短い間隔で繰り返すと、TIME_WAIT のコネクションがたまり、RAM や、スタックが同時に持てるコネクションの数を使い切ることがある。機器では、コネクションを張ったまま使い続ける（13 章）か、サーバの側から先に閉じてもらう設計が考えられる。

RST — 直ちに打ち切る

RST を受け取った側は、FIN のような手続きをせず、コネクションを直ちに捨てる（送信バッファに残っていたデータも捨てられる）。RST が送られるのは、主に次の場合である。

  • 待っているプログラムの無いポートに SYN が届いたとき。接続は断られる（図の (a)）。
  • 知らないコネクションへのセグメントが届いたとき。たとえば、機器が再起動してコネクションの情報を失った後に、サーバが古いコネクションでデータを送ってきた場合である（図の (b)）。
  • アプリケーションが、コネクションを打ち切ると決めたとき。

ソケットでは、これらは決まったエラーとしてアプリケーションに知らされる（11 章 4 節）。

ハーフオープンと TCP キープアライブ

FIN も RST も届かないまま、片方だけがコネクションを失うことがある。機器の電源が切れた、機器が再起動した、途中の NAT の変換表の行が消えてパケットが黙って捨てられるようになった（08 章 5 節）、などの場合である。もう片方は、コネクションがまだあると思い続ける。この状態をハーフオープンという。残った側は、自分から何かを送るまで気づかない。送れば、相手が再起動していれば RST が返り、経路が切れていれば再送を繰り返した後に諦める（Linux の既定では 15 分ほどかかる）。サーバが機器からのデータを待つだけ、機器がサーバからの命令を待つだけの間は、どちらも送らないので、いつまでも気づかない。

そこで、やり取りが一定の時間無かったら、相手が生きているかを確かめるセグメントを送る。08 章 5 節では、変換表の行を保つために定期的に送るパケットをキープアライブと呼んだ。TCP にも、TCP 自身が送るキープアライブがあり、これを TCP キープアライブという。データを運ばない（または 1 バイトだけの）、すでに確認された番号のセグメントで、受け取った相手の TCP は ACK を返す。決めた回数続けて ACK が返らなければ、コネクションは切れたとみなす。RFC 1122 は、TCP キープアライブを使うかどうかを選べるようにし、既定では使わず、使う場合の間隔の既定は 2 時間以上と定めている。Linux の既定では、2 時間（7200 秒）やり取りが無ければ確かめ始め、75 秒ごとに 9 回まで送るので、切れたと分かるまでの時間は 7200 + 9 × 75 = 7875 秒（約 2 時間 11 分）である（図）。この長さは、機器の用途には 2 つの点で合わない。1 つは、08 章 5 節の NAT の保持時間である。変換表の行は数分で消えることも多く、2 時間ごとのキープアライブでは行を保てない。もう 1 つは、気づくまでの遅れである。サーバが機器の切断に 2 時間以上気づかないと、その間の命令は届かないまま捨てられる。間隔はソケットの設定で変えられる（Linux では SO_KEEPALIVE で有効にし、TCP_KEEPIDLE・TCP_KEEPINTVL・TCP_KEEPCNT で時間と回数を決める。組み込みの TCP/IP スタックにも同様の設定があることが多い）。ただし TCP キープアライブが確かめるのは、相手の TCP が動いていることまでで、相手のアプリケーションが応じられることまでは確かめない。そのため機器では、アプリケーション層のキープアライブ（MQTT では、決めた時間ごとに小さな要求と応答を交わす。13 章 5 節）を使うことが多い。
