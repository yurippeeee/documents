Chapter 16

BLE の全体像 — チャネル・役割・プロトコルスタック

この章で扱う問い. 01 章 2 節では、BLE もインターネットと同じく層に分かれていることを見た。06 章 5 節では、BLE の下の層を受け持つコントローラと、上の層を受け持つホストの間を流れるパケットを見た。この章から第 III 部として BLE を扱う。最初に、BLE が電波の帯のどこを使い、ビットをどう電波にし、機器がどんな役割を持ち、どの層が何を受け持つのかという全体像を見る。17〜20 章で使う用語の土台も、この章でそろえる。

この章では次の 3 つの問いに答える。

  1. BLE は、同じ 2.4 GHz の帯を使う Bluetooth Classic や Wi-Fi と何が違い、帯の中のどこを使うのか。
  2. ビットはどのように電波になるのか。速く送る方式と遠くへ届く方式は、何を引き換えにしているのか。
  3. 機器はどんな役割を持ち、どの層が何を受け持つのか。接続した 2 台は、Wi-Fi などで混んだ帯の中で、どのチャネルで送るかをどう決めるのか。

答えの道具は、チャネルの番号と周波数の対応、1 ビットにかける時間から届く距離を比べる計算、そしてチャネルを巡る規則（チャネル選択アルゴリズム）である。

この章で使う既出の用語（定義は各リンク先）. 機器・ゲートウェイ・クラウド（01 章 1 節）、プロトコル・階層・プロトコルスタック・ヘッダ（01 章 2 節）、ビットレート・通信距離（01 章 3 節）、平均電流（01 章 5 節）、ビット時間・ボーレート（02 章 2 節）、CRC（03 章 5 節）、状態機械（05 章 1 節）、確認応答（ACK）・再送・ストップアンドウェイト・シーケンス番号（05 章 4 節）、SoC・ホスト・コントローラ（06 章 1 節）、dBm（06 章 2 節）、HCI（06 章 5 節）、リンク層（07 章 1 節）、プリアンブル（07 章 2 節）、パケット（07 章 3 節）、ポート番号（07 章 4 節）、カプセル化（07 章 5 節）、アクセスポイント（AP）・チャネル・帯域幅・キャリアセンス（09 章 1 節）、スキャン（09 章 2 節）、プロビジョニング（09 章 6 節）

1. Bluetooth Classic と BLE

Bluetooth は、数 m〜数十 m の近い距離で機器どうしをつなぐ無線の規格の名前である。企業の集まりである Bluetooth SIG（Special Interest Group）が規格を決め、仕様書 Bluetooth Core Specification（以下、Core Specification）として公開している。Core Specification には、同じ Bluetooth の名前で、2 つの別の方式が入っている。

  • Bluetooth Classic: 最初の版からある方式。Core Specification での名前は BR/EDR（Basic Rate / Enhanced Data Rate）で、物理層の速さ（01 章 3 節）は BR が 1 Mbps、EDR が 2 Mbps と 3 Mbps である。ワイヤレスのイヤホンの音声のように、途切れずに流れるデータを運ぶのに使われる。
  • Bluetooth Low Energy（BLE）: 2010 年の版 4.0 で加わった方式。Core Specification での名前は LE（Low Energy）である。センサの測定値や設定のような少ないデータを、少ない電力で運ぶために作られた。

2 つは同じ 2.4 GHz の帯（2 節）を使い、名前も同じだが、チャネルの分け方・パケットの形・相手とつなぐ手順が違うので、互いに通信できない。スマートフォンや PC の多くは両方を持ち、相手に合わせて使い分ける。センサのような機器は、BLE だけを持つことが多い。このシリーズで扱うのは BLE である。

BLE が少ない電力で動くのは、送受信する時間を短くまとめ、その間を眠って過ごせるように作られているからである。接続している 2 台は、決まった間隔ごとに短い時間だけ起きてパケットをやり取りする（6 節、18 章）。相手を見つける手順も、決まった 3 本のチャネルに短いパケットを送るだけで済む（17 章）。01 章 5 節の平均電流の式でいえば、起きている時間 \(t_\mathrm{a}\) を短く、周期 \(T\) を長くできる形である。電流と電池寿命は 19 章で計算する。

スマートフォンのほとんどが BLE に対応しているので、BLE は、機器とスマートフォンをつなぐ方式として広く使われている。画面の無い機器に Wi-Fi の設定を渡すプロビジョニング（09 章 6 節）や、測定値をスマートフォン経由でクラウドに送る使い方（スマートフォンが 01 章 1 節のゲートウェイの役目をする）がその例である。Matter の機器も、最初の設定のときに BLE を使う（Matter シリーズ 05 章 4 節）。

Core Specification は、版を重ねて機能を足してきた。BLE に関係する主なものを示す（このあとの版でも機能は足されている）。

版BLE に加わった主な機能このシリーズ
4.0BLE そのもの（2〜6 節で見る仕組みの基本の部分）16〜18 章
4.21 つのパケットで運べるデータを 27 バイトから最大 251 バイトに増やす仕組み（データ長の拡張）、楕円曲線を使って暗号化の鍵を作る、より安全な鍵の決め方（LE Secure Connections）19・20 章

版の番号は、その版の仕様書に従って作られたことを表すだけで、新しく加わった機能の多くは任意（オプション）である。たとえば 5.0 に対応したコントローラ（06 章 1 節）でも、LE Coded を持つとは限らない。使いたい機能があるときは、両方の機器（たとえば自分の SoC と、相手のスマートフォン）が対応しているかを製品ごとに確かめる。コントローラが持つ機能は、HCI（06 章 5 節）の命令で問い合わせることもできる。

2. 周波数とチャネル

BLE が使うのは、2400〜2483.5 MHz の 2.4 GHz 帯である。09 章 1 節の Wi-Fi と同じ帯で、IEEE 802.15.4（Thread・Zigbee）や電子レンジもこの帯の電波を使う。この帯は、産業・科学・医療（Industrial, Scientific and Medical）の機器のために国際的に割り当てられた周波数の帯の 1 つで、ISM 帯と呼ばれる。多くの国で、送信の電力などの決まりを守った無線の機器（日本では技術基準適合証明などの認証を受けたもの。06 章 1 節）なら、免許を受けずに使える。そのため、さまざまな機器が、同じ場所で同じ周波数を分け合うことになる。

BLE は、この帯を 2 MHz おきの 40 本に分けて使う。この 40 本を BLE のチャネルという（09 章 1 節の Wi-Fi のチャネルとは、間隔も幅も番号の付け方も違う）。周波数の低いほうから k = 0, 1, …, 39 と数えると、k 番目のチャネルの中心の周波数は

\[ f = 2402 + 2k\ \text{[MHz]} \]

で、いちばん低いチャネルが 2402 MHz、いちばん高いチャネルが 2480 MHz である。09 章 1 節の Wi-Fi は、5 MHz おきに置いた中心の周波数で、帯域幅 20 MHz の信号を送るので、隣どうしのチャネルの信号が重なった。BLE のチャネルは 2 MHz おきに並び、この章の図では、1 本のチャネルの信号を中心から ±1 MHz の幅で描く（3 節で見るいちばん基本の方式では、信号の主な部分はこの幅に収まる）。

BLE の仕様書は、この 40 本に、周波数の順とは別の番号を付けて使う。これをチャネルの番号（チャネルインデックス）という。以下、BLE のチャネルの番号といえば、この番号を指す。番号は、使い道で 2 つに分かれる。

  • アドバタイズチャネル: 番号 37・38・39 の 3 本（2402・2426・2480 MHz）。接続する前の機器が、自分の存在を知らせるパケットを送り（アドバタイズ。17 章）、相手がそれを受け取って見つけるのに使う。
  • データチャネル: 番号 0〜36 の 37 本。接続した 2 台が、データをやり取りするのに使う（6 節）。5.0 で加わった拡張アドバタイズ（17 章 6 節）では、アドバタイズの続きのパケットもこれらのチャネルで送る。

データチャネルの番号は、アドバタイズチャネルを除いた 37 本に、周波数の低い順に付ける。

図のように、2402 MHz（k = 0）が 37 番なので、2404 MHz（k = 1）が 0 番になり、0〜10 番は k = i + 1、つまり 2404 + 2i MHz である（i はチャネルの番号）。2426 MHz（k = 12）の 38 番を飛ばすので、その上の 2428 MHz が 11 番になり、11〜36 番は k が 1 つ多い k = i + 2、つまり 2406 + 2i MHz である。C で書くと次のようになる。

/* チャネルの番号 idx（0〜39）の中心の周波数 [MHz] を返す。範囲外なら 0 */
static unsigned ble_chan_mhz(unsigned idx)
{
    if (idx == 37) return 2402;            /* アドバタイズチャネル */
    if (idx == 38) return 2426;
    if (idx == 39) return 2480;
    if (idx <= 10) return 2404 + 2 * idx;  /* データチャネル 0〜10: k = idx + 1 */
    if (idx <= 36) return 2406 + 2 * idx;  /* データチャネル 11〜36: k = idx + 2 */
    return 0;
}

この関数は、40 本の番号がすべて違う周波数（2402 + 2k MHz の k = 0〜39 を 1 回ずつ）になることを、gcc でコンパイルしたテストで確かめてある。

Wi-Fi のチャネルとの重なり

アドバタイズチャネルの 3 本は、帯の両端と、下から 3 分の 1 ほどの所に離れて置かれている。これを、09 章 1 節で見た Wi-Fi のチャネル 1・6・11（重ならない組としてよく使われる）の信号と重ねる。

図の色分けを、計算で確かめる。

方針: 09 章 1 節の図と同じく、Wi-Fi の信号を中心から ±10 MHz（20 MHz の幅）、BLE の信号を中心から ±1 MHz とみなす。BLE のチャネルの中心 \(f\) と Wi-Fi のチャネルの中心 \(f_\mathrm{c}\) の差を \(d = f - f_\mathrm{c}\) とし、BLE の信号の 2 MHz の幅が、Wi-Fi の信号の範囲に全部入るか（重なる）、一部だけ入るか（端にかかる）、まったく入らないか（重ならない）で分ける。

導出: BLE の信号の範囲は \([f - 1,\ f + 1]\)、Wi-Fi の信号の範囲は \([f_\mathrm{c} - 10,\ f_\mathrm{c} + 10]\) である。全部入るのは \(f - 1 \ge f_\mathrm{c} - 10\) かつ \(f + 1 \le f_\mathrm{c} + 10\)、つまり \(|d| \le 9\) のときである。まったく入らないのは \(f + 1 \le f_\mathrm{c} - 10\) か \(f - 1 \ge f_\mathrm{c} + 10\)、つまり \(|d| \ge 11\) のときで、その間の \(9 < |d| < 11\) が端にかかる場合である。BLE の中心は 2402 + 2k なので偶数の MHz、Wi-Fi のチャネル 1・6・11 の中心は 2412・2437・2462 MHz である。

  • チャネル 1（2412 MHz）: \(d\) は偶数である。\(|d| \le 8\) の 2404〜2420 MHz（データチャネル 0〜8 番の 9 本）が重なり、\(|d| = 10\) の 2402 MHz（37 番）と 2422 MHz（9 番）が端にかかる。
  • チャネル 6（2437 MHz）: \(d\) は奇数なので、\(|d| = 10\) にはならない。\(|d| \le 9\) の 2428〜2446 MHz（11〜20 番の 10 本）が重なる。\(|d| = 11\) の 2426 MHz（38 番）と 2448 MHz（21 番）は、範囲の端どうしが接するだけで入らない。
  • チャネル 11（2462 MHz）: \(d\) は偶数で、2454〜2470 MHz（24〜32 番の 9 本）が重なり、2452 MHz（23 番）と 2472 MHz（33 番）が端にかかる。

合わせて、37 本のデータチャネルのうち 28 本が重なり、3 本（9・23・33 番）が端にかかり、重ならないのは 10・21・22・34・35・36 番の 6 本である。アドバタイズチャネルは、37 番がチャネル 1 の端にかかるだけで、38 番と 39 番はどれにも入らない ∎

3 本のアドバタイズチャネルは、よく使われる Wi-Fi のチャネル 1・6・11 の信号をよけた位置にある。Wi-Fi が混んでいる場所でも、機器が互いを見つけられるようにするための配置と説明されることが多い。一方、データチャネルの多くは Wi-Fi の信号に重なるので、接続した後の 2 台は、重なるチャネルを避ける仕組みを使う（6 節）。なお、チャネル 13 まで使える国で、Wi-Fi の AP がチャネル 13（2472 MHz）を選ぶと、39 番（2480 MHz）はその信号に入る。実際の Wi-Fi の信号の裾は ±10 MHz より広く（09 章 1 節）、BLE の信号の幅も送り方（3 節）によって違うので、この数え方は目安である。

下の図で、近くの Wi-Fi の AP のチャネルと信号の幅を選ぶと、BLE のどのチャネルが重なるかと、重ならずに残るデータチャネルの数が表示される。

3. 変調と PHY

電波は、決まった周波数で振動する波である。BLE の機器は、使うチャネルの中心の周波数の波を送り、送りたいビットに合わせて、その波の性質を変える。ビットに合わせて波の性質（強さ・周波数・位相）を変えることを変調という。受け手は、受け取った波の変化を読んで、ビットに戻す。ビットを電波にして送り、電波からビットを取り出す仕事を、BLE の仕様書は物理層という層として決めている（07 章 1 節の 4 つの層の分け方では、リンク層に含めた仕事である）。

GFSK — 周波数を少し上げ下げする

BLE の変調は GFSK（Gaussian Frequency Shift Keying）である。FSK は、ビットが 1 の間は中心より少し高い周波数の波を、0 の間は少し低い周波数の波を送る変調である。ビットが変わる所で周波数を急に切り替えると、信号が使う周波数の幅が広がり、隣のチャネルにはみ出す。そこで GFSK では、ガウス形（正規分布の形）のフィルタで周波数の変化をなめらかにしてから送る。G はこのフィルタの名前から来ている。

受け手は、決まった時間の区切りごとに、周波数が中心より高いか低いかを判定して、1 か 0 かを決める。この区切りの 1 つ、つまり送り手が 1 つの値を表す最小の単位をシンボルという。1 秒あたりのシンボルの数をシンボルの速さといい、Msym/s（100 万シンボル毎秒）で表す。02 章 2 節で、1 秒あたりに送る信号の区切りの数をボーレートと呼んだのと同じものである。GFSK の 1 シンボルは、高いか低いかの 2 通りなので、1 ビットを運ぶ。

周波数をどれだけずらすかは、高いときと低いときの周波数の差をシンボルの速さで割った値で決まる。この値を変調指数といい、Core Specification は 0.45〜0.55 と決めている。0.5 なら、1 Msym/s では周波数の差が 0.5 MHz、つまり中心から ±250 kHz である。中心の 2440 MHz などに比べれば、ごくわずかなずれである。

3 つの PHY

物理層の方式（シンボルの速さと、ビットをシンボルにする方法の組）を、BLE の仕様書は PHY と呼ぶ（07 章 2 節で Ethernet の PHY と呼んだのは物理層の回路の部品で、ここでは同じ略語を方式の名前に使っている）。BLE の PHY は 3 つある。

  • LE 1M: 1 Msym/s で、1 シンボルが 1 ビット。ビットレートは 1 Mbps で、ビット時間（02 章 2 節）は 1 µs、1 バイトは 8 µs で送る。4.0 からあり、すべての BLE の機器が対応している。
  • LE 2M: 2 Msym/s で、1 シンボルが 1 ビット。2 Mbps で、ビット時間は 0.5 µs。5.0 で加わった（任意）。周波数のずれは LE 1M の 2 倍の ±500 kHz（変調指数 0.5 のとき）で、信号の幅も広い。
  • LE Coded: シンボルの速さは 1 Msym/s のままで、誤り訂正の符号（暗号と誤り訂正シリーズ 06 章）を使い、1 ビットを S 個のシンボルに広げて送る。まず畳み込み符号という誤り訂正の符号で 1 ビットを 2 シンボルにし（S = 2）、S = 8 では、さらにその 1 つずつを決まった 4 シンボルの並びに置き換える。S = 2 で 500 kbps（ビット時間 2 µs）、S = 8 で 125 kbps（ビット時間 8 µs）である。受け手は、いくつかのシンボルを読み誤っても、符号の性質から元のビットを推し量れる。5.0 で加わった（任意）。パケットの先頭の部分は、S = 2 を選んでも S = 8 で送る（19 章）。

どの BLE の機器も LE 1M には対応しているので、アドバタイズ（17 章）と接続の始まりは LE 1M で行うのが基本である。接続した後に、両方が対応していれば LE 2M や LE Coded に切り替える手順もある（5.0 から）。LE Coded でアドバタイズする方法もある（17 章 6 節）。

ビット時間と届く距離

LE Coded は、同じデータを送るのに LE 1M の 2〜8 倍の時間をかける。その代わりに何が得られるのかを、1 ビットの間に受け取るエネルギーで比べる。

方針: 受け手が 1 ビットを正しく判定できるかは、そのビットの間に受け取る信号のエネルギーで決まり、同じ確かさで判定するのに要るエネルギーは PHY によらず同じとする（受け手の雑音は同じ性質のものとし、誤り訂正の符号の効果は除く）。この仮定で、要る受信電力を PHY ごとに比べる。次に、電波が距離とともに弱くなる割合から、届く距離（01 章 3 節の通信距離）を比べる。

導出: 受信電力を \(P\)、ビット時間を \(T_\mathrm{b}\) とすると、1 ビットの間に受け取るエネルギーは \(E_\mathrm{b} = P T_\mathrm{b}\) である（電力 × 時間 = エネルギー）。同じ確かさで判定するのに要るエネルギーを \(E_0\) とすると、\(P T_\mathrm{b} \ge E_0\) から、要る受信電力の最小の値は

\[ P_\mathrm{min} = \frac{E_0}{T_\mathrm{b}} \]

で、ビット時間に反比例する。LE 1M（1 µs）と比べると、LE 2M（0.5 µs）は 2 倍の受信電力が要り、S = 2（2 µs）は 1/2、S = 8（8 µs）は 1/8 の受信電力で済む。電力の比 \(r\) を \(10 \log_{10} r\) で表した値を dB（デシベル）という（06 章 2 節の dBm は、1 mW との比をこの目盛で表したもの）。\(10 \log_{10} 2 \approx 3.0\)、\(10 \log_{10} 8 \approx 9.0\) なので、それぞれ +3 dB、−3 dB、−9 dB である。

受信電力は、送り手からの距離 \(d\) が延びると弱くなる。何もない空間では \(d\) の 2 乗に反比例し、建物の中では壁や床でさらに弱まるので、\(n\) を 3 前後とおいた \(d^{\,n}\) に反比例するとして近似することが多い。そこで受信電力を \(P = K / d^{\,n}\)（\(K\) は送信の電力やアンテナで決まる定数）とおく。届く距離 \(d_\mathrm{max}\) は、受信電力がちょうど \(P_\mathrm{min}\) になる距離なので、\(K / d_\mathrm{max}^{\,n} = E_0 / T_\mathrm{b}\) である。両辺に \(d_\mathrm{max}^{\,n} T_\mathrm{b} / E_0\) を掛けると \(d_\mathrm{max}^{\,n} = K T_\mathrm{b} / E_0\)、両辺を \(1/n\) 乗すると

\[ d_\mathrm{max} = \left( \frac{K T_\mathrm{b}}{E_0} \right)^{1/n} \]

となる。PHY によって変わるのは \(T_\mathrm{b}\) だけなので、届く距離は \(T_\mathrm{b}^{\,1/n}\) に比例する。LE 1M を 1 とすると、\(n = 2\) では LE 2M が \(0.5^{1/2} \approx 0.71\) 倍、S = 2 が \(2^{1/2} \approx 1.41\) 倍、S = 8 が \(8^{1/2} \approx 2.83\) 倍、\(n = 3\) ではそれぞれ 0.79 倍、1.26 倍、2.00 倍である ∎

1 ビットに 8 倍の時間をかけると、受け手は、8 倍弱い電波からでも同じだけのエネルギーを集められる。LE Coded では、これに誤り訂正の符号の効果が加わる。製品のデータシートに載っている PHY ごとの受信感度（決まった誤りの率以下で受け取れる、最も弱い受信電力）の差も、この見積もりに近い数 dB〜十 dB 程度であることが多い（代表値）。5.0 を発表したとき、Bluetooth SIG は、LE Coded で届く距離が 4 倍になると説明していた（条件がよい場合の目安）。その代わり、同じデータを送る時間は 8 倍になり、送受信の電流が流れる時間も延びる（19 章）。01 章 3 節で見た「遠くまで届く方式ほど遅い」という交換条件を、BLE の中で選べるようにしたものである。

下の図で PHY と送るバイト、電波の弱まり方 \(n\) を選ぶと、周波数の動き、8 ビットを送る時間、要る受信電力の差と届く距離の比が表示される。

4. 役割

BLE の 2 台がつながるまでと、つながった後に、それぞれの機器が何をしているかを見る。Core Specification は、コントローラ（06 章 1 節）の送受信の動きを、次の 5 つの状態を持つ状態機械（05 章 1 節）として決めている。

  • スタンバイ（Standby）: 送りも受けもしない。電源を入れた直後や、ほかの状態をやめた後。
  • アドバタイズ（Advertising）: アドバタイズチャネルで、自分の存在を知らせるパケットを送る（アドバタイズ。17 章）。送った直後に、相手からの求めを受け取ることもある。
  • スキャン（Scanning）: アドバタイズチャネルで受信して、アドバタイズのパケットを集める（09 章 2 節の Wi-Fi と同じく、スキャンと呼ぶ。17 章 4 節）。
  • イニシエート（Initiating）: つなぎたい相手のアドバタイズを待ち、受け取ったら、すぐ後に接続を求めるパケット（CONNECT_IND。17 章 2 節）を送る。
  • 接続（Connection）: 相手と接続し、データチャネルでやり取りしている（6 節、18 章）。

アドバタイズの状態にある機器をアドバタイザ、スキャンの状態にある機器をスキャナ、イニシエートの状態にある機器をイニシエータという。イニシエータが接続を求めるパケットを送ると、2 台はそろって接続の状態に入る。このとき、イニシエータだった側をセントラル、アドバタイザだった側をペリフェラルという（古い版の仕様書では master と slave と呼んでいた）。セントラルは、接続のやり取りをする時刻の決まりと、使うチャネルの決まり（6 節）を決め、接続を求めるパケットに入れて知らせる（18 章 1 節）。接続している間は、やり取りのたびにセントラルが先に送り、ペリフェラルが答える。

スマートフォンと温湿度センサなら、ふつうはセンサがアドバタイザ、スマートフォンがスキャナになり、センサを見つけたスマートフォンがイニシエータとして接続を求める。接続した後は、スマートフォンがセントラル、センサがペリフェラルである。セントラルは、相手ごとに時刻をずらしてやり取りできるので、スマートフォンやゲートウェイは、同時に何台もの機器と接続できる。1 台の機器が、接続したまま、別の相手のためにアドバタイズを続けるように、同時に複数の状態を持つこともある（対応は製品による）。

接続しない使い方もある。アドバタイズのパケットに測定値などのデータを入れて送り続け、誰とも接続しない機器をブロードキャスタ、アドバタイズを受け取るだけで接続しない機器をオブザーバという。たとえば、温度を自分のアドバタイズに入れて送るセンサ（ブロードキャスタ）と、近くの多くのセンサの値を集めるゲートウェイ（オブザーバ）である。接続しないので、オブザーバは、コントローラが同時に保てる接続の数に縛られずに、多くのブロードキャスタの値を受け取れる。その代わり、受け取ったことを知らせる確認応答（05 章 4 節）は無く、ブロードキャスタは届いたかどうかを知らない。

ブロードキャスタ・オブザーバ・セントラル・ペリフェラルの 4 つは、機器が見つけ合ってつながる手順を決める層（5 節の GAP）が決める役割の名前で、アドバタイザ・スキャナ・イニシエータは、コントローラの状態から見た名前である。このほかに、値を持って読み書きされる側（サーバ）と、読み書きしに行く側（クライアント）という区別もある（18 章 2 節）。これはセントラルとペリフェラルとは別に決まる。センサ（ペリフェラル）が測定値を持ち、スマートフォン（セントラル）が読みに行く形が多いが、逆の組み合わせもありうる。

5. プロトコルスタックの層

BLE のスタックの層と、それぞれの役割を図に示す。06 章 1 節で見たとおり、下の 2 つの層をまとめた部分がコントローラ、その上の層（L2CAP から GAP まで。それぞれ図の下で説明する）が BLE のホストで、両者の間は HCI（06 章 5 節）で結ばれる。1 つの SoC で全部を動かす場合も、ソフトウェアの中に同じ境目がある。

  • 物理層（3 節）: ビットを 2.4 GHz の電波にして送り、電波からビットを取り出す。PHY は LE 1M・LE 2M・LE Coded。
  • リンク層: 物理層のすぐ上にあり、4 節の 5 つの状態を受け持つ。どのパケットを、いつ、どのチャネルで送るかを決め（6 節、17 章）、受け取ったパケットに確認応答を返し、届かなかったものを送り直す。接続中の確認応答は、05 章 4 節のストップアンドウェイトと同じく、1 ビットのシーケンス番号で行う。パケットの暗号化もこの層が行う（鍵は、この一覧の後のほうで説明する SMP が作る。20 章）。07 章 1 節のリンク層と同じく、隣の機器まで届ける層で、仕様書での名前は Link Layer である。リンク層が 1 回に送るビットの列のまとまりを、仕様書にならってパケットと呼ぶ（07 章 3 節の IP のパケットとは別物）。LE 1M と LE 2M のパケットは、先頭のプリアンブル（07 章 2 節）、どの接続のパケットかを表す 4 バイトのアクセスアドレス（17 章 2 節）、ヘッダとデータ、最後の 3 バイトの CRC（03 章 5 節）からなる（LE Coded では、符号のための欄が加わる）。
  • L2CAP（Logical Link Control and Adaptation Protocol）: リンク層が運んだデータを、上のどのプロトコル（ATT・SMP など）に渡すかを番号で振り分ける（07 章 4 節のポート番号と同じ考え方。番号は 18 章 2 節）。リンク層の 1 つのパケットに入らない長さのデータは、分けて送り、受け手で組み立て直す。
  • ATT（Attribute Protocol）: 相手の機器が持つ値（仕様書では属性と呼ぶ。18 章 2 節）を、値ごとに付いた番号を指定して、読む・書く・変化を知らせる、といったやり取りの形を決める。
  • GATT（Generic Attribute Profile）: ATT で扱う値を、機能のまとまり（サービス）と 1 つ 1 つの値（キャラクタリスティック）の階層に整理する決まりと、それを探して読み書きする手順を決める（18 章）。
  • SMP（Security Manager Protocol）: 2 台が暗号化の鍵を作って交換する手続き（ペアリング）を行う（20 章）。
  • GAP（Generic Access Profile）: 機器がどう見つけ合い、どうつながるか（アドバタイズとスキャンの使い方、接続の手順、機器の名前とアドレスの扱い）と、4 節の 4 つの役割を決める（17 章）。
  • アプリケーション: 機器ごとの値（温度など）を GATT の決まりで表し、読み書きに応える（18 章 6 節）。

GATT と GAP の名前の Profile（プロファイル）は、下の層のプロトコルを、ある目的のためにどう使うかの決まりを指す。

接続したスマートフォンが、センサの温度を読む場合を例に、データが層をどう通るかを図に示す。各層は、相手の機器の同じ層とやり取りするのに必要な情報をヘッダとして付けて、下の層に渡す（07 章 5 節のカプセル化）。

アドバタイズのパケットは、L2CAP より上を通らない。アドバタイズに入れるデータ（17 章 3 節）は、ホストが HCI の命令でコントローラに渡し、リンク層がそのまま送る。接続した後のデータだけが、L2CAP を通って ATT や SMP に振り分けられる。各層が足すバイト数は 19 章で数える。完成した機器のアドバタイズや GATT の中身を外から調べる方法は、組み込みテストシリーズ 09 章 2 節 にある。

6. 周波数ホッピング

2 節で見たとおり、データチャネルの多くは Wi-Fi の信号と重なる。BLE のリンク層は、Wi-Fi のキャリアセンス（09 章 1 節）のように、送る前にチャネルが空くのを待つことはしない。接続した 2 台が 1 本のチャネルだけを使い続けると、そのチャネルに Wi-Fi の信号が重なっている間、パケットは壊れ続ける。そこで BLE は、使うチャネルを規則に従って次々に替える。2 台が同じ規則で、送受信するチャネルを替えていくことを周波数ホッピングという。

接続している 2 台は、決まった間隔ごとに短い時間だけ起きて、パケットをやり取りする。この 1 回のやり取りを接続イベントという（18 章 1 節）。1 つの接続イベントの間は 1 本のデータチャネルを使い、次の接続イベントでは別のチャネルに移る。パケットが壊れても、リンク層が確認応答と再送（05 章 4 節）で送り直すので、その送り直しが次の接続イベントになれば、別のチャネルで届く。各接続イベントのチャネルを決める規則をチャネル選択アルゴリズムという。4.0 からあるものを #1、5.0 で加わったものを #2 と呼ぶ。

チャネル選択アルゴリズム #1

#1 は、前の接続イベントのチャネルの番号に、決まった数を足していく。足す数をホップ量といい、セントラルが 5〜16 の中から乱数で選び、接続を求めるパケットに入れて知らせる（17 章 2 節）。ホップ量を \(h\) とし、最初の接続イベントの前の値を \(u = 0\) として、接続イベントごとに

\[ u \leftarrow (u + h) \bmod 37 \]

を計算する（mod 37 は 37 で割った余り）。すべてのデータチャネルを使う場合は、この \(u\) がそのままチャネルの番号になる。\(h = 7\) なら 7、14、21、28、35、5（= 42 − 37）、12、… と進む。

図の列では、1〜37 回目の接続イベントに 37 本のデータチャネルが 1 回ずつ現れている。これが、どのホップ量でも成り立つことを確かめる。

方針: \(k\) 回目の接続イベントの番号が \(kh \bmod 37\) であることを確かめ、1〜37 回目に同じ番号が 2 回出たと仮定して、矛盾を導く。

導出: 最初の前の値は 0 で、毎回 \(h\) を足して 37 で割った余りをとる。余りをとってから足しても、足してから余りをとっても、37 で割った余りは同じなので、\(k\) 回目の番号は \(kh\) を 37 で割った余りである。\(a\) 回目と \(b\) 回目（\(1 \le a < b \le 37\)）の番号が同じだとすると、\(bh - ah = (b - a)h\) が 37 で割り切れる。37 は素数で、\(h\)（5〜16）は 37 で割り切れないので、37 が \((b - a)h\) を割り切るには、37 が \(b - a\) を割り切らなければならない。しかし \(0 < b - a < 37\) なので、それは起こらない。したがって、1〜37 回目の番号はすべて違い、37 本を 1 回ずつ使う。38 回目の番号は \(38h \bmod 37 = h\) なので、列は 37 回ごとに同じものを繰り返す ∎

続く 2 回の接続イベントの番号は、\(h\) だけ増えるか（37 以上にならないとき）、\(37 - h\) だけ減る（37 以上になって 37 を引いたとき）。\(h\) は 16 以下なので \(37 - h\) は 21 以上で、どちらの場合も番号は \(h\) 以上離れる。番号が 1 違うと中心の周波数は 2 MHz 以上違う（2 節）ので、使わないチャネルが無ければ、続く 2 回のチャネルの中心は少なくとも \(2h\) MHz（\(h = 5\) で 10 MHz）離れる（Python でも 5〜16 のすべてについて確かめた）。

チャネルマップと割り当て直し

Wi-Fi の信号に重なるチャネルを使わないように、セントラルは、37 本のデータチャネルのうちどれを使うかを決める。37 本のそれぞれについて、使う（1）か使わない（0）かを並べた 37 ビットの値をチャネルマップという。セントラルは、接続を求めるパケットにチャネルマップを入れて知らせ、接続の途中で替えることもできる（下の AFH）。使うチャネルの数を \(N\) とする。\(N\) は 2 以上にすることになっている（たとえば NimBLE のコントローラは、使うチャネルが 2 本より少なくなる指定を受け付けない）。

#1 で計算した \(u\) が使わないチャネルだったときは、使うチャネルの 1 本に割り当て直す。使うチャネルを番号の小さい順に 0 番目、1 番目、…、\(N - 1\) 番目と並べ、\(u \bmod N\) 番目のチャネルを使う。次の接続イベントの計算には、割り当て直す前の \(u\) を使う。2 節で Wi-Fi のチャネル 1・6・11 に重なった 28 本を使わず、残りの 9 本（9・10・21・22・23・33・34・35・36 番）を使う場合を、\(h = 7\) で計算する（Core Specification が #2 の計算の例に使っているチャネルマップも、この 9 本である）。

1 回目は \(u = 7\) で、7 番は使わないので、\(7 \bmod 9 = 7\) 番目の 35 番を使う。2 回目は \(u = 14\) で、\(14 \bmod 9 = 5\) 番目の 33 番を使う。3 回目の \(u = 21\) は使うチャネルなので、そのまま 21 番を使う。こうして、Wi-Fi に重なるチャネルを使わずにホッピングを続けられる。C で書くと次のようになる。

struct csa1 {
    uint8_t hop;          /* ホップ量（5〜16）。接続を求めるパケットで決まる */
    uint8_t last;         /* 前の接続イベントの、割り当て直す前の番号（最初は 0） */
    uint8_t map[5];       /* チャネルマップ: 番号 n のビット（map[n / 8] の n % 8）が 1 なら使う */
};

static int chan_used(const uint8_t map[5], unsigned n)
{
    return (map[n / 8] >> (n % 8)) & 1u;
}

/* 次の接続イベントのチャネルの番号を返す。使うチャネルが 1 本も無ければ 0xFF */
static uint8_t csa1_next(struct csa1 *s)
{
    uint8_t un = (uint8_t)((s->last + s->hop) % 37);   /* 割り当て直す前の番号 u */
    s->last = un;                                      /* 次の計算はこの値から */
    if (chan_used(s->map, un))
        return un;
    unsigned n_used = 0;                               /* 使うチャネルの数 N */
    for (unsigned n = 0; n < 37; n++)
        n_used += chan_used(s->map, n);
    if (n_used == 0)
        return 0xFF;
    unsigned want = un % n_used;                       /* 使うチャネルの、小さいほうから何番目か */
    for (unsigned n = 0; n < 37; n++)
        if (chan_used(s->map, n) && want-- == 0)
            return (uint8_t)n;
    return 0xFF;                                       /* ここには来ない */
}

このコードは、すべてのホップ量で 37 回に 37 本を 1 回ずつ使うこと、上の 9 本のチャネルマップで図と同じ列になること、乱数で作った 3000 通りのホップ量とチャネルマップで、Python で計算した列と一致することを確かめてある（gcc、AddressSanitizer 付き）。

適応型周波数ホッピング（AFH）

チャネルマップを、接続している間の電波の状態に合わせて替えていくことを、適応型周波数ホッピング（AFH、Adaptive Frequency Hopping）という。セントラルは、パケットが壊れやすいチャネルを調べ（チャネルごとに受け取れなかったパケットの割合を数える、ホストから HCI でチャネルの良し悪しを教えてもらう、など。調べ方は製品によって違う）、新しいチャネルマップと、それを使い始める接続イベントを、ペリフェラルに送る。2 台は、その接続イベントから新しいチャネルマップで計算する。

Wi-Fi のチャネル 1・6・11 がすべて使われている場所で、全部のチャネルを使う #1 なら、37 回の接続イベントのうち 28 回は、Wi-Fi の信号に重なるチャネルで行われる（端にかかるものを含めると 31 回）。重なる 28 本を外したチャネルマップにすれば、その回数は 0 になる。Wi-Fi の AP が止まったりチャネルを替えたりしたら、外したチャネルを戻すこともできる。

#1 の割り当て直しは単純なので、使うチャネルの数によっては、同じチャネルが何回も続く。続く 2 回の、割り当て直す前の番号が \(u\) と \(u + h\)（37 以上にならない場合）で、どちらも使わないチャネルなら、割り当て直した位置は \(u \bmod N\) 番目と \((u + h) \bmod N\) 番目である。\(h\) が \(N\) で割り切れるとき、この 2 つは等しいので、同じチャネルが続く。上の 9 本のチャネルマップで \(h = 9\) なら、続く 2 回の接続イベントのおよそ 6 割が同じチャネルになる（下のデモで確かめられる）。同じチャネルが続くと、そのチャネルが妨げられたとき、送り直しも同じチャネルで失敗しやすい。

#2 は、接続ごとに決まる 16 ビットの値（アクセスアドレスの上位と下位の 16 ビットの XOR）と、接続イベントの通し番号から、16 ビットの擬似乱数を作り（作り方は Core Specification にある）、その乱数を 37 で割った余りをチャネルの番号にする。使わないチャネルに当たったときは、使うチャネルのうち \(\lfloor N \times \text{乱数} / 65536 \rfloor\) 番目（\(\lfloor\ \rfloor\) は小数点以下の切り捨て）に割り当て直す。一定の歩幅で進まないので、#1 のような規則的な重なりは起きず、同じチャネルが続くのは偶然の分（平均でおよそ \(1/N\)）だけになる。2 台がどちらも #2 に対応していれば #2 を使う（アドバタイズと、接続を求めるパケットのヘッダの 1 ビットで知らせる。17 章 2 節）。

下の図で、ホップ量・チャネルマップ・アルゴリズムを変えると、接続イベントごとのチャネルの列と、チャネルごとに使った回数が表示される。チャネルマップの升目を押すと、そのチャネルを使うか使わないかが切り替わる。

7. まとめ

項目内容
Classic と BLE同じ 2.4 GHz 帯を使う別の方式で、互いに通信できない。BLE は少ないデータを短い時間で送り、その間を眠ることで電力を小さくする。4.0 で加わり、4.2・5.0 などで機能が足された（多くは任意）
ISM 帯とチャネル2400〜2483.5 MHz。BLE は 2 MHz おきの 40 本（中心は 2402 + 2k MHz）
チャネルの番号アドバタイズチャネル 37・38・39（2402・2426・2480 MHz）、データチャネル 0〜36（0〜10 番は 2404 + 2i MHz、11〜36 番は 2406 + 2i MHz）
Wi-Fi との重なりチャネル 1・6・11 の 20 MHz の信号に、データチャネルの 28 本が重なり、3 本が端にかかる。アドバタイズチャネルは 37 番が端にかかるだけ
変調・GFSK・シンボルビットが 1 なら少し高い、0 なら少し低い周波数にする（LE 1M で ±250 kHz 程度）。周波数の変化はガウス形のフィルタでなめらかにする。1 シンボルが 1 ビット
PHYLE 1M（1 ビット 1 µs）、LE 2M（0.5 µs）、LE Coded（S = 2 で 2 µs、S = 8 で 8 µs）。要る受信電力はビット時間に反比例し、届く距離は \(T_\mathrm{b}^{\,1/n}\) に比例する（符号の効果を除く）
役割接続前はアドバタイザ・スキャナ・イニシエータ。接続後は、イニシエータだった側がセントラル、アドバタイザだった側がペリフェラル。接続しないブロードキャスタとオブザーバ。GATT のサーバ・クライアントは別の軸
スタックの層コントローラ（物理層・リンク層）と BLE のホスト（L2CAP・ATT・GATT・SMP・GAP）を HCI が結ぶ。アドバタイズは L2CAP より上を通らない
周波数ホッピング接続イベントごとにデータチャネルを替える。#1 は \(u \leftarrow (u + h) \bmod 37\)（h = 5〜16）で、37 回で 37 本を 1 回ずつ使う
チャネルマップ・AFH使うデータチャネルを 37 ビットで表す。使わないチャネルに当たったら \(u \bmod N\) 番目の使うチャネルに割り当て直す。電波の状態に合わせてマップを替えるのが AFH。#2 は擬似乱数で選ぶ
