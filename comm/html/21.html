LPWA — LoRaWAN とセルラーで遠くへ少ない電力で

この章で扱う問い. 01 章 3 節では、遠くまで届く方式ほど遅いこと、LoRaWAN や NB-IoT がゆっくり送ることで遠くまで届かせていることを見た。この章では、数 km 先の機器から、電池で何年もかけて少しずつデータを集める方式を、19 章で BLE に使った「電波の上の時間」の数え方で調べる。

この章では次の 3 つの問いに答える。

  1. LoRa は、なぜ遅い代わりに遠くまで届くのか。1 回の送信は電波の上でどれだけの時間を占め、電波の規則のもとで 1 時間に何回送れるのか。
  2. LoRaWAN の機器は、眠っている間に生じたサーバからのデータを、いつ受け取るのか。同じフレームの再送や、盗聴して記録したフレームの送り直しを、どう見分けるのか。
  3. 携帯電話の網を使う LTE-M と NB-IoT は、網につながったまま深く眠ることを、どう実現しているのか。平均電流と、機器へ届くまでの遅れは、設定でどう変わるのか。どの方式を選べばよいのか。

答えの道具は、シンボル時間と空中時間の式、送信時間の割合の上限から送れる回数を求める計算、そして 01 章 5 節の平均電流の式である。

1. LPWA とは

01 章 3 節の表で、届く距離が数 km を超える無線の方式は、LoRaWAN・LTE-M・NB-IoT の 3 つだった。数 km 以上の距離を、電池で何年も動く機器で、少しずつのデータを送るための無線の方式を、まとめて LPWA（Low Power Wide Area）という。水道やガスのメータ、農地や河川のセンサ、荷物の位置の追跡のように、機器が広い範囲に散らばり、電源の配線が難しく、送るデータは 1 日に数十〜数千バイト程度、という用途に向けた方式である。

LPWA は、使う電波の帯域で 2 つに分かれる。

  • 免許不要の帯域: 国から免許を受けずに使える周波数の帯域。認証を受けた機器（06 章 1 節）を、送信の電力や送信の時間の規則（4 節）の範囲で使えば、誰でも使える。日本の 920 MHz 帯、欧州の 868 MHz 帯がこれにあたる（09 章の Wi-Fi や 16 章の BLE が使う 2.4 GHz 帯も、同じ種類の帯域である）。LoRaWAN はこの帯域を使い、利用者が自分でゲートウェイを置いて網を作ることもできる。その代わり、同じ帯域をほかの人の機器も使う。
  • 免許の帯域: 国から免許を受けた通信事業者だけが使える帯域。LTE-M と NB-IoT は、携帯電話の事業者の帯域と基地局を使う。機器には SIM（契約者を示すカード、またはそれに当たる部品）と回線の契約が要る。

この章では、免許不要の帯域を使う LoRaWAN（LoRa という変調（2 節）の上で動くプロトコル。5 節）と、携帯電話の規格 LTE に、少ないデータを少ない電力で送るために加えられた LTE-M と NB-IoT（6 節）を扱う（ほかに Sigfox などの方式もあるが、この章では扱わない）。

主な違いを、代表値で比べる。値は条件・製品・網の設定で大きく変わるので、桁の目安として読んでほしい。

2. LoRa の変調 — チャープと拡散率

LoRa は、Semtech 社が開発した、無線の変調（16 章 3 節）の方式である。LoRaWAN（5 節）は LoRa の上で動くプロトコルである。LoRaWAN を使わずに、LoRa の電波の上で、自分で決めたプロトコルを使って機器どうしが通信することもできる。

チャープ — 周波数が上がり続ける信号

周波数が時間とともに連続的に変わる信号をチャープという。LoRa のシンボル（16 章 3 節）は、周波数が一定の速さで上がっていくチャープで、周波数は決まった幅の中を動く。この幅は信号の帯域幅（09 章 1 節）で、LoRa では BW と書き、125 kHz・250 kHz・500 kHz から選ぶ（LoRaWAN では 125 kHz が多い）。

1 シンボルで運ぶビットの数を拡散率（SF、spreading factor）といい、LoRaWAN では 7〜12 を使う（SF7〜SF12 と書く）。SF ビットで表せる値は、0 から \(2^{\mathrm{SF}} - 1\) までの \(2^{\mathrm{SF}}\) 通りである。送る値は、チャープの始まりの周波数で表す。値 0 のシンボルは、幅の下端から始まって上端まで上がる。値 k のシンボルは、下端より \(k \times \mathrm{BW}/2^{\mathrm{SF}}\) だけ高い周波数から始まり、上端に達すると下端に戻って同じ速さで上がり続け、シンボルの終わりに始まりの周波数に戻る。

チャープを使って、データの速さに比べてずっと広い帯域に信号を広げて送る方式を、CSS（Chirp Spread Spectrum、チャープによるスペクトル拡散）という。後で求めるように、SF7 のビットレート（5469 bps）は、帯域幅 125 kHz の 1/23 ほどにすぎない。広げて送った信号を、受け手は 1 つの周波数に集め直す。

受け手はチャープを一定の周波数に直す

受け手は、受け取った信号の周波数から、自分で作った値 0 のチャープの周波数を、時刻ごとに引く（実際の回路では、2 つの信号を掛け合わせて、周波数の差の成分を取り出す。チャープどうしを掛け合わせると周波数の差の波が残ることは、レーダーシリーズ 08 章 で導いている）。値 k のシンボルの周波数は、折り返すまでは値 0 のチャープより常に \(k \,\mathrm{BW}/2^{\mathrm{SF}}\) だけ高い。折り返した後は \(k \,\mathrm{BW}/2^{\mathrm{SF}} - \mathrm{BW}\) になるが、受け手は信号を 1 秒に BW 回の割合で読む（標本化する）ので、ちょうど BW だけ違う 2 つの周波数は、読んだ値の上では区別できず、同じ周波数に見える（DSP シリーズ 01 章 の標本化と同じ現象）。したがって、引き算の結果は、シンボルの全体を通して \(k \,\mathrm{BW}/2^{\mathrm{SF}}\) の一定の周波数になる。受け手は、その周波数を調べて k を知る（多くは、\(2^{\mathrm{SF}}\) 点の離散フーリエ変換で、最も強い周波数を探す）。

シンボル時間とビットレート

1 シンボルの長さをシンボル時間という。シンボル時間は、受け手が \(2^{\mathrm{SF}}\) 通りの値を見分けられる長さにする必要がある。

方針: 上の引き算の後、隣り合う値は、周波数が \(\mathrm{BW}/2^{\mathrm{SF}}\) だけ違う一定の波になる。周波数の違う 2 つの波を見分けるのに要る時間から、シンボル時間を求める。

導出: 周波数が \(\Delta f\) だけ違う 2 つの波を、時間 T の間見ると、その間に振動する回数が \(\Delta f \, T\) 回違う。この差が 1 回に満たないと、2 つの波は時間 T の中でほとんど同じ形をしていて、区別できない。したがって、見分けるには \(\Delta f \, T \ge 1\)、すなわち \(T \ge 1/\Delta f\) が要る。\(\Delta f = \mathrm{BW}/2^{\mathrm{SF}}\) を代入すると \(T \ge 2^{\mathrm{SF}}/\mathrm{BW}\) である。LoRa は、この下限そのものをシンボル時間にしている。

\[ T_\mathrm{sym} = \frac{2^{\mathrm{SF}}}{\mathrm{BW}} \]

∎

SF7・BW 125 kHz なら \(T_\mathrm{sym} = 128 / 125000 = 1.024\) ms である。SF を 1 上げると、値の数 \(2^{\mathrm{SF}}\) が 2 倍になり、シンボル時間も 2 倍になる。

LoRa は、送るビットに誤り訂正のためのビットを足してから、シンボルに載せる。データ 4 ビットごとに CR ビット（CR = 1〜4）を足して 4 + CR ビットにする。データの割合 \(4/(4 + \mathrm{CR})\) を符号化率といい、4/5・4/6・4/7・4/8 と書く（LoRaWAN では 4/5 を使う）。CR が大きいほど誤りに強いが、送るビットが増える。

方針: 1 秒あたりのシンボルの数に、1 シンボルのビット数と、データの割合を掛ける。

導出: 1 秒あたりのシンボルの数は \(1/T_\mathrm{sym} = \mathrm{BW}/2^{\mathrm{SF}}\) で、1 シンボルは SF ビットを運ぶ。そのうちデータは \(4/(4 + \mathrm{CR})\) なので、ビットレートは

\[ R_\mathrm{b} = \mathrm{SF} \times \frac{\mathrm{BW}}{2^{\mathrm{SF}}} \times \frac{4}{4 + \mathrm{CR}} \]

である ∎

BW 125 kHz、符号化率 4/5 の値を表に示す。LoRaWAN では、SF と BW の組にデータレートの番号（DR）を付けて呼ぶ。欧州（EU868）と日本を含むアジアの一部（AS923）の地域の設定では、DR0 が SF12・125 kHz、DR5 が SF7・125 kHz である（地域の設定は 5 節）。

信号の電力と雑音の電力の比を SN 比といい、dB で表す。LoRa の受信の回路のデータシートには、SF ごとに、受け取れる最も小さい SN 比が載っている。Semtech のデータシートの代表値は、SF7 の −7.5 dB から 2.5 dB ずつ下がり、SF12 で −20 dB である。差の 12.5 dB は、上の見積もりの 12.7 dB とほぼ一致する。SN 比が負の値、つまり雑音より弱い信号でも受け取れるのは、受け手が、\(2^{\mathrm{SF}}\) 通りに広げた 1 シンボル分の信号を、1 つの周波数に集めてから判定するからである。

同じ見積もりで BLE の LE 1M（ビット時間 1 µs）と比べると、SF7 のビット時間は 183 倍（22.6 dB）、SF12 は 3413 倍（35.3 dB）長い。LoRa は、要る受信電力を BLE より 20〜35 dB 小さくし、さらに BLE より大きな送信の電力（規則の範囲で 10 数 dBm の代表値）と低い周波数（壁などで弱まりにくい）を使うことで、数 km〜十数 km 届く（代表値。地形・建物・アンテナで大きく変わる）。その代わりに、16 章 3 節の LE Coded と同じく、同じデータを送る時間が長くなる。どれだけ長くなるかを、次の節で数える。

3. 空中時間を計算する

LoRa の無線の回路が 1 回に送るひとまとまり（この章では LoRa のパケットと呼ぶ）の空中時間（19 章 1 節）を求める。LoRa のパケットは、次の 4 つの部分からなる。

  • プリアンブル（07 章 2 節）: 値 0 のチャープを n 回（LoRaWAN では n = 8）送り、続けて、網を区別する同期の印の 2 シンボルと、周波数が下がるチャープ 2.25 シンボル分を送る。合わせて n + 4.25 シンボルである。周波数が下がるチャープは、データの始まりの印になる（07 章 2 節の SFD と同じ役割）。
  • 明示ヘッダ: ペイロードの長さ・符号化率・CRC の有無を表す 20 ビット。両者が前もってこれらを知っているときは省ける（LoRaWAN は省かない）。
  • ペイロード: PL バイト。LoRaWAN では、5 節のフレームがここに入る。
  • CRC: 16 ビット（03 章 5 節）。付けないこともできる。

シンボル時間が長いと、送り手と受け手の周波数や時計のわずかなずれの影響を受けやすくなる。そこで、シンボル時間が 16 ms を超える設定（BW 125 kHz の SF11 と SF12）では、1 シンボルで運ぶビットを SF − 2 に減らして誤りに強くする。この設定を低データレート最適化（LDRO、Low Data Rate Optimization）という。Semtech のデータシートは、シンボル時間が 16 ms を超えるときに LDRO を使うよう求めている。

方針: ヘッダ・ペイロード・CRC のビットの合計を数え、それを何シンボルで送るかを、誤り訂正の符号化をまとめて行う単位（ブロック）ごとに数える。プリアンブルのシンボル数を足し、シンボル時間を掛ける。

導出: 明示ヘッダを使うとき H = 1、CRC を付けるとき C = 1、LDRO を使うとき \(D_\mathrm{E}\) = 1（使わなければそれぞれ 0）とする。送るビットの合計は \(8\,\mathrm{PL} + 16\,C + 20\,H\) である。最初のブロックは必ず 8 シンボルで、誤りに強くするため、符号化率 4/8・1 シンボル SF − 2 ビットで送る。8 シンボルが運ぶ符号化後のビットは \(8(\mathrm{SF} - 2)\) で、そのうちデータは半分の \(4(\mathrm{SF} - 2)\) ビットである。残りのビットは

\[ 8\,\mathrm{PL} + 16\,C + 20\,H - 4(\mathrm{SF} - 2) = 8\,\mathrm{PL} - 4\,\mathrm{SF} + 8 + 16\,C + 20\,H \]

である。2 つ目からのブロックは 4 + CR シンボルで、1 シンボルが \(\mathrm{SF} - 2D_\mathrm{E}\) ビットを運ぶので、符号化後の \((4 + \mathrm{CR})(\mathrm{SF} - 2D_\mathrm{E})\) ビットのうち、データは \(4(\mathrm{SF} - 2D_\mathrm{E})\) ビットである。残りのビットを送るのに要るブロックの数は、残りを \(4(\mathrm{SF} - 2D_\mathrm{E})\) で割って切り上げた数（残りが 0 以下なら 0）である。したがって、プリアンブルの後のシンボル数は

\[ N_\mathrm{pay} = 8 + \max\left( \left\lceil \frac{8\,\mathrm{PL} - 4\,\mathrm{SF} + 8 + 16\,C + 20\,H}{4(\mathrm{SF} - 2D_\mathrm{E})} \right\rceil,\ 0 \right) (\mathrm{CR} + 4) \]

で、空中時間は

\[ T_\mathrm{air} = (n + 4.25 + N_\mathrm{pay})\, T_\mathrm{sym} \]

となる ∎

Semtech のデータシートの式は、ヘッダを省くとき 1 になる記号 \(I_\mathrm{H} = 1 - H\) を使って、分子を \(8\,\mathrm{PL} - 4\,\mathrm{SF} + 28 + 16\,C - 20\,I_\mathrm{H}\) と書いている。\(H = 1 - I_\mathrm{H}\) を代入すると、上の分子と同じになる。

例として、LoRaWAN の上りで 12 バイトのデータを送る場合を計算する。5 節で見るとおり、LoRaWAN のフレームはデータに 13 バイトを足すので、PL = 25 バイトである（BW 125 kHz、符号化率 4/5、n = 8、明示ヘッダと CRC あり）。

SF を 1 上げるごとに空中時間はほぼ 2 倍になり、SF12 は SF7 の 24 倍である。SF12 では、プリアンブルだけで 0.4 秒かかる。データを 1 バイト増やしても、ブロックの数が変わらなければ空中時間は変わらず、ブロックの境目を越えると 4 + CR シンボル分（SF7 で 5.1 ms、SF12 で 164 ms）増える。そのため、空中時間はペイロードの長さに対して階段の形になる。

機器のファームウェアは、送る前に空中時間を計算して、4 節の規則を守れるかを確かめる。整数だけで計算する関数を示す。

/* LoRa の 1 パケットの空中時間 [µs]（Semtech のデータシートの式）。
   sf: 7〜12、bw_hz: 125000・250000・500000、cr: 1〜4（4/5〜4/8）、pl: ペイロードのバイト数、
   n_pre: プリアンブルのシンボル数、hdr: 明示ヘッダなら 1、crc: CRC を付けるなら 1 */
uint32_t lora_toa_us(unsigned sf, uint32_t bw_hz, unsigned cr, unsigned pl,
                     unsigned n_pre, int hdr, int crc)
{
    int de = (1000u << sf) > 16u * bw_hz;           /* 2^sf / bw > 16 ms なら LDRO */
    int32_t bits = 8 * (int32_t)pl + (crc ? 16 : 0) + (hdr ? 20 : 0)
                   - 4 * ((int32_t)sf - 2);          /* 最初の 8 シンボルで運ぶ分を引く */
    int32_t per = 4 * ((int32_t)sf - 2 * de);        /* 1 ブロックで運ぶデータのビット */
    uint32_t nblk = bits > 0 ? (uint32_t)((bits + per - 1) / per) : 0;
    uint32_t sym4 = 4 * (n_pre + 8 + nblk * (cr + 4)) + 17;   /* シンボル数の 4 倍 */
    uint64_t num = ((uint64_t)sym4 << sf) * 1000000u; /* × 2^sf × 10^6 */
    uint64_t den = 4u * (uint64_t)bw_hz;
    return (uint32_t)((num + den - 1) / den);         /* µs に切り上げ */
}
/* lora_toa_us(7, 125000, 1, 25, 8, 1, 1) は 61696、SF12 なら 1482752 を返す */

シンボル数を 4 倍して整数にしている（4.25 × 4 = 17）。(1000u << sf) > 16u * bw_hz は \(2^{\mathrm{SF}}/\mathrm{BW} > 16/1000\) の両辺に 1000 BW を掛けたもので、BW 125 kHz の SF11・SF12 と、250 kHz の SF12 で LDRO を使う。この関数は、SF7〜12・3 つの BW・4 つの符号化率・ペイロード 0〜255 バイトなどの 294,912 通りで、Python で計算した式の値（µs への切り上げ）と一致することを、AddressSanitizer を付けた gcc で確かめてある。

4. 電波の規則 — デューティサイクルと送信時間の制限

免許不要の帯域は誰でも使えるので、1 台の機器が電波を占め続けると、近くのほかの機器が使えなくなる。そこで国ごとの規則が、送信の電力のほかに、送信の時間にも上限を決めている。

決まった観測の時間の中で、送信している時間が占める割合の上限を、デューティサイクルという。01 章 5 節のデューティ比（周期のうち起きている時間の割合）とは別物で、こちらは電波の規則が決める、送信の時間の割合の上限である。

欧州の 868 MHz 帯は、いくつかの小さな周波数の範囲（サブバンド）に分かれていて、範囲ごとに上限が違う（1 %・0.1 %・10 % など）。LoRaWAN の機器が必ず使える 3 つのチャネル（868.1・868.3・868.5 MHz）が入る範囲の上限は 1 % で、観測の時間は 1 時間とされることが多い。

方針: 1 時間の送信の合計が上限以下という条件から、1 時間に送れる回数を求める。次に、送るたびに決まった時間を休む、という簡単な守り方でも、長い時間で平均すると同じ回数になることを確かめる。

導出: 上限を d、1 回の空中時間を \(T_\mathrm{air}\) とする。1 時間に N 回送るときの送信の合計は \(N T_\mathrm{air}\) なので、条件は \(N T_\mathrm{air} \le 3600\, d\) 秒、すなわち

\[ N \le \frac{3600\, d}{T_\mathrm{air}} \]

である。d = 1 % なら 36 秒 ÷ \(T_\mathrm{air}\) で、3 節の例（PL = 25 バイト）では SF7（61.7 ms）で 583 回、SF12（1482.8 ms）で 24 回になる。

簡単な守り方では、送り終えてから \((1/d - 1)\, T_\mathrm{air}\) の間は送らない。d = 1 % なら \(99\, T_\mathrm{air}\) である。送り始めの間隔は \(T_\mathrm{air} + 99\,T_\mathrm{air} = 100\, T_\mathrm{air}\) 以上になるので、長い時間で平均した送信の割合は 1/100 以下で、1 時間あたりの回数は \(3600/(100\, T_\mathrm{air}) = 36/T_\mathrm{air}\) と、上の上限に等しくなる ∎

送り始めの間隔の最小は、SF7 で 6.2 秒、SF12 で 148 秒（約 2.5 分）である。10 分ごとに送る機器なら、SF12 でも上限の 1/4 しか使わない。しかし、送れなかったデータを後からまとめて送る（15 章 3 節）、命令の応答を急いで返す、といった使い方では、すぐに上限に達する。

この規則は、ゲートウェイが送る下りにもかかる。1 台のゲートウェイが多くの機器に下りを送ると、ゲートウェイの送信の時間が上限に達するので、LoRaWAN では下りはもともと少なくしか送れない（5 節で見る、確認付きの上りに返す ACK も、ゲートウェイの送信の時間を使う）。

日本の 920 MHz 帯で使う機器の条件は、電波法の技術基準と、それをもとにした民間の規格 ARIB STD-T108 にまとめられている。送る前に一定の時間チャネルを聞いて、使われていないときだけ送るキャリアセンス（09 章 1 節。LBT、Listen Before Talk ともいう）、1 回に続けて送ってよい時間、送った後に休む時間、1 時間あたりの送信時間の合計などの条件があり、値は使うチャネルの範囲と送信の電力によって違う。キャリアセンスをする代わりに送信時間の割合を抑える、という選び方ができる範囲もある。規格の版によっても変わるので、使う無線モジュールと LoRaWAN の地域の設定（日本では AS923。5 節）が、どの条件に従っているかを確かめる。地域の設定には、1 回の送信を 400 ms 以下に抑える条件（滞留時間の制限）を使う選び方もあり、それを使う網では、400 ms を超える設定は使えない（3 節の表の PL = 25 バイトでは SF10〜SF12 が超える。SF10 でも、データを 11 バイト以下にすれば 400 ms 以下になる）。

規則を守るために、送る前に、チャネルの範囲ごとに次に送ってよい時刻を確かめる。05 章 3 節の、ティックの数が一周しても正しい比べ方を使う。

struct dc_band {
    uint32_t next_ms;    /* この時刻から送ってよい（1 ms ごとに増えるティック） */
    uint32_t inv;        /* 上限の逆数。1 % なら 100、0.1 % なら 1000 */
};

/* いま送ってよいか（05 章 3 節の、一周しても正しい比べ方） */
int dc_may_send(const struct dc_band *b, uint32_t now_ms)
{
    return (int32_t)(now_ms - b->next_ms) >= 0;
}

/* now_ms に、空中時間 toa_ms の送信を始めたときに呼ぶ */
void dc_on_send(struct dc_band *b, uint32_t now_ms, uint32_t toa_ms)
{
    b->next_ms = now_ms + toa_ms * b->inv;   /* 送り終えてから (inv − 1) × toa_ms 休む */
}

送り始めの時刻から inv × toa_ms 後は、送り終えてから (inv − 1) × toa_ms 後と同じである。ティックの数が一周する直前に送った場合も含めて、次に送れるのがちょうど 100 倍の時間の後になることを、gcc で確かめてある。LoRaWAN のスタックの中には、1 時間の観測の時間の中で送信の時間を積み上げて数える実装もある（版によって違う）。

規則の内側でも、送信はぶつかる

送る前にチャネルを聞かない地域では、LoRaWAN の機器は、送りたいときに送る。同じチャネル・同じ SF の 2 つの送信が時間の上で重なると、ゲートウェイはたいてい、どちらも受け取れない（一方が十分に強ければ、強いほうを受け取れることもある）。

方針: N 台の機器が、それぞれ周期 \(T_\mathrm{r}\) に 1 回、互いに無関係な時刻に、空中時間 \(T_\mathrm{air}\) の送信をするとする。ある 1 つの送信が、ほかのどれとも重ならない確率を求める。

導出: 自分の送信が時刻 t に始まるとき、ほかの 1 台の送信が重なるのは、その始まりが \(t - T_\mathrm{air}\) から \(t + T_\mathrm{air}\) までの、長さ \(2T_\mathrm{air}\) の間にあるときである。ほかの機器の送り始めは、長さ \(T_\mathrm{r}\) の周期の中のどこでも同じ確からしさとすると、重なる確率は \(2T_\mathrm{air}/T_\mathrm{r}\) である。ほかの N − 1 台が互いに無関係に送るので、どれとも重ならない確率は

\[ P = \left(1 - \frac{2 T_\mathrm{air}}{T_\mathrm{r}}\right)^{N-1} \approx \exp\left(-\frac{2 (N-1) T_\mathrm{air}}{T_\mathrm{r}}\right) \]

である。近似は、x が小さいとき \(\ln(1 - x) \approx -x\) であることから、\((1 - x)^{N-1} = e^{(N-1)\ln(1-x)} \approx e^{-(N-1)x}\) とした ∎

1000 台が 1 時間に 1 回ずつ、1 つのチャネルで送るとき、SF7 なら 96.6 % の送信が重ならないが、SF12 では 43.9 % にとどまる。ゲートウェイの多くは複数のチャネル（8 チャネルの代表値）を同時に受信し、機器はチャネルを乱数で選ぶので、8 チャネルに分かれれば 1 チャネルあたり 125 台になり、SF7 で 99.6 %、SF12 で 90.3 % になる。SF の違う送信どうしは、重なっても受け取れることが多い（完全ではない）。いずれにしても、空中時間が長いほど、ほかの機器と重なりやすい。

空中時間を短くすることは、機器の電池（5 節）にも、規則の上限にも、同じ帯域を使うほかの機器にもよい。5 節の ADR は、この考え方で SF を選ぶ。

5. LoRaWAN の仕組み

LoRaWAN は、LoRa の上で、機器とサーバの間のフレームの形・送り方・鍵の扱いと、網の構成を決めたプロトコルである。LoRa Alliance という団体が仕様を決めていて、1.0 系（1.0.2・1.0.3・1.0.4 など）と 1.1 の版があり、細部が違う。周波数・データレート・受信の既定値など、地域ごとの値は、地域の設定（Regional Parameters）という別の文書で決まっている（欧州は EU868、日本は AS923）。この節は 1.0 系に沿って説明する。

網の構成

  • エンドデバイス: LoRaWAN の機器（このシリーズの機器）。
  • ゲートウェイ（LoRaWAN の）: LoRa の電波で受けたフレームを、中身を解かずに、IP の網（Ethernet や携帯電話の回線）でネットワークサーバへ送り、ネットワークサーバに頼まれた下りを電波で送る機器（01 章 1 節のゲートウェイの一種）。複数のチャネルと SF を同時に受信できる。エンドデバイスは特定のゲートウェイにつながるのではなく、電波が届いたゲートウェイがすべて受け取る。
  • ネットワークサーバ: 複数のゲートウェイから届いた同じフレームを 1 つにまとめ（重複を除き）、この節で述べる MIC とフレームカウンタを確かめ、下りを送るゲートウェイを選ぶ。
  • アプリケーションサーバ: 暗号化されたアプリケーションのデータを復号して使う。

ゲートウェイを自分で置けば自分の網になり、事業者が置いたゲートウェイの網を契約して使うこともできる。

フレームの形

LoRaWAN のフレームは、LoRa のパケットのペイロード（3 節）に入る。

MHDR はフレームの種類（参加の要求と応答、確認なしと確認付きの上り・下り）、DevAddr は網の中で機器を指す 4 バイトのアドレス（参加の手続きで決まる）、FCtrl は ADR（この節の最後で説明する）のためのビットと FOpts の長さ、FCnt は後で述べるフレームカウンタの下位 16 ビット、FOpts は網の制御のための短い命令（MAC コマンド）、FPort はアプリケーションのデータの種類（0 は MAC コマンドだけを運ぶ）、FRMPayload はアプリケーションのデータである。DevAddr と FCnt はリトルエンディアン（03 章 6 節）で並ぶ。FOpts が空なら、データに足されるのは 1 + 4 + 1 + 2 + 1 + 4 = 13 バイトで、3 節の例の 13 バイトはこれである。1 回に送れるデータの長さには、データレートごとの上限がある（EU868 では、SF12 で 51 バイト、SF7 で 242 バイト）。

FRMPayload は、機器と網の側だけが持つ鍵（12 章 2 節のセッション鍵。手に入れ方はこの節の後半）とフレームカウンタから AES（暗号シリーズ 14 章）で作ったバイトの列と、XOR をとって暗号化される。最後の MIC は、19 章 1 節の BLE の MIC と同じ役割の 4 バイトで、フレームの全体とフレームカウンタの 32 ビットの値から、別のセッション鍵を使って AES で計算する MAC（暗号シリーズ 18 章）である。鍵を持たない者は、正しい MIC を作れない。

クラス A・B・C — 下りをいつ受け取るか

クラス A は、すべての LoRaWAN の機器が持つ基本の動き方である。機器は、上りを送り終えてから決まった時間の後に、2 回だけ受信を始める。この受信の時間を受信窓といい、1 回目を RX1、2 回目を RX2 という。既定では、RX1 は送り終えてから 1 秒後に開く（EU868 や AS923 では、上りと同じチャネルを使う）。RX2 は 2 秒後に、地域の設定で決まった周波数とデータレートで開く（既定は、EU868 で 869.525 MHz・SF12、AS923 で 923.2 MHz・SF10。網が変えることもある）。下りが無ければ、窓は、プリアンブルを探す数シンボルの間だけ開いて閉じる。RX1 で下りを受け取れば、RX2 は開かない。

ネットワークサーバは、機器あての下りを預かっておき、その機器から次の上りが届いたときに、その受信窓で送る。したがって、クラス A の下りの遅れは、最大で上りの間隔になる。

クラス B は、クラス A の受信窓に加えて、ゲートウェイが 128 秒ごとに送るビーコン（時刻を知らせる信号）で時計を合わせ、決まった周期で短い受信窓を開く。下りの遅れはその周期まで縮むが、ビーコンと窓を受信する分だけ電流が増える。クラス C は、送信している間を除いて、ずっと受信している。下りはすぐ届くが、受信の電流（数 mA〜十数 mA の代表値）が流れ続けるので、電池で動く機器には向かない。

クラス A の上り 1 回の電荷を、19 章と同じく、電流 × 時間を足して求める。送信の電流を 40 mA、受信の電流を 10 mA、眠っている間の電流を 2 µA とし（いずれも代表値）、受信窓の長さを、プリアンブルを探すのに要る 6 シンボル以上と、時計の誤差の余裕を含めた長さ（SF7 で 24.6 ms、SF12 で 197 ms）とする。3 節の例（PL = 25 バイト）で、RX2 を SF12 とすると次のようになる。

参加の手続き — OTAA と ABP

データを送る前に、機器は DevAddr とセッション鍵を持つ必要がある。その手に入れ方が 2 つある。

OTAA（Over-The-Air Activation）は、電波で参加の手続きをする方法である。機器には、出荷の前に次の 3 つを入れておく。

  • DevEUI: 機器ごとの 64 ビットの識別子。
  • JoinEUI: 参加を受け付けるサーバを指す 64 ビットの識別子（古い版では AppEUI と呼んだ）。
  • AppKey: 機器ごとの 128 ビットの AES の鍵。機器と網の側のサーバだけが持ち、電波には乗せない。

機器は、JoinEUI・DevEUI と、毎回違う数（DevNonce）を入れた Join-request を送る。網はそれを確かめ、既定では 5 秒後と 6 秒後に開く受信窓で、DevAddr・網が選んだ数・設定を入れた Join-accept を、AppKey で暗号化して返す。両者は、AppKey と互いが選んだ数から、同じセッション鍵（1.0 系では、MIC のための鍵と、データを暗号化するための鍵の 2 つ）を計算する。参加のたびに新しい鍵が作られ、フレームカウンタは 0 から始まる。

ABP（Activation By Personalization）は、DevAddr とセッション鍵を、前もって機器と網の側の両方に書いておく方法である。参加の手続きは要らないが、鍵が変わらないので、次に述べるフレームカウンタを、電源が切れても保ち続けなければならない。

鍵を機器にどう入れて守るかは IoT セキュリティシリーズ 12 章 と 06 章、LoRaWAN の安全の要点は 同シリーズ 16 章 4 節 にある。

フレームカウンタ — 再送と送り直しを見分ける

機器は、上りを送るたびに 1 ずつ増やす 32 ビットの数を持ち、網の側も、下りのために別の数を持つ。この数をフレームカウンタという。フレームカウンタには 3 つの役割がある。

  1. 重複を見分ける: 確認付きの上り（網に ACK を求める上り）で ACK が来なければ、機器は同じフレームを再送する（05 章 4 節）。再送ではフレームカウンタを変えないので、網は重複と分かる（05 章 4 節のシーケンス番号と同じ使い方）。複数のゲートウェイが同じフレームを受け取ったときも、同じ値で 1 つにまとめる。
  2. 送り直しを捨てる: 盗聴して記録したフレームを後から送り直されても、フレームカウンタが最後に受け入れた値以下なので捨てる。フレームカウンタを書き換えると、MIC が合わなくなる。
  3. 暗号化を安全に保つ: データを暗号化するバイトの列はフレームカウンタから作るので、同じ鍵で同じ値を 2 回使うと、2 つのフレームの中身の XOR が分かってしまう（暗号シリーズ 14 章 8 節 の利用モードの注意と同じ）。

フレームの FCnt の欄には、下位 16 ビットだけを入れる。受け手が 32 ビットの値をどう復元するかを示す。

方針: 受け取った下位 16 ビット r と、最後に受け入れた値 L から、送り手の値を決める規則を立て、規則が正しい値を返す条件を求める。

導出: L の上位 16 ビットに r をつないだ値を c とする。c > L なら c を、c < L なら下位 16 ビットが一周したとみて c + 65536 を、送り手の値とする。c = L なら重複である。送り手の本当の値を v = L + g（g ≥ 1）とする。L より大きく L + 65536 より小さい範囲には、下位 16 ビットが r の値が（r が L の下位 16 ビットと等しい場合を除いて）ただ 1 つあり、規則が返すのはその値である（c > L なら c − L ≤ 65535、c < L なら c + 65536 − L < 65536 となるので）。g < 65536 なら v もこの範囲にあるので、規則は v を返す。g ≥ 65536、つまり間のフレームが 65535 個以上続けて失われると、規則は誤った値を返す ∎

ABP では、電源が切れてフレームカウンタが 0 に戻ると、網は以後の上りを送り直しとして捨てる（網の側の確かめ方を緩めると、送り直しを防げなくなる）。そこで値をフラッシュメモリに残すが、送るたびに書くと、10 分ごとの上りで 1 年に約 5 万回になり、15 章 3 節の書き込み回数の上限（1 万〜10 万回の代表値）に届いてしまう。16 回に 1 回だけ「ここまでは使ってよい」という値を書き、起動したらその値から始める。起動のたびに最大 15 個の値を飛ばすが、同じ値を使うことはない。

uint32_t fcnt_flash_read(void);          /* この章で仮に置く関数（フラッシュの読み書き） */
void fcnt_flash_write(uint32_t v);

#define FCNT_STEP 16u                    /* 何回に 1 回フラッシュに書くか */

struct fcnt_up {
    uint32_t next;     /* 次の上りに使う値 */
    uint32_t limit;    /* フラッシュに書いてある値。これより小さい値だけを使ってよい */
};

/* 起動したとき: フラッシュの値から始める（前回は、それより小さい値しか使っていない） */
void fcnt_boot(struct fcnt_up *c)
{
    c->next = c->limit = fcnt_flash_read();
}

/* 上りを送る前に呼び、そのフレームに使う値を返す */
uint32_t fcnt_take(struct fcnt_up *c)
{
    if (c->next == c->limit) {           /* 書いてある範囲を使い切った */
        c->limit = c->next + FCNT_STEP;
        fcnt_flash_write(c->limit);      /* 先に書いてから使う */
    }
    return c->next++;
}

フラッシュに書いた後でしかその値を使わないので、どこで電源が切れても、使った値はすべてフラッシュの値より小さい。乱数で選んだ時点で起動し直すことを 2000 回の試行で繰り返し、使った値が常に増え続けることを gcc で確かめてある。書き込みの途中で電源が切れる場合は、15 章 3 節の書き方で守る。OTAA でも、起動のたびに参加し直すと、空中時間と下りを使うので、セッション鍵とフレームカウンタを残しておく実装が多い。

ADR — SF を網に決めてもらう

ADR（Adaptive Data Rate）は、ネットワークサーバが、機器の最近の上りがどれだけの余裕で届いたか（SN 比が、その SF で受け取れる限度をどれだけ上回ったか。2 節）を見て、余裕が大きければ SF を下げ、送信の電力を下げるよう、機器に命じる仕組みである（命令は MAC コマンドで、下りに載せて送る）。4 節で見たとおり、SF を下げると空中時間が短くなり、電池にも、規則の上限にも、ほかの機器との重なりにもよい。

機器の側は、下りがしばらく届かないと、SF を下げすぎて届いていないおそれがあるので、応答を求めるビットを立て、それでも応答が無ければ、送信の電力を元に戻し、SF を少しずつ上げる（既定では、64 回の上りの間に下りが無ければ応答を求め、その後は 32 回ごとに上げる。地域の設定による）。ADR は、電波の状態があまり変わらない、止まっている機器に向く。動く機器では、送るたびに電波の状態が変わり、網の判断が追いつかないので、ADR を使わずに機器の側で SF を決めることが多い。

6. セルラー LPWA — LTE-M と NB-IoT

LTE-M（規格の上では LTE Cat-M1 など。eMTC とも呼ぶ）と NB-IoT（Narrowband IoT）は、携帯電話の規格を決める 3GPP が、Release 13（2016 年に固まった版）で LTE に加えた、少ないデータを少ない電力で送る機器のための方式である。どちらも、通信事業者の免許の帯域と基地局を使う。機器では、セルラーの無線モジュール（06 章 1 節の (b)）が、網への登録と IP の通信（07〜14 章）を受け持ち、ホストのマイコンは AT コマンド（06 章 2 節）でモジュールを操作することが多い。通信を続けたまま、つなぐ基地局を切り替えることをハンドオーバという。2 つの方式を比べる。

網につながったまま眠る — アイドル・DRX・eDRX・PSM

機器は、電源を入れると、近くの基地局を探して網に登録する（06 章 2 節の AT+CEREG? で、登録の状態が 1 になる）。データを送受信している間は、基地局と無線の接続を持つ。何も送らない時間が、網の決めた時間（数秒〜数十秒の代表値）続くと、基地局が無線の接続を切る。網への登録は残したまま、無線の接続が無い状態を、アイドルという。アイドルの機器が次に送るときは、無線の接続だけを短い手順で作り直せばよい。09 章 4 節の Wi-Fi で、送るときだけつなぐ作り方が、送るたびにスキャンから接続をやり直したのと比べると、ずっと軽い。

アイドルの機器あてに下りのデータが届くと、網は、基地局から機器を呼び出す。これをページングという。機器は、決まった周期で受信の回路を短い時間だけ動かして、呼び出しを聞く。この間欠的な受信を DRX（Discontinuous Reception）といい、周期は 1.28 秒・2.56 秒などである。09 章 4 節で、Wi-Fi の機器が DTIM ごとに起きてビーコンを聞いたのと同じ考え方である。

  • eDRX（extended DRX）: 呼び出しを聞く周期を延ばす仕組み。周期は決まった値の中から選び、規格の上の最長は、LTE-M で 2621.44 秒（約 44 分）、NB-IoT で 10485.76 秒（約 2.9 時間）である。下りの遅れは、最大でこの周期になる。
  • PSM（Power Saving Mode）: アイドルになってから、アクティブタイマ T3324 の間だけ呼び出しを聞き、その後は呼び出しも聞かずに深く眠る仕組み。網への登録は残るが、深く眠っている間は下りが届かない。機器は、送るデータができたとき、または周期的な更新のタイマ T3412 が切れたときに起きる。T3412 が切れたときは、まだ網の中にいることを知らせる手続き TAU（Tracking Area Update）を行い、またアイドルを経て深く眠る。データを送ると T3412 は数え直しになるので、報告の間隔が T3412 より短ければ、TAU は起きない。

PSM は、09 章 4 節の「送るときだけつなぐ」作り方に似ているが、登録を保ったまま眠るので、起きるたびに払う電荷（09 章 4 節の \(Q_\mathrm{c}\) にあたる）が小さい。eDRX は、DTIM の周期を延ばすのにあたる。

PSM と eDRX は、機器が網に頼み、網が認めた値を使う。PSM は AT+CPSMS=1,,,"01000001","00000101" のように頼む（3GPP TS 27.007 の命令。最初の 2 つの空の欄は、古い方式の網のためのタイマ）。最後の 2 つの 8 文字が T3412 と T3324 で、3GPP TS 24.008 の形で、上位 3 ビットが単位、下位 5 ビットが値（0〜31）を表す。網は、頼んだ値と違う値を認めることがあるので、AT+CEREG=4 を送っておき、+CEREG の中間応答や URC（06 章 3 節）の最後の 2 つの欄で、網が認めた T3324 と T3412 を読む。eDRX は AT+CEDRXS=1,4,"0101" のように頼む（2 つ目の引数は 4 が LTE-M、5 が NB-IoT で、3 つ目は周期を表す 4 ビットの番号。番号と周期の対応は規格の表による）。命令の細部と対応の有無は、モジュールの製品と版で違うので、説明書で確かめる。

8 文字を秒に直す関数を示す。

/* AT コマンドの 8 ビットの文字列（"01000001" など）を秒に直す。
   tau = 1 なら T3412（GPRS Timer 3 の形）、0 なら T3324（GPRS Timer 2 の形）。
   タイマが止められている値・扱わない単位・形の誤りは -1 を返す */
long psm_timer_s(const char *s, int tau)
{
    static const long u3[7] = { 600, 3600, 36000, 2, 30, 60, 1152000 };
    static const long u2[3] = { 2, 60, 360 };
    unsigned v = 0;
    for (int i = 0; i < 8; i++) {
        if (s[i] != '0' && s[i] != '1')
            return -1;                   /* 8 文字に足りない場合もここで止まる */
        v = (v << 1) | (unsigned)(s[i] - '0');
    }
    if (s[8] != '\0')
        return -1;
    unsigned unit = v >> 5, n = v & 0x1Fu;   /* 上位 3 ビットが単位、下位 5 ビットが値 */
    if (tau)
        return unit < 7 ? u3[unit] * (long)n : -1;
    return unit < 3 ? u2[unit] * (long)n : -1;
}

psm_timer_s("01000001", 1) は 36000（10 時間）、psm_timer_s("00000101", 0) は 10 を返す。256 通りの文字列のすべてと、短すぎる・長すぎる・0 と 1 以外を含む文字列で、図の表どおりの値を返すことを gcc で確かめてある。

平均電流と下りの遅れ

方針: 01 章 5 節と同じく、1 周期の電荷を足して周期で割る。周期は報告の間隔 \(T_\mathrm{r}\) とし、\(T_\mathrm{r}\) は T3412 より短い（TAU が起きない）とする。

導出: 深く眠っている間の電流を \(I_\mathrm{s}\)、1 回の報告（無線の接続を作り、送受信し、網が接続を切るまで）の電荷を \(Q_\mathrm{r}\) とする。報告の後のアクティブタイマ \(T_\mathrm{a}\)（T3324）の間は、DRX の周期 \(T_\mathrm{d}\) ごとに、1 回 \(q_\mathrm{p}\) の電荷で呼び出しを聞くので、その電荷は \((T_\mathrm{a}/T_\mathrm{d})\, q_\mathrm{p}\) である。1 周期の電荷は、眠りの分 \(I_\mathrm{s} T_\mathrm{r}\)（起きている短い時間の分の重なりは無視する）とこれらの和なので、\(T_\mathrm{r}\) で割って

\[ I_\mathrm{PSM} = I_\mathrm{s} + \frac{Q_\mathrm{r} + (T_\mathrm{a}/T_\mathrm{d})\, q_\mathrm{p}}{T_\mathrm{r}} \]

となる。PSM を使わず、eDRX の周期 \(T_\mathrm{e}\) で呼び出しを聞き続けるなら、その間の眠りの電流を \(I_\mathrm{e}\) として、呼び出し 1 回の電荷が \(T_\mathrm{e}\) ごとに加わるので

\[ I_\mathrm{eDRX} = I_\mathrm{e} + \frac{Q_\mathrm{r}}{T_\mathrm{r}} + \frac{q_\mathrm{p}}{T_\mathrm{e}} \]

となる ∎

下りの遅れは、PSM では、深く眠っている間に届いた下りを、機器が次に報告してアクティブタイマの間に受け取るので、最大でほぼ \(T_\mathrm{r}\) である。eDRX では最大で \(T_\mathrm{e}\) である。

例: \(I_\mathrm{s}\) = 5 µA、\(Q_\mathrm{r}\) = 60 mC、\(T_\mathrm{a}\) = 20 s、\(T_\mathrm{d}\) = 1.28 s、\(q_\mathrm{p}\) = 0.3 mC、\(I_\mathrm{e}\) = 15 µA、\(T_\mathrm{e}\) = 81.92 s、電池 2000 mAh とする（いずれも代表値。\(Q_\mathrm{r}\) は電波の状態（繰り返しの回数）と網の設定で 1 桁変わる）。アクティブタイマの分は \(20/1.28 \times 0.3 = 4.69\) mC である。

下りの設計では、08 章 5 節の NAT にも気をつける。携帯電話の網の中の NAT の変換表は、深く眠っている間に保持時間を過ぎて消えるので、サーバは、好きなときに機器へパケットを送ることができない。機器が報告を送ると変換表に行ができるので、サーバは、預かっておいた下りを、その報告への返事として送る（クラス A の LoRaWAN と同じ形）。TCP の上の MQTT のように、数分ごとのキープアライブ（13 章 5 節）で接続を保つ作り方は、PSM の眠りと両立しない。UDP の上の CoAP（14 章）で送るか、起きるたびに接続し直し、TLS のセッションの再開（12 章 6 節）で接続の電荷を減らす。
