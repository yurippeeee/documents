Chapter 03

フレーミングと誤り検出 — バイトの列をメッセージに区切る

この章で扱う問い. 02 章の UART は、1 本の線の上のビットを 1 バイトずつに区切って届けた。しかし、機器が送りたいのは、測定値の組や命令のような、何バイトかで 1 つの意味を持つまとまりである。この章では、バイトの列をそのまとまりに区切る方法と、途中でバイトが壊れたことに気づく方法を見る。

この章では次の 3 つの問いに答える。

  1. 切れ目のないバイトの流れから、受け手はどうやってまとまりの境目を見つけるのか。途中から聞き始めたときや、バイトが壊れたときにも、境目を見つけ直せるのか。
  2. 届いたまとまりが途中で壊れたことに、受け手はどうやって気づくのか。
  3. 数値や、項目の数が変わるデータを、どんなバイトの並びにして送ればよいのか。

答えの道具は、区切りの印をデータと見分けるための置き換え（SLIP・COBS）と長さのフィールド、割り算の余りで誤りに気づく CRC、そしてバイトの順番を決めて 1 バイトずつ組み立てる書き方である。

この章で使う既出の用語（定義は各リンク先）. 機器・マイコン（01 章 1 節）、プロトコル・ヘッダ（01 章 2 節）、bps（01 章 3 節）、RAM・フラッシュメモリ・ファームウェア（01 章 4 節）、UART（02 章 1 節）、UART のフレーム・スタートビット・ストップビット・最下位ビット（LSB）・最上位ビット（MSB）・パリティ・8N1（02 章 2 節）、フレーミングエラー（02 章 3 節）、RS-485（02 章 5 節）、受信バッファ（02 章 6 節）

1. バイトの流れには切れ目がない

02 章の UART は、スタートビットとストップビットで 1 バイトずつを区切って届ける。受け手のソフトウェアに届くのは、バイトが 1 つずつ並んだ列だけで、何バイト目から何バイト目までが 1 つのまとまりなのかを示す印は、どこにも無い。

例として、温湿度センサの機器が、4 バイトを 1 組にして 1 秒ごとに送るとする。1 バイト目はセンサの番号、2 バイト目は温度（°C）、3 バイト目は湿度（%）、4 バイト目は電池の残り（%）である。このように、アプリケーションが 1 回に送りたいデータのまとまりをメッセージという。受け手が送り手より後に電源を入れた場合と、途中で 1 バイトを取りこぼした場合に、受け手が 4 バイトずつ読むと何が起きるかを図に示す。

受け手 B は 2 バイト目から読み始めたので、温度を番号として、湿度を温度として読み、「センサ 23 の温度は 45 °C」と解釈している。読み取った値はどれもありえない値ではないので、受け手は誤りに気づかない。受け手 C は、取りこぼした所から後を、すべて 1 バイトずれたまま読み続ける。4 バイトずつ読むという決まりだけでは、一度ずれると二度と直らない。

したがって、メッセージの境目は、バイトの列そのものに書き込んで送る必要がある。メッセージ 1 つ分を送るために、区切りの印や長さなどを付け足して作ったバイトの列を、この章ではフレームという。02 章の UART のフレーム（1 バイト分の信号のまとまり）とは別のものであり、02 章のフレーミングエラー（UART のフレームの区切りが合わないこと）も、この章の話とは別である。フレームのうち、運びたいメッセージそのものの部分をペイロードという（ペイロードの前に付ける情報が、01 章のヘッダである）。送り手がメッセージをフレームにし、受け手がバイトの流れからフレームを切り出してペイロードを取り出すための決まりを、フレーミングという。

フレーミングに求められることは 2 つある。受け手がフレームの境目を見つけられることと、受け手が境目を見失っても（途中から聞き始めた、バイトを取りこぼした、バイトが壊れた）、その後の正しい境目をもう一度見つけられることである。見失った境目をもう一度見つけることを、この章では同期し直すという（02 章の同期式とは関係がない）。方法は大きく 3 つに分けられる。

(c) の例には、RS-485 でよく使われる Modbus RTU というプロトコルがあり、3.5 文字分（UART のフレーム 3.5 個分）以上の空きでフレームを区切る。(c) では、送り手の処理が途中で止まってバイトの間に空きができると受け手はそこで区切ってしまい、PC と USB の変換器をはさむとバイトの間の時間が保たれないこともある。この章では、バイトの値だけで境目が決まる (a)（2・3 節）と (b)（4 節）を扱う。フレームの中身が壊れたことには、どの方法でも別の仕組みで気づく必要がある（5 節）。

2. 区切り文字とバイトスタッフィング — SLIP

フレームの終わりの印として使う、決めておいたバイトの値を区切り文字という。文字だけを送るプロトコルなら、改行（0x0A）を区切り文字にできる。文字の列の中に改行は現れないので、受け手は改行までを 1 つのメッセージとすればよい（06 章の AT コマンドはこの形である）。しかし、数値をそのまま送るバイナリのデータには 0x00〜0xFF のどの値も現れうるので、区切り文字と同じ値がデータの中に現れると、受け手はそこでフレームが終わったと誤解する。

そこで、データの中に区切り文字と同じ値が現れたら、別の決まった 2 バイトの並びに置き換えて送り、受け手が元に戻す。この置き換えをバイトスタッフィング、またはエスケープという。置き換えに使う並びの 1 バイト目は「次のバイトと組で 1 つの値を表す」という印になるので、データの中にその印と同じ値が現れたら、それも置き換える。この方法の代表が SLIP（Serial Line Internet Protocol。RFC 1055）である。もとはインターネットのデータ（IP のパケット。07 章）をシリアルの線で送るための決まりだが、仕組みが簡単なので、ほかのデータを運ぶのにも使われている。SLIP は次の 4 つの値を使う。

名前値意味
END0xC0区切り文字
ESC0xDB次のバイトと組で 1 つの値を表す印
ESC_END0xDCESC の後に置いて、データの 0xC0 を表す
ESC_ESC0xDDESC の後に置いて、データの 0xDB を表す

送り手は、データの 0xC0 を DB DC に、0xDB を DB DD に置き換え、ほかの値はそのまま送り、最後に END を送る。RFC 1055 の例のコードは、フレームの先頭にも END を送る。先頭の END は、それより前に雑音などで受け手にたまったバイトを、別の（壊れた）フレームとして区切らせるためのものである。

受け手は、届いたバイトを 1 つずつ扱う。END が来たら、それまでにためたバイトを 1 つのフレームとして渡し（何もたまっていなければ何もしない）、ESC が来たら、次のバイトを元の値に戻してためる。C で書くと次のようになる。

#define SLIP_END 0xC0
#define SLIP_ESC 0xDB
#define SLIP_MAX 64                      /* 受け取るペイロードの最大の長さ */

struct slip_rx {
    uint8_t buf[SLIP_MAX];               /* 元に戻したペイロード */
    size_t  len;
    bool    esc, bad;                    /* 直前が ESC だった・このフレームは壊れている */
};

/* 受信した 1 バイト c を渡す。フレームが完成したらその長さを返し（中身は r->buf）、
   まだなら 0 を返す。空のフレームと壊れたフレームは、END の所で捨てる */
size_t slip_rx_byte(struct slip_rx *r, uint8_t c)
{
    if (c == SLIP_END) {
        size_t n = (r->bad || r->esc) ? 0 : r->len;
        r->len = 0; r->esc = r->bad = false;
        return n;
    }
    if (r->esc) {                        /* ESC の次: DC なら C0、DD なら DB に戻す */
        r->esc = false;
        if (c == 0xDC) c = SLIP_END;
        else if (c == 0xDD) c = SLIP_ESC;
        else { r->bad = true; return 0; }    /* 規則にない並び */
    } else if (c == SLIP_ESC) {
        r->esc = true;
        return 0;
    }
    if (r->len < SLIP_MAX) r->buf[r->len++] = c;
    else r->bad = true;                  /* 長すぎる */
    return 0;
}

slip_rx_byte は届いたバイトごとに呼べばよく、バイトがどんな間隔で届いても正しく組み立てられる。ESC の後に規則にない値が来たフレームと、受信バッファの大きさ SLIP_MAX を超えたフレームは、壊れたものとして捨てる。

最悪の場合の長さ

送り手は、符号化したフレームを入れる場所（送信用のバッファ）を、最悪の場合に合わせて用意しなければならない。その長さを求める。

方針: n バイトのデータのうち、0xC0 か 0xDB であるバイトの数を k として、フレームの長さを n と k で表し、k が最も大きい場合を考える。

導出: 0xC0 と 0xDB の k バイトは 2 バイトずつに、残りの \(n - k\) バイトは 1 バイトずつになる。これに先頭と最後の END の 2 バイトを足すと、フレームの長さは \(2k + (n - k) + 2 = n + k + 2\) である。k は 0 以上 n 以下なので、最も長くなるのはデータのすべてが 0xC0 か 0xDB のとき（\(k = n\)）で、長さは \(2n + 2\) バイトになる ∎

データのバイトの値がでたらめなら、1 バイトが 0xC0 か 0xDB である確率は 2/256 なので、増える量の平均はデータの約 0.78 % にすぎない。しかし最悪の場合に備えて送信用のバッファは \(2n + 2\) バイト要り、送る時間もデータの中身によって最大でほぼ 2 倍に延びる。

境目を見失ったときと、バイトが壊れたとき

置き換えのおかげで、END の値はフレームの中には現れない。したがって、境目を見失った受け手も、次の END が届けば、その後からは正しいフレームを受け取れる。つまり、次の END で同期し直せる。

ただし、受け手が渡すものが正しいフレームだとは限らない。途中から聞き始めた受け手は、最初の END までの切れ端を 1 つのフレームとして渡す。データのバイトが壊れて 0xC0 になれば、1 つのフレームが 2 つに分かれる。END が壊れればフレームの終わりが消えるが、次のフレームの先頭にも END があるので、次のフレームまでは巻き込まない（先頭の END の効果である）。どの場合も、渡したものは SLIP の規則としては正しい形をしているので、SLIP だけでは見分けられない。中身が壊れたことには、5 節の誤り検出で気づく。

3. COBS — 0 を区切りに使い、増えるのは 254 バイトに 1 バイト

SLIP では、フレームの長さがデータの中身によって最大ほぼ 2 倍まで変わる。最悪の場合に合わせて送信用のバッファを用意するのは、RAM の少ないマイコンには負担である。COBS（Consistent Overhead Byte Stuffing）は、増えるバイトの数がデータの中身にほとんどよらないように作られた置き換えの方法である。COBS では 0x00 を区切り文字にし、データの中の 0x00 を「次の 0x00 が何バイト先にあるか」を表す値に置き換える。手順は次のとおりである。

  1. データの最後に、仮の 0x00 を 1 つ足す。
  2. データの先頭の前に、1 バイトの場所を空ける。
  3. 先頭に空けた場所と、データの中の各 0x00 を、そこから次の 0x00（仮の 0x00 を含む）までの距離、つまり次の 0x00 が何バイト先にあるかの値に置き換える。
  4. 仮の 0x00 を取り除き、代わりに区切り文字の 0x00 を最後に置く。

手順 3 で置いた値をコードバイトという。データ 11 22 00 33 00 00 44 を符号化する手順を、筆算のように示す。

0x00 はすべてコードバイト（1 以上の値）に置き換わるので、符号化した列の中に 0x00 は現れない。受け手は、図の最下段のように、先頭のコードバイトから始めて、コードバイトの値だけ先へ飛びながら元に戻す。コードバイトは 1 バイトなので、表せる距離は 1〜255 である。0x00 を含まない並びが長く続くと、距離が 255 を超えてしまう。そこで、0x00 でないバイトが 254 個続いたら、そこで区切ってコードバイト 0xFF を置き、「続く 254 バイトの後には 0x00 は無い（その次のバイトは単に次のコードバイトである）」という意味にする。コードバイト 1 つと、それに続く 0x00 でないバイトの組を、ここではブロックと呼ぶ。ブロックの終わり方は、次の 3 通りである。

受け手は、コードバイト c を読んだら続く \(c - 1\) バイトを写し、c が 0xFF でなく、しかも列の終わりでなければ 0x00 を 1 つ出して（列の終わりなら、それは仮の 0x00 なので出さない）、次のバイトを次のコードバイトとして読む。コードバイトが 0 だったり、列の終わりを越える先を指したりしたら、壊れたフレームとして捨てる。送り手の符号化を C で書くと次のようになる。

/* in[0..n-1] を COBS で符号化して out に書き、書いたバイト数を返す
   （区切りの 0 は含まない）。out には n + n/254 + 1 バイトの空きが要る */
size_t cobs_encode(const uint8_t *in, size_t n, uint8_t *out)
{
    size_t code_pos = 0, k = 1;          /* out[0] はコードバイトの場所 */
    uint8_t code = 1;                    /* (ブロックの 0 でないバイトの数) + 1 */
    for (size_t i = 0; i < n; i++) {
        if (in[i] == 0) {                /* 0 はコードバイトに置き換わる */
            out[code_pos] = code;
            code_pos = k++;
            code = 1;
        } else {
            out[k++] = in[i];
            if (++code == 0xFF) {        /* 0 を含まずに 254 バイト続いた */
                out[code_pos] = code;
                code = 1;
                if (i + 1 == n) return k;    /* データの終わりなら空のブロックを足さない */
                code_pos = k++;
            }
        }
    }
    out[code_pos] = code;
    return k;
}

254 個たまった所でちょうどデータが終わったときは、空のブロック（コードバイト 0x01 だけ）を足さずに終える（足しても受け手は同じデータに戻せるが、1 バイト長くなる）。受け手は 0x00 が届くまでのバイトをためておき、0x00 が届いたら元に戻せばよい。0x00 はフレームの中に現れないので、SLIP の END と同じく、境目を見失っても次の 0x00 で同期し直せる。

増える量を導く

以下、\(\lceil x \rceil\) は x 以上の最も小さい整数を表す。

方針: 符号化した列（区切りの 0x00 を除く）の長さを、ブロックの数で表す。ブロックの数は、上の図の 3 通りの終わり方を数えれば分かる。

導出: データを n バイト（\(n \ge 1\)）、その中の 0x00 の数を z とする。符号化した列は、ブロックごとのコードバイトと、写した 0x00 でないバイト（\(n - z\) 個）からなる。ブロックは、0x00 の手前で終わるものが z 個、254 個たまって終わるもの（コードバイト 0xFF）が F 個、データの終わりで終わるものが 1 個ある。ただし、254 個たまった所でちょうどデータが終わったときは、その 0xFF のブロックが最後のブロックを兼ねるので 1 個少ない。このときだけ \(\delta = 1\)、ほかは \(\delta = 0\) とすると、ブロックの数は \(z + F + 1 - \delta\) なので、符号化した列の長さは

\[ (n - z) + (z + F + 1 - \delta) = n + 1 + F - \delta \]

で、増える量は \(g = 1 + F - \delta\) である。0xFF のブロックには 0x00 でないバイトが 254 個ずつ入るので、\(254F \le n\) である。

  • \(\delta = 1\) のとき: \(g = F \le n/254\) なので \(g \le \lceil n/254 \rceil\)。最後のブロックが 0xFF のブロックなので \(F \ge 1\)、つまり \(g \ge 1\) でもある。
  • \(\delta = 0\) のとき: \(254F = n\) となるのは、データに 0x00 が無く、すべてのバイトが 0xFF のブロックに入ってデータが終わる場合で、それは \(\delta = 1\) の場合なので、ここでは \(254F < n\)、すなわち \(F < n/254\) である。\(n/254\) より小さい整数のうち最大のものは \(\lceil n/254 \rceil - 1\) なので \(F \le \lceil n/254 \rceil - 1\) で、\(g = 1 + F \le \lceil n/254 \rceil\)。\(g \ge 1\) は明らかである。

どちらの場合も \(1 \le g \le \lceil n/254 \rceil\) が成り立つ ∎

上限に等しくなるのは、データに 0x00 が無く、F が最も多くなるときである。n が 254 以下なら \(\lceil n/254 \rceil = 1\) なので、増える量はデータの中身によらずちょうど 1 バイトで、区切りの 0x00 を加えたフレームの長さはいつも \(n + 2\) バイトになる。送信用のバッファは、区切りを含めて \(n + \lceil n/254 \rceil + 1\) バイトあれば足りる。

その代わり、COBS の送り手は、コードバイトを書くために次の 0x00 の位置（最大で 254 バイト先）を知っている必要があり、SLIP のように、データを 1 バイトずつその場で置き換えて送り出すことはできない。

下の図で 16 進のデータを入れると、SLIP と COBS で符号化した列と、それぞれ何バイト増えたかが表示される。データが短いときは、COBS のコードバイトがどこを指すかも矢印で表示される。

4. 長さを先に送る方式と、その弱点

区切り文字を使わずに、フレームの先頭近くに「この後に何バイト続くか」を書いておく方法もある。この値を入れる欄を長さフィールドという。受け手は長さフィールドを読めばどこまで読めばよいかが分かるので、置き換えは要らない。ただし、境目を見失った受け手には、どのバイトが長さフィールドなのかが分からない。そこで、フレームの先頭に決まった値のバイトの並びを置き、受け手はそれを探してフレームの始まりとする。この並びを同期パターン（マジックとも）という。

この例では、同期パターンを AA 55、長さフィールドを 1 バイトとし、最後に CRC を 2 バイト付けている。CRC は、送り手がフレームの中身から計算して付ける値で、受け手は同じ計算をし直して付いてきた値と比べ、届いたバイトが壊れていないかを確かめる（計算のしかたは 5 節）。

この方法には、置き換えが要らないことと、受け取る前にフレームの長さが分かることという利点がある。長さが分かれば、受け取る場所を用意したり、決まった数のバイトを CPU を使わずに受け取る仕組み（04 章の DMA）を使ったりできる。TCP もバイトの流れしか運ばない（11 章）ので、その上の MQTT（13 章）なども、メッセージの先頭に長さを置いている。

長さが化けると

この方法の弱点は、長さフィールドが壊れたときに現れる。

1 つ目のフレームの長さ 0x04 が、雑音で 0x0C（12）に化けたとする。受け手は 12 バイトのペイロードと 2 バイトの CRC を読もうとして、2 つ目のフレームの途中までを飲み込み、CRC が合わないので捨てる。問題はその後で、読み終えた位置から同期パターンを探し直すと、2 つ目のフレームの同期パターンはすでに通り過ぎているので、壊れていない 2 つ目のフレームまで失う。長さが 0x44（68）に化ければ、その後のいくつものフレームを飲み込み、送り手がそれ以上送らなければ、来ないバイトを待ち続ける。また、置き換えをしないので、同期パターンと同じ並びがペイロードの中に現れうる。境目を見失った受け手は、ペイロードの中の AA 55 を同期パターンと誤ることがある（その場合も、たいていは CRC が合わないので捨てられる）。対策は 4 つある。

  • 長さの上限を確かめる: ペイロードの最大の長さを決めておき（受信バッファの大きさ以下にする）、それを超える長さを読んだら、すぐにそのフレームを捨てる。0x44 に化けた場合は、上限を 16 としておけばここで気づく。
  • ヘッダにも CRC を付ける: 同期パターンと長さだけから計算した 1 バイトの CRC を長さの直後に置けば、ペイロードを読む前に長さの誤りに気づける。0x0C のように上限の内側に化けた場合も見つけられる。
  • 探し直す位置を戻す: フレームを捨てたら、読み終えた位置からではなく、捨てたフレームの同期パターンの次のバイトから探し直す。そのために、受け取ったバイトをすぐには捨てずにとっておく。
  • 待つ時間に上限を設ける: 同期パターンを見つけてから決まった時間がたっても残りが届かなければ、そのフレームを捨てて探し直す。決まった時間が過ぎたら待つのをやめるこの仕組みを、タイムアウトという（05 章で詳しく扱う）。

待つ時間の目安は、フレームが届くのにかかる時間から決める。115200 bps・8N1 では 1 バイトに 86.8 µs かかる（02 章 2 節）。ペイロードの上限を 16 バイトとすると、フレーム全体は \(2 + 1 + 16 + 2 = 21\) バイトで、\(21 \times 86.8\ \text{µs} \approx 1.8\) ms で届く。送り手の処理の遅れも見込んで、たとえば 10 ms を待つ時間の上限にする。

下の図で、フレーミングの方式と、起きること（1 バイトの書き換え・1 バイトの喪失・途中から聞き始める）とその位置を選ぶと、受け手がどこでフレームを捨て、どこで同期し直し、4 つのメッセージのうちいくつを受け取れたかが表示される。どの方式も、ペイロードの後ろに CRC を付けてあり、CRC が合わないフレームは受け手が捨てる。長さフィールドの方式では、上の対策のうち 3 つを入れたり外したりできる（メッセージ 3 のペイロードには、同期パターンと同じ AA 55 が入っている）。

5. 誤りに気づく — チェックサムと CRC

線の上の雑音で、ビットが反転することがある。02 章のパリティは 1 バイトの中の 1 ビットの反転に気づく方法だったが、2 ビットの反転は見逃し、8N1 のようにパリティを付けない使い方も多い。そこで、フレーム全体から計算した値を付けて送る。受け手が、届いたデータが送り手の送ったものと違うことに気づくことを誤り検出という。送り手はデータから決まった計算で求めた値をフレームに付け、受け手は届いたデータから同じ計算をして、付いてきた値と比べる。一致しなければ、途中のどこかが壊れている。

チェックサム — バイトを足す

最も簡単な計算は、データのバイトを足し合わせることである。データのバイトの和（または、それに似た簡単な計算の結果）をチェックサムという。ここでは、和を 256 で割った余り（8 ビットに収まる和）を考える。データ 12 34 56 なら \(\mathtt{0x12} + \mathtt{0x34} + \mathtt{0x56} = \mathtt{0x9C}\) である。

誤りが 1 つのバイトの中だけで起きたなら、何ビット反転しても、8 ビットの和は必ず気づく。バイトの値が a から a' に変わると和は \(a' - a\) だけ変わり、\(a' - a\) は 0 でなく大きさが 255 以下なので、256 の倍数にならないからである。しかし、2 つ以上のバイトにまたがる誤りには、見逃すものがある。

足し算は順番によらないので、バイトが入れ替わっても和は変わらない。また、2 つのバイトの同じ桁のビット（ビット k）が、一方では 0 から 1 に、他方では 1 から 0 に反転すると、一方は \(2^k\) 増え、他方は \(2^k\) 減るので、和は変わらない。

CRC — 割り算の余り

足し算の代わりに割り算の余りを使うと、バイトの順番やビットの位置が結果に効くようになる。これが CRC（Cyclic Redundancy Check、巡回冗長検査）である。CRC では、ビットの列を、係数が 0 か 1 の多項式とみなす。左端のビットを最も高い次数の係数とし、たとえば 1101 は \(x^3 + x^2 + 1\) を表す。係数どうしの計算は 2 で割った余りで行う（\(1 + 1 = 0\)）ので、足し算も引き算も XOR になり、繰り上がりも繰り下がりも起きない。このような多項式の割り算は、筆算で「割る数の左端を、残っている列の左端の 1 にそろえて XOR し、次のビットを下ろす」ことの繰り返しになる。

CRC で割る数として使う多項式を生成多項式という。生成多項式の次数を r とすると、余りは r ビットになる。送り手は、データの後ろに 0 を r 個並べて生成多項式で割り、その余りを 0 の代わりにデータの後ろに付けて送る。受け手は、届いたビットの列全体を生成多項式で割り、余りが 0 なら誤りなし、0 でなければ誤りありと判定する。生成多項式を \(x^3 + x + 1\)（ビット列 1011、r = 3）として、データ 1101 を送る例を示す。

送り手が付けた余りによって、送る列全体が割り切れるようになる理由を確かめる。

方針: データを \(m(x)\)、生成多項式を \(g(x)\) とし、送り手の割り算の結果を式に書いて、送るビット列 \(T(x)\) に代入する。

導出: データの後ろに 0 を r 個並べたものは \(x^r m(x)\) である（x を 1 回掛けるごとに、ビット列は 1 ビット左にずれ、右端に 0 が入る）。これを \(g(x)\) で割った商を \(q(x)\)、余りを \(R(x)\) とすると、\(x^r m(x) = q(x)\, g(x) + R(x)\) である。送るビット列は、並べた 0 の代わりに余りを付けたものなので \(T(x) = x^r m(x) + R(x)\) で、これに上の式を代入すると

\[ T(x) = q(x)\, g(x) + R(x) + R(x) = q(x)\, g(x) \]

となる。係数を 2 で割った余りで計算するので、\(R(x) + R(x) = 0\) だからである。よって、\(T(x)\) は \(g(x)\) で割り切れる ∎

反転したビットの位置に 1 を立てたビット列を \(E(x)\) とすると、受け手に届くのは \(T(x) + E(x)\) である。和を割った余りは、それぞれを割った余りの和に等しく、\(T(x)\) の余りは 0 なので、受け手の余りは \(E(x)\) を \(g(x)\) で割った余りに等しい。したがって、CRC が誤りを見逃すのは、\(E(x)\) が 0 でなく、\(g(x)\) で割り切れるときだけである。

連続した何ビットかの範囲の中だけで起きた誤りをバースト誤りといい、最初に反転したビットから最後に反転したビットまでのビットの数を、その長さという。線の上の雑音は、続けて何ビットかをまとめて壊すことが多い。長さ b のバースト誤りの \(E(x)\) は、次数が \(b - 1\) の多項式に x のべきを掛けた形をしている。\(b \le r\) ならその多項式の次数は r より小さく、0 でない \(g(x)\) の倍数の次数は r 以上なので、\(g(x)\) の倍数にはならない。そのため、生成多項式の右端のビット（定数項）が 1 なら、長さ r 以下のバースト誤りは必ず見つかる（x のべきを掛けても割り切れるようにならないことの証明は、暗号と誤り訂正シリーズ 09 章 4 節）。CRC-16 なら長さ 16 ビット以下、CRC-32 なら 32 ビット以下のバースト誤りを、すべて見つける。誤りの形がでたらめなら、見逃す割合はおよそ \(2^{-r}\) である（同じ節）。

パラメータと検査値

生成多項式は、最も高い次数の項（係数は必ず 1）を省いた r ビットを 16 進で書く。たとえば 0x1021 は \(x^{16} + x^{12} + x^5 + 1\) を表す。同じ生成多項式を使っても、実装によって計算の細部が違い、値が合わないことがある。違いは、生成多項式と次の 3 つにまとめられる（暗号と誤り訂正シリーズ 09 章 6 節）。

  • 初期値: 割り算を始める前に、余りとして置いておく値。上の筆算は 0 から始めた場合にあたる。0 のままだと、データの先頭に 0x00 のバイトが増えても余りが変わらない（先頭の 0 は割り算に効かない）ので、0 以外の値にして、先頭の 0x00 の増減にも気づけるようにする。
  • 入力の反転・出力の反転: 各バイトのビットを LSB から順に割り算に入れるか（入力の反転。反転しなければ MSB から）と、最後の余りのビットの順番を逆にして出すか（出力の反転）。UART も Ethernet も 1 バイトを LSB から送る（02 章 2 節）ので、入力を反転すると、割り算に入れる順番が線の上の順番と同じになり、線の上で続けて起きた誤りが、そのままバースト誤りとして扱われる。
  • 最終 XOR: 最後に余りに XOR する値。末尾に 0x00 のバイトが増えたことにも気づけるようにするために使う（同じ節）。

ASCII の文字列 "123456789"（9 バイト 31 32 33 34 35 36 37 38 39）の CRC を検査値といい、パラメータの一覧に載っている。自分の実装が検査値を返せば、パラメータが合っていると確かめられる。同じ計算が別の名前で呼ばれることもあるので、名前ではなくパラメータと検査値で確かめる。

実装

筆算の各段で見ているのは、いまの余り（r ビット）と次に下ろすビットだけである。そこで余りを r ビットの変数に入れておき、「左へずらし、左端からはみ出したビットが 1 なら、生成多項式の下位 r ビットを XOR する」を繰り返す。実際には、データを 1 バイトずつ余りの上位 8 ビットに XOR してから 8 回ずらす形で書く（これが筆算と同じ結果になることは暗号と誤り訂正シリーズ 09 章 5 節）。表の CRC-16/CCITT-FALSE を書くと次のようになる。

/* CRC-16/CCITT-FALSE（生成多項式 0x1021、初期値 0xFFFF、反転なし、最終 XOR 0） */
uint16_t crc16_bitwise(const uint8_t *p, size_t n)
{
    uint16_t crc = 0xFFFF;                               /* 初期値 */
    for (size_t i = 0; i < n; i++) {
        crc ^= (uint16_t)(p[i] << 8);                    /* 次の 8 ビットを上位に XOR */
        for (int b = 0; b < 8; b++)                      /* はみ出すビットが 1 なら */
            crc = (crc & 0x8000) ? (uint16_t)((crc << 1) ^ 0x1021)   /* ずらして XOR */
                                 : (uint16_t)(crc << 1);
    }
    return crc;                                          /* 最終 XOR は 0 */
}

1 バイトあたり 8 回の繰り返しの結果は、余りの上位 8 ビットとデータのバイトの XOR（256 通り）だけで決まる。そこで 256 通りの結果を前もって表にしておけば、1 バイトあたり 1 回の表引きで済む。

static uint16_t crc16_tab[256];          /* i を上位 8 ビットに置いて 8 回ずらした結果 */

void crc16_make_table(void)
{
    for (int i = 0; i < 256; i++) {
        uint16_t c = (uint16_t)(i << 8);
        for (int b = 0; b < 8; b++) c = (c & 0x8000) ? (uint16_t)((c << 1) ^ 0x1021) : (uint16_t)(c << 1);
        crc16_tab[i] = c;
    }
}
uint16_t crc16_table(const uint8_t *p, size_t n)
{
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < n; i++) crc = (uint16_t)((crc << 8) ^ crc16_tab[(crc >> 8) ^ p[i]]);
    return crc;
}

どちらの関数も "123456789" に対して検査値 0x29B1 を返す。表は 512 バイト（2 バイト × 256）で、値を書いた const の配列にすれば、RAM ではなくフラッシュメモリに置ける。速さとメモリのどちらを優先するかで、2 つの実装を選ぶ。入力と出力を反転する CRC は、右へずらす形で書き、ビットの順番を逆にした生成多項式（CRC-32 なら 0xEDB88320）を XOR すると、反転の操作そのものは要らなくなる（暗号と誤り訂正シリーズ 09 章 6 節にコードがある）。

チェックサムと CRC を比べる

16 バイトのデータに 4 つの方法で値を付け、いろいろな形の誤りを入れて、見逃した割合を数えた結果を示す。

8 ビットの和は、ばらばらの 2 ビットの反転を約 7 % 見逃し、バイトの入れ替えにはまったく気づけない。CRC は r ビット以下のバースト誤りをすべて見つけ、それより長い誤りの見逃しもほぼ \(2^{-r}\) にとどまる。誤り検出は、気づくだけで直さない。受け手は壊れたフレームを捨て、失ったメッセージをどうするかは上の層の決まりによる（送り直してもらう仕組みは 05 章）。また、CRC は偶然に起きた誤りに気づくためのもので、わざと書き換えられたデータには役に立たない。計算方法が公開されていて、書き換えた人が CRC も計算し直せるからである（暗号と誤り訂正シリーズ 09 章 7 節）。書き換えを防ぐには、送り手と受け手だけが知る秘密の値（鍵）を使う仕組みが要る（12 章の TLS）。

下の図で、データと誤りの形を選んで誤りを入れると、4 つの方法がそれぞれ気づいたかどうかが表示される。「1 万回試す」を押すと、データを毎回乱数で作って同じ形の誤りを 1 万回入れ、見逃した割合が表示される。

6. 数値の並べ方 — エンディアンと構造体

ここからは、ペイロードの中身の作り方を見る。2 バイト以上の数値を送るには、そのバイトをどの順番で並べるかを決めなければならない。

32 ビットの値 0x12345678 は、4 つのバイト 0x12・0x34・0x56・0x78 からなる。数値をメモリやバイトの列に並べるときの、バイトの順番の決まりをエンディアンという。下位のバイト（0x78）から並べるのがリトルエンディアン、上位のバイト（0x12）から並べるのがビッグエンディアンである。多くのマイコン（Arm Cortex-M や RISC-V を使ったものなど）と PC は、リトルエンディアンでメモリに置く。

プロトコルでは、どちらの順番で送るかをプロトコルごとに決める。インターネットのプロトコル（IP・TCP・UDP のヘッダなど。07 章）はビッグエンディアンで送ると決めており、これをネットワークバイトオーダという。一方、BLE は多くの値をリトルエンディアンで送る（18 章）。4 節のフレームの 2 バイトの CRC も、どちらの順番で付けるかを決めておく必要がある。メモリの中身を書き出したものを読むときの見分け方は、バイナリ解析シリーズ 03 章 2 節にある。

構造体をそのまま送らない

C の構造体をメモリの上の形のまま送る（memcpy でバッファに写す、構造体へのポインタを送信の関数に渡す）と、次の 3 つの理由で、相手が正しく読めないことがある。

  1. 詰め物: コンパイラは、メンバをその大きさの倍数の番地に置くために、メンバの間や後ろに使わないバイトを入れることがある。入れ方は、コンパイラと CPU によって違う。
  2. エンディアン: 送り手と受け手の CPU のエンディアンが違えば、同じバイトの列から違う値を読む。
  3. 型の大きさ: int は 16 ビットの CPU では 2 バイト、32 ビットの CPU では 4 バイトである。long も環境によって 4 バイトか 8 バイトになる。

図の構造体は、PC の gcc（x86-64）や Cortex-M のコンパイラでは、5 バイトの詰め物が入って 12 バイトになる。8 ビットのマイコン向けのコンパイラには詰め物を入れないものがあり、その場合は 7 バイトになる（詰め物の規則はバイナリ解析シリーズ 03 章 4 節）。

そこで、送る形（どの値を、何バイトで、どの順番で並べるか）をプロトコルとして決め、値を 1 バイトずつ組み立てる。メモリの上のデータを、送るためのバイトの列に直すことをシリアライズという。次の関数はシフトと代入だけで書いてあるので、CPU のエンディアンにかかわらず同じバイトの列を作り、同じ値を読む。

static void put_le16(uint8_t *p, uint16_t v) { p[0] = (uint8_t)v; p[1] = (uint8_t)(v >> 8); }
static void put_le32(uint8_t *p, uint32_t v) { for (int i = 0; i < 4; i++) p[i] = (uint8_t)(v >> (8 * i)); }
static void put_be32(uint8_t *p, uint32_t v) { for (int i = 0; i < 4; i++) p[i] = (uint8_t)(v >> (24 - 8 * i)); }
static uint16_t get_le16(const uint8_t *p) { return (uint16_t)(p[0] | (p[1] << 8)); }
static uint32_t get_be32(const uint8_t *p)
{
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) | ((uint32_t)p[2] << 8) | p[3];
}
/* 2 の補数の 16 ビットを符号付きの値に直す */
static int16_t as_int16(uint16_t u)
{
    return (u < 0x8000u) ? (int16_t)u : (int16_t)((int32_t)u - 0x10000);
}

/* 図の struct reading を送る形（type 1 | time_s 4 | temp_c100 2。どれもリトルエンディアン）に */
static void reading_put(uint8_t out[7], const struct reading *r)
{
    out[0] = r->type;
    put_le32(&out[1], r->time_s);
    put_le16(&out[5], (uint16_t)r->temp_c100);
}

1 バイトずつ読み書きするので、番地が 4 の倍数でない所から 4 バイトの値を読むこともできる（4 バイトをまとめて読むと、番地によっては例外になる CPU もある）。get_be32 で (uint32_t) を付けているのは、uint8_t の値は int に直されてからずらされるので、0x80 以上の値を 24 ビット左へずらすと 32 ビットの int の範囲を超え、C では未定義の動作になるからである。as_int16 は、0x8000 以上の値を負の数（2 の補数）として読み直す。受け手は、get_le16 のような関数で、同じ順番に値を組み立て直す。

小数を送る — 固定小数点

温度の 23.45 °C のような小数は、float（4 バイト）のまま送ることもできるが、組み込みの通信では、決まった倍率を掛けた整数にして送ることが多い。たとえば温度に 100 を掛けて 2345 とし、int16_t（2 バイト）で送る。受け手は 100 で割って元に戻す。このように、整数に決まった倍率を掛けた値で小数を表す方法を固定小数点という。

倍率を s、整数の型を int16_t（−32768〜32767）とすると、表せる範囲は \(-32768/s\)〜\(32767/s\)、刻みは \(1/s\) である。s = 100 なら −327.68〜327.67 °C を 0.01 °C 刻みで、s = 10 なら −3276.8〜3276.7 °C を 0.1 °C 刻みで表せる。必要な範囲と刻みから、倍率と型を決める。float より短く、浮動小数点の計算の回路を持たないマイコンでも速く扱える。

整数にするときは、切り捨てずに四捨五入する。図の 16.05 °C のように、10 進の小数の多くは 2 進では正確に表せないので、100 を掛けた結果がわずかに小さくなり、切り捨てると 1 だけ小さい値になるからである。

/* 温度 [°C] を × 100 の整数にする（四捨五入。範囲外は端の値にする） */
static int16_t temp_to_c100(float t)
{
    long v = lroundf(t * 100.0f);
    return (int16_t)(v > INT16_MAX ? INT16_MAX : v < INT16_MIN ? INT16_MIN : v);
}

7. 可変長のデータ — TLV

6 節の reading のように、何バイト目に何の値があるかを固定した形は、後から項目を足すのが難しい。新しいファームウェアが項目を 1 つ足すと、古い受け手は、その後ろの値をずれた位置から読んでしまう。いつも送るとは限らない項目にも、場所を空けておかなければならない。そこで、項目ごとに、何の値か（型）、値が何バイトか（長さ）、値そのものを並べる形がよく使われる。この形を、型（Type）・長さ（Length）・値（Value）の頭文字をとって TLV という。

TLV の受け手は、知らない型の項目に出会っても、長さを見てその値を読み飛ばせる。そのため、送り手が新しい型の項目を足しても、古い受け手は知っている項目だけを読み続けられる。項目の順番も自由で、無い項目は送らなくてよい。

長さを確かめてから読む

TLV の長さも、4 節の長さフィールドと同じく、化けたり、わざと書き換えられたりする。長さを信じたまま読むと、受け取ったバイトの列の外（ほかの変数の場所など）を読んでしまう。

読む前に、残りのバイトの数と比べて確かめる。

struct tlv {
    uint8_t type, len;
    const uint8_t *val;                  /* 値の先頭（p の中を指す） */
};

/* p[*pos..n-1] から TLV を 1 つ読む（*pos <= n であること）。
   戻り値: 1 = 読めた（*pos は次の項目へ進む）、0 = 列の終わり、-1 = 形が壊れている */
int tlv_next(const uint8_t *p, size_t n, size_t *pos, struct tlv *t)
{
    size_t i = *pos;
    if (i == n) return 0;
    if (n - i < 2) return -1;            /* 型と長さの 2 バイトが無い */
    t->type = p[i];
    t->len  = p[i + 1];
    if (t->len > n - i - 2) return -1;   /* 値が列の終わりを越える */
    t->val = &p[i + 2];
    *pos = i + 2 + t->len;
    return 1;
}

n - i - 2 は、その前に \(n - i \ge 2\) を確かめてあるので、符号なしの引き算でも負にならない（符号なしの型で負になるはずの引き算をすると、非常に大きな値になってしまう）。受け手は tlv_next が 1 を返す間、型を見て値を取り出し、知らない型は何もせずに次へ進む。型ごとに決まった値の長さ（温度なら 2）も確かめ、合わなければ、tlv_next が -1 を返したときと同じく、そのメッセージを途中まで読めた値も含めて捨てる。

tlv_next とそれを使う解析に、乱数で作った 30 万個の入力（壊れた長さを多く含む）を与え、配列の外の読み書きを見つける gcc の機能（AddressSanitizer）で確かめたところ、配列の外は一度も読まなかった。一方、長さを確かめない解析は、図の例の入力だけで、配列の外を読んだと報告された。乱した入力を大量に与えて確かめるこの方法は、23 章で扱う。

TLV には、並べ方の違う形もある。BLE の機器が周りに存在を知らせるために送るデータ（アドバタイズのデータ。17 章）は、長さを先に置き、長さに型の 1 バイトを含める。IP アドレスを借りる手順（DHCP。08 章）のオプションは、ここで見たのと同じ型・長さ・値の順である。長さが 1 バイトなら値は 255 バイトまでなので、それより長い値を許すプロトコルは、長さを 2 バイトにしたり、長さそのものを可変長にしたりする（13 章の MQTT）。

下の図で、送る項目と壊し方を選ぶと、TLV のバイトの列と、長さを確かめる解析・確かめない解析が、それぞれどこまで読んだかが表示される。

8. まとめ

項目内容
メッセージ・フレーム・ペイロードアプリケーションが 1 回に送るデータのまとまり／それを送るために区切りや検査の値を付けたバイトの列（UART のフレームとは別）／フレームの中のメッセージそのもの
フレーミングバイトの流れの中にフレームの境目を書き込む決まり。境目を見つけられることと、見失っても同期し直せることが要る
SLIP区切り文字 END = 0xC0。データの 0xC0 は DB DC、0xDB は DB DD に置き換える。最悪の長さは 2n + 2 バイト
COBS区切り文字は 0x00。データの 0x00 を、次の 0x00 までの距離（コードバイト）に置き換える。増えるのは 1〜⌈n/254⌉ バイトで、n ≤ 254 ならちょうど 1 バイト
長さフィールド同期パターン + 長さ + ペイロード + CRC。長さが化けると後のフレームまで失う。上限の確認・ヘッダの CRC・探し直す位置・待つ時間の上限で防ぐ
チェックサムバイトの和。1 バイトの中の誤りは必ず見つけるが、入れ替えや打ち消し合う誤りを見逃す
CRCビットの列を多項式とみなした割り算の余り。長さ r 以下のバースト誤りをすべて見つけ、ほかの誤りの見逃しもおよそ \(2^{-r}\)。生成多項式・初期値・入力と出力の反転・最終 XOR を、検査値（"123456789" の CRC）で確かめる
エンディアン・シリアライズリトルエンディアン（下位のバイトから）とビッグエンディアン（上位から。ネットワークバイトオーダ）。構造体をそのまま送らず、送る形を決めて 1 バイトずつ組み立てる
固定小数点決まった倍率を掛けた整数で小数を送る（温度 × 100 を int16_t）。整数にするときは四捨五入する
TLV型・長さ・値の並び。知らない型は読み飛ばせるので、後から項目を足せる。長さは残りのバイトの数と比べてから使う
