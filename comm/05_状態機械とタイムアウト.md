# 05. 状態機械とタイムアウト — 確認応答と再送を組み立てる

> **この章で扱う問い.**
> 03 章ではバイトの列をメッセージに区切り、壊れたメッセージに気づく方法を、04 章では届いたバイトを取りこぼさずに受け取る方法を見た。しかし通信では、送ったメッセージが途中で失われることも、相手が答えないこともある。この章では、相手の応答を待ち、来なければ送り直す、という手順を、ファームウェアとして組み立てる。
>
> この章では次の 3 つの問いに答える。
>
> 1. 「送る・待つ・応答によって分かれる」手順を、いつ何が起きても破綻しないように書くには、どうすればよいか。
> 2. 応答が来ないことに、いつ、どう気づくのか。失われたメッセージを、重複させずにどう送り直すのか。
> 3. 多くの機器の送り直しが重なったときや、ファームウェアそのものが止まったときに、どう立て直すのか。
>
> 答えの道具は、状態機械、ティックで測るタイムアウト、番号付きの確認応答と再送、指数バックオフとジッタ、そしてウォッチドッグタイマである。

## 1. 手順を状態と遷移で表す — 状態機械

通信の多くは、要求と応答の組で進む。例として、マイコン（親機）が、UART でつないだセンサの子機に測定値を問い合わせる手順を考える。子機は READ というコマンド（03 章の形で区切ったメッセージ）を受け取ると、測定値を入れた応答を返す。ただし、メッセージが途中で壊れて捨てられたり（03 章 5 節）、子機が止まっていたりすると、応答は来ない。そこで、手順を次のように決める。

- 応答を最大 100 ms 待つ。来なければ、もう一度送る。
- 3 回送っても応答がなければ、子機をリセットし（リセットの信号線を操作する）、500 ms 待ってから、依頼した処理に失敗を知らせる。
- 子機が「測れない」というエラーの応答を返したら、失敗を知らせる。

このように、待つ時間に上限を決めておき、それを過ぎたら待つのをやめて次の動作に移ることを**タイムアウト**という。時間の測り方は 3 節で扱う。

### 順に書いた形と、その限界

この手順は、送る関数と応答を待つ関数を順に呼べば、そのまま書ける。

```c
/* 順に書いた形: 送って、待って、来なければ送り直す */
int read_sensor(int16_t *val)
{
    struct resp r;
    for (int i = 0; i < MAX_TRIES; i++) {
        send_cmd();
        if (wait_resp(&r, T_RESP)) {      /* 応答が来るか、T_RESP たつまで戻らない */
            if (!r.ok) return -1;         /* エラーの応答 */
            *val = r.val;
            return 0;
        }
    }
    reset_slave();                        /* 3 回とも応答なし */
    delay_ms(T_RESET);
    return -1;
}
```

`send_cmd`・`wait_resp`・`reset_slave`・`delay_ms` は、この章で仮に置く関数である（`wait_resp` は応答が届けば 1 を、`T_RESP` ミリ秒たっても届かなければ 0 を返す）。`MAX_TRIES` は 3、`T_RESP` は 100、`T_RESET` は 500 とする。

手順が 1 つだけなら、これで動く。しかし `wait_resp` は応答が来るか時間切れになるまで戻らないので、その間マイコンはほかの仕事ができない。待つ間にボタンやサーバからの命令にも応じようとすると、待つループの中に、ほかの仕事を書き足すことになる。

```fig
e05_nest
```

書き足した仕事がそれ自体も応答を待つ手順なら、待つループの中に、もう 1 つ待つループができる（図の左）。内側のループで待っている間にセンサの応答が届いても、それを外側の手順に渡す場所がない。

もう 1 つの問題は、手順が終わった後に起きる出来事である。1 回目の応答が 100 ms を少し過ぎて届いた場合を考える。

```fig
e05_shift
```

`read_sensor` は、遅れて届いた 1 回目の応答を送り直しへの応答として受け取って戻る。その後に届く送り直しへの応答は、誰にも読まれずに受信バッファに残り、次の依頼の応答として読まれる。順に書いた形では、「いつ、どの順で起きるか分からない出来事」を手順のどこで扱うかが、書かれていない。

### 状態・イベント・遷移・動作

そこで、手順を次の 4 つの言葉で表し直す。

- **状態**: 手順がいまどの段階にいるか。あらかじめ決めた有限個の状態のうち、いつもどれか 1 つにいる。この例では「待機」「応答待ち」「リセット待ち」の 3 つである。
- **イベント**: 状態を変えるきっかけになる出来事。この例では「依頼が来た」「応答（正常）が届いた」「応答（エラー）が届いた」「時間切れ」の 4 つである。
- **遷移**: イベントによって、ある状態から次の状態へ移ること。同じ状態にとどまる遷移もある。
- **動作**: 遷移のときに行う処理。コマンドを送る、タイマを始める（決めた時間の後に時間切れのイベントが起きるようにする）、結果を渡す、などである。

この 4 つで手順を表したものを**状態機械**（有限状態機械）という。状態を箱、遷移を矢印で描いた図を**状態遷移図**という。この例の状態遷移図は次のとおりである。

```fig
e05_fsm
```

応答待ちで時間切れが起きたとき、送った回数が 3 未満なら応答待ちにとどまって送り直し、3 ならリセット待ちへ移る。このように、同じイベントでも条件によって行き先が分かれるときは、条件を [ ] の中に書く。

状態とイベントのすべての組み合わせについて、動作と次の状態を書いた表を**状態遷移表**という。この例の状態遷移表は次のとおりである（→ の後は次の状態。書いていなければ同じ状態にとどまる）。

| 状態 ＼ イベント | 依頼 | 応答（正常） | 応答（エラー） | 時間切れ |
|---|---|---|---|---|
| 待機 | 送る、回数 = 1、タイマ 100 ms → 応答待ち | 捨てる（遅れて届いた応答） | 捨てる | 起きない（タイマは止まっている） |
| 応答待ち | 「使用中」と答える | 結果を渡す → 待機 | エラーを渡す → 待機 | 回数 < 3 なら、送り直す、回数 + 1、タイマ 100 ms。回数 = 3 なら、子機をリセット、タイマ 500 ms → リセット待ち |
| リセット待ち | 「使用中」と答える | 捨てる | 捨てる | 失敗を渡す → 待機 |

図では矢印を引かなかった組み合わせも、表では欄が空かないので、扱いを決めることになる。たとえば「待機」で「応答」が届く欄は、上の取り違えの図で、送り直しへの応答が手順の終わった後に届いた場合にあたる。ここを「捨てる」と決めておけば、待機中に届いた古い応答が、次の依頼の応答と取り違えられることはない。ただし、次の依頼の「応答待ち」の間に古い応答が届く場合まで見分けるには、依頼と応答に番号を付ける必要がある（4 節のシーケンス番号）。

### 実装 — switch による形と、表による形

状態機械は、イベントを 1 つ受け取るたびに呼ばれる関数として書く。`switch` で状態ごとに分ける形を示す。

```c
enum state { ST_IDLE, ST_WAIT, ST_RESET };                   /* 待機・応答待ち・リセット待ち */
enum event { EV_REQ, EV_RESP_OK, EV_RESP_ERR, EV_TIMEOUT };  /* 依頼・応答（正常）・応答（エラー）・時間切れ */
struct fsm { enum state st; int tries; uint32_t deadline; };

void fsm_handle(struct fsm *m, enum event ev)
{
    switch (m->st) {
    case ST_IDLE:
        if (ev == EV_REQ) {                          /* 応答・時間切れは捨てる */
            send_cmd(); m->tries = 1; start_timer(m, T_RESP); m->st = ST_WAIT;
        }
        break;
    case ST_WAIT:
        if (ev == EV_REQ) reply_busy();
        else if (ev == EV_RESP_OK)  { report(1); m->st = ST_IDLE; }
        else if (ev == EV_RESP_ERR) { report(0); m->st = ST_IDLE; }
        else if (m->tries < MAX_TRIES) {             /* 時間切れ: まだ送り直せる */
            send_cmd(); m->tries++; start_timer(m, T_RESP);
        } else {                                     /* 時間切れ: 3 回とも応答なし */
            reset_slave(); start_timer(m, T_RESET); m->st = ST_RESET;
        }
        break;
    case ST_RESET:
        if (ev == EV_REQ) reply_busy();
        else if (ev == EV_TIMEOUT) { report(0); m->st = ST_IDLE; }
        break;                                       /* 応答は捨てる */
    }
}
```

`fsm_handle` は、動作をして状態を書き換えたら、すぐに戻る。中で待つことはない。応答を待っていることは、状態 `ST_WAIT` として覚えている。`start_timer` は期限（`deadline`）を覚えるだけの関数で、期限が来たら `EV_TIMEOUT` を渡す仕組みは 3 節で作る。`reply_busy`（「使用中」と答える）と `report`（結果を渡す）も、この章で仮に置く関数である。

同じ状態機械を、状態遷移表をそのまま配列にした形でも書ける。表の各欄には、動作をして次の状態を返す関数を入れる。

```c
typedef enum state (*action)(struct fsm *m);       /* 動作をして、次の状態を返す */
static enum state a_start(struct fsm *m)  { send_cmd(); m->tries = 1; start_timer(m, T_RESP); return ST_WAIT; }
static enum state a_retry(struct fsm *m)
{
    if (m->tries >= MAX_TRIES) { reset_slave(); start_timer(m, T_RESET); return ST_RESET; }
    send_cmd(); m->tries++; start_timer(m, T_RESP); return ST_WAIT;
}
static enum state a_ok(struct fsm *m)     { (void)m; report(1); return ST_IDLE; }
static enum state a_fail(struct fsm *m)   { (void)m; report(0); return ST_IDLE; }
static enum state a_busy(struct fsm *m)   { reply_busy(); return m->st; }
static enum state a_ignore(struct fsm *m) { return m->st; }

static const action TABLE[3][4] = {
    /*             依頼     応答（正常） 応答（エラー） 時間切れ */
    [ST_IDLE]  = { a_start, a_ignore,   a_ignore,     a_ignore },
    [ST_WAIT]  = { a_busy,  a_ok,       a_fail,       a_retry  },
    [ST_RESET] = { a_busy,  a_ignore,   a_ignore,     a_fail   },
};

void fsm_handle_table(struct fsm *m, enum event ev)
{
    action a = TABLE[m->st][ev];                    /* 表の欄を引いて */
    m->st = a(m);                                   /* 動作をし、次の状態に移る */
}
```

表の形では、状態やイベントを足すときに、配列の行や列を足し、すべての欄を埋めることになる。条件で行き先が分かれる遷移（応答待ちの時間切れ）は、動作の関数 `a_retry` が次の状態を選んで返す。2 つの形は同じ動きをする（乱数で作った 2 万通りのイベントの列で、動作と状態の列が一致することを確かめてある）。状態と遷移が少ないうちは `switch` の形が読みやすく、多くなったら表の形のほうが、抜けている組み合わせに気づきやすい。

下の図でイベントのボタンを押すと、状態機械が 1 回ずつ遷移し、状態遷移図と状態遷移表の該当する所が強調される。

## 2. 待ち方 — ブロッキング・ノンブロッキング・イベント駆動

1 節の `wait_resp` のように、呼んだ関数が、待っている出来事が起きるまで戻らないことを**ブロッキング**という（その関数は「ブロックする」という）。反対に、その時点で受け取れるものだけを返し、何もなければ「まだない」と返して、すぐに戻ることを**ノンブロッキング**という。04 章のリングバッファから読む関数を、空なら 0 バイトを返してすぐ戻るように作れば、ノンブロッキングになる。

同じ出来事の列に対して、3 つの待ち方を比べる。

```fig
e05_wait
```

- **ブロッキングで応答だけを待つ**と、その間に起きたほかの出来事（ボタン）への対応は、応答が来るまで遅れる。RTOS を使わない場合は、待つ関数の中で CPU が回り続ける。RTOS を使う場合は、待つ間そのタスクは止まり、ほかのタスクが動くが、そのタスク自身は、待っている出来事以外には応じられない。
- **ノンブロッキングの関数をループで繰り返し呼ぶ**（04 章 1 節のポーリング）と、ほかの出来事にも応じられる。ただし、何も起きていない間も確かめ続けるので CPU は眠れず、対応の遅れはループ 1 周の時間で決まる。
- 3 つ目は、何かが起きるまで眠り、起きた出来事を 1 つずつ処理する方式である。割り込みハンドラ（04 章）やタイマが、何が起きたかを知らせ、プログラムはそれに応じた処理を呼ぶ。このように、出来事が起きたときに、それに応じた処理を呼ぶ作り方を**イベント駆動**という。出来事を 1 つ取り出し、処理し、次の出来事を待つことを繰り返すループを**イベントループ**という（1 節の図の右の「出来事を配るループ」がこれにあたる）。

イベントループも、次の出来事を待つ間は止まっている。ブロッキングで応答だけを待つ場合との違いは、どの出来事が起きても戻ることである。1 節の状態機械は、イベントを受け取ってすぐ戻るので、イベントループからそのまま呼べる。手順がいくつあっても、イベントループが出来事をそれぞれの状態機械に渡せばよい。何も起きていない間は CPU を眠らせられるので、電池で動く機器の間欠動作（01 章 5 節）とも相性がよい。

出来事の知らせ方として、ドライバやライブラリに関数を登録しておき、出来事が起きたときに、その関数を呼んでもらう形もよく使われる。このように登録しておいて、後で呼ばれる関数を**コールバック**という。たとえば UART のドライバに「メッセージを 1 つ受け取ったら、この関数を呼ぶ」と登録しておく。コールバックは、割り込みハンドラの中や、ライブラリが持つタスクの中から呼ばれることが多いので、長い処理や待つ処理を書いてはいけない。出来事をキューに入れるだけにして、処理はイベントループで行うのが安全である。後の章で使う TCP/IP スタックや BLE のスタックの多くも、コールバックで出来事を知らせる（11・18 章）。

### 通信路の持ち主を 1 つのタスクに決める

RTOS を使う場合、処理を複数のタスクに分ける（01 章 4 節）。測定をするタスクと、設定を変えるタスクが、どちらも子機と通信したいとする。それぞれのタスクが UART に直接書くと、次の図の上のようになる。

```fig
e05_owner
```

2 つのタスクが続けて送ると、メッセージのバイトが混ざる。応答が届いたときに、どちらのタスクが読むかも決まらない。ミューテックス（[OS シリーズ 12 章](../freertos/12_セマフォとミューテックス.md#ミューテックス-所有者がいる-ロック)）で 1 つのタスクずつに限れば、バイトが混ざることは防げる。しかし、応答を待つ間ずっとほかのタスクを止めることになり、依頼と関係なく届くメッセージ（無線モジュールからの通知など。06 章 3 節）を受け取るタスクもいない。

そこで、1 つの通信路（UART・無線モジュール・ソケットなど）の送受信を、すべて 1 つのタスクに任せる。このタスクを、この章では**通信タスク**と呼ぶ。ほかのタスクは通信路に触らず、通信タスクのキュー（[OS シリーズ 11 章](../freertos/11_キュー.md#キューとは何か)）に依頼を入れる。通信タスクはイベントループで、依頼・受信したメッセージ・時間切れを 1 つずつ状態機械に渡し、結果を依頼したタスクに返す（返事用のキューや、タスク通知（[OS シリーズ 14 章](../freertos/14_タスク通知とイベントグループ.md#タスク通知-tcb-に直接書き込む)）を使う）。受信の側では、UART の割り込みハンドラがバイトをリングバッファに入れて通信タスクに知らせ（04 章）、通信タスクがメッセージを 1 つ取り出すたびに、それをイベントとして状態機械に渡す。こうすると、

- 送受信が 1 か所で順に行われるので、バイトが混ざらない。
- どの依頼の応答を待っているかを、1 つの状態機械が知っている（1 節の「使用中」の判断もここで行う）。
- 依頼と関係なく届くメッセージも、通信タスクが受け取って振り分けられる。

## 3. タイムアウトとタイマ

1 節の状態機械は、期限が来たら「時間切れ」のイベントを受け取る必要がある。そのためには、今の時刻を知る仕組みと、期限を過ぎたかを判定する方法が要る。

### ティック — 時刻を数える

時刻は、マイコンの周辺回路のタイマ（決まった間隔で割り込みを起こせる回路）で数える。タイマを 1 ms ごとに割り込みを起こすように設定し、その割り込みハンドラで変数を 1 ずつ増やす。この 1 増える時間の単位を**ティック**といい、変数の値（それまでに数えたティックの数）を、その時点の時刻として使う。RTOS を使う場合は、RTOS 自身がティックを数えているので、それを使えばよい（FreeRTOS では `xTaskGetTickCount()`。[OS シリーズ 08 章](../freertos/08_ティックとタイムスライス.md)）。1 節の `start_timer(m, t)` は、期限 `m->deadline = tick_now() + t` を覚えるだけの関数になる。つまり 1 節の「タイマ」は、手順ごとに周辺回路のタイマを 1 つずつ使うのではなく、1 つのティックのカウンタと比べる期限の値として持つ。

ティックで測る時間には、1 ティック分の幅がある。期限を「今 + k ティック」にすると、今を読んだのが 1 ティックの区間のどこだったかによって、実際の待ち時間は k − 1 ティックより長く、k ティック以下になる。少なくとも k ティック待ちたいときは、1 を足しておく。

32 ビットのマイコンでは、32 ビットの変数は 1 回の命令で読めるので、読んでいる途中で割り込みハンドラが値を書き換えることはない。8 ビットや 16 ビットのマイコンでは、読む間だけ割り込みを止める（04 章 4 節のクリティカルセクション）。

### 一周するカウンタと、期限の比較

32 ビットのカウンタは、$`2^{32}`$ ティックで一周して 0 に戻る。1 ティックが 1 ms なら、$`2^{32}`$ ms ≈ 49.7 日である。機器は何か月も動き続けるので、一周は必ず起きる。

期限を過ぎたかを `now >= deadline` で判定すると、一周の前後で誤る。たとえば今のティックが 0xFFFFFFF0 のときに、0x20 ティック（32 ms）先を期限にすると、和 0x1_0000_0010 の下位 32 ビットをとって、期限は 0x00000010 になる。今の 0xFFFFFFF0 はこれより大きいので、`now >= deadline` は待ち始めた瞬間に成り立ち、32 ms 待たずに時間切れになる。そこで、差 `now - deadline` を符号付きの数として読む。

| now | deadline | now >= deadline | now - deadline（uint32_t） | int32_t として読んだ値 | 期限を過ぎたか |
|---|---|---|---|---|---|
| 0xFFFFFFF0 | 0x00000010 | 成り立つ（誤り） | 0xFFFFFFE0 | −32 | まだ |
| 0x00000005 | 0x00000010 | 成り立たない | 0xFFFFFFF5 | −11 | まだ |
| 0x00000010 | 0x00000010 | 成り立つ | 0x00000000 | 0 | 過ぎた |
| 0x00000020 | 0x00000010 | 成り立つ | 0x00000010 | 16 | 過ぎた |

```fig
e05_wrap
```

表のとおり、符号付きで読んだ差の符号が、期限の前か後かを正しく表している。これがいつでも成り立つ条件を求める。

**方針**: カウンタが一周しないとした本当のティックの数を、整数 $`N`$（今）と $`D`$（期限）とする。カウンタに入っているのは、それぞれを $`2^{32}`$ で割った余りである。`(int32_t)(now - deadline)` が $`N - D`$ に等しくなる条件を求め、そのとき符号で前後が分かることを示す。

**導出**:

1. `uint32_t` どうしの引き算は、$`2^{32}`$ を法として行われる（C の符号なし整数の演算は一周する）。したがって `now - deadline` の値 $`u`$ は、$`0 \le u < 2^{32}`$ で、$`u \equiv N - D \pmod{2^{32}}`$ を満たす。
2. 32 ビットの 2 の補数では、同じビットの並びを符号付きとして読むと、$`u < 2^{31}`$ なら $`u`$、$`u \ge 2^{31}`$ なら $`u - 2^{32}`$ になる。どちらの場合も、読んだ値 $`r`$ は $`-2^{31} \le r < 2^{31}`$ の範囲にあり、$`r \equiv u \equiv N - D \pmod{2^{32}}`$ である。
3. ここで、今と期限が $`2^{31}`$ ティックより離れていない、すなわち $`-2^{31} \le N - D < 2^{31}`$ とする。この範囲には $`2^{32}`$ 個の整数があり、そのうち $`2^{32}`$ を法として $`N - D`$ と等しいものは $`N - D`$ ただ 1 つである。$`r`$ も同じ範囲にあり、$`N - D`$ と等しい（法 $`2^{32}`$）ので、$`r = N - D`$ となる。
4. したがって、$`N < D`$（まだ）なら $`r < 0`$、$`N \ge D`$（過ぎた）なら $`r \ge 0`$ である ∎

この条件から、使い方の決まりが 2 つ出てくる。

- 期限は、今から $`2^{31}`$ ティック未満の先に置く。1 ティックが 1 ms なら、約 24.8 日未満である。
- 期限を過ぎてから $`2^{31}`$ ティックたつ前に判定する。それより後に判定すると、$`r`$ が負に戻り、「まだ」と読まれる。

なお、C の規格では、`int32_t` で表せない値（$`2^{31}`$ 以上）を `int32_t` に変換した結果は処理系定義である。gcc をはじめ多くのコンパイラは、上の 2 の補数の読み方をする。規格の範囲だけで書きたいときは、`(uint32_t)(now - deadline) < 0x80000000u` と書けば同じ判定になる。

```c
static volatile uint32_t g_tick;              /* 1 ms ごとのタイマ割り込みで 1 増やす */

void timer_isr(void) { g_tick++; }            /* 周期のタイマ割り込みのハンドラ */
uint32_t tick_now(void) { return g_tick; }

/* now が deadline に達したか（期限までの距離が 2^31 ティック未満であること） */
int tick_reached(uint32_t now, uint32_t deadline)
{
    return (int32_t)(now - deadline) >= 0;
}
```

経過時間 `now - start` を待つ時間と比べる書き方（[OS シリーズ 08 章](../freertos/08_ティックとタイムスライス.md)）も、同じ理由で一周に強い。期限で持つ書き方は、覚える値が 1 つで済み、2 つの期限のどちらが先かも同じ形の式（`(int32_t)(d1 - d2) < 0` なら d1 が先）で比べられる。03 章 4 節の、同期パターンを見つけてからフレームの残りを待つ時間の上限も、同期パターンを見つけたときに期限を決め、`tick_reached` で確かめれば作れる。

### イベントループに期限を組み込む

2 節のイベントループに、期限を組み込む。通信タスクは、次の処理を繰り返す。

```c
static int has_deadline(const struct fsm *m) { return m->st != ST_IDLE; }   /* 応答待ち・リセット待ち */

/* 通信タスクの 1 回分の処理。実際には for (;;) comm_step(&m); と繰り返す */
void comm_step(struct fsm *m)
{
    uint32_t now = tick_now();
    if (has_deadline(m) && tick_reached(now, m->deadline)) {
        fsm_handle(m, EV_TIMEOUT);                    /* 期限を過ぎた */
        return;
    }
    uint32_t wait = has_deadline(m) ? m->deadline - now : WAIT_FOREVER;
    struct comm_ev ev;
    if (os_queue_get(&ev, wait))                      /* 何かが来るか、期限まで眠る */
        fsm_handle(m, ev.type);
}
```

`os_queue_get` は、この章で仮に置く関数で、通信タスクのキューに出来事が来るか、`wait` ティックたつまでタスクを眠らせ、出来事を受け取れば 1、何も来なければ 0 を返す（FreeRTOS の `xQueueReceive` にあたる）。`struct comm_ev` はキューに入る出来事で、`type` にイベントの種類を入れる。期限のある状態では、眠る時間を期限までの残り `m->deadline - now` にする（期限の前なので、この差は $`2^{31}`$ 以下の正の数になる）。期限の判定を先に行っているのは、依頼などの出来事が途切れなく届いても、時間切れが後回しにならないようにするためである。このコードは、カウンタが一周する直前から始めて、時間切れ・送り直し・リセット待ちが正しい時刻に起きることを、PC の上で確かめてある（時刻を返す関数を差し替えてテストする方法は 23 章）。

## 4. 確認応答と再送 — ストップアンドウェイト

1 節の手順は、応答がなければ同じコマンドを送り直した。この節では、データを相手に確実に届けるための送り直しの仕組みを、一般的な形で組み立てる。

受け手は、メッセージを正しく受け取ったら、そのことを知らせる短いメッセージを送り手に返す。これを**確認応答**（**ACK**、acknowledgement）という。届いたメッセージが壊れていた（CRC が合わなかった。03 章 5 節）ことを知らせるメッセージを**否定応答**（**NAK**）という。送り手は、決めた時間のうちに ACK が来なければ、同じメッセージをもう一度送る。これを**再送**という。確認応答・タイムアウト・再送の組み合わせで、失われたメッセージを届け直す方式を **ARQ**（Automatic Repeat reQuest、自動再送要求）という。ARQ のうち最も簡単な、1 つ送ったら、その ACK が届くまで次を送らない方式を**ストップアンドウェイト**という。

NAK を使うと、壊れたことがすぐに分かるので、時間切れを待たずに再送できる。ただし、壊れ方によっては、受け手は何かが届いたことさえ分からない。そのため NAK を使う場合でも、時間切れによる再送は欠かせない。この節では ACK と時間切れだけで組み立てる。

```fig
e05_arq
```

(b) ではデータが失われ、送り手は時間切れで再送する。(c) ではデータは届いたが ACK が失われた。送り手から見ると (b) と区別がつかないので、同じように再送し、受け手には同じデータが 2 回届く。同じメッセージが 2 回以上届くことを**重複**という。データが「カウンタを 1 増やす」「弁を開ける」のような操作だと、重複は誤動作になる。

### 1 ビットのシーケンス番号

重複を見分けるために、送り手はメッセージに番号を付ける。メッセージを見分けるために付ける番号を**シーケンス番号**という。ストップアンドウェイトでは、0 と 1 を交互に使う 1 ビットの番号で足りる。受け手は次に来るはずの番号を覚えておき、その番号のメッセージなら受け取って番号を進め、もう一方の番号なら重複として捨てる。どちらの場合も ACK は返す（重複に ACK を返さないと、送り手は再送を続ける）。

```fig
e05_seq
```

1 ビットで足りる理由を確かめる。

**方針**: 受け手が k 番目（0 から数える）のメッセージを待っているとき、届きうるのは k − 1 番目か k 番目の写しだけであることを示す。この 2 つは k の偶奇が違うので、番号の最下位ビットだけで区別できる。前提は 2 つある。(1) 通信路は、メッセージを失うことはあっても、順番を入れ替えない（送った順に届く）。(2) 送り手は、k 番目への ACK を受け取るまで k + 1 番目を送らない。

**導出**:

1. k + 1 番目以降の写しは、まだ存在しない。送り手が k + 1 番目を送るのは k 番目への ACK を受け取った後で、その ACK は受け手が k 番目を受け取ったときにしか送られない。受け手はまだ k 番目を待っているので、その ACK は送られていない。
2. k − 2 番目以前の写しは、もう届かない（k = 0 なら、それより前のメッセージはないので、この場合は考えなくてよい。以下 k ≥ 1 とする）。受け手は k − 1 番目の写しを 1 つ受け取っている。送り手は k − 2 番目以前の写しをすべて、k − 1 番目を初めて送る前に送り終えているので、受け取った k − 1 番目の写しより先に送られている。前提 (1) から、それらはその写しより先に届いたか、失われている。
3. したがって、届きうるのは k − 1 番目（受け取り済みのものの再送）か k 番目（新しいもの）であり、k を 2 で割った余りを番号にすれば区別できる ∎

ACK も同じ理由で、送り手に届きうるのは、今のメッセージへの ACK と、1 つ前のメッセージへの ACK だけである。そこで ACK にも番号を入れ、今のメッセージの番号の ACK だけを受け付ける（その必要性は、次の「タイムアウトの長さ」で見る）。この方式は交互ビットプロトコル（alternating bit protocol）とも呼ばれる。前提 (1) の成り立たない通信路、たとえば途中の経路で順番が入れ替わったり、ずっと遅れて届いたりすることのあるインターネットでは、1 ビットでは足りない。TCP は 32 ビットの番号を使う（10 章）。

送り手と受け手のコードを示す。`link_send_data`・`link_send_ack`（03 章の形で区切り、CRC を付けて送る）・`link_failed`・`deliver` は、この章で仮に置く関数である。

```c
#define MAX_MSG   64
#define MAX_TRIES 5
#define T_ACK     20u          /* ACK を待つ時間 [ティック]（送る時間 + RTT より長く） */

struct saw_tx {
    uint8_t  seq;              /* 今のメッセージの番号（0 か 1） */
    uint8_t  busy;             /* ACK を待っている間 1 */
    uint8_t  tries;            /* 送った回数 */
    uint32_t deadline;         /* ACK を待つ期限 */
    uint8_t  buf[MAX_MSG];     /* ACK が届くまで持ち続ける写し */
    size_t   len;
};

int saw_send(struct saw_tx *t, const uint8_t *msg, size_t len)
{
    if (t->busy || len > MAX_MSG) return -1;     /* 前のメッセージがまだ確認されていない */
    memcpy(t->buf, msg, len); t->len = len;
    t->busy = 1; t->tries = 1;
    link_send_data(t->seq, t->buf, t->len);
    t->deadline = tick_now() + T_ACK;
    return 0;
}

void saw_on_ack(struct saw_tx *t, uint8_t ack_seq)
{
    if (t->busy && ack_seq == t->seq) {          /* 今のメッセージへの ACK */
        t->busy = 0; t->seq ^= 1;                /* 次のメッセージは反対の番号 */
    }                                            /* それ以外（古い ACK）は捨てる */
}

void saw_poll(struct saw_tx *t)                 /* 期限に（または定期的に）呼ぶ */
{
    if (!t->busy || !tick_reached(tick_now(), t->deadline)) return;
    if (t->tries >= MAX_TRIES) {                 /* 諦める。番号のそろえ直しは上の層で */
        t->busy = 0; link_failed(); return;
    }
    link_send_data(t->seq, t->buf, t->len);      /* 再送: 番号は変えない */
    t->tries++; t->deadline = tick_now() + T_ACK;
}
```

```c
struct saw_rx { uint8_t expect; };              /* 次に来るはずの番号 */

void saw_on_data(struct saw_rx *r, uint8_t seq, const uint8_t *msg, size_t len)
{
    if (seq == r->expect) {                      /* 新しいメッセージ */
        deliver(msg, len); r->expect ^= 1;
    }                                            /* 1 つ前の番号なら重複: 渡さずに捨てる */
    link_send_ack(seq);                          /* どちらの場合も ACK は返す */
}
```

送り手は、再送できるように、ACK が届くまでメッセージの写し（`buf`）を持ち続ける。`MAX_TRIES` 回送っても ACK が来なければ、諦めて上の層に知らせる。このとき、受け手が最後のメッセージを受け取ったかどうかは分からない（ACK だけが失われたのかもしれない）。送り手と受け手の番号がずれている可能性があるので、通信を続ける前に、両方の番号を 0 に戻す手順（接続のやり直しなど）が要る。このコードは、データと ACK をそれぞれ 30 % の確率で失う模擬の通信路で、50 個のメッセージを 2000 回送り、すべてが 1 回ずつ順に渡されることを確かめてある（`MAX_TRIES` を十分大きくした場合）。

### タイムアウトの長さと往復時間

送り手がメッセージを送り終えてから、それへの ACK を受け取り終えるまでの時間を**往復時間**（**RTT**、round-trip time）という。RTT は、信号が伝わる時間（01 章 3 節の遅延の一部）の往復分、受け手の処理時間、ACK を送る時間の和である。以下、メッセージを送るのにかかる時間（長さ ÷ 速さ）を $`T_\mathrm{f}`$、タイムアウト（送り始めてから再送するまでの時間。コードの `T_ACK`）を $`T_\mathrm{o}`$ と書く。

ACK は、送り始めてから $`T_\mathrm{f}`$ + RTT 後に届く。したがって $`T_\mathrm{o}`$ が $`T_\mathrm{f}`$ + RTT より短いと、何も失われていなくても再送してしまう。再送した写しは受け手で重複として捨てられるが、線の時間を余分に使う。ACK に番号がなければ、さらに悪いことが起きる。1 回目の写しへの ACK が遅れて届くと、送り手はそれを次のメッセージへの ACK と取り違え、次のメッセージが失われていても再送しない（模擬の通信路で、番号のない ACK・短すぎる $`T_\mathrm{o}`$・データの喪失 10 % とすると、1 万個のうち 841 個が気づかれずに失われた。番号付きでは 0 個）。逆に $`T_\mathrm{o}`$ が長すぎると、失われたときに再送するまでの待ちが長くなる。RTT が大きく揺れる通信路では、測った RTT から $`T_\mathrm{o}`$ を決め直す（TCP の RTO の計算。10 章）。

### 効率

ストップアンドウェイトは、ACK を待つ間は何も送らない。この待ちが、線をどれだけ無駄にするかを求める。

```fig
e05_eff
```

**方針**: 何も失われないとき、1 つのメッセージは「送る時間」と「ACK を待つ時間（RTT）」で 1 周期になる。1 周期のうち、データを送っている時間の割合を求める。

**導出**: 送り手は時刻 0 に送り始め、$`T_\mathrm{f}`$ で送り終える。ACK は $`T_\mathrm{f}`$ + RTT に届き、送り手はすぐに次のメッセージを送り始める。1 周期 $`T_\mathrm{f}`$ + RTT のうち、データを送っているのは $`T_\mathrm{f}`$ なので、線を使う効率 $`\eta`$ は

$$
\eta = \frac{T_\mathrm{f}}{T_\mathrm{f} + \mathrm{RTT}}
$$

である ∎

**例 1（UART）**: 115200 bps・8N1 では 1 秒に 11520 バイト送れる（02 章 2 節）。64 バイトのメッセージなら $`T_\mathrm{f}`$ = 64 ÷ 11520 s ≈ 5.556 ms である。ACK を 8 バイト（0.694 ms）、受け手の処理を 1 ms（代表値）とし、数 m の線を伝わる時間は無視すると、RTT ≈ 1.694 ms、$`\eta`$ = 5.556 ÷ (5.556 + 1.694) ≈ 76.6 % となる。

**例 2（インターネットの先のサーバ）**: 1 Mbps の回線で 100 バイトを送ると $`T_\mathrm{f}`$ = 0.8 ms、RTT を 100 ms（代表値）とすると $`\eta`$ = 0.8 ÷ 100.8 = 0.79 % である。1 秒に送れるのは 1 ÷ 0.1008 s ≈ 9.9 個（約 990 バイト）で、回線を速くしても、ほとんど増えない。RTT が送る時間よりずっと長いときは、ACK を待たずに続けて送る方式が要る（10 章のスライディングウィンドウ）。

失われる場合も考える。データが失われる確率を $`p_\mathrm{d}`$、ACK が失われる確率を $`p_\mathrm{a}`$ とし、どの送信の喪失も互いに独立とする。1 回送って ACK まで届く確率は $`s = (1 - p_\mathrm{d})(1 - p_\mathrm{a})`$ である。

**方針**: 1 つのメッセージに要る時間の期待値を、失敗した送信と成功した送信に分けて足す（$`T_\mathrm{o} > T_\mathrm{f}`$ + RTT とする）。

**導出**: 失敗した送信は、送り始めてから再送まで $`T_\mathrm{o}`$ かかり、成功した送信は $`T_\mathrm{f}`$ + RTT かかる。成功するまでに送る回数 $`J`$ が $`j`$ になる確率は、$`j - 1`$ 回失敗して最後に成功する確率 $`(1 - s)^{j-1} s`$ である。その期待値は、和の公式 $`\sum_{j \ge 1} j x^{j-1} = 1/(1 - x)^2`$（$`|x| < 1`$）に $`x = 1 - s`$ を入れて

$$
E[J] = \sum_{j \ge 1} j (1 - s)^{j-1} s = \frac{s}{s^2} = \frac{1}{s}
$$

となる。失敗した送信の回数の期待値は $`E[J] - 1 = 1/s - 1`$ なので、1 つのメッセージに要る時間の期待値は

$$
E[T] = \left(\frac{1}{s} - 1\right) T_\mathrm{o} + T_\mathrm{f} + \mathrm{RTT}
$$

である ∎ 効率は $`T_\mathrm{f} / E[T]`$ になる。例 1 で $`p_\mathrm{d} = p_\mathrm{a}`$ = 5 %、$`T_\mathrm{o}`$ = 20 ms とすると、$`s`$ = 0.9025、$`E[T]`$ = 0.108 × 20 + 7.25 = 9.41 ms、効率は 59.0 % に下がる（乱数による模擬でも 9.4 ms になる）。5 回送っても届かずに諦める確率は $`(1 - s)^5 \approx 8.8 \times 10^{-6}`$ である。

## 5. 再送の間隔 — 指数バックオフとジッタ

4 節の再送は、1 組の送り手と受け手の間の話だった。ここでは、多くの機器が同じサーバにつながっている場合を考える。サーバが止まると、すべての機器がほぼ同時に通信の失敗に気づき、接続をやり直そうとする（接続のやり直しの手順は 15 章）。1 台ごとには正しい手順でも、全台が同じ規則で動くと問題が起きる。

### 待ち時間を 2 倍ずつ延ばす

失敗するたびに、次に試みるまでの待ち時間を 2 倍（一般には決まった倍率）に延ばすことを**指数バックオフ**という。待ち時間が際限なく延びないように決めておく最大値を**上限**（**キャップ**）という。最初の待ち時間を $`b`$、上限を $`c`$ とすると、k 回目の試みの前の待ち時間は次のようになる。

$$
w_k = \min\left(c,\ b \cdot 2^{k-1}\right) \quad (k = 1, 2, \ldots)
$$

```fig
e05_waits
```

指数バックオフで、サーバへの試みがどれだけ減るかを数える。

**方針**: サーバが 1 時間止まっている間に、1 台の機器が何回試みるかを、$`b`$ = 1 s、$`c`$ = 64 s として数える（切断に気づいた時刻を 0 とする）。

**導出**: k 回目の試みの時刻は、待ち時間の和 $`w_1 + w_2 + \cdots + w_k`$ である。上限に達するまでは $`w_j = 2^{j-1}`$ s なので、等比数列の和から $`1 + 2 + \cdots + 2^{k-1} = 2^k - 1`$ [s] となる。$`w_7 = \min(64, 64)`$ で上限に達するので、6 回目の試みは $`2^6 - 1 = 63`$ s、それ以後は 64 s ごとである。$`63 + 64m \le 3600`$ を満たす最大の $`m`$ は 55 なので、1 時間の試みは 6 + 55 = 61 回である。1 s ごとに試みれば 3600 回なので、およそ 1/59 に減る ∎

上限は、サーバが戻ってから機器がつながるまでの遅れを抑える。サーバが戻った時刻から次の試みまでの待ちは、多くとも 1 回分の待ち時間、すなわち $`c`$ である。上限がないと、たとえば 11 回目の試み（$`2^{11} - 1`$ = 2047 s）の直後にサーバが戻っても、12 回目の試みは $`2^{12} - 1`$ = 4095 s で、30 分以上つながらない。

### 同じ規則で待つ機器は、同じ時刻に試み続ける

指数バックオフだけでは足りない。同じ時刻に切断に気づいた機器を並べてみる。

```fig
e05_sync
```

**方針**: 同じ時刻に失敗した N 台が、同じ規則で待つとき、k 回目の試みの時刻を比べる。

**導出**: どの機器も同じ $`w_1, w_2, \ldots`$ を使うので、k 回目の試みの時刻 $`w_1 + \cdots + w_k`$ は全台で等しい。間隔が延びても、N 台が同じ瞬間に試みることは変わらない。サーバには N 件の試みが同時に届き、その後しばらく何も届かない、が繰り返される ∎

そこで、待ち時間に乱数でばらつきを加える。これを**ジッタ**という。加え方には、決めた待ち時間に小さな乱数を足す方法（たとえば ±1 s。08 章の DHCP）や、最初の待ち時間を決めた値の 1〜1.5 倍の乱数で選ぶ方法（14 章の CoAP）、待ち時間の全体を 0 から $`\min(c,\ b \cdot 2^{k-1})`$ までの一様乱数にする方法がある。この章では、最後の方法を「全部をランダムに」と呼ぶ（英語では full jitter と呼ばれることが多い）。

「全部をランダムに」で、サーバに 1 秒あたりに届く試みの数を見積もる。$`W_k = \min(c,\ b \cdot 2^{k-1})`$ とし、$`W_k \ge 1`$ s とする。ある機器の k 回目の試みの時刻は、k − 1 回目の時刻から長さ $`W_k`$ の区間のどこかに、一様に選ばれる。k − 1 回目の時刻がどこであっても、決めた 1 秒の区間とその区間が重なる長さは 1 s 以下なので、その 1 秒に k 回目の試みが入る確率は $`1/W_k`$ 以下である。N 台について足せば、1 秒あたりの k 回目の試みは、平均 $`N / W_k`$ 件以下になる。たとえば N = 1000、$`W_k`$ = 64 s なら、k 回目の試みは同時に 1000 件届くのではなく、1 秒あたり平均 15.6 件以下に散らばる。

3 つの方式で、1000 台がつながり直すまでを計算した結果を示す。サーバは 30 s 止まり、戻った後は 1 秒に 50 件まで接続を受け付け、それを超える試みは断るとする。

```fig
e05_storm
```

- **固定の間隔**（1 s）では、止まっている間も毎秒 1000 件の試みが届く。戻った後は 1 秒に 50 台ずつつながり、49 s で全台がつながるが、試みは合計 39,500 件になる。
- **ジッタのない指数バックオフ**では、試みは減るが、1000 台が同じ瞬間に試み続ける。1 回の山で 50 台しかつながらず、次の山まで間隔が空くので、全台がつながるまでに 1215 s かかる。
- **指数バックオフ + 全部をランダムに**では、試みが散らばり、92 s で全台がつながる。試みの合計は 6,519 件と最も少ない（乱数の種を変えても 91〜94 s）。

再送や再接続の間隔には、TCP の再送タイマ（10 章）、DHCP（08 章）、CoAP（14 章）、クラウドへの再接続（15 章）のように、指数バックオフとジッタが広く使われている。

下の図で、台数・サーバが止まっている時間・サーバが 1 秒に受け付けられる数・方式・最初の待ち時間・上限を変えると、サーバに届く試みの数と、全台がつながるまでの時間が表示される。

## 6. ウォッチドッグ — 最後の砦

ここまでの仕組みは、相手が答えない、メッセージが失われる、といった通信の失敗に備えるものだった。しかし、ファームウェアそのものが止まることもある。ドライバが来ない合図を永久に待つ、2 つのタスクが互いを待って止まる（デッドロック。[OS シリーズ 19 章](../freertos/19_排他制御の設計.md#デッドロック)）、状態機械が期限のない状態に入ったまま出られなくなる、雑音で周辺回路がおかしな状態になる、などである。止まったプログラムは、自分で自分を立て直せない。

**ウォッチドッグタイマ**は、ソフトウェアから決まった時間ごとに知らせを受けないと、マイコンをリセットする回路である。この知らせを「キックする」という。中身は時間を数えるカウンタで、キックされるたびに数え直し、決めた時間（ウォッチドッグの時間）のうちにキックされなければリセットをかける。多くのマイコンが内蔵しており、CPU とは別の発振器で動くもの、一度動かし始めるとソフトウェアからは止められないものが多い（製品による）。ウォッチドッグの時間は、数 ms〜数十 s 程度の範囲で設定できることが多い（代表値）。

```fig
e05_wdt
```

### どこでキックするか

ファームウェアが止まったことをウォッチドッグで検出できるかどうかは、どこでキックするかで決まる。キックは「正しく動いている」ことの証拠になる場所で行う必要がある。

```fig
e05_kick
```

- **タイマ割り込みの中**でキックすると、タスクが止まっていても割り込みは動き続けるので、CPU ごと止まったときしか検出しない。
- **アイドル**（ほかに動くタスクがないときに動く、最も優先度の低い処理。[OS シリーズ 09 章](../freertos/09_アイドルタスクとフック.md)）でキックすると、どれかのタスクが CPU を使い続けたときは、アイドルが動けなくなるので検出できる。しかし、タスクが永久に待っている（眠っている）だけなら、アイドルは動くので検出しない。
- **監視タスク**を置き、各タスクが仕事を 1 回進めるたびに「チェックイン」（自分のビットを立てる）し、監視タスクが決まった周期で、全員のビットがそろっているときだけキックする形にすれば、永久に待っているタスクもチェックインしないので検出できる。
- それでも、通信タスクのループは回っているのに、状態機械が同じ状態から進まないことがある（期限を付け忘れた状態に入った場合など）。そこで通信タスクは、待機以外の状態に決めた時間より長くいるときは、チェックインしない。決めた時間は、正常な手順が 1 つの状態にとどまりうる最長の時間（1 節の例なら、応答待ちは 3 回送る間の 300 ms、リセット待ちは 500 ms）より長くする。

```c
#define WDT_COMM   (1u << 0)                 /* 監視するタスクごとのビット */
#define WDT_SENSOR (1u << 1)
#define WDT_ALL    (WDT_COMM | WDT_SENSOR)
#define MAX_BUSY   1000u                     /* 待機以外の状態にいてよい最長の時間 [ms] */

struct wdt_note { uint32_t missing; uint32_t comm_state; };
struct wdt_note g_note;                      /* 起動時に 0 にしない RAM の領域に置く（リンカの設定による） */
static volatile uint32_t g_alive;            /* チェックインしたタスクのビット */

void wdt_checkin(uint32_t bit)               /* 各タスクが、仕事が進んだときに呼ぶ */
{
    irq_disable();                           /* 読む・変える・書くの間に割り込まれないように */
    g_alive |= bit;
    irq_enable();
}

void supervisor_poll(uint32_t comm_state)    /* 監視タスクが一定の周期で呼ぶ */
{
    irq_disable();
    uint32_t a = g_alive;
    g_alive = 0;
    irq_enable();
    if ((a & WDT_ALL) == WDT_ALL) {
        wdt_hw_kick();                       /* 全員が進んでいた: ウォッチドッグを戻す */
    } else {                                 /* キックしない。誰が止まったかを残す */
        g_note.missing = WDT_ALL & ~a;
        g_note.comm_state = comm_state;
    }
}

/* 通信タスクは、手順が決めた時間の中で進んでいるときだけチェックインする */
void comm_checkin(const struct fsm *m)
{
    if (m->st == ST_IDLE || !tick_reached(tick_now(), m->since + MAX_BUSY))
        wdt_checkin(WDT_COMM);
}
```

`irq_disable`・`irq_enable`（割り込みを止める・戻す）と `wdt_hw_kick`（ウォッチドッグをキックする）は、この章で仮に置く関数である。`struct fsm` には、今の状態に入った時刻 `since` を足してある（状態が変わるたびに記録する）。`g_alive` は複数のタスクが読み・変え・書くので、その間に割り込まれないようにクリティカルセクション（04 章 4 節）にしている。通信タスクは、待機中で何も届かないときも、監視の周期より短い間隔で起きてチェックインするように、3 節の `os_queue_get` で眠る時間に上限を付ける。

あるタスクが止まってからリセットまでの時間は、多くとも「監視の周期 + ウォッチドッグの時間」である。止まる直前のチェックインで、次の監視までは 1 回キックされうるが、その次の監視からはキックされないからである。逆に、正常なのにリセットされないように、各タスクは監視の周期より短い間隔でチェックインし、監視の周期はウォッチドッグの時間より十分短くする。このコードは、監視の周期 250 ms・ウォッチドッグの時間 1 s で、通信タスクが止まった場合・状態機械が応答待ちから進まなくなった場合・センサのタスクが止まった場合のそれぞれで、リセットが起き、止まったタスクが記録されることを確かめてある。

下の図で、キックする場所と、3 s に起こす故障を選ぶと、各タスクの動き・キック・ウォッチドッグの残り時間と、リセットされるかどうかが表示される。通信タスク・センサのタスク・監視タスクの順に優先度（RTOS がどのタスクを先に動かすかの順位。[OS シリーズ 06 章](../freertos/06_スケジューリング方針.md)）が高いとする。

### リセットの理由を残す

ウォッチドッグによるリセットは、最後の手段である。相手が答えない、メッセージが失われる、といったよくある失敗は、ここまでの状態機械・タイムアウト・再送で扱い、ウォッチドッグに頼らない。それでもリセットが起きたなら、それは直すべき不具合なので、原因を調べられるように記録を残す。

- 多くのマイコンには、直前のリセットの原因（電源の投入・リセット端子・ウォッチドッグなど）を示すレジスタがある。起動の初めに読んで記録する。
- 監視タスクが書いた `g_note`（止まったタスク・通信の状態）は、起動時に 0 で初期化されない RAM の領域に置く（リンカの設定で用意する。名前は開発環境による）。電源を入れた直後は中身が不定なので、決まった値（マジック）と CRC（03 章 5 節）を一緒に書いて、正しく残っているかを確かめる。
- 記録は、次にサーバにつながったときに送る（ログの集め方は 23 章）。
- ウォッチドッグによるリセットが続けて起きる回数を数え、決めた回数を超えたら、通信を止めた安全な動作に入る、または前のファームウェアに戻す（22 章）。

## 7. まとめ

| 項目 | 内容 |
|---|---|
| 状態機械 | 状態・イベント・遷移・動作で手順を表す。イベントを 1 つ受け取ったら動作をしてすぐ戻り、待っていることは状態として覚える |
| 状態遷移表 | 状態 × イベントのすべての欄を埋めた表。遅れて届いた応答のような「起きないと思いがちな組み合わせ」の扱いも決まる。配列にすれば、そのまま実装になる |
| 待ち方 | ブロッキング（待つ出来事が起きるまで戻らない）、ノンブロッキング（すぐ戻る）、イベント駆動（何かが起きるまで眠り、イベントループで 1 つずつ処理する） |
| 通信タスク | 1 つの通信路の送受信を 1 つのタスクに任せ、ほかのタスクはキューで依頼する。バイトが混ざらず、応答の受け取り手も決まる |
| ティックと期限 | 期限 = 今 + 待つティック数。判定は `(int32_t)(now - deadline) >= 0`。今と期限が $`2^{31}`$ ティック未満しか離れていなければ、カウンタが一周しても正しい |
| ARQ | ACK が決めた時間のうちに来なければ再送する。ACK が失われると重複が起きる |
| ストップアンドウェイト | 1 つ送って ACK を待つ。順番の入れ替わらない通信路なら、1 ビットのシーケンス番号で重複を見分けられる。ACK にも番号を入れる |
| 効率 | 失われなければ $`T_\mathrm{f} / (T_\mathrm{f} + \mathrm{RTT})`$。失われるときの 1 メッセージの時間の期待値は $`(1/s - 1) T_\mathrm{o} + T_\mathrm{f} + \mathrm{RTT}`$ |
| 指数バックオフ・上限・ジッタ | 待ち時間を失敗のたびに 2 倍にし（試みが減る）、上限で止め（戻った後の遅れを抑える）、乱数でずらす（同時に試み続けるのを防ぐ） |
| ウォッチドッグ | キックされないとリセットする回路。全タスクと通信の手順が進んでいることを確かめてからキックし、リセットの理由を残す |
