# 13. MQTT — 小さな機器のためのパブリッシュとサブスクライブ

> **この章で扱う問い.**
> 08 章 5 節では、家庭のルータの NAT の内側にいる機器へは外から接続を始められないので、機器の側からサーバへ接続を張り、それを保つ必要があることを見た。10〜12 章では、その接続（TCP と TLS）の仕組みを見た。この章では、その接続の上で測定値と命令をやり取りするアプリケーション層のプロトコルとして、組み込み機器で広く使われている MQTT を扱う。
>
> この章では次の 3 つの問いに答える。
>
> 1. 送り手と受け手が互いを知らないまま、データを届け合うには、どんな仕組みにすればよいか。届け先は何で決まるのか。
> 2. MQTT のやり取りは、TCP のバイトの列の上でどんなバイトの列になるのか。届け方を確かにすると、何が増えるのか。
> 3. 接続が黙って切れたことに、機器とサーバはどう気づくのか。機器のファームウェアは、何を持ち、何を管理すればよいのか。
>
> 答えの道具は、トピックの照合の規則、残りの長さの符号化、05 章の確認応答と再送を当てはめた QoS の手順、そしてキープアライブの時間の計算である。

## 1. ブローカを介したパブリッシュとサブスクライブ

家の温湿度センサが 1 分ごとに測定値をクラウドへ送り、利用者のスマートフォンのアプリがそれを表示する。アプリからは機器へ「測る間隔を変える」などの命令を送る。測定値を受け取りたいものは 1 つとは限らず、値を蓄えるデータベースや、異常を知らせる警報のサービスも受け取りたい。

受け手のそれぞれが機器へ直接つなぐ形（図の上）では、2 つの問題が起きる。1 つは、送り手と受け手が互いの数と宛先を知っていなければならず、受け手が増えるたびに設定を変えることである。もう 1 つは、機器が NAT の内側にいるので、アプリやサービスの側から機器へ接続を始められないことである（08 章 5 節）。

```fig
e13_direct
```

そこで、全員が 1 つの中継のサーバへ接続を張り、データはそのサーバを通して届ける（図の下）。**MQTT** は、このための、TCP の上で動くアプリケーション層のプロトコルである。版 3.1.1 と 5.0 が、標準化団体 OASIS の標準になっている。この章は 3.1.1 を基本にし、5.0 との違いは 6 節で触れる。

- **ブローカ**: 中継するサーバ。受け取ったメッセージを、それを欲しがっているクライアントへ配る。
- **クライアント**: ブローカにつなぐもの。機器もアプリもデータベースもクライアントで、1 つのクライアントが送り手と受け手を兼ねてよい。
- **トピック**: メッセージに付ける名前（文字列）。`dev/1/temp` のように、/ で区切って階層を表す（2 節）。
- **メッセージ**（MQTT の）: トピック名と、運ぶデータ（03 章 1 節のペイロード）の組。
- **パブリッシュ**: クライアントが、トピック名を付けたメッセージをブローカへ送ること。
- **サブスクライブ**（**購読**）: クライアントが、受け取りたいトピックの範囲（トピックフィルタ。2 節）をブローカに登録しておくこと。購読しているクライアントを**購読者**という。ブローカは、パブリッシュされたメッセージのトピック名を登録と照らし合わせ、一致した購読者のそれぞれへ写しを送る。

クライアントは、ブローカへ TCP の接続を張り（ポート 1883。TLS を使うなら 8883。07 章 4 節）、その接続を保ったまま、パブリッシュと受信を行う。やり取りの例を図に示す。

```fig
e13_flow
```

図から、3 つのことが読み取れる。

1. **送り手は受け手を知らない。** 機器は `dev/1/temp` に送るだけで、誰が何人受け取るかを知らない。受け手を足しても、機器は何も変えなくてよい。一致する購読が 1 つも無ければ、ブローカはそのメッセージを捨てる（最後の値をブローカに覚えさせる保持メッセージは例外である。5 節）。
2. **下りも、機器が張った接続で届く。** アプリが送った命令は、機器がつないでいる接続を通って、ブローカから機器へ届く。機器から外へ向かう接続だけで上りと下りがそろうので、NAT の内側でも動く。
3. **接続の数は、送り手と受け手を足した数で済む。** 機器 N 台と受け手 M 個が直接つなぐと N × M 本の接続が要るが、ブローカを介せば N + M 本である。

その代わりに、ブローカはすべてのクライアントが頼る 1 点になる。ブローカが止まれば誰も届け合えない。どのクライアントがどのトピックに送り、どのトピックを受け取ってよいかの権限も、ブローカが管理する（2 節）。ブローカには、クラウドの事業者が提供するものや、オープンソースのもの（Eclipse Mosquitto など）がある。この章のバイト列と振る舞いは、手元で動かした Mosquitto 2.0.18 に実際に送って確かめてある。

## 2. トピックの設計

トピック名は UTF-8 の文字列で、/ で区切った 1 つ 1 つを**トピックレベル**（以下、レベル）という。`dev/1/temp` は `dev`・`1`・`temp` の 3 つのレベルからなる。大文字と小文字は区別し、空のレベルも 1 つのレベルとして数える（`dev//temp` は 3 レベル、`/dev` は空のレベルと `dev` の 2 レベル）。

購読のときに登録するのは、トピック名そのものではなく、一致するトピック名の範囲を表す**トピックフィルタ**（以下、フィルタ）である。フィルタには、1 つのレベル全体の代わりに置ける 2 つの**ワイルドカード**を使える。

- `+`: どんな 1 つのレベルにも一致する。`dev/+/temp` は `dev/1/temp` にも `dev/2/temp` にも一致するが、`dev/1/temp/raw` にはレベルの数が違うので一致しない。
- `#`: その位置から後のレベルすべてに一致する。0 個でもよいので、`dev/1/#` は `dev/1/temp` にも、親の `dev/1` にも一致する。フィルタの最後のレベルにだけ置ける。`#` だけのフィルタは、すべてのトピック名に一致する。

```fig
e13_tree
```

規則の細かい所を、実例の表で確かめる（MQTT 3.1.1 の 4.7 節。どの行も、Mosquitto で同じ結果になった）。

| フィルタ | トピック名 | 一致するか | 理由 |
|---|---|---|---|
| `dev/+/temp` | `dev/7/temp` | する | `+` が `7` に一致する |
| `dev/+/temp` | `dev/1/temp/raw` | しない | トピック名のレベルが 1 つ多い |
| `dev/+` | `dev/` | する | `+` は空のレベルにも一致する |
| `dev/+` | `dev` | しない | `+` に当たるレベルが無い |
| `dev/#` | `dev` | する | `#` は 0 個のレベル（親）にも一致する |
| `+` | `/dev` | しない | `/dev` は 2 レベル（空と `dev`） |
| `Dev/1/temp` | `dev/1/temp` | しない | 大文字と小文字を区別する |
| `#` | `$SYS/broker/uptime` | しない | `$` で始まる名前に、ワイルドカードで始まるフィルタは一致しない |
| `$SYS/#` | `$SYS/broker/uptime` | する | フィルタも `$` で始まれば一致する |

`$` で始まるトピック名は、ブローカが自分の情報を出すのに使う（Mosquitto は `$SYS/` の下に接続の数などを出す）。`#` で全部を購読しても、それが混ざらないようにするための規則である。フィルタの中でも、ワイルドカードはレベル全体を占めなければならず（`dev+` は誤り）、`#` は最後のレベルにしか置けない（`dev/#/temp` は誤り）。パブリッシュするトピック名には、ワイルドカードを使えない。規則に合わないフィルタやトピック名を送ると、ブローカは接続を切る（規則に反するパケットを受けた側は接続を閉じる、と 3.1.1 は定めている。Mosquitto でもそうなった）。

照合を C で書くと、次のようになる。フィルタとトピック名を、先頭からレベルごとに比べていく。

```c
/* フィルタ f がトピック名 t に一致すれば 1、しなければ 0 を返す（MQTT 3.1.1 の規則）。
   f は規則に合う（+ と # はレベル全体を占め、# は最後のレベルだけ）ものとする */
int topic_match(const char *f, const char *t)
{
    if ((*f == '+' || *f == '#') && *t == '$')
        return 0;                        /* $ で始まる名前に、ワイルドカードで始まるフィルタは一致しない */
    for (;;) {
        if (*f == '#')
            return 1;                    /* 残りのレベルすべて（0 個でもよい） */
        if (*f == '+') {                 /* t のレベルを 1 つ、中身によらず飛ばす */
            f++;
            while (*t != '\0' && *t != '/') t++;
        } else {                         /* ふつうのレベルは 1 文字ずつ比べる */
            while (*f != '\0' && *f != '/')
                if (*f++ != *t++) return 0;
            if (*t != '\0' && *t != '/') return 0;   /* t のレベルのほうが長い */
        }
        if (*f == '\0' || *t == '\0')    /* どちらかが終わった */
            return *f == *t || (f[0] == '/' && f[1] == '#' && f[2] == '\0');
        f++; t++;                        /* 両方の / を越えて、次のレベルへ */
    }
}
```

どちらかの文字列が終わったら、両方が同時に終わったときと、フィルタの残りが `/#` だけのとき（`dev/#` と `dev` のような親のレベル）に一致とする。この関数は、20 個のフィルタと 19 個のトピック名の 380 通りの組を Mosquitto に実際に振り分けさせた結果と、乱数で作った 2 万通りの組をレベルに分けて比べる別の実装（Python）の結果の、どちらとも一致することを確かめてある。

### 設計の指針

トピックの付け方は、購読のしかたと、ブローカの権限の設定のしやすさを決める。同じ機器の同じデータに、2 通りの名前を付けて比べる。

```fig
e13_design
```

- **上りと下りを、別のトピックに分ける。** 3.1.1 のブローカは、送り手自身の購読にも一致すれば写しを送る（自分の送ったものを受け取らない設定は 5.0 で加わった）。命令と測定値が 1 つのフィルタで一致する名前だと、命令を受け取りたい機器に、自分の測定値が送り返される。
- **機器の ID を、前のほうのレベルに入れる。** `dev/1/…` の形なら、「機器 1 は `dev/1/` の下の上りに送れて、`dev/1/cmd` だけを購読できる」という権限が短く書け、「機器 1 のすべて」も `dev/1/#` で購読できる。
- **先頭に / を付けない。** `/dev/1/temp` は空のレベルが 1 つ増えるだけで、`dev/1/temp` とは別の名前になる。2 つが混ざると、`dev/#` の購読に一致しない名前ができる。
- **値をトピック名に入れない。** トピック名は宛先を表す名前である。測定値や時刻を入れると、値ごとに別のトピックになり、購読も保持メッセージ（5 節）も役に立たない。
- **短く、英数字と記号だけで。** トピック名は、すべての PUBLISH に毎回そのまま入る（3 節）。`factory/building-a/line-3/device-0042/telemetry/temperature`（59 バイト）を使うと、`dev/1/temp`（10 バイト）より、メッセージ 1 つごとに 49 バイト多く送ることになる。

機器には、`#` のような広いフィルタでの購読を許さない（ほかの機器のデータが見えてしまう）。権限の設定は [IoT セキュリティシリーズ 16 章 6 節](../iotsec/16_通信セキュリティ.md#mqtt-の設定) が詳しい。

## 3. パケットの形 — 固定ヘッダと残りの長さ

TCP が届けるのはバイトの列で、送る側の書き込みの区切りは保たれない（07 章 4 節）。そこで MQTT は、やり取りの 1 単位ごとに、先頭に種類と長さを置く（03 章 4 節の長さフィールドの方式）。この 1 単位を、規格の呼び方に合わせて**パケット**と呼ぶ。07 章 3 節の IP のパケットとは別のもので、TCP のバイトの列の中の 1 まとまりである。以下、この章で単に「パケット」と書けば、MQTT のパケットを指す。

すべてのパケットは**固定ヘッダ**で始まる。固定ヘッダは、種類とフラグの 1 バイトと、その後に続くバイト数を表す**残りの長さ**（1〜4 バイト）からなる。その後には、種類ごとに決まった欄の並び（**可変ヘッダ**）と、種類によってはペイロードが続く（規格はこの部分をペイロードと呼ぶ。PUBLISH のペイロードは運ぶデータそのもので、03 章 1 節の意味と同じである）。

```fig
e13_fixhdr
```

1 バイト目の上位 4 ビットがパケットの種類、下位 4 ビットがフラグである。3.1.1 の 14 種類を表に示す（値の 0 と 15 は使わない）。

| 値 | 名前 | 1 バイト目 | 向き | 役目 |
|---|---|---|---|---|
| 1 | CONNECT | `10` | クライアント → ブローカ | 接続を始める |
| 2 | CONNACK | `20` | ブローカ → クライアント | CONNECT への答え |
| 3 | PUBLISH | `30`〜`3D` | 両方 | メッセージを運ぶ（下位 4 ビットは下で説明する） |
| 4 | PUBACK | `40` | 両方 | QoS 1 の確認（4 節） |
| 5 | PUBREC | `50` | 両方 | QoS 2 の 1 つ目の確認（4 節） |
| 6 | PUBREL | `62` | 両方 | QoS 2 の 2 段目の始まり（4 節） |
| 7 | PUBCOMP | `70` | 両方 | QoS 2 の終わりの確認（4 節） |
| 8 | SUBSCRIBE | `82` | クライアント → ブローカ | 購読を登録する |
| 9 | SUBACK | `90` | ブローカ → クライアント | SUBSCRIBE への答え |
| 10 | UNSUBSCRIBE | `A2` | クライアント → ブローカ | 購読をやめる |
| 11 | UNSUBACK | `B0` | ブローカ → クライアント | UNSUBSCRIBE への答え |
| 12 | PINGREQ | `C0` | クライアント → ブローカ | 接続が生きているかを確かめる（5 節） |
| 13 | PINGRESP | `D0` | ブローカ → クライアント | PINGREQ への答え（5 節） |
| 14 | DISCONNECT | `E0` | クライアント → ブローカ | 正常に切断する（5 節） |

PUBLISH 以外の種類では、フラグの値は決まっている（PUBREL・SUBSCRIBE・UNSUBSCRIBE は 0010、ほかは 0000）。PUBLISH だけは、下位 4 ビットを 3 つの欄に使う。ビット 3 の DUP（送り直したものであることの印。4 節）、ビット 2〜1 の **QoS**（届け方の確かさの段階で、0・1・2 のどれか。4 節）、ビット 0 の RETAIN（このメッセージを、そのトピックの最後の値としてブローカに覚えさせる印。5 節）である。

### 残りの長さ

残りの長さは、その後に続くバイト数（可変ヘッダとペイロードの合計）を、7 ビットずつに分けて書く。各バイトの下位 7 ビットに値を入れ、最上位ビットを「まだ続きのバイトがある」印にして、値の下の桁から順に書く。321 と 16384 を書く手順を示す。

```fig
e13_remlen
```

321 を 128 で割ると、商 2、余り 65 である。1 バイト目の下位 7 ビットに余りの 65（0x41）を入れ、続きがあるので最上位ビットを 1 にして 0xC1 とする。2 バイト目には商の 2 を入れ、もう続かないので 0x02 のまま書く。読む側は逆に、i 番目（0 から数える）のバイトの下位 7 ビットに $`128^i`$ を掛けて足していき、最上位ビットが 0 のバイトで止まる（$`65 + 2 \times 128 = 321`$）。

残りの長さは 4 バイトまでと決められている。表せる最大の値を求める。

**方針**: 4 バイトのそれぞれの下位 7 ビットの値を $`d_0, d_1, d_2, d_3`$（各 0〜127）とすると、残りの長さは $`d_0 + 128 d_1 + 128^2 d_2 + 128^3 d_3`$ である。すべての $`d_i`$ を最大の 127 にした値を、等比数列の和で求める。

**導出**:

$$
127 \times (1 + 128 + 128^2 + 128^3) = 127 \times \frac{128^4 - 1}{128 - 1} = 128^4 - 1 = 2^{28} - 1 = 268{,}435{,}455
$$

1 つ目の等号は、等比数列の和の公式 $`1 + r + r^2 + r^3 = (r^4 - 1)/(r - 1)`$ に $`r = 128`$ を入れた。2 つ目の等号は、分子の 127 と分母の $`128 - 1 = 127`$ を約した。$`128 = 2^7`$ なので $`128^4 = 2^{28}`$ である ∎

同じ計算で、k バイトで表せるのは $`128^k - 1`$ までである。残りの長さが 127 以下なら 1 バイト、16,383 以下なら 2 バイト、2,097,151 以下なら 3 バイトで済む。組み込み機器のやり取りのパケットは多くが 127 バイト以下なので、長さの欄はたいてい 1 バイトで済み、それでいて 1 つのパケットで約 256 MB まで運べる。長さをいつも 4 バイトで書く形に比べ、小さなパケットごとに 3 バイトを節約している。その代わり、読む側は、最上位ビットを見るまで長さの欄が何バイトあるかを知らない（6 節の受信のコードで扱う）。

```c
#define REMLEN_MAX 268435455u            /* 4 バイトで表せる最大 */

/* 残りの長さ n を p に符号化し、使ったバイト数（1〜4）を返す。n が大きすぎれば 0 */
size_t mqtt_put_remlen(uint8_t *p, uint32_t n)
{
    size_t k = 0;
    if (n > REMLEN_MAX) return 0;
    do {
        uint8_t d = n % 128;             /* 下位 7 ビット */
        n /= 128;
        if (n > 0) d |= 0x80;            /* まだ続くなら、最上位ビットを 1 にする */
        p[k++] = d;
    } while (n > 0);
    return k;
}
```

### CONNECT と CONNACK — 接続を始める

TCP の接続（TLS を使うなら、その上）ができたら、クライアントは最初に **CONNECT** を送る。ブローカは **CONNACK** で答え、受け入れたときだけ、その後のやり取りができる。クライアント ID を `dev-1` とした CONNECT のバイト列を示す。

```fig
e13_connect
```

- プロトコル名とレベル: 2 バイトの長さ 0x0004 に続く `MQTT` の 4 文字と、版を表すレベル 4（3.1.1 のこと。5.0 では 5）。MQTT の文字列は、どれもこのように 2 バイトの長さをビッグエンディアン（03 章 6 節）で先に書き、続けて UTF-8 の文字を書く。
- 接続フラグ: 後に続く欄などを表す 1 バイト。この例は、クリーンセッション（前の接続のときの状態を捨てて始める。4 節）のビットだけを 1 にした 0x02 である。ウィル（不意に切れたときにブローカが代わりに送るメッセージ。5 節）・ユーザ名・パスワードのビットを 1 にすると、それぞれの文字列が、クライアント ID の後に続く。
- キープアライブ: 接続を見張る時間を表す、秒単位の 16 ビットの値（5 節）。0x003C は 60 秒である。
- **クライアント ID**: ブローカがクライアントを見分ける文字列。同じクライアント ID の新しい接続が来ると、ブローカは前の接続を切る（6 節で、これが起こす問題を見る）。3.1.1 では、ブローカは 1〜23 バイトの英数字の ID を必ず受け付けなければならず、それより長い ID を受け付けるかは実装による。

CONNACK は 4 バイトで、受け入れたときは `20 02 00 00` である。3 バイト目の最下位ビットは Session Present（前の接続のときの状態をブローカが引き継いだか。4 節）、4 バイト目は結果を表す。0 が受け入れで、1〜5 は断った理由（版が合わない、ID を受け付けない、ブローカが使えない、ユーザ名かパスワードが違う、権限が無い）である。

### PUBLISH と SUBSCRIBE

07 章 5 節で使った例（トピック名 `dev/1/temp`、データ `{"t":23.5,"h":41.25}` の 20 バイト）を運ぶ **PUBLISH** を示す。

```fig
e13_publish
```

可変ヘッダはトピック名（2 バイトの長さと 10 バイトの文字）で、QoS が 1 か 2 のときは、その後に 2 バイトのパケット識別子が入る。ペイロードには長さを書かない。残りの長さから可変ヘッダの長さを引けば分かるからである。この例では残りの長さが 2 + 10 + 20 = 32（0x20）で、PUBLISH の全体は 34 バイトになる。データのほかに MQTT の層で足されるのは 14 バイトで、07 章 5 節で使った値はこれである。

**パケット識別子**は、答えを求めるパケットに送り手が付ける 16 ビットの番号（1〜65535。0 は使わない）で、答えには同じ番号が入る。答えを、どの要求へのものかに対応させるための番号で、08 章 4 節の DNS の ID と同じ考え方である。たとえば、`dev/1/cmd` を QoS 1 で購読する **SUBSCRIBE** は `82 0E 00 01 00 09 64 65 76 2F 31 2F 63 6D 64 01` で、パケット識別子 1、フィルタ、希望する QoS が並ぶ。ブローカは **SUBACK** の `90 03 00 01 01` で、同じ識別子と、認めた QoS を返す（認めないときは 0x80）。

PUBLISH を組み立てる関数を示す。

```c
/* PUBLISH を buf（cap バイト）に組み立て、全体のバイト数を返す。入りきらないか、値が不正なら 0。
   qos が 1・2 のときだけパケット識別子 pid（0 は使えない）を入れる */
size_t mqtt_build_publish(uint8_t *buf, size_t cap, const char *topic, const uint8_t *data,
                          size_t len, unsigned qos, int retain, int dup, uint16_t pid)
{
    size_t tlen = strlen(topic);
    if (tlen == 0 || tlen > 65535 || qos > 2 || (qos > 0 && pid == 0) || len > REMLEN_MAX)
        return 0;
    size_t rem = 2 + tlen + (qos > 0 ? 2 : 0) + len;        /* 可変ヘッダ + ペイロード */
    uint8_t hdr[5];
    hdr[0] = (uint8_t)(0x30 | (dup ? 0x08 : 0) | (qos << 1) | (retain ? 1 : 0));
    size_t h = (rem > REMLEN_MAX) ? 0 : 1 + mqtt_put_remlen(hdr + 1, (uint32_t)rem);
    if (h == 0 || h + rem > cap) return 0;
    uint8_t *p = buf;
    memcpy(p, hdr, h); p += h;                              /* 固定ヘッダ */
    *p++ = (uint8_t)(tlen >> 8); *p++ = (uint8_t)tlen;      /* トピック名の長さ（ビッグエンディアン） */
    memcpy(p, topic, tlen); p += tlen;
    if (qos > 0) { *p++ = (uint8_t)(pid >> 8); *p++ = (uint8_t)pid; }
    memcpy(p, data, len); p += len;                         /* ペイロード（長さは書かない） */
    return (size_t)(p - buf);
}
```

この関数の出力は、Python で別に組み立てたバイト列と、12 通りの例（QoS・RETAIN・DUP の組み合わせ、残りの長さが 1・2・3 バイトになる大きさ）で一致し、大きさが 1 バイトでも足りないバッファでは 0 を返すことを確かめてある。QoS 0 の PUBLISH を Mosquitto に送ると、ブローカは同じバイト列をそのまま購読者へ送った。

## 4. QoS — 0・1・2 の届け方

TCP は、失われたセグメントを送り直し、送った順に届ける（10 章）。それなら MQTT のメッセージは必ず届くかというと、そうではない。TCP が約束するのは接続が続いている間だけで、接続が切れると、送り手が書き込んだのにまだ相手に届いていないバイトは失われ、送り手にはどこまで届いたかが分からない。Wi-Fi の切断（09 章 5 節）や、NAT の変換表の行が消えること（08 章 5 節）で、接続は実際に切れる。

```fig
e13_cut
```

MQTT は、接続が切れたときに送りかけのメッセージをどう扱うかを、メッセージごとに 3 つの段階から選ばせる。この段階が 3 節の QoS で、PUBLISH の 2 ビットに書く。

- **QoS 0**（最大 1 回）: PUBLISH を 1 回送るだけで、確認応答は無い。送り手は送ったらすぐメッセージを忘れてよい。接続が切れると失われることがある。
- **QoS 1**（最低 1 回）: 受け手は **PUBACK** で確認応答を返す（05 章 4 節の ACK）。送り手は PUBACK が届くまでメッセージを持ち続け、届かないまま接続が切れたら、つなぎ直した後に同じパケット識別子で送り直す。失われないが、同じメッセージが 2 回以上届くことがある。
- **QoS 2**（ちょうど 1 回）: **PUBREC**・**PUBREL**・**PUBCOMP** を加えた 4 つのパケットで、重複も起きないようにする。

```fig
e13_qos
```

### QoS 1 — 送り直すと重複する

QoS 1 の送り直しには、05 章 4 節の ARQ と同じ問題がある。PUBLISH が失われた場合と PUBACK が失われた場合は、送り手からは区別がつかない。送り直す PUBLISH では、固定ヘッダの DUP のビットを 1 にする。このビットを **DUP フラグ**という。しかし 3.1.1 の受け手は、PUBACK を返した後に同じパケット識別子の PUBLISH が来たら、DUP が 1 でも新しいメッセージとして扱う（規格がそう定めている）。05 章 4 節では受け手が番号を覚えて重複を捨てたが、QoS 1 の受け手は番号を覚えておかない。送り手がいつまで送り直してくるかが決まっていないので、覚えた番号を忘れてよい時が無いからである。したがって、PUBACK が失われると、受け手は同じメッセージを 2 回先へ渡す（Mosquitto に同じ番号の PUBLISH を DUP = 1 でもう一度送ると、購読者には 2 回届いた）。

### QoS 2 — 2 段に分けて、受け手が番号を忘れる時を決める

QoS 2 では、受け手は受け取ったパケット識別子を覚えて、重複を捨てる。番号を忘れてよい時を決めるために、送り手は 2 段目の往復で「その PUBLISH はもう送らない」と知らせる。

1. 送り手は PUBLISH を送り、PUBREC が届くまでメッセージを持ち続ける。届かないまま接続が切れたら、DUP を 1 にして送り直す。
2. 受け手は、パケット識別子を覚えてメッセージを受け取り、PUBREC を返す。番号を覚えている間に同じ番号の PUBLISH が来たら、メッセージを先へ渡さずに PUBREC だけを返す。
3. 送り手は PUBREC を受け取ったらメッセージを捨て、PUBREL を送る。以後、その PUBLISH を送ることはない。PUBREL は、PUBCOMP が届くまで送り直す。
4. 受け手は PUBREL を受け取ったら番号を忘れ、PUBCOMP を返す。送り手は PUBCOMP を受け取って、その番号を使い終える。

QoS 1 と同じく確認が 1 つ失われた場合を、並べて比べる。

```fig
e13_qosfail
```

PUBREC を返した直後に番号を忘れる作りにすると、PUBREC が失われたときに送り直された PUBLISH を、新しいメッセージと取り違える。受け手が番号を忘れるのは、送り手がもう PUBLISH を送らないと分かった PUBREL の後でなければならない。これが、往復が 2 回要る理由である。受け手がメッセージを先へ渡す（ブローカなら購読者へ、機器ならアプリケーションへ）時期は、PUBLISH を受け取ったときと PUBREL を受け取ったときの 2 通りが規格で認められていて、どちらでも 1 回しか渡さない（Mosquitto に同じ番号の PUBLISH を PUBREL の前に 2 回送ると、購読者には 1 回だけ届いた）。

### セッション — 接続をまたいで覚えておくもの

QoS 1・2 の送り直しは、つなぎ直した後に行う。3.1.1 は、つながっている間に時間切れで送り直すことを求めていない。その間は TCP が届けるからである。送り直しが義務づけられているのは、次に述べる永続セッションでつなぎ直したときだけである。

そのために、クライアントとブローカは、接続が切れても次のものを覚えておく。接続をまたいで両者が持ち続けるこの状態を**セッション**という。

- ブローカ: そのクライアントの購読の一覧、そのクライアントへ送ったが確認の済んでいない QoS 1・2 のメッセージ、そのクライアントが留守の間に届いた QoS 1・2 のメッセージ、そのクライアントから受け取った QoS 2 のパケット識別子
- クライアント: 送ったが確認の済んでいない QoS 1・2 のメッセージ、受け取った QoS 2 のパケット識別子

CONNECT の接続フラグのクリーンセッションのビット（3 節）を 1 にすると、ブローカは前のセッションを捨てて新しく始め、接続が切れたら、そのセッションも捨てる。これを**クリーンセッション**という。0 にすると、ブローカは前のセッションがあれば引き継ぎ、接続が切れた後も持ち続ける。これを**永続セッション**という。CONNACK の Session Present のビットは、ブローカが前のセッションを引き継いだときに 1 になる（Mosquitto で、永続セッションで 2 回つなぐと、2 回目の CONNACK は `20 02 01 00` になった）。

永続セッションでつなぎ直すと、両者は確認の済んでいない PUBLISH（DUP を 1 にし、同じパケット識別子で）と PUBREL を、元の順に送り直す。ブローカは、留守の間に届いた QoS 1・2 のメッセージも送る。クリーンセッションでつなぎ直すと、確認の済んでいないメッセージは両方の側で捨てられるので、QoS 1・2 でも失われうる（送り直すなら、アプリケーションが新しいメッセージとして送る）。さらに、機器が再起動して RAM の中身を失えば、確認待ちのメッセージも覚えていたパケット識別子も消える。QoS 1・2 の約束が機器の再起動をまたぐのは、それらをフラッシュに書いておく実装の場合だけである。

### QoS は区間ごとに決まる

QoS は、クライアントとブローカの間の 1 つの区間ごとの約束である。送り手からブローカまでは、送り手が PUBLISH に書いた QoS で運ばれる。ブローカから購読者までは、ブローカが SUBACK で認めた購読の QoS と、PUBLISH の QoS のうち、小さいほうで運ばれる。

### 何が増えるか

QoS を上げると、パケットの数、往復の数、両者が覚えておくものが増える。07 章 5 節の例（トピック名 10 バイト、データ 20 バイト）を 1 つ送るときの、1 つの区間の数を示す。線の上のバイト数は、07 章 5 節と同じく Ethernet・IPv4・TCP で数え、パケットを 1 つずつ別のセグメントで送るとし、TCP の確認応答のセグメントは数えない。

| QoS | 送るパケット | MQTT の層のバイト数 | 線の上のバイト数 | TLS 1.3 を使うとき | 送り手がメッセージを捨てられるまで |
|---|---|---|---|---|---|
| 0 | PUBLISH | 34 | 112 | 134 | 送ったらすぐ |
| 1 | PUBLISH・PUBACK | 36 + 4 = 40 | 114 + 84 = 198 | 240 | 1 往復（PUBACK） |
| 2 | PUBLISH・PUBREC・PUBREL・PUBCOMP | 36 + 4 × 3 = 48 | 114 + 84 × 3 = 366 | 448 | 1 往復（PUBREC）。番号を使い終えるまで 2 往復 |

QoS 1・2 の PUBLISH は、パケット識別子の分だけ 2 バイト長い。4 バイトの確認のパケットは、IP のパケットにしても 44 バイトで、Ethernet のペイロードの最小の 46 バイトに満たないので詰め物が入り、線の上では 84 バイトになる（07 章 2 節）。

選び方の目安は次のとおりである。

- 一定の間隔で送る測定値は、1 つ失われても次の値が来るので、QoS 0 か 1 で足りる。
- 命令や警報のように失いたくないものは QoS 1 にし、重複しても困らないように作る（何度行っても結果が同じ操作にする、メッセージに通し番号を入れて受け手が見分ける。15 章 4 節）。
- QoS 2 は、パケットと往復の数が多く、両者が番号を覚えておく必要もある。重複を受け手の側で見分けられない場合に限って使う。

## 5. 接続を見張る — キープアライブとウィルメッセージ

4 節で見たとおり、QoS 1・2 の送り直しは、接続が切れたことに気づいてから始まる。ところが TCP の接続は、黙って切れることがある。機器の電源が突然切れたとき、途中の回線が切れたとき、NAT の変換表の行が消えたとき（08 章 5 節）は、相手に何も届かないので、残った側は接続がまだあると思い続ける（ハーフオープン。10 章 7 節）。TCP キープアライブは、既定では 2 時間など長い間隔のことが多い（10 章 7 節）。そこで MQTT は、自分でも接続を見張る。

### キープアライブ — 黙っている時間に上限を決める

CONNECT のキープアライブの欄に書く秒数 K を、MQTT の**キープアライブ**という。3.1.1 は、K について次の 3 つを定めている。

1. クライアントは、パケットを送り終えてから次のパケットを送り始めるまでの時間を、K 以下にする。送るものが無ければ **PINGREQ**（`C0 00`）を送る。ブローカは **PINGRESP**（`D0 00`）で答える。
2. ブローカは、クライアントから 1.5 K の間なにも受け取らなければ、ネットワークが壊れたものとみなして接続を切る。
3. クライアントは、PINGREQ を送ってから妥当な時間のうちに PINGRESP が来なければ、接続を閉じるべきである。

K = 0 にすると、見張りをしない。K の最大は 65535 秒（18 時間 12 分 15 秒）で、3.1.1 は数分を典型としている。1.5 倍の余裕は、クライアントの送る時刻のわずかな遅れや、途中の遅延のばらつき、TCP の再送で届くのが遅れることを見込んだものである。

```fig
e13_ka
```

### 気づくまでの時間

接続が黙って切れてから、それぞれが気づくまでの最大の時間を求める。

**方針**: 故障が起きる直前に、クライアントが最後のパケットを送ったとする（このとき、両者が気づくのが最も遅くなる）。その時刻を 0 として、ブローカの期限と、クライアントが次の PINGREQ を送って答えを待つ期限を求める。PINGRESP を待つ時間を $`T_\mathrm{r}`$ とする（規格の「妥当な時間」で、実装が決める）。故障の後、クライアントは PUBLISH を送らないとする。

**導出**: ブローカが最後に受け取ったのは時刻 0 のパケットなので、ブローカは時刻 1.5 K に接続を切る。故障が時刻 0 より後に起きたなら、故障から切るまでの時間は 1.5 K より短い。クライアントは、時刻 0 から K の間なにも送らないので、時刻 K に PINGREQ を送る。それへの PINGRESP は来ないので、時刻 K + $`T_\mathrm{r}`$ に切断に気づく。こちらも、故障が時刻 0 より後なら、故障から気づくまでの時間は短くなる。したがって、気づくまでの時間は、ブローカで最大 1.5 K、クライアントで最大 K + $`T_\mathrm{r}`$ である ∎

K = 60 秒、$`T_\mathrm{r}`$ = 10 秒なら、ブローカは 90 秒以内、クライアントは 70 秒以内に気づく。ただし、ブローカの実装によっては、期限を一定の間隔でまとめて調べるので、実際に切るのはこれより遅れる（手元の Mosquitto 2.0.18 は約 6 秒ごとに調べていて、K = 2 秒では、黙ってから切るまでに 7.6 秒かかった）。

導出では、故障の後にクライアントが PUBLISH を送らないとした。1 つ目の決まりは「送る」間隔の上限なので、QoS 0 の PUBLISH を K より短い間隔で送り続けるクライアントは、PINGREQ を一度も送らない。QoS 0 の PUBLISH には答えが返らないので、回線が切れていても気づかず、TCP が送り直しをあきらめるまで（数分〜十数分になることがある）送り続ける。PINGREQ はいつ送ってもよいので、「最後に受け取ってから K たったら PINGREQ を送る」決まりを足しておけば、受け取りの側からも切断に気づける。

### NAT の保持時間との関係

キープアライブは、08 章 5 節の、NAT の変換表の行を保つためのパケットも兼ねる。クライアントは少なくとも K ごとにパケットを送るので、08 章 5 節の条件 $`T_\mathrm{k} < T_\mathrm{h}`$ に $`T_\mathrm{k}`$ = K を当てはめ、K を保持時間 $`T_\mathrm{h}`$ より短くすれば、行は消えない。TCP では、失われたセグメントは TCP が送り直すので、間隔の延びは送り直しにかかる時間で済むが、その分の余裕を見て、K を $`T_\mathrm{h}`$ より十分短くする。K が長すぎて行が消えると、その後にブローカから送った命令は NAT で捨てられ、その TCP の接続は使えなくなる（機器の次の PINGREQ は、NAT で捨てられるか、知らない接続のものとしてサーバに断られる）。逆に、K を短くすると、電池で動く機器の平均電流が増える（08 章 5 節の $`Q_\mathrm{k} / T_\mathrm{k}`$。Wi-Fi の場合は 09 章 4 節）。

### ウィルメッセージ — 切れたことを、ほかのクライアントに知らせる

機器が黙って消えたことに、ブローカは気づいても、その機器のデータを待っているアプリには分からない。そこで機器は、自分が不意に切れたときにブローカが代わりにパブリッシュするメッセージを、CONNECT に入れておける。これを**ウィルメッセージ**という（will は遺言の意味）。CONNECT の接続フラグのウィルのビットを 1 にし、トピック名・ペイロード・QoS・RETAIN を指定する。

ブローカは、ネットワークの誤りに気づいたとき、キープアライブの 1.5 K が過ぎたとき、クライアントが DISCONNECT を送らずに TCP の接続を閉じたときなどに、ウィルメッセージをパブリッシュする。クライアントが **DISCONNECT**（`E0 00`）を送ってから閉じる正常な切断では、ブローカはウィルメッセージを捨て、パブリッシュしない（どちらも Mosquitto で確かめた）。

### 保持メッセージ — 最後の値を、後から来た購読者に渡す

ふつうのメッセージは、その時点で購読している者にしか届かない。後から購読を始めたアプリは、次のメッセージが来るまで機器の状態を知らない。そこで、PUBLISH の RETAIN のビット（3 節）を 1 にして送ると、ブローカはそのメッセージを、そのトピックの最後の値として覚えておく。こうして覚えさせたメッセージを**保持メッセージ**という。

- ブローカは、トピックごとに保持メッセージを 1 つだけ持ち、新しいものが来れば置き換える。
- 新しい購読が一致すると、ブローカはすぐに保持メッセージを送る。このとき RETAIN を 1 にして送るので、受け手は、それが以前の値だと分かる。購読を続けている受け手には、RETAIN を 0 にして送る。
- ペイロードが 0 バイトの保持メッセージを送ると、そのトピックの保持メッセージは消える。

ウィルメッセージと保持メッセージを組み合わせると、機器がつながっているかどうかを、いつ購読を始めた者にも知らせられる。

```fig
e13_will
```

機器は、つないだら状態のトピック `dev/1/status` に `online` を保持メッセージとしてパブリッシュし、ウィルメッセージには、同じトピックの `offline`（保持）を入れておく。機器が黙って消えると、ブローカは 1.5 K の後に `offline` をパブリッシュし、それが新しい保持メッセージになる。後から `dev/+/status` を購読したアプリにも、各機器の最後の状態がすぐ届く。機器が自分から切るとき（眠る前など）はウィルメッセージが出ないので、DISCONNECT の前に `offline` を自分でパブリッシュする。

下の図で、キープアライブ・NAT の保持時間・測定値を送る間隔・故障の種類を変えると、機器が送るパケット、変換表の行、ブローカの期限と、それぞれが切断に気づく時刻が表示される。

## 6. 機器側の実装

ここまでの仕組みを、機器のファームウェアにどう置くかを見る。構成の例を図に示す。

05 章 2 節の通信タスクの考え方で、MQTT の接続は 1 つのタスク（以下、MQTT タスク）だけが扱う。測定のタスクなどは、送りたいメッセージをキューで MQTT タスクに頼み、受け取ったメッセージもキューで受け取る。MQTT タスクは、TLS（12 章）の上の TCP の接続（11 章）を持ち、次のものを管理する。

- 受信: TLS から届いたバイトの列を、パケットに区切る。
- QoS 1・2 の確認待ちのメッセージと、パケット識別子。
- キープアライブ: 最後に送った時刻と受け取った時刻、PINGRESP を待つ期限。
- 接続の状態と、つなぎ直し。

組み込み向けの MQTT のライブラリ（Eclipse Paho の組み込み向け、lwIP に含まれる MQTT のクライアント、ESP-IDF の esp-mqtt など。版によって細部が異なる）も、名前は違うが、これらを中に持っている。ここでは、ライブラリを使う場合にも中で何が起きているかが分かるように、要の所を書く。

### 受信 — バイトの列をパケットに区切る

TCP（TLS）からの受信は、パケットの区切りと関係なく届く。1 回の受信に 2 つのパケットが入っていることも、1 つのパケットの途中で切れていることもある（11 章 2 節）。そこで、届いたバイトを 1 つずつ、3 つの状態を持つ状態機械（05 章 1 節）に通して区切る。

```fig
e13_rxsm
```

```c
#define RX_MAX 512                       /* 受け取れる残りの長さの上限（RAM に合わせて決める） */
enum rx_state { RX_FIRST, RX_LEN, RX_BODY };
struct mqtt_rx {
    enum rx_state st;                    /* 1 バイト目待ち・残りの長さ・残りのバイト */
    uint8_t  first;                      /* 固定ヘッダの 1 バイト目 */
    uint32_t rem, mult;                  /* 残りの長さと、次の 7 ビットの重み（1, 128, 128^2, …） */
    uint32_t got;                        /* 残りのうち受け取ったバイト数 */
    uint8_t  body[RX_MAX];               /* 可変ヘッダとペイロード */
};

/* TCP（TLS）から届いたバイトを、届いた単位のまま渡す。パケットが 1 つそろうたびに on_packet を呼ぶ。
   残りの長さが壊れているか、受け取れない大きさなら -1 を返す（呼び手は接続を閉じる） */
int mqtt_rx_feed(struct mqtt_rx *r, const uint8_t *p, size_t n,
                 void (*on_packet)(uint8_t first, const uint8_t *body, uint32_t len))
{
    for (size_t i = 0; i < n; i++) {
        uint8_t b = p[i];
        if (r->st == RX_FIRST) {                          /* 固定ヘッダの 1 バイト目 */
            r->first = b; r->rem = 0; r->mult = 1; r->got = 0; r->st = RX_LEN;
        } else if (r->st == RX_LEN) {                     /* 残りの長さを 7 ビットずつ */
            r->rem += (uint32_t)(b & 0x7F) * r->mult;
            if (b & 0x80) {
                if (r->mult == 128u * 128 * 128) return -1;   /* 4 バイト目でも続く: 壊れている */
                r->mult *= 128;
            } else if (r->rem > RX_MAX) {
                return -1;                                /* 受け取れない大きさ（03 章 4 節） */
            } else if (r->rem == 0) {
                on_packet(r->first, r->body, 0); r->st = RX_FIRST;   /* PINGRESP など */
            } else {
                r->st = RX_BODY;
            }
        } else {                                          /* 残りのバイトをためる */
            r->body[r->got++] = b;
            if (r->got == r->rem) { on_packet(r->first, r->body, r->rem); r->st = RX_FIRST; }
        }
    }
    return 0;
}
```

残りの長さは、3 節の符号化の逆で、届いたバイトの下位 7 ビットに重み（1、128、$`128^2`$、$`128^3`$）を掛けて足していく。4 バイト目でも続きの印が立っていれば壊れた長さとし、受け取れる大きさ `RX_MAX` を超える長さなら、残りを受け取る前に -1 を返して接続を閉じる（03 章 4 節の、長さの上限を確かめる対策）。3.1.1 には、受け取れる大きさをブローカに知らせる方法が無いので、機器が購読するトピックには大きなメッセージを送らない、と決めておく。このコードは、7 種類のパケットを 200 個並べた 23,063 バイトの列を、でたらめな大きさに 300 通りに区切って渡し、どの区切り方でも 200 個のパケットを正しく取り出すことと、壊れた長さと大きすぎる長さで -1 を返すことを確かめてある。

### QoS 1 の確認待ち

QoS 1 のメッセージは、PUBACK が届くまで写しを持ち続ける（4 節）。05 章のストップアンドウェイトと違い、MQTT では確認を待たずに次の PUBLISH を送ってよい。確認待ちを何個まで持つかは 3.1.1 では決まっていないので、RAM に合わせて実装が決める。確認待ちの列を、04 章 3 節のリングバッファの、増え続ける添字の形で持つ例を示す。

```c
#define INFLIGHT 4                       /* 確認待ちにできる QoS 1 のメッセージの数 */
struct pending { uint16_t pid, len; uint8_t pkt[128]; };   /* pid = 0 は確認済みの印 */
static struct pending q[INFLIGHT];
static uint32_t q_head, q_tail;          /* 増え続ける添字。確認待ちの数は q_head - q_tail */

uint16_t mqtt_next_pid(void)             /* 1〜65535 を順に使う（0 は使わない） */
{
    static uint16_t n;
    if (++n == 0) n = 1;
    return n;
}

/* QoS 1 の PUBLISH を確認待ちの列に入れてから送る。列が満杯なら -1（呼び手は後で送る） */
int mqtt_publish_q1(const char *topic, const uint8_t *data, size_t len)
{
    if (q_head - q_tail == INFLIGHT) return -1;
    struct pending *e = &q[q_head % INFLIGHT];
    uint16_t pid = mqtt_next_pid();
    size_t n = mqtt_build_publish(e->pkt, sizeof e->pkt, topic, data, len, 1, 0, 0, pid);
    if (n == 0) return -1;
    e->pid = pid; e->len = (uint16_t)n; q_head++;
    return net_send(e->pkt, n);
}

void mqtt_on_puback(uint16_t pid)        /* PUBACK が届いたら、その番号に確認済みの印を付ける */
{
    for (uint32_t i = q_tail; i != q_head; i++)
        if (q[i % INFLIGHT].pid == pid) q[i % INFLIGHT].pid = 0;
    while (q_tail != q_head && q[q_tail % INFLIGHT].pid == 0)
        q_tail++;                        /* 古い側から、確認済みのものを外す */
}

void mqtt_resend_inflight(void)          /* つなぎ直した直後に、送った順に送り直す */
{
    for (uint32_t i = q_tail; i != q_head; i++) {
        struct pending *e = &q[i % INFLIGHT];
        if (e->pid == 0) continue;
        e->pkt[0] |= 0x08;               /* DUP = 1。パケット識別子は変えない */
        net_send(e->pkt, e->len);
    }
}
```

`net_send` は、TLS の接続に全部を書き込む関数（11 章 2 節の、全部を送り終えるまで繰り返す形）で、この章で仮に置く。3.1.1 では、PUBACK は PUBLISH を受け取った順に返すことになっているが、順番が違っても列が詰まらないように、確認済みの印を付けてから古い側から外している。確認待ちは多くとも 4 個で、番号は 1 から順に使うので、使用中の番号と重なることはない。SUBSCRIBE の番号も、同じ `mqtt_next_pid` から取る。このコードは、満杯のとき、順番の違う確認、送り直しの DUP と順番、番号の一周（65535 の次が 1）を PC の上で確かめ、Mosquitto に実際に送って PUBACK で列が空になることも確かめてある。

### つなぎ直す

接続が切れたら（TLS・TCP の誤り、PINGRESP の期限切れ、壊れたパケット）、MQTT タスクは 05 章 5 節の指数バックオフとジッタで待ってから、つなぎ直す。Wi-Fi・DNS・TCP・TLS のどの層からやり直すかは 15 章 2 節で扱う。MQTT の層の手順は次のとおりである。

```fig
e13_reconn
```

1. CONNECT を送り、CONNACK の結果を見る。0 以外（ID を受け付けない、権限が無いなど）は、繰り返しても直らないので、長く待つか、利用者に知らせる。
2. Session Present が 0 なら、ブローカはセッションを持っていない（クリーンセッションでつないだか、ブローカの再起動などでセッションが消えた）ので、購読をやり直す。永続セッションのつもりでも消えていることがあるので、必ずこのビットを見る。
3. 確認待ちのメッセージを、送った順に送り直す。Session Present が 1 なら規格どおりの送り直しになり、0 ならブローカには新しいメッセージとして届く。
4. 状態のトピックに `online` を保持メッセージとしてパブリッシュし直す（5 節）。

受け取ったメッセージは、ライブラリがコールバック（05 章 2 節）で知らせることが多い。コールバックは MQTT タスクの中で呼ばれるので、そこでフラッシュに書いたり、ほかの応答を待ったりすると、その間 MQTT タスクは何もできない。PINGREQ が遅れてブローカに切られ、受信のバッファもあふれる。コールバックでは、メッセージを写してキューに入れるだけにし、処理はほかのタスクで行う。

クライアント ID は、機器ごとに異なるもの（製造番号や、クライアント証明書の名前。12 章 5 節）から作る。同じ ID を書き込んでしまった 2 台は、互いに相手の接続をブローカに切らせ、切られた側がつなぎ直してまた相手を切る、を繰り返す。切られるたびにその接続のウィルメッセージも出るので（Mosquitto で確かめた）、状態は `online` と `offline` の間を行き来し続ける。

### ペイロードの形

MQTT は、ペイロードの中身を決めていない。よく使われるのは、JSON のような文字の形と、決まった並びのバイナリである。07 章 5 節の測定値を、2 つの形で比べる。

```fig
e13_payload
```

バイナリの形では、温度を 100 倍した 2350 を符号付き 16 ビット、湿度を 100 倍した 4125 を符号なし 16 ビットにし、ビッグエンディアンで並べた 4 バイトになる（03 章 6 節の固定小数点）。PUBLISH は 34 バイトから 18 バイトに、07 章 5 節の線の上のバイト数は 112 バイトから 96 バイトになる。トピック名と下の層のヘッダは残るので、線の上で減るのは 14 % である。JSON は、受け手が読みやすく、項目を足しても古い受け手が困らない。バイナリは小さいが、並びを変えるときのために版の番号を入れる（03 章 7 節の TLV のように、型と長さを付けて後から項目を足せる形にする方法もある）。どちらにするかは、大きさだけでなく、サーバの側で読む手間や、項目を足す見込みで決める。

### MQTT 5.0 で加わったもの

5.0 は、3.1.1 と同じ形の固定ヘッダと残りの長さを使い（CONNECT のレベルは 5）、主に次のものを加えた。

- 理由コード: CONNACK・PUBACK・SUBACK・DISCONNECT などが、結果や断った理由を 1 バイトで返す。ブローカからも DISCONNECT を送れるようになった。
- プロパティ: 可変ヘッダに、追加の欄の列を置ける。その長さは、残りの長さと同じ符号化で書く。
- トピックエイリアス: 一度送ったトピック名を、以後は 2 バイトの番号で表せる。長いトピック名を毎回送らずに済む。
- セッションの有効期限: クリーンセッションの代わりに、切れた後にセッションを何秒持ち続けるかを指定する。
- そのほか、確認待ちの数の上限（Receive Maximum）、受け取れるパケットの大きさの上限、自分の送ったものを受け取らない購読の設定、メッセージの有効期限など。

TLS を使う設定（ポート 8883、クライアント証明書による認証、機器ごとのトピックの権限）は、[IoT セキュリティシリーズ 16 章 6 節](../iotsec/16_通信セキュリティ.md#mqtt-の設定) が詳しい。

| 項目 | 内容 |
|---|---|
| ブローカとクライアント | 全員がブローカへ外向きに接続を張り、ブローカがメッセージを配る。送り手は受け手を知らない。下りも機器が張った接続で届くので、NAT の内側でも動く |
| パブリッシュ・サブスクライブ | トピック名を付けてブローカへ送る／受け取りたいフィルタを登録する。ブローカは一致した購読者のそれぞれへ写しを送る |
| トピックとフィルタ | / で区切ったレベルの列。`+` は 1 レベル、`#` は残りすべて（0 個でもよく、最後のレベルだけ）。`$` で始まる名前に、ワイルドカードで始まるフィルタは一致しない |
| トピックの設計 | 上りと下りを分け、機器の ID を前のほうに入れ、先頭に / を付けず、値を入れず、短くする |
| 固定ヘッダ | 種類 4 ビット・フラグ 4 ビットの 1 バイトと、残りの長さ。PUBLISH のフラグは DUP・QoS・RETAIN |
| 残りの長さ | 7 ビットずつ下の桁から書き、最上位ビットが続きの印。1 バイトで 127 まで、4 バイトで最大 $`2^{28} - 1`$ = 268,435,455 |
| PUBLISH | トピック名（2 バイトの長さ付き）・パケット識別子（QoS 1・2 だけ）・ペイロード（長さは書かない）。10 バイトのトピック名と 20 バイトのデータで 34 バイト |
| QoS | 0: 1 回送るだけ（失われうる）。1: PUBACK が来るまで持ち、つなぎ直したら送り直す（重複しうる）。2: PUBREC・PUBREL・PUBCOMP で、受け手が番号を忘れてよい時を決める（重複しない）。QoS は区間ごとで、購読者へは小さいほう |
| セッション | 接続をまたいで両者が持つ状態（購読・確認待ち）。クリーンセッションは捨て、永続セッションは引き継ぐ。CONNACK の Session Present で分かる |
| キープアライブ | クライアントは K 以内に何かを送る（無ければ PINGREQ）。ブローカは 1.5 K の間なにも受け取らなければ切る。気づくまで、ブローカで最大 1.5 K、クライアントで最大 K + $`T_\mathrm{r}`$。K は NAT の保持時間より十分短くする |
| ウィルと保持 | ウィルは不意の切断のときにブローカが代わりに出すメッセージ、保持は最後の値を新しい購読者に渡すメッセージ。組み合わせて online / offline を知らせる |
| 機器側の実装 | 1 つのタスクが接続を持つ。受信は状態機械でパケットに区切り、長さの上限を確かめる。確認待ちの列と番号を管理し、つなぎ直したら Session Present を見て購読をやり直す |
