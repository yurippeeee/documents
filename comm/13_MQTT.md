# 13. MQTT — 小さな機器のためのパブリッシュとサブスクライブ

> **この章で扱う問い.**
> 08 章 5 節では、NAT の内側にいる機器へは外から接続を始められないので、機器の側からサーバへ接続を張り、それを保つ必要があることを見た。10〜12 章では、その接続（TCP と TLS）の仕組みを見た。この章では、その接続の上で測定値と命令をやり取りするアプリケーション層のプロトコルとして、組み込み機器で広く使われている MQTT を扱う。
>
> この章では次の 3 つの問いに答える。
>
> 1. 送り手と受け手が互いを知らないまま、データを届け合うには、どんな仕組みにすればよいか。届け先は何で決まるのか。
> 2. MQTT のやり取りは、TCP のバイトの列の上でどんなバイトの列になるのか。届け方を確かにすると、何が増えるのか。
> 3. 接続が黙って切れたことに、機器とサーバはどう気づくのか。機器のファームウェアは、何を持ち、何を管理すればよいのか。
>
> 答えの道具は、トピックの照合の規則、残りの長さの符号化、05 章の確認応答と再送を当てはめた QoS の手順、そしてキープアライブの時間の計算である。

## 1. ブローカを介したパブリッシュとサブスクライブ

家の温湿度センサが 1 分ごとに測定値をクラウドへ送り、利用者のスマートフォンのアプリがそれを表示する。アプリからは機器へ「測る間隔を変える」などの命令を送る。測定値を受け取りたいものは 1 つとは限らず、値を蓄えるデータベースや、異常を知らせる警報のサービスも受け取りたい。

受け手のそれぞれが機器へ直接つなぐ形（図の上）では、2 つの問題が起きる。送り手と受け手が互いの数と宛先を知っていなければならず、受け手が増えるたびに設定が増える。そして、機器が NAT の内側にいるので、受け手の側から機器へ接続を始められない（08 章 5 節）。

```fig
e13_direct
```

そこで、全員が 1 つの中継のサーバへ接続を張り、データはそのサーバを通して届ける（図の下）。**MQTT** は、このための、TCP の上で動くアプリケーション層のプロトコルである。版 3.1.1 と 5.0 が、標準化団体 OASIS の標準になっている。この章は 3.1.1 を基本にし、5.0 との違いは 6 節で触れる。

- **ブローカ**: 中継するサーバ。受け取ったデータを、それを欲しがっている相手へ配る。
- **クライアント**: ブローカにつなぐもの。機器もアプリもデータベースもクライアントで、1 つのクライアントが送り手と受け手を兼ねてよい。
- **トピック**: メッセージに付ける名前（文字列）。`dev/1/temp` のように、/ で区切って書く（2 節）。
- **メッセージ**（MQTT の）: トピック名と、運ぶデータ（03 章 1 節のペイロード）の組。
- **パブリッシュ**: クライアントが、トピック名を付けたメッセージをブローカへ送ること。
- **サブスクライブ**（**購読**）: クライアントが、受け取りたいトピックの範囲（トピックフィルタ。2 節）をブローカに登録しておくこと。購読しているクライアントを**購読者**という。ブローカは、パブリッシュされたメッセージのトピック名を登録と照らし合わせ、一致した購読者のそれぞれへ写しを送る。

クライアントは、ブローカへ TCP の接続を張り（ポート 1883。TLS を使うなら 8883。07 章 4 節）、その接続を保ったまま、パブリッシュと受信を行う。やり取りの例を図に示す。

```fig
e13_flow
```

図から、3 つのことが読み取れる。

1. **送り手は受け手を知らない。** 機器は `dev/1/temp` に送るだけで、誰が何人受け取るかを知らない。受け手を足しても、機器は何も変えなくてよい。一致する購読が 1 つも無ければ、ブローカはそのメッセージを捨てる（例外は 5 節の保持メッセージ）。
2. **下りも、機器が張った接続で届く。** アプリが送った命令は、機器がつないでいる接続を通って届く。機器から外へ向かう接続だけで上りと下りがそろうので、NAT の内側でも動く。
3. **接続の数は、送り手と受け手を足した数で済む。** 機器 N 台と受け手 M 個が直接つなぐと N × M 本の接続が要るが、ブローカを介せば N + M 本である。

その代わり、ブローカはすべてのクライアントが頼る 1 点になり、誰がどのトピックに送り、何を購読してよいかの権限もブローカが管理する。ブローカには、クラウドの事業者が提供するものや、オープンソースのもの（Eclipse Mosquitto など）がある。この章のバイト列と振る舞いは、手元で動かした Mosquitto 2.0.18 に実際に送って確かめてある。

## 2. トピックの設計

トピック名は UTF-8 の文字列で、/ で区切った 1 つ 1 つを**トピックレベル**（以下、レベル）という。`dev/1/temp` は `dev`・`1`・`temp` の 3 レベルである。大文字と小文字は区別し、空のレベルも 1 つと数える（`/dev` は空のレベルと `dev` の 2 レベル）。

購読で登録するのは、一致するトピック名の範囲を表す**トピックフィルタ**（以下、フィルタ）である。フィルタには、1 つのレベル全体の代わりに置ける 2 つの**ワイルドカード**を使える。

- `+`: どんな 1 つのレベルにも一致する。`dev/+/temp` は `dev/1/temp` にも `dev/2/temp` にも一致するが、レベルの数が違う `dev/1/temp/raw` には一致しない。
- `#`: その位置から後のレベルすべてに一致する。0 個でもよいので、`dev/1/#` は `dev/1/temp` にも、親の `dev/1` にも一致する。フィルタの最後のレベルにだけ置ける。`#` だけのフィルタは、すべてのトピック名に一致する。

```fig
e13_tree
```

規則の細かい所を、実例の表で確かめる（MQTT 3.1.1 の 4.7 節。どの行も Mosquitto で同じ結果になった）。

| フィルタ | トピック名 | 一致するか | 理由 |
|---|---|---|---|
| `dev/+/temp` | `dev/7/temp` | する | `+` が `7` に一致する |
| `dev/+/temp` | `dev/1/temp/raw` | しない | トピック名のレベルが 1 つ多い |
| `dev/+` | `dev/` | する | `+` は空のレベルにも一致する |
| `dev/+` | `dev` | しない | `+` に当たるレベルが無い |
| `dev/#` | `dev` | する | `#` は 0 個のレベル（親）にも一致する |
| `+` | `/dev` | しない | `/dev` は 2 レベル（空と `dev`） |
| `Dev/1/temp` | `dev/1/temp` | しない | 大文字と小文字を区別する |
| `#` | `$SYS/broker/uptime` | しない | `$` で始まる名前に、ワイルドカードで始まるフィルタは一致しない |

`$` で始まる名前は、ブローカが自分の情報（接続の数など）を出すのに使うので、`#` の購読に混ざらないようにしてある（`$SYS/#` のように `$` から書けば一致する）。ワイルドカードはレベル全体を占めなければならず（`dev+` は誤り）、パブリッシュするトピック名には使えない。規則に反するものを受けた側は接続を閉じる、と 3.1.1 は定めていて、Mosquitto もそうした。

照合を C で書くと、次のようになる。フィルタとトピック名を、先頭からレベルごとに比べていく。

```c
/* フィルタ f がトピック名 t に一致すれば 1、しなければ 0 を返す（MQTT 3.1.1 の規則）。
   f は規則に合う（+ と # はレベル全体を占め、# は最後のレベルだけ）ものとする */
int topic_match(const char *f, const char *t)
{
    if ((*f == '+' || *f == '#') && *t == '$')
        return 0;                        /* $ で始まる名前に、ワイルドカードで始まるフィルタは一致しない */
    for (;;) {
        if (*f == '#')
            return 1;                    /* 残りのレベルすべて（0 個でもよい） */
        if (*f == '+') {                 /* t のレベルを 1 つ、中身によらず飛ばす */
            f++;
            while (*t != '\0' && *t != '/') t++;
        } else {                         /* ふつうのレベルは 1 文字ずつ比べる */
            while (*f != '\0' && *f != '/')
                if (*f++ != *t++) return 0;
            if (*t != '\0' && *t != '/') return 0;   /* t のレベルのほうが長い */
        }
        if (*f == '\0' || *t == '\0')    /* どちらかが終わった */
            return *f == *t || (f[0] == '/' && f[1] == '#' && f[2] == '\0');
        f++; t++;                        /* 両方の / を越えて、次のレベルへ */
    }
}
```

どちらかが終わったら、両方が同時に終わったときと、フィルタの残りが `/#` だけのとき（`dev/#` と `dev` のような親のレベル）に一致とする。この関数の結果は、380 通りの組を Mosquitto に振り分けさせた結果とも、乱数で作った 2 万通りの組を別の方法（レベルに分けて比べる Python の実装）で判定した結果とも一致した。

### 設計の指針

トピックの付け方は、購読のしかたと、ブローカの権限の設定のしやすさを決める。同じ機器の同じデータに、2 通りの名前を付けて比べる。

```fig
e13_design
```

- **上りと下りを、別のトピックに分ける。** 3.1.1 のブローカは、送り手自身の購読に一致すれば、送り手にも写しを送る（送り返さない設定は 5.0 で加わった）。命令と測定値が 1 つのフィルタに一致すると、命令を待つ機器に自分の測定値が送り返される。
- **機器の ID を前のほうのレベルに入れ、先頭に / を付けない。** `dev/1/…` なら、機器 1 のすべてを `dev/1/#` で購読でき、「機器 1 は `dev/1/cmd` だけを購読できる」という権限も短く書ける。`/dev/1/temp` は空のレベルが増えるだけで、`dev/#` に一致しない。
- **値を入れず、短くする。** 値を入れると値ごとに別のトピックになる。トピック名はメッセージを送るたびに毎回送る（3 節）ので、59 バイトの `factory/building-a/line-3/device-0042/telemetry/temperature` では、`dev/1/temp` よりメッセージ 1 つごとに 49 バイト多く送る。

機器には `#` のような広いフィルタでの購読を許さない（ほかの機器のデータが見えてしまう）。権限の設定は [IoT セキュリティシリーズ 16 章 6 節](../iotsec/16_通信セキュリティ.md#mqtt-の設定) が詳しい。

## 3. パケットの形 — 固定ヘッダと残りの長さ

TCP が届けるのはバイトの列で、送る側の書き込みの区切りは保たれない（07 章 4 節）。そこで MQTT は、やり取りの 1 単位ごとに、先頭に種類と長さを置く（03 章 4 節の長さフィールドの方式）。この 1 単位を、規格の呼び方に合わせて**パケット**と呼ぶ。07 章 3 節の IP のパケットとは別のもので、TCP のバイトの列の中の 1 まとまりである。以下、この章で単に「パケット」と書けば、MQTT のパケットを指す。

すべてのパケットは**固定ヘッダ**で始まる。固定ヘッダは、種類とフラグの 1 バイトと、その後に続くバイト数を表す**残りの長さ**（1〜4 バイト）からなる。その後に、種類ごとに決まった欄の並び（**可変ヘッダ**）と、種類によってはペイロードが続く（PUBLISH のペイロードは運ぶデータそのもので、03 章 1 節の意味と同じである）。

```fig
e13_fixhdr
```

1 バイト目の上位 4 ビットがパケットの種類（3.1.1 では 1〜14 の 14 種類。図の下の段）、下位 4 ビットがフラグである。各種類の役目は、この節と 4・5 節で順に見る。PUBLISH 以外では、フラグの値は決まっている（PUBREL・SUBSCRIBE・UNSUBSCRIBE は 0010、ほかは 0000）。PUBLISH だけは、下位 4 ビットを 3 つの欄に使う。ビット 3 の DUP（送り直したものの印。4 節）、ビット 2〜1 の **QoS**（届け方の確かさの段階で、0・1・2 のどれか。4 節）、ビット 0 の RETAIN（このメッセージを、そのトピックの最後の値としてブローカに覚えさせる印。5 節）である。

### 残りの長さ

残りの長さは、その後に続くバイト数（可変ヘッダとペイロードの合計）を 7 ビットずつに分けて書く。各バイトの下位 7 ビットに値を入れ、最上位ビットを「まだ続きのバイトがある」印にして、値の下の桁から順に並べる。321 と 16384 を書く手順を示す。

```fig
e13_remlen
```

読む側は逆に、i 番目（0 から数える）のバイトの下位 7 ビットに $`128^i`$ を掛けて足していき、最上位ビットが 0 のバイトで止まる。

残りの長さは 4 バイトまでと決められている。表せる最大の値を求める。

**方針**: 4 バイトの下位 7 ビットの値を $`d_0, d_1, d_2, d_3`$（各 0〜127）とすると、残りの長さは $`d_0 + 128 d_1 + 128^2 d_2 + 128^3 d_3`$ である。すべての $`d_i`$ を 127 にした値を、等比数列の和で求める。

**導出**:

$$
127 \times (1 + 128 + 128^2 + 128^3) = 127 \times \frac{128^4 - 1}{128 - 1} = 128^4 - 1 = 2^{28} - 1 = 268{,}435{,}455
$$

1 つ目の等号は等比数列の和の公式 $`1 + r + r^2 + r^3 = (r^4 - 1)/(r - 1)`$ に $`r = 128`$ を入れ、2 つ目の等号は 127 と分母の $`128 - 1`$ を約した。$`128 = 2^7`$ なので $`128^4 = 2^{28}`$ である ∎

同じ計算で、k バイトで表せるのは $`128^k - 1`$ まで、つまり 1 バイトなら 127、2 バイトなら 16,383、3 バイトなら 2,097,151 までである。機器が送るパケットの多くは 127 バイト以下なので、長さの欄はたいてい 1 バイトで済み、それでいて 1 つのパケットで約 256 MB まで運べる。その代わり、読む側は最上位ビットを見るまで、長さの欄が何バイトあるかを知らない（6 節）。

### CONNECT と CONNACK — 接続を始める

TCP の接続（TLS を使うなら、その上）ができたら、クライアントは最初に **CONNECT** を送る。ブローカは **CONNACK** で答え、受け入れたときだけ、その後のやり取りができる。`dev-1` と名乗る CONNECT のバイト列を示す。

```fig
e13_connect
```

- プロトコル名とレベル: 2 バイトの長さ 0x0004 に続く `MQTT` の 4 文字と、版を表すレベル 4（3.1.1 のこと。5.0 では 5）。MQTT の文字列は、どれもこのように 2 バイトの長さをビッグエンディアン（03 章 6 節）で先に書き、続けて UTF-8 の文字を書く。
- 接続フラグ: クリーンセッション（前の接続のときの状態を捨てて始める。4 節）のビットだけを 1 にした 0x02。ウィル（不意に切れたときにブローカが代わりに送るメッセージ。5 節）・ユーザ名・パスワードのビットを 1 にすると、それぞれの文字列がクライアント ID の後に続く。
- キープアライブ: 接続を見張る時間（5 節）。秒単位の 16 ビットの値で、0x003C は 60 秒である。
- **クライアント ID**: ブローカがクライアントを見分ける文字列。同じ ID の新しい接続が来ると、ブローカは前の接続を切る（6 節）。3.1.1 のブローカは 1〜23 バイトの英数字の ID を必ず受け付け、それより長い ID を受け付けるかは実装による。

CONNACK は 4 バイトで、受け入れたときは `20 02 00 00` である。3 バイト目の最下位ビットは Session Present（前の接続のときの状態をブローカが引き継いだか。4 節）、4 バイト目は結果で、0 が受け入れ、1〜5 は断った理由（版が合わない、ID を受け付けない、ブローカが使えない、ユーザ名かパスワードが違う、権限が無い）である。

### PUBLISH と SUBSCRIBE

メッセージを運ぶのは **PUBLISH** である。可変ヘッダはトピック名で、QoS が 1 か 2 のときは、その後に 2 バイトの**パケット識別子**が入る。パケット識別子は、答えを求めるパケットに送り手が付ける 16 ビットの番号（1〜65535。0 は使わない）で、答えには同じ番号が入る（08 章 4 節の DNS の ID と同じく、答えを要求に対応させる）。07 章 5 節の例（トピック名 `dev/1/temp`、データ `{"t":23.5,"h":41.25}` の 20 バイト）を運ぶ PUBLISH を示す。

```fig
e13_publish
```

ペイロードの長さは書かない。残りの長さから可変ヘッダの長さを引けば分かるからである。この例では残りの長さが 2 + 10 + 20 = 32（0x20）で、全体は 34 バイト、データのほかに MQTT の層で足されるのは 14 バイトになる（07 章 5 節で使った値はこれである）。

パケット識別子は、購読でも使う。たとえば `dev/1/cmd` を QoS 1 で購読する **SUBSCRIBE** は `82 0E 00 01 00 09 64 65 76 2F 31 2F 63 6D 64 01`（パケット識別子 1、フィルタ、希望する QoS）で、ブローカは **SUBACK** の `90 03 00 01 01`（同じ識別子と、認めた QoS。認めなければ 0x80）で答える。

PUBLISH を組み立てる関数を示す。残りの長さは、図の手順のとおり 7 ビットずつ書く。

```c
#define REMLEN_MAX 268435455u            /* 残りの長さの最大（4 バイト） */

/* PUBLISH を buf（cap バイト）に組み立て、全体のバイト数を返す。入りきらないか、値が不正なら 0。
   qos が 1・2 のときだけパケット識別子 pid（0 は使えない）を入れる */
size_t mqtt_build_publish(uint8_t *buf, size_t cap, const char *topic, const uint8_t *data,
                          size_t len, unsigned qos, int retain, int dup, uint16_t pid)
{
    size_t tlen = strlen(topic);
    if (tlen == 0 || tlen > 65535 || qos > 2 || (qos > 0 && pid == 0) || len > REMLEN_MAX)
        return 0;
    size_t rem = 2 + tlen + (qos > 0 ? 2 : 0) + len;        /* 可変ヘッダ + ペイロード */
    if (rem > REMLEN_MAX) return 0;
    uint8_t hdr[5];
    size_t h = 0, n = rem;
    hdr[h++] = (uint8_t)(0x30 | (dup ? 0x08 : 0) | (qos << 1) | (retain ? 1 : 0));
    do {                                                    /* 残りの長さ: 7 ビットずつ下の桁から */
        uint8_t d = n % 128;
        n /= 128;
        hdr[h++] = (n > 0) ? (uint8_t)(d | 0x80) : d;       /* まだ続くなら最上位ビットを 1 に */
    } while (n > 0);
    if (h + rem > cap) return 0;
    uint8_t *p = buf;
    memcpy(p, hdr, h); p += h;                              /* 固定ヘッダ */
    *p++ = (uint8_t)(tlen >> 8); *p++ = (uint8_t)tlen;      /* トピック名の長さ（ビッグエンディアン） */
    memcpy(p, topic, tlen); p += tlen;
    if (qos > 0) { *p++ = (uint8_t)(pid >> 8); *p++ = (uint8_t)pid; }
    memcpy(p, data, len); p += len;                         /* ペイロード（長さは書かない） */
    return (size_t)(p - buf);
}
```

この関数の出力は、Python で別に組み立てたバイト列と、12 通りの例（QoS・RETAIN・DUP の組み合わせと、残りの長さが 1〜3 バイトになる大きさ）で一致し、残りの長さの境目（127 と 128、16,383 と 16,384 など）でも正しかった。QoS 0 の PUBLISH を Mosquitto に送ると、ブローカは同じバイト列をそのまま購読者へ送った。

## 4. QoS — 0・1・2 の届け方

TCP は、失われたセグメントを送り直し、送った順に届ける（10 章）。しかし TCP が約束するのは接続が続いている間だけで、接続が切れると、送り手が書き込んだのにまだ届いていないバイトは失われ、送り手にはどこまで届いたかが分からない。Wi-Fi の切断（09 章 5 節）や、NAT の変換表の行が消えること（08 章 5 節）で、接続は実際に切れる。

```fig
e13_cut
```

MQTT は、接続が切れたときに送りかけのメッセージをどう扱うかを、メッセージごとに 3 つの段階から選ばせる。これが 3 節の QoS である。

- **QoS 0**（最大 1 回）: PUBLISH を 1 回送るだけで、確認応答は無い。送り手は送ったらすぐメッセージを忘れてよい。接続が切れると失われることがある。
- **QoS 1**（最低 1 回）: 受け手は **PUBACK** で確認応答を返す（05 章 4 節の ACK）。送り手は PUBACK が届くまでメッセージを持ち続け、届かないまま接続が切れたら、つなぎ直した後に同じパケット識別子で送り直す。失われないが、同じメッセージが 2 回以上届くことがある。
- **QoS 2**（ちょうど 1 回）: **PUBREC**・**PUBREL**・**PUBCOMP** を加えた 4 つのパケットで、重複も起きないようにする。

```fig
e13_qos
```

### QoS 1 — 送り直すと重複する

QoS 1 の送り直しには、05 章 4 節の ARQ と同じ問題がある。PUBLISH が失われた場合と PUBACK が失われた場合を、送り手は区別できない。送り直す PUBLISH では、固定ヘッダの DUP のビットを 1 にする。このビットを **DUP フラグ**という。しかし 3.1.1 の受け手は、PUBACK を返した後に同じパケット識別子の PUBLISH が来たら、DUP が 1 でも新しいメッセージとして扱う。05 章 4 節の受け手は番号を覚えて重複を捨てたが、QoS 1 の受け手は番号を覚えておかない。送り手がいつまで送り直してくるかが決まっていないので、覚えた番号を忘れてよい時が無いからである。したがって、PUBACK が失われると、受け手は同じメッセージを 2 回先へ渡す（Mosquitto に、同じ番号の PUBLISH を DUP = 1 でもう一度送ると、購読者には 2 回届いた）。

### QoS 2 — 2 段に分けて、受け手が番号を忘れる時を決める

QoS 2 の受け手は、受け取ったパケット識別子を覚えておき、覚えている間に同じ番号の PUBLISH が来たら、メッセージを渡さずに PUBREC だけを返す。そして、番号を忘れてよい時を決めるために、もう 1 往復を足す。送り手は PUBREC を受け取ったらメッセージを捨て、「その PUBLISH はもう送らない」という知らせの PUBREL を送る（PUBCOMP が届くまで送り直す）。受け手は PUBREL を受け取ったら番号を忘れて PUBCOMP を返し、送り手は PUBCOMP を受け取ってその番号を使い終える。QoS 1 と同じく、確認が 1 つ失われた場合を並べて比べる。

```fig
e13_qosfail
```

受け手が PUBREC を返した直後に番号を忘れると、PUBREC が失われたときに送り直された PUBLISH を、新しいメッセージと取り違える。番号を忘れてよいのは、送り手がもう PUBLISH を送らないと分かった PUBREL の後である。これが、往復が 2 回要る理由である。受け手がメッセージを先へ渡す（ブローカなら購読者へ、機器ならアプリケーションへ）のは、PUBLISH を受け取ったときでも PUBREL を受け取ったときでもよく、どちらでも 1 回しか渡さない（Mosquitto に、同じ番号の PUBLISH を PUBREL の前に 2 回送ると、購読者には 1 回だけ届いた）。

### セッション — 接続をまたいで覚えておくもの

QoS 1・2 の送り直しは、つなぎ直した後に行う。つながっている間は TCP が届けるので、3.1.1 は時間切れで送り直すことを求めていない。つなぎ直した後に送り直せるように、両者は接続が切れても次のものを覚えておく。接続をまたいで持ち続けるこの状態を**セッション**という。ブローカは、そのクライアントの購読の一覧、そのクライアントへ送ったが確認の済んでいない QoS 1・2 のメッセージ、留守の間に届いた QoS 1・2 のメッセージ、受け取った QoS 2 の番号を覚える。クライアントは、送ったが確認の済んでいない QoS 1・2 のメッセージと、受け取った QoS 2 の番号を覚える。

CONNECT のクリーンセッションのビット（3 節）を 1 にすると、ブローカは前のセッションを捨てて新しく始め、接続が切れたらそれも捨てる。これを**クリーンセッション**という。0 にすると、前のセッションがあれば引き継ぎ、切れた後も持ち続ける。これを**永続セッション**という。CONNACK の Session Present は、前のセッションを引き継いだときに 1 になる（Mosquitto に永続セッションで 2 回つなぐと、2 回目の CONNACK は `20 02 01 00` になった）。

永続セッションでつなぎ直すと、両者は確認の済んでいない PUBLISH（DUP = 1、同じパケット識別子）と PUBREL を、元の順に送り直し、ブローカは留守の間に届いたメッセージも送る（3.1.1 が送り直しを義務づけているのは、この場合だけである）。クリーンセッションでつなぎ直すと、確認の済んでいないメッセージは両方の側で捨てられるので、QoS 1・2 でも失われうる。また、機器が再起動して RAM の中身を失えば、確認待ちのメッセージも覚えた番号も消える。QoS 1・2 の約束が再起動をまたぐのは、それらをフラッシュに書いておく実装の場合だけである。

### QoS は区間ごとに決まる

QoS は、クライアントとブローカの間の 1 つの区間ごとの約束である。送り手からブローカまでは送り手が PUBLISH に書いた QoS で、ブローカから購読者までは、その QoS と、SUBACK で認めた購読の QoS のうち、小さいほうで運ばれる（Mosquitto でも、QoS 0 で購読したクライアントには、QoS 2 でパブリッシュしたメッセージが QoS 0 で届いた）。

```fig
e13_legs
```

QoS を上げると何が増えるかを、07 章 5 節の例（トピック名 10 バイト、データ 20 バイト）を 1 つ送るときの、1 つの区間の数で示す。線の上のバイト数は、07 章 5 節と同じく Ethernet・IPv4・TCP で数え、パケットを 1 つずつ別のセグメントで送るとし、TCP の確認応答のセグメントは数えない。

| QoS | 送るパケット | MQTT の層のバイト数 | 線の上のバイト数 | TLS 1.3 を使うとき | 送り手がメッセージを捨てられるまで |
|---|---|---|---|---|---|
| 0 | PUBLISH | 34 | 112 | 134 | 送ったらすぐ |
| 1 | PUBLISH・PUBACK | 36 + 4 = 40 | 114 + 84 = 198 | 240 | 1 往復（PUBACK） |
| 2 | PUBLISH・PUBREC・PUBREL・PUBCOMP | 36 + 4 × 3 = 48 | 114 + 84 × 3 = 366 | 448 | 1 往復（PUBREC）。番号を使い終えるまで 2 往復 |

QoS 1・2 の PUBLISH は、パケット識別子の分だけ 2 バイト長い。4 バイトの確認は、IP のパケットにしても 44 バイトで、Ethernet のペイロードの最小の 46 バイトに満たないので詰め物が入り、線の上では 84 バイトになる（07 章 2 節）。

選び方の目安は次のとおりである。一定の間隔で送る測定値は、1 つ失われても次の値が来るので、QoS 0 か 1 で足りる。命令や警報のように失いたくないものは QoS 1 にし、重複しても困らないように作る（何度行っても結果が同じ操作にする、通し番号で受け手が見分ける。15 章 4 節）。QoS 2 は、パケットと往復が多く、両者が番号を覚えておく必要もあるので、重複を受け手の側で見分けられない場合に限って使う。

## 5. 接続を見張る — キープアライブとウィルメッセージ

QoS 1・2 の送り直しは、接続が切れたことに気づいてから始まる。ところが TCP の接続は、黙って切れることがある。機器の電源が突然切れたとき、途中の回線が切れたとき、NAT の変換表の行が消えたときは、相手に何も届かないので、残った側は接続がまだあると思い続ける（10 章 7 節のハーフオープン）。TCP キープアライブは、既定では使われないか、2 時間など長い間隔のことが多い（10 章 7 節）。そこで MQTT は、自分でも接続を見張る。

### キープアライブ — 黙っている時間に上限を決める

CONNECT のキープアライブの欄に書く秒数 K を、MQTT の**キープアライブ**という。3.1.1 は、K について次の 3 つを定めている。

1. クライアントは、パケットを送り終えてから次のパケットを送り始めるまでの時間を K 以下にする。送るものが無ければ **PINGREQ**（`C0 00`）を送り、ブローカは **PINGRESP**（`D0 00`）で答える。
2. ブローカは、クライアントから 1.5 K の間なにも受け取らなければ、ネットワークが壊れたものとみなして接続を切る。
3. クライアントは、PINGREQ を送ってから妥当な時間のうちに PINGRESP が来なければ、接続を閉じるべきである。

K = 0 にすると見張りをしない。K の最大は 65535 秒（18 時間 12 分 15 秒）で、3.1.1 は数分を典型としている。ブローカの期限が K ではなく 1.5 K なので、クライアントの送る時刻がわずかに遅れたり、途中の遅延がばらついたり、TCP の再送で届くのが遅れたりしても、正常な接続は切られない。

```fig
e13_ka
```

接続が黙って切れてから、それぞれが気づくまでの最大の時間を求める。

**方針**: 故障の直前に、クライアントが最後のパケットを送ったとする（このとき、両者が気づくのが最も遅くなる）。その時刻を 0 として、ブローカの期限と、クライアントが次の PINGREQ を送って答えを待つ期限を求める。PINGRESP を待つ時間を $`T_\mathrm{r}`$（規格の「妥当な時間」。実装が決める）とし、故障の後、クライアントは PUBLISH を送らないとする。

**導出**: ブローカが最後に受け取ったのは時刻 0 のパケットなので、ブローカは時刻 1.5 K に接続を切る。クライアントは時刻 0 から何も送らないので、時刻 K に PINGREQ を送り、PINGRESP は来ないので、時刻 K + $`T_\mathrm{r}`$ に切断に気づく。故障が時刻 0 より後に起きたなら、故障からの時間はどちらもこれより短い。したがって、気づくまでの時間は、ブローカで最大 1.5 K、クライアントで最大 K + $`T_\mathrm{r}`$ である ∎

K = 60 秒、$`T_\mathrm{r}`$ = 10 秒なら、ブローカは 90 秒以内、クライアントは 70 秒以内に気づく。ただし、ブローカの実装によっては期限を一定の間隔でまとめて調べるので、実際に切るのはこれより遅れる（手元の Mosquitto 2.0.18 は約 6 秒ごとにまとめて調べていて、K = 2 秒（1.5 K = 3 秒）では、黙ってから切るまでに、試すたびに 4.7〜8.1 秒かかった）。

導出では、故障の後に PUBLISH を送らないとした。1 つ目の決まりは送る間隔の上限なので、QoS 0 の PUBLISH を K より短い間隔で送り続けるクライアントは、PINGREQ を一度も送らない。QoS 0 の PUBLISH には答えが返らないので、回線が切れても気づかず、TCP が送り直しをあきらめるまで（Linux の既定で 15 分ほど。10 章 7 節）送り続ける。PINGREQ はいつ送ってもよいので、「最後に受け取ってから K たったら PINGREQ を送る」決まりを足しておけば、受け取る側からも切断に気づける。

キープアライブは、08 章 5 節の、NAT の変換表の行を保つためのパケットも兼ねる。クライアントは少なくとも K ごとにパケットを送るので、08 章 5 節の条件 $`T_\mathrm{k} < T_\mathrm{h}`$ に $`T_\mathrm{k}`$ = K を当てはめ、K を保持時間 $`T_\mathrm{h}`$ より短くすれば、行は消えない。失われたセグメントは TCP が送り直すので、間隔の延びはその時間の分で済むが、余裕を見て K を $`T_\mathrm{h}`$ より十分短くする。K が長すぎて行が消えると、その後にブローカから送った命令は NAT で捨てられ、その TCP の接続は使えなくなる。逆に K を短くすると、電池で動く機器の平均電流が増える（08 章 5 節の $`Q_\mathrm{k} / T_\mathrm{k}`$。Wi-Fi では 09 章 4 節）。

### ウィルメッセージと保持メッセージ

機器が黙って消えたことに、ブローカは気づいても、その機器のデータを待っているアプリには分からない。そこで機器は、自分が不意に切れたときにブローカが代わりにパブリッシュするメッセージを、CONNECT に入れておける。これを**ウィルメッセージ**という（will は遺言の意味）。接続フラグのウィルのビットを 1 にし、トピック名・ペイロード・QoS・RETAIN を指定する。クライアントが正常に切断するときは、**DISCONNECT**（`E0 00`）を送ってから閉じ、ブローカはウィルメッセージを捨てる。ブローカがウィルメッセージをパブリッシュするのは、ネットワークの誤りに気づいたとき、1.5 K が過ぎたとき、クライアントが DISCONNECT を送らずに接続を閉じたときなどである。

また、ふつうのメッセージは、その時点の購読者にしか届かず、後から購読を始めたアプリは、次のメッセージが来るまで機器の状態を知らない。そこで PUBLISH の RETAIN のビット（3 節）を 1 にすると、ブローカはそのメッセージを、そのトピックの最後の値として覚えておく。こうして覚えさせたメッセージを**保持メッセージ**という。ブローカは、トピックごとに 1 つだけを持って新しいもので置き換え、新しい購読が一致するとすぐに送る（RETAIN を 1 にして送るので、受け手は以前の値だと分かる。購読を続けている受け手には 0 にして送る）。ペイロードが 0 バイトの保持メッセージを送ると、そのトピックの保持メッセージは消える。

2 つを組み合わせると、機器がつながっているかどうかを、いつ購読を始めた者にも知らせられる（この流れは Mosquitto で確かめた）。

```fig
e13_will
```

機器は、つないだら `dev/1/status` に `online` を保持メッセージとしてパブリッシュし、ウィルメッセージには同じトピックの `offline`（保持）を入れておく。機器が黙って消えると、ブローカは 1.5 K の後に `offline` をパブリッシュし、それが新しい保持メッセージになる。後から `dev/+/status` を購読したアプリにも、各機器の最後の状態がすぐに届く。機器が自分から切るとき（眠る前など）はウィルメッセージが出ないので、DISCONNECT の前に `offline` を自分でパブリッシュする。

05 章 2 節の通信タスクの考え方で、MQTT の接続は 1 つのタスク（以下、MQTT タスク）だけが扱う。ほかのタスクは、送りたいメッセージをキューで MQTT タスクに頼み、受け取ったメッセージもキューで受け取る。MQTT タスクは、TLS（12 章）の上の TCP の接続（11 章）を持ち、受信の区切り、確認待ちのメッセージとパケット識別子、キープアライブの時刻（最後に送った時刻・受け取った時刻、PINGRESP の期限）、接続の状態を管理する。組み込み向けの MQTT のライブラリ（Eclipse Paho の組み込み向け、lwIP に含まれる MQTT のクライアント、ESP-IDF の esp-mqtt など。版によって細部が異なる）も、名前は違うが、これらを中に持っている。

### 受信 — バイトの列をパケットに区切る

TCP（TLS）からは、パケットの区切りと関係なく届く。1 回の受信に 2 つのパケットが入っていることも、1 つのパケットが途中で切れていることもある（11 章 2 節の部分受信）。そこで、届いたバイトを 1 つずつ、3 つの状態を持つ状態機械（05 章 1 節）に通して区切る。

```fig
e13_rxsm
```

```c
#define RX_MAX 512                       /* 受け取れる残りの長さの上限（RAM に合わせて決める） */
enum rx_state { RX_FIRST, RX_LEN, RX_BODY };   /* 1 バイト目待ち・残りの長さ・残りのバイト */
struct mqtt_rx {
    enum rx_state st;
    uint8_t  first;                      /* 固定ヘッダの 1 バイト目 */
    uint32_t rem, mult, got;             /* 残りの長さ、次の 7 ビットの重み、受け取ったバイト数 */
    uint8_t  body[RX_MAX];               /* 可変ヘッダとペイロード */
};

/* 届いたバイトを、届いた単位のまま渡す。パケットが 1 つそろうたびに on_packet を呼ぶ。
   残りの長さが壊れているか、受け取れない大きさなら -1 を返す（呼び手は接続を閉じる） */
int mqtt_rx_feed(struct mqtt_rx *r, const uint8_t *p, size_t n,
                 void (*on_packet)(uint8_t first, const uint8_t *body, uint32_t len))
{
    for (size_t i = 0; i < n; i++) {
        uint8_t b = p[i];
        if (r->st == RX_FIRST) {                          /* 固定ヘッダの 1 バイト目 */
            r->first = b; r->rem = 0; r->mult = 1; r->got = 0; r->st = RX_LEN;
        } else if (r->st == RX_LEN) {                     /* 残りの長さを 7 ビットずつ */
            r->rem += (uint32_t)(b & 0x7F) * r->mult;
            if (b & 0x80) {
                if (r->mult == 128u * 128 * 128) return -1;   /* 4 バイト目でも続く: 壊れている */
                r->mult *= 128;
            } else if (r->rem > RX_MAX) {
                return -1;                                /* 受け取れない大きさ（03 章 4 節） */
            } else if (r->rem == 0) {
                on_packet(r->first, r->body, 0); r->st = RX_FIRST;   /* PINGRESP など */
            } else {
                r->st = RX_BODY;
            }
        } else {                                          /* 残りのバイトをためる */
            r->body[r->got++] = b;
            if (r->got == r->rem) { on_packet(r->first, r->body, r->rem); r->st = RX_FIRST; }
        }
    }
    return 0;
}
```

残りの長さは 3 節の符号化の逆で、下位 7 ビットに重み（1、128、$`128^2`$、$`128^3`$）を掛けて足していく。4 バイト目でも続きの印が立っていれば壊れた長さとし、`RX_MAX` を超える長さなら、残りを受け取る前に -1 を返して接続を閉じる（03 章 4 節の、長さの上限を確かめる対策）。3.1.1 には、受け取れる大きさをブローカに知らせる方法が無いので、機器が購読するトピックには大きなメッセージを送らないと決めておく。このコードは、7 種類のパケットを 200 個並べた 23,063 バイトの列を、でたらめな大きさに 300 通りに区切って渡し、どの区切り方でも 200 個を正しく取り出すことと、壊れた長さと大きすぎる長さで -1 を返すことを確かめてある。

### QoS 1 の確認待ち

QoS 1 のメッセージは、PUBACK が届くまで写しを持ち続ける。05 章のストップアンドウェイトと違い、MQTT は確認を待たずに次の PUBLISH を送ってよい。確認待ちを何個まで持つかは 3.1.1 では決まっていないので、RAM に合わせて実装が決める。確認待ちの列を、04 章 3 節のリングバッファの形で持つ例を示す。

```c
#define INFLIGHT 4                       /* 確認待ちにできる QoS 1 のメッセージの数 */
struct pending { uint16_t pid, len; uint8_t pkt[128]; };   /* pid = 0 は確認済みの印 */
static struct pending q[INFLIGHT];
static uint32_t q_head, q_tail;          /* 増え続ける添字（04 章 3 節）。確認待ちの数は q_head - q_tail */
uint16_t g_pid;                          /* 最後に使ったパケット識別子（SUBSCRIBE と共有） */

/* QoS 1 の PUBLISH を確認待ちの列に入れてから送る。列が満杯なら -1（呼び手は後で送る） */
int mqtt_publish_q1(const char *topic, const uint8_t *data, size_t len)
{
    if (q_head - q_tail == INFLIGHT) return -1;
    struct pending *e = &q[q_head % INFLIGHT];
    if (++g_pid == 0) g_pid = 1;         /* 1〜65535 を順に使う（0 は使わない） */
    size_t n = mqtt_build_publish(e->pkt, sizeof e->pkt, topic, data, len, 1, 0, 0, g_pid);
    if (n == 0) return -1;
    e->pid = g_pid; e->len = (uint16_t)n; q_head++;
    return net_send(e->pkt, n);
}

void mqtt_on_puback(uint16_t pid)        /* 確認済みの印（pid = 0）を付け、古い側から外す */
{
    for (uint32_t i = q_tail; i != q_head; i++)
        if (q[i % INFLIGHT].pid == pid) q[i % INFLIGHT].pid = 0;
    while (q_tail != q_head && q[q_tail % INFLIGHT].pid == 0) q_tail++;
}

void mqtt_resend_inflight(void)          /* つなぎ直した直後に、送った順に送り直す */
{
    for (uint32_t i = q_tail; i != q_head; i++) {
        struct pending *e = &q[i % INFLIGHT];
        if (e->pid != 0) { e->pkt[0] |= 0x08; net_send(e->pkt, e->len); }   /* DUP = 1、番号は同じ */
    }
}
```

`net_send` は、TLS の接続に全部を書き込む関数（11 章 2 節の `send_all` にあたる）で、この章で仮に置く。3.1.1 では PUBACK は PUBLISH を受け取った順に返すことになっているが、順番が違っても列が詰まらないように、確認済みの印を付けてから古い側から外す。確認待ちは多くとも 4 個で、番号は 1 から順に使うので、使用中の番号と重なることはない。このコードは、満杯のとき、順番の違う確認、送り直しの DUP と順番、番号の一周（65535 の次が 1）を PC の上で確かめ、Mosquitto に実際に送って PUBACK で列が空になることも確かめてある。

### つなぎ直す

接続が切れたら（TLS・TCP の誤り、PINGRESP の期限切れ、壊れたパケット）、MQTT タスクは 05 章 5 節の指数バックオフとジッタで待ってから、つなぎ直す。Wi-Fi・DNS・TCP・TLS のどの層からやり直すかは 15 章 2 節で扱う。MQTT の層の手順を図に示す。

```fig
e13_reconn
```

CONNACK の結果が 0 以外（ID を受け付けない、権限が無いなど）なら、繰り返しても直らないので、長く待つか利用者に知らせる。Session Present が 0 なら、ブローカはセッションを持っていない（クリーンセッションでつないだか、ブローカの再起動などで消えた）ので、購読をやり直す。永続セッションのつもりでも消えていることがあるので、このビットは必ず見る。確認待ちのメッセージは、送った順に送り直す。Session Present が 1 なら規格どおりの送り直しである。0 なら前のセッションは捨てられているので、ブローカには新しいメッセージとして届く（失わないために、アプリケーションの判断で送り直すことになる）。最後に、状態のトピックに `online` を保持メッセージとしてパブリッシュし直す（5 節）。

受け取ったメッセージは、ライブラリがコールバック（05 章 2 節）で知らせることが多い。コールバックは MQTT タスクの中で呼ばれるので、そこでフラッシュに書いたり、ほかの応答を待ったりすると、その間 MQTT タスクは止まり、PINGREQ が遅れてブローカに切られ、受信のバッファもあふれる。コールバックではメッセージを写してキューに入れるだけにし、処理はほかのタスクで行う。

クライアント ID は、機器ごとに異なるもの（製造番号や、クライアント証明書の名前。12 章 5 節）から作る。同じ ID を書き込んでしまった 2 台は、互いに相手の接続をブローカに切らせ、つなぎ直してはまた相手を切る、を繰り返す。切られるたびにその接続のウィルメッセージも出るので（Mosquitto で確かめた）、状態は `online` と `offline` の間を行き来し続ける。

### ペイロードの形

MQTT はペイロードの中身を決めていない。よく使われるのは、文字の形と、決まった並びのバイナリである。文字の形の代表は、07 章 5 節の `{"t":23.5,"h":41.25}` のように、名前と値の組を `:` でつなぎ、`,` で区切って `{` `}` で囲む **JSON**（RFC 8259）である。07 章 5 節の測定値を、2 つの形で比べる。

```fig
e13_payload
```

バイナリの形では、温度を 100 倍した 2350 を符号付き 16 ビット、湿度を 100 倍した 4125 を符号なし 16 ビットにし、ビッグエンディアンで並べる（03 章 6 節の固定小数点）。PUBLISH は 34 バイトから 18 バイトに、線の上のバイト数は 112 バイトから 96 バイトになる。トピック名と下の層のヘッダは残るので、線の上で減るのは 14 % である。JSON は受け手が読みやすく、項目を足しても古い受け手が困らない。バイナリは小さいが、並びを変えるときのために版の番号を入れる（03 章 7 節の TLV のように、後から項目を足せる形にする方法もある）。どちらにするかは、大きさだけでなく、サーバの側で読む手間や項目を足す見込みで決める。

### MQTT 5.0 で加わったもの

5.0 は、3.1.1 と同じ形の固定ヘッダと残りの長さを使い（CONNECT のレベルは 5）、主に次のものを加えた。確認や DISCONNECT が結果や断った理由を 1 バイトで返す理由コード（ブローカからも DISCONNECT を送れる）。可変ヘッダに追加の欄を置けるプロパティ（その長さは残りの長さと同じ符号化で書く）。一度送ったトピック名を以後は 2 バイトの番号で表すトピックエイリアス。クリーンセッションを、始めるときに前のセッションを捨てるかと、切れた後にセッションを何秒持ち続けるか（セッションの有効期限）の 2 つに分けたこと。そのほか、確認待ちの数の上限（Receive Maximum）、受け取れるパケットの大きさの上限、自分の送ったものを受け取らない購読の設定などである。

TLS を使う設定（ポート 8883、クライアント証明書による認証、機器ごとのトピックの権限）は、[IoT セキュリティシリーズ 16 章 6 節](../iotsec/16_通信セキュリティ.md#mqtt-の設定) が詳しい。
