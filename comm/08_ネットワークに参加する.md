# 08. ネットワークに参加する — ARP・DHCP・DNS・NAT

> **この章で扱う問い.**
> 07 章では、データが層ごとのヘッダに包まれて宛先まで運ばれる様子を見た。そこでは、宛先の IP アドレスと、リンク層で渡す相手の MAC アドレスは分かっているものとしていた。しかし、電源を入れた直後の機器は、自分の IP アドレスも、サーバの IP アドレスも、隣の機器の MAC アドレスも知らない。
>
> この章では次の 3 つの問いに答える。
>
> 1. 機器は、宛先が自分と同じネットワークの中にいるかをどう判断し、まず誰に渡すのか。
> 2. 自分のアドレス、サーバのアドレス、渡す相手の MAC アドレスを、機器はどう手に入れるのか。
> 3. 家庭や会社のネットワークの中にいる機器へ、外のサーバからはなぜ接続できないのか。機器の側では何をすればよいのか。
>
> 答えの道具は、アドレスとネットマスクの AND、問い合わせて答えをもらう 3 つのプロトコル（ARP・DHCP・DNS）、そして NAT の変換表とその保持時間である。

## 1. 同じネットワークの中と外

家庭のネットワークを例に、機器がパケットを送るとき、まず誰に渡すのかを考える。この節と次の節では、機器は自分の IP アドレスと、この節で定義するネットマスクとデフォルトゲートウェイを、すでに知っているものとする。それらを機器が手に入れる方法は 3 節で扱う。

```fig
e08_lan
```

図の機器（192.168.1.23）と PC（192.168.1.40）は、同じ Wi-Fi のアクセスポイント（09 章）または同じ Ethernet につながっている。リンク層のフレームは、このように同じリンクにつながった機器の間でしか届かない（07 章 2 節）。そのため、機器は PC にはフレームを直接届けられるが、インターネットの先のサーバ（203.0.113.10）には直接届けられない。サーバへ送るときは、フレームをいったんルータに渡し、ルータが IP の宛先を見てその先へ運ぶ（07 章 3 節）。したがって機器は、パケットを送るたびに、宛先が同じリンクにいるかどうかを判断しなければならない。この判断には、IP アドレスの上位のビットを使う。

IPv4 アドレスの 32 ビットのうち、上位の決まった数のビットが等しいアドレスのまとまりを**サブネット**といい、その上位の部分を**ネットワーク部**という。ネットワークを管理する人（家庭ではルータの設定）は、1 つのリンクにつながる機器に、ネットワーク部が等しいアドレスを割り当てる。だから機器は、宛先のネットワーク部が自分と等しければ、宛先は同じリンクにいると判断できる。

ネットワーク部の長さは、上位のそのビット数だけ 1 を並べ、残りを 0 にした 32 ビットの値で表す。この値を**ネットマスク**（マスク）という。ネットワーク部のビット数を**プレフィックス長**といい、アドレスの後ろに `/24` のように書く。192.168.1.23/24 は「アドレスは 192.168.1.23、上位 24 ビットがネットワーク部」を表し、ネットマスクは 255.255.255.0 である。よく使うプレフィックス長の実例を示す。

| プレフィックス長 | ネットマスク | 16 進 | サブネットの中のアドレスの数 |
|---|---|---|---|
| /8 | 255.0.0.0 | 0xFF000000 | $`2^{24}`$ = 16,777,216 |
| /16 | 255.255.0.0 | 0xFFFF0000 | $`2^{16}`$ = 65,536 |
| /24 | 255.255.255.0 | 0xFFFFFF00 | $`2^{8}`$ = 256 |
| /26 | 255.255.255.192 | 0xFFFFFFC0 | $`2^{6}`$ = 64 |
| /30 | 255.255.255.252 | 0xFFFFFFFC | $`2^{2}`$ = 4 |

プレフィックス長が $`n`$ なら、ネットワーク部の後ろに残る $`32 - n`$ ビットの組み合わせの数だけ、つまり $`2^{32-n}`$ 個のアドレスが 1 つのサブネットに入る。

### ネットワーク部を比べる — マスクとの AND

宛先が同じサブネットにいるかは、2 つのアドレスのネットワーク部を比べれば分かる。ネットワーク部だけを取り出すのに、ネットマスクとのビットごとの AND を使う。

**方針**: どのビット $`x`$ についても $`x \;\mathrm{AND}\; 1 = x`$、$`x \;\mathrm{AND}\; 0 = 0`$ であることから、アドレスとマスクの AND が「ネットワーク部はそのまま、残りのビットは 0」の値になることを示す。そのうえで、2 つのアドレスのネットワーク部が等しいことと、AND の結果が等しいことが同じだと導く。

**導出**: アドレス $`a`$ の第 $`i`$ ビット（$`i = 31`$ が最上位）を $`a_i`$、マスク $`m`$ の第 $`i`$ ビットを $`m_i`$ とし、プレフィックス長を $`n`$ とする。$`m`$ は上位 $`n`$ ビット（$`i = 31, \dots, 32 - n`$）が 1、残りが 0 である。AND はビットごとの演算なので、$`a \;\mathrm{AND}\; m`$ の第 $`i`$ ビットは $`a_i \;\mathrm{AND}\; m_i`$ である。上位 $`n`$ ビットでは $`m_i = 1`$ なので $`a_i \;\mathrm{AND}\; 1 = a_i`$、残りのビットでは $`m_i = 0`$ なので $`a_i \;\mathrm{AND}\; 0 = 0`$ となる。つまり $`a \;\mathrm{AND}\; m`$ は、$`a`$ のネットワーク部をそのまま残し、残りのビットをすべて 0 にした値である。

もう 1 つのアドレス $`b`$ についても、$`b \;\mathrm{AND}\; m`$ は $`b`$ のネットワーク部と、すべて 0 のビットからなる。残りのビットはどちらも 0 で常に等しいので、$`a \;\mathrm{AND}\; m`$ と $`b \;\mathrm{AND}\; m`$ が等しいのは、上位 $`n`$ ビット、つまりネットワーク部が等しいときであり、そのときに限る。したがって

$$
a \text{ と } b \text{ が同じサブネットにある} \iff (a \;\mathrm{AND}\; m) = (b \;\mathrm{AND}\; m)
$$

である ∎

実際の値で計算すると次のようになる。

```fig
e08_and
```

上の段の /24 では、PC の 192.168.1.40 は AND の結果が自分と同じ 192.168.1.0 なので同じサブネット、サーバの 203.0.113.10 は 203.0.113.0 なので外である。下の段のように、同じ 192.168.1.23 でもマスクが /26 なら、192.168.1.100 は外になる。4 つ目の数の上位 2 ビットまでがネットワーク部に入り、23（0b0001_0111）では 00、100（0b0110_0100）では 01 と異なるからである。アドレスの見た目が似ていても、中か外かはマスクで決まる。

C で書くと次のようになる。アドレスは 32 ビットの数として持ち、最初の数（192）を上位 8 ビットに置く。

```c
/* IPv4 アドレスを 32 ビットの数にする（最初の数が上位 8 ビット） */
#define IP4(a, b, c, d) \
    ((uint32_t)(a) << 24 | (uint32_t)(b) << 16 | (uint32_t)(c) << 8 | (uint32_t)(d))

/* プレフィックス長 n（0〜32）からネットマスクを作る */
static uint32_t prefix_to_mask(unsigned n)
{
    if (n == 0) return 0;        /* 32 ビットずらすのは C では未定義なので分ける */
    if (n > 32) n = 32;
    return 0xFFFFFFFFu << (32 - n);        /* 上位 n ビットが 1 */
}

/* a と b が、マスク m のもとで同じサブネットにあるか（ネットワーク部が等しいか） */
static bool same_subnet(uint32_t a, uint32_t b, uint32_t m)
{
    return (a & m) == (b & m);
}

/* 宛先 dst へ送るとき、リンク層で次に渡す相手の IP アドレス
   （その相手の MAC アドレスを 2 節の方法で調べる） */
static uint32_t next_hop(uint32_t me, uint32_t mask, uint32_t gw, uint32_t dst)
{
    return same_subnet(me, dst, mask) ? dst : gw;
}
/* 例: IP4(192,168,1,23) は 0xC0A80117、prefix_to_mask(26) は 0xFFFFFFC0。
   192.168.1.23 と 192.168.1.100 は、/26 では same_subnet が false になる */
```

TCP/IP スタックによっては、アドレスをネットワークバイトオーダ（03 章 6 節）のバイトの並びのまま 32 ビットの変数に入れている。その場合も、マスクを同じ並びで持っていれば判定の結果は変わらない。AND と比較はビットごとの演算なので、$`a`$ と $`m`$ のバイトを同じように並べ替えても、結果のバイトが同じように並べ替わるだけだからである。ただし、上の `prefix_to_mask` が作るマスクは数としての並びなので、そのような変数と組み合わせるときは、マスクもネットワークバイトオーダに直してから使う。

### 外の宛先はデフォルトゲートウェイへ

宛先が同じサブネットにないとき、機器はパケットを、同じサブネットにいるルータに渡す。このために設定しておくルータの IP アドレスを**デフォルトゲートウェイ**という（「ほかに当てはまる道が無いときに使う出口」という意味）。名前は似ているが、01 章 1 節のゲートウェイ（異なる通信方式の間を取り次ぐ機器）とは別の用語である。初期のインターネットの文書で、ルータをゲートウェイと呼んでいた名残である。デフォルトゲートウェイは、自分と同じサブネットの中になければならない。そうでなければ、デフォルトゲートウェイにもフレームを直接届けられないからである。

上の `next_hop` は、この判断をそのまま書いたものである。宛先が同じサブネットにあれば宛先そのものを、なければデフォルトゲートウェイを返す。どちらの場合も、機器はリンク層のフレームの宛先に、返された相手の MAC アドレスを書かなければならない。

まとめると、機器が最初のパケットをサーバへ送るまでに要るものは、自分の IP アドレス・ネットマスク・デフォルトゲートウェイ、次に渡す相手の MAC アドレス、宛先のサーバの IP アドレスである。次の 2 節では MAC アドレスを知る方法（ARP）を、3 節では自分のアドレスとネットマスク・デフォルトゲートウェイを借りる方法（DHCP）を、4 節ではサーバの名前から IP アドレスを調べる方法（DNS）を扱う。

## 2. ARP — IP アドレスから MAC アドレスを知る

1 節で、次に渡す相手の IP アドレスが決まった。しかし Ethernet や Wi-Fi のフレームの宛先には、IP アドレスではなく MAC アドレスを書く（07 章 2 節）。相手の MAC アドレスを知らなければ、リンクにつながる全員に問い合わせるしかない。

リンクにつながるすべての機器に同時に届けることを**ブロードキャスト**という。Ethernet と Wi-Fi では、宛先の MAC アドレスを FF:FF:FF:FF:FF:FF（48 ビットすべて 1）にしたフレームを、同じリンクのすべての機器が受け取る。IP にもブロードキャストのアドレスがある。255.255.255.255 は自分のリンクの全員を、ネットワーク部の後ろをすべて 1 にしたアドレス（192.168.1.0/24 なら 192.168.1.255）はそのサブネットの全員を表す。ルータは、ふつうの設定ではブロードキャストを外のネットワークへ転送しないので、ブロードキャストが届くのはリンクの中だけである。

サブネットのアドレスのうち、ネットワーク部の後ろがすべて 0 のもの（192.168.1.0）はサブネットそのものを表し、すべて 1 のもの（192.168.1.255）はブロードキャストに使う。どちらも機器には割り当てないので、/24 のサブネットで機器に割り当てられるのは 256 − 2 = 254 個である。

**ARP**（Address Resolution Protocol、RFC 826）は、IP アドレスから MAC アドレスを知るためのプロトコルである。機器がデフォルトゲートウェイ 192.168.1.1 の MAC アドレスを知る手順を図に示す。図の MAC アドレスは、文書の例のために予約された範囲（RFC 7042）のものである。

```fig
e08_arp_seq
```

1. 機器は「192.168.1.1 を持っている機器は、MAC アドレスを教えてほしい」という ARP の要求を、ブロードキャストで送る。
2. リンクのすべての機器が要求を受け取る。尋ねられた IP アドレスを持たない機器（図の PC）は捨てる。
3. 192.168.1.1 を持つルータだけが、自分の MAC アドレスを入れた ARP の応答を、要求した機器あてに返す。ルータは同時に、要求に入っていた機器の IP アドレスと MAC アドレスの組を覚える。直後に機器へ送るものがあることが多いからである。

ARP の要求と応答は、IP のパケットには入れず、EtherType 0x0806 の Ethernet フレームのデータとして直接運ぶ（07 章 2 節）。中身は次の 28 バイトである。

```fig
e08_arp_bytes
```

### ARP キャッシュ

パケットを送るたびに問い合わせると、そのたびに 1 往復の待ち時間と、リンクの全員が受け取るブロードキャストが増える。そこで機器は、得た IP アドレスと MAC アドレスの組を表に記録しておき、しばらくの間はそれを使う。この表を **ARP キャッシュ**という。記録には期限があり、期限が切れたら問い合わせ直す。同じ IP アドレスが、機器の入れ替えなどで別の MAC アドレスに変わることがあるからである。期限の長さは実装によって違い、数十秒から数十分まで幅がある。答えを待つ間、送ろうとしたパケットは保留されるが、小さな TCP/IP スタックでは保留できるパケットの数が少ない（設定による）。

### 外の宛先では、ゲートウェイの MAC アドレスを聞く

宛先がインターネットの先のサーバでも、ARP で聞くのはデフォルトゲートウェイの MAC アドレスである。3 つの場合を比べる。

```fig
e08_arp_mac
```

外の宛先へのフレームでは、宛先の MAC アドレスはルータのもの、その中の IP パケットの宛先 IP アドレスはサーバのものになる。ルータはフレームを受け取ると、IP の宛先を見て次の区間へ送り、そのときリンク層のヘッダを付け替える。IP の宛先は最後まで変わらないが、MAC アドレスは区間ごとに変わる。図の (c) のようにサーバの IP アドレスで ARP の要求を出しても、サーバは同じリンクにいないので、答えは返ってこない。

ARP には、答えた相手が本物かどうかを確かめる仕組みが無い。同じリンクにいる悪意のある機器が偽の応答を返すと、機器はその機器にフレームを渡してしまう（ARP スプーフィング）。そのため、通信の中身は TLS（12 章）で暗号化し、相手を確かめる。

## 3. DHCP — アドレスを借りる

1・2 節では、機器が自分の IP アドレス・ネットマスク・デフォルトゲートウェイを知っているものとした。これらを機器ごとに手で設定することもできる（固定の設定）。しかし機器の数が多いと手間がかかり、同じアドレスを 2 台に設定してしまう誤りも起きる。そこで多くのネットワークでは、ネットワークの中のサーバが、つながってきた機器にアドレスを貸し出す。

**DHCP**（Dynamic Host Configuration Protocol、RFC 2131）は、機器がネットワークの設定をサーバから受け取るためのプロトコルである。家庭では、ルータが DHCP のサーバを兼ねていることが多い。機器が受け取る主なものを、例の値とともに示す。アドレス以外の値は、メッセージの中に「オプション」として、番号 1 バイト・長さ 1 バイト・値の順に並ぶ（03 章 7 節の TLV と同じ形。番号は RFC 2132 による）。

| 受け取るもの | 例の値 | 入る場所 |
|---|---|---|
| 機器の IP アドレス | 192.168.1.23 | メッセージの固定の欄（yiaddr） |
| ネットマスク | 255.255.255.0 | オプション 1 |
| デフォルトゲートウェイ | 192.168.1.1 | オプション 3 |
| 名前を調べるサーバ（DNS サーバ。4 節） | 192.168.1.1 | オプション 6（複数を並べられる） |
| リース時間（下で定義） | 86400 秒（1 日） | オプション 51 |

DHCP のメッセージは UDP で運ばれ、機器はポート 68、サーバはポート 67 を使う。機器はまだ IP アドレスを持たないので、最初のメッセージは送信元を 0.0.0.0、宛先を 255.255.255.255（2 節のブロードキャスト）にして送る。

### 4 つのメッセージ

アドレスを借りるまでに、機器とサーバは 4 つのメッセージをやり取りする。リンクに DHCP のサーバが 2 台ある場合を図に示す（ふつうの家庭では 1 台だが、2 台あると、4 つが必要な理由が分かる）。

```fig
e08_dhcp_seq
```

1. **DISCOVER**: 機器が「アドレスを貸してほしい」とブロードキャストする。自分の MAC アドレスと、やり取りを見分けるための乱数の番号（xid）を入れる。
2. **OFFER**: DHCP のサーバが「このアドレスを貸せる」と、アドレスと設定の値を提示する。サーバが 2 台あれば、OFFER も 2 つ届く。
3. **REQUEST**: 機器は 1 つの OFFER を選び、「サーバ A が提示した 192.168.1.23 を借りる」と送る。選んだサーバの識別子（オプション 54。サーバの IP アドレス）を入れて、これもブロードキャストで送る。選ばれなかったサーバ B にも、自分の提示が断られたことを知らせるためである。B は、提示のために取っておいたアドレスを、ほかの機器に貸せるようになる。
4. **ACK**: 選ばれたサーバが貸し出しを確定させる。機器はこの ACK を受け取ってから、アドレスを使い始める。05 章 4 節の確認応答（ACK）と同じ考え方だが、ここでは DHCP のメッセージの名前である。

サーバの応答には、機器の要求と同じ xid が入る。リンクのほかの機器もブロードキャストで DHCP を使っていることがあるので、機器は xid が自分のものと一致する応答だけを受け取る。サーバから機器への OFFER と ACK は、機器の MAC アドレスあてに送られる（機器がまだアドレスを使えないことを示したときは、ブロードキャストで送られる）。

RFC 2131 は、ACK を受けた機器が、そのアドレスをほかの機器が使っていないかを ARP で確かめることを勧めている。使われていれば、機器は DECLINE を送って断り、DISCOVER からやり直す。確かめ方の手順は RFC 5227 にあり、それどおりに行うと、0〜1 秒の乱数だけ待ってから、1〜2 秒の乱数の間隔で 3 回問い合わせ、最後の問い合わせから 2 秒待つ。かかる時間は、最も短くて 0 + 1 + 1 + 2 = 4 秒、最も長くて 1 + 2 + 2 + 2 = 7 秒である。起動してから早く通信したい機器では、この確認をどうするかが、接続までの時間に大きく効く（7 節）。

### リース — 期限付きで借りる

DHCP で得たアドレスは、期限付きで借りたものである。この貸し出しを**リース**、その期間を**リース時間**という。機器は、期限が切れる前に延長を求める。これをリースの**更新**という。RFC 2131 では、リース時間を L として、次の時刻に動く（サーバがオプション 58・59 で別の時刻を指定することもある）。

- **T1** = 0.5 L: 貸してくれたサーバに、REQUEST を直接（ブロードキャストではなく、サーバのアドレスあてに）送って延長を求める。ACK が来れば、リースはその時点から始まり直す（新しい長さは ACK で知らされる。ふつうは同じ L である）。
- **T2** = 0.875 L: T2 までにサーバが答えなければ、どのサーバでもよいので延長してほしいと、REQUEST をブロードキャストで送る。
- L: L を過ぎても延長できなければ、そのアドレスを使うのをやめ、DISCOVER からやり直す。

L = 86400 秒（1 日）なら、T1 = 43200 秒（12 時間）、T2 = 75600 秒（21 時間）である。延長の REQUEST に答えが無いとき、RFC 2131 は、T2 まで（T2 の後は L まで）の残り時間の半分だけ待って送り直す（ただし 60 秒より短くはしない）としている。

```fig
e08_lease
```

ふつうは上の段のように、T1 で送った REQUEST にすぐ ACK が来て、リースが始まり直す。下の段は、サーバが止まっている場合である。送り直す間隔は、残り時間の半分ずつなので、T2 と L に近づくほど短くなる。

機器の側の DHCP の動きを状態機械（05 章 1 節）で表すと、次のようになる（RFC 2131 の図を簡単にしたもの）。

```fig
e08_dhcp_states
```

図の上の段の流れは、前に借りたアドレスを覚えている場合である。機器がアドレスとリースの残りをフラッシュなどに保存しておけば、再起動したときに DISCOVER と OFFER を省き、そのアドレスを指定した REQUEST から始められる。リースがまだ有効ならサーバは ACK を返し、そうでなければ断り（NAK）を返すので、機器は DISCOVER からやり直す。サーバがその機器の記録を持っていなければ（ルータを入れ替えた場合など）答えが来ないので、そのときも DISCOVER からやり直す。うまくいけば往復が 1 回減るので、接続までの時間が短くなる。

電池で動く機器が長く眠る場合も、リースの時計は進んでいる。起きたときには、眠っていた時間を足して T1・T2・L を過ぎていないかを確かめる。眠っている時間は、眠っている間も動く時計（15 章）で測る。

### 答えが無いとき — 再送の間隔

DISCOVER や REQUEST に答えが無ければ、機器は送り直す（05 章 4 節の再送）。RFC 2131 は、最初の再送までを 4 秒とし、以後は 8 秒、16 秒と倍にして、最大 64 秒にすること、そしてそれぞれの間隔に −1〜+1 秒の一様な乱数を足すことを勧めている。これは 05 章 5 節の指数バックオフとジッタである。サーバが止まっているとき、機器が何回目の DISCOVER をいつ送るかを求める。

**方針**: k 回目の送信の時刻は、1 回目からの間隔の和である。間隔を「中心の値」と「乱数」に分け、それぞれの和を求める。

**導出**: 1 回目の送信の時刻を 0 とする。i 回目の送信から i + 1 回目の送信までの間隔は、中心の値 $`c_i = \min(4 \times 2^{i-1},\ 64)`$ 秒に、−1 以上 +1 以下の乱数 $`u_i`$ を足したものである。k 回目の送信の時刻 $`t_k`$ は、1 回目から k − 1 個の間隔を足したものなので

$$
t_k = \sum_{i=1}^{k-1} (c_i + u_i) = \sum_{i=1}^{k-1} c_i + \sum_{i=1}^{k-1} u_i
$$

である。第 1 項は、$`c_i`$ = 4, 8, 16, 32, 64, 64, … を順に足したもので、k = 2, 3, 4, 5, 6 では 4, 12, 28, 60, 124 秒となる。第 2 項は、−1 以上 +1 以下の値を k − 1 個足したものなので、−(k − 1) 以上 k − 1 以下である。したがって、たとえば 6 回目の送信は、124 − 5 = 119 秒から 124 + 5 = 129 秒の間に行われる ∎

```fig
e08_dhcp_retx
```

サーバが止まっている間、機器は 1 分余りごとに送り続ける。乱数の和の幅は回を重ねるほど広がるので、停電の後に一斉に起動した多数の機器の送信も、回を重ねるほど時刻がばらける。サーバが復旧した瞬間に、すべての機器の要求が同時に押し寄せることを避けられる（05 章 5 節）。

ここまでで、機器は DHCP によって、アドレス・ネットマスク・デフォルトゲートウェイ・DNS サーバとリース時間を受け取る。アドレスは借り物なので、T1 と T2 で更新し、延長できなければ使うのをやめる。

## 4. DNS — 名前からアドレスへ

機器が接続するサーバは、ふつう `mqtt.example.com` のような名前で指定する。サーバの IP アドレスは、サーバの移転や、負荷を複数のサーバに分けるために変わることがある。ファームウェアに IP アドレスを書き込んでおくと、変わったときにつながらなくなるが、名前で指定しておけば、管理する側が名前とアドレスの対応を書き換えるだけで済む。

名前に対応する IP アドレスを調べることを**名前解決**という。インターネットでは、名前解決に **DNS**（Domain Name System、RFC 1034・RFC 1035）を使う。DNS の名前は、. で区切った部分（**ラベル**）の列で、右ほど大きな区分を表す。`mqtt.example.com` は、com の中の example の中の mqtt である。名前とアドレスの対応は、区分ごとに受け持つサーバが分担して持っている。

機器の中で名前解決を受け持つ部分を**リゾルバ**という。機器のリゾルバは、自分で世界中のサーバを調べて回るのではなく、DHCP で知らされた DNS サーバ（家庭ではルータ、またはプロバイダのサーバ）に質問を 1 つ送り、答えを待つだけである。DNS サーバは、答えを知らなければ、最上位（ルート）のサーバ、com を受け持つサーバ、example.com を受け持つサーバの順に問い合わせて答えを得る。

```fig
e08_dns_path
```

DNS サーバは得た答えを覚えておき（キャッシュ）、同じ質問には自分で答える。そのため、2 回目からの名前解決は、機器と DNS サーバの間の 1 往復で終わることが多い。

### レコードと TTL

DNS が持つ対応の 1 つ 1 つを**レコード**という。名前に対応する IPv4 アドレスを表すのが **A レコード**、IPv6 アドレスを表すのが **AAAA レコード**である（IPv6 のアドレスが IPv4 の 4 倍の 128 ビットであることから A を 4 つ並べた名前）。どのレコードにも、**TTL**（Time To Live）という秒単位の値が付いている。DNS の TTL は、答えを受け取った側が、そのレコードを覚えておいてよい時間である。IP のヘッダの TTL（ルータを通れる回数の上限。07 章 3 節）とは、名前は同じだが別のものである。

### メッセージの形

DNS のメッセージは、ふつう UDP のポート 53 で送る。質問も答えも同じ形で、12 バイトのヘッダの後に、質問の部分と答えの部分などが続く。16 ビットと 32 ビットの値は、すべてビッグエンディアン（ネットワークバイトオーダ。03 章 6 節）で並べる。`mqtt.example.com` の A レコードを尋ねる質問と、その答えの例を示す。

```fig
e08_dns_bytes
```

- **ID**: 質問ごとに機器が決める 16 ビットの番号で、答えには同じ ID が入る。DHCP の xid と同じく、答えを質問に対応させるのに使う。
- **フラグ**: 質問では 0x0100 で、RD（Recursion Desired）= 1 は「最後まで調べて答えてほしい」という意味である。答えでは QR = 1（答えである）になり、下位 4 ビットの RCODE が結果を表す。0 は成功、3 は「その名前は無い」（**NXDOMAIN**）、2 は「サーバが失敗した」（SERVFAIL）である。
- **数**: 質問・答え・権威・追加の 4 つの部分に、それぞれいくつのレコードが入るか。質問では質問の数が 1 で、残りは 0 である。
- **名前**: ラベルごとに、長さ 1 バイトを先に書き、続けて文字を書く（03 章 4 節の、長さを先に送る形）。最後に長さ 0 のバイトで終わる。1 つのラベルは 63 バイトまで、名前の全体は 255 バイトまでと決められている。
- **型とクラス**: 型は A が 1、AAAA が 28、クラスはインターネットを表す IN = 1 である。

フラグの 16 ビットを、質問と 2 つの答えで比べる。

```fig
e08_dns_flags
```

質問を組み立てる C の関数を示す。名前の規則に合わないとき（空のラベル、63 バイトを超えるラベル、全体で 255 バイトを超える名前）や、バッファに入りきらないときは 0 を返し、範囲の外には書かない。

```c
#define DNS_A     1     /* IPv4 アドレス */
#define DNS_AAAA 28     /* IPv6 アドレス */

/* name（例 "mqtt.example.com"。末尾に . を付けない）の型 qtype の質問を
   buf に組み立て、長さを返す。名前が規則に合わないか、buf に入りきらなければ 0 */
static size_t dns_build_query(uint8_t *buf, size_t cap, uint16_t id,
                              const char *name, uint16_t qtype)
{
    if (cap < 12) return 0;
    buf[0] = id >> 8;  buf[1] = id & 0xFF;   /* ID（ビッグエンディアン） */
    buf[2] = 0x01;     buf[3] = 0x00;        /* フラグ: RD = 1 */
    buf[4] = 0;        buf[5] = 1;           /* 質問の数 = 1 */
    memset(buf + 6, 0, 6);                   /* 答え・権威・追加の数 = 0 */
    size_t n = 12;
    const char *p = name;
    for (;;) {                               /* ラベル（. で区切った部分）ごとに */
        const char *dot = strchr(p, '.');
        size_t len = dot ? (size_t)(dot - p) : strlen(p);
        if (len == 0 || len > 63) return 0;  /* 空のラベル・長すぎるラベル */
        if (n + 1 + len > cap) return 0;
        buf[n++] = (uint8_t)len;             /* 長さを先に書き、 */
        memcpy(buf + n, p, len);             /* 続けて文字を書く */
        n += len;
        if (!dot) break;
        p = dot + 1;
    }
    if (n + 1 - 12 > 255 || n + 5 > cap) return 0;   /* 名前は全体で 255 バイトまで */
    buf[n++] = 0;                            /* 長さ 0 のラベルで名前が終わる */
    buf[n++] = qtype >> 8;  buf[n++] = qtype & 0xFF;   /* 型（A = 1、AAAA = 28） */
    buf[n++] = 0;           buf[n++] = 1;              /* クラス IN = 1 */
    return n;
}
/* dns_build_query(buf, sizeof buf, 0x1A2B, "mqtt.example.com", DNS_A) は 34 を返す */
```

この関数の出力は、Python の `struct` で別に組み立てたバイト列と一致すること、Python で書いた解析器で読み戻せることを確かめてある（ラベルが 63 バイトと 64 バイトの場合、名前が全体で 255 バイトと 256 バイトの場合、0〜40 バイトのすべての大きさのバッファの場合を含む）。

答えでは、質問の部分がそのまま繰り返された後に、答えのレコードが続く。答えのレコードの名前には、同じ名前をもう一度書く代わりに、メッセージの先頭から何バイト目に同じ名前があるかを指す 2 バイトがよく使われる（名前の圧縮）。上位 2 ビットが 11 で、残りの 14 ビットが位置を表すので、図の C0 0C は「12 バイト目（質問の名前）と同じ」という意味である。答えを読む側は、長さや指す位置がメッセージの中に収まっているか、指す先をたどって同じ所に戻ってこないかを確かめる。確かめないと、壊れた答えや悪意のある答えで、範囲の外を読んだり、読み終わらなくなったりする。

ID は乱数で決める。偽の答えを送り込む攻撃は、ID と、質問を送った UDP の送信元のポート番号の両方を当てなければ受け入れられないので、どちらも推測しにくい値にしておく（RFC 5452）。

### TTL の間はキャッシュを使う

機器のリゾルバも、答えを TTL の間だけ覚えておき、その間は質問を送らずにその答えを使う。

```fig
e08_dns_ttl
```

TTL が切れた後に必要になったら、問い合わせ直す。サーバの接続が切れて張り直すとき（15 章）も、覚えている答えの TTL が切れていれば、名前解決からやり直す。こうしておくと、サーバのアドレスが変わっても、遅くとも TTL の時間が過ぎれば、機器は新しいアドレスにつながるようになる。逆に、TTL を無視していつまでも同じアドレスを使い続ける機器は、サーバの移転についていけない。

### 答えが来ないとき・名前が無いとき

質問か答えが途中で失われると、答えは来ない。リゾルバは数秒待って質問を送り直し（待つ時間と回数は実装と設定による）、DNS サーバが 2 つ知らされていれば、2 つ目にも問い合わせる。一方、RCODE が 3（NXDOMAIN）の答えは、通信の失敗ではなく、その名前が存在しないこと、つまり設定の誤りなどを表す。すぐに繰り返しても結果は変わらないので、長めに待ってからやり直す。この 2 つは分けて扱う（7 節）。

家庭のネットワークの中で、サーバを置かずに機器どうしが名前で見つけ合う方法として、リンクの全員に質問を送る mDNS（DNS と同じ形のメッセージを使う）がある。[Matter シリーズ 06 章 1 節](../matter/06_探索とメッセージング.md#dns-sd-による探索) を参照してほしい。

## 5. プライベートアドレスと NAT

ここまでの例では、家庭の機器のアドレスは 192.168.1.23、サーバのアドレスは 203.0.113.10 だった。この 2 つは、種類の違うアドレスである。

IPv4 のアドレスは 32 ビットなので、全部で $`2^{32}`$（約 43 億）個しかなく、インターネットにつながる機器の数に足りない。そこで IPv4 では、家庭や会社のネットワークの中だけで使うアドレスの範囲を決め、同じアドレスを別々のネットワークで使い回している。この範囲のアドレスを**プライベートアドレス**といい、RFC 1918 で次の 3 つが決められている。

| 範囲 | プレフィックス長での書き方 | アドレスの数 |
|---|---|---|
| 10.0.0.0〜10.255.255.255 | 10.0.0.0/8 | 16,777,216 |
| 172.16.0.0〜172.31.255.255 | 172.16.0.0/12 | 1,048,576 |
| 192.168.0.0〜192.168.255.255 | 192.168.0.0/16 | 65,536 |

プライベートアドレスは、多くのネットワークで同じ値が使われているので、インターネットの上では宛先として使えない。インターネットの上で 1 つの機器だけを指すアドレスを、**グローバルアドレス**という。家庭のルータは、ふつうプロバイダからグローバルアドレスを 1 つ借りて、インターネットの側に持つ（プロバイダの網の中で、さらに NAT を通す方式もある）。

### NAT — 出ていくパケットのアドレスを書き換える

家庭の機器がインターネットのサーバへ送るとき、ルータは、パケットの送信元のプライベートアドレスを、自分のグローバルアドレスに書き換えてから送り出す。このように、ルータがパケットのアドレスを書き換えることを **NAT**（Network Address Translation）という。家庭のルータは、アドレスに加えて送信元のポート番号も書き換え、1 つのグローバルアドレスを多数の機器で共有する。この形を、とくに **NAPT**（Network Address Port Translation）という。家庭のルータの NAT は、ほとんどがこの形である。

ルータは書き換えるたびに、内側のアドレスとポート番号・書き換えた後のポート番号・相手のアドレスとポート番号の組を、表の 1 行として記録する。この表を**変換表**という。サーバからの答えは、ルータのグローバルアドレスと書き換えた後のポート番号あてに届く。ルータは変換表を引いて、宛先を内側の機器のアドレスとポート番号に書き戻し、中へ送る。

```fig
e08_nat
```

外から始まるパケット、たとえばサーバが機器に命令を送ろうとして、ルータのグローバルアドレスあてに送ったパケットには、対応する行が変換表に無い。ルータは、どの機器に渡せばよいか分からないので、捨てる。したがって、NAT の内側の機器には、外から接続を始められない。サーバから機器へ下り（01 章 1 節）のデータを届けるには、機器の側から先にサーバへ接続を張り、その接続を保っておく。サーバは、その接続を通して送る。13 章の MQTT は、この形を前提にしている。ルータに「外のこのポートに来たものは、中のこの機器へ渡す」と手で設定する方法（ポート転送）もあるが、利用者に設定を求めることになるうえ、外から機器を直接攻撃できる入口にもなるので、製品の設計の前提にはしにくい。

携帯電話の網（21 章の LTE-M など）につながる機器にも、プライベートアドレスや 100.64.0.0/10（網の中の NAT のために RFC 6598 が決めた範囲）のアドレスが割り当てられ、網の中の NAT を通ることがある。外から接続を始められない点は同じである。

### 変換表の保持時間

変換表の行は、その行を通るパケットがしばらく無いと消される。最後のパケットから行を消すまでの時間を、変換表の**保持時間**という。行が消えた後に、サーバが接続を通して送ったパケットは、行が無いので捨てられる。機器は接続がまだあると思っているが、実際には切れている。保持時間について、RFC 4787 は UDP では 2 分以上（既定の値は 5 分以上を推奨）、RFC 5382 は TCP のつながっている接続では 2 時間 4 分以上にするよう求めている。しかし実際の値は、ルータや携帯電話の網の設定によって違い、これより短いものもある。UDP では数十秒〜数分のことが多い。

そこで機器は、送るデータが無い間も、保持時間より短い間隔で小さなパケットを送り、行を保つ。この目的で定期的に送るパケットを、**キープアライブ**という（MQTT のキープアライブは 13 章、TCP のキープアライブは 10 章で扱う）。間隔をどこまで長くできるかを求める。

**方針**: 行の時計は、行を通るパケットがあるたびに 0 に戻る（RFC 4787 は、少なくとも内から外へのパケットで時計を戻すことを求めている）。時計が保持時間に達する前に次のパケットが届く条件を、パケットの間隔と保持時間で表す。

**導出**: 機器が間隔 $`T_\mathrm{k}`$ でパケットを送り、保持時間を $`T_\mathrm{h}`$ とする。行が消えるのは、最後にパケットが通ってから $`T_\mathrm{h}`$ の間、次のパケットが通らなかったときである。パケットがすべてルータに届くなら、パケットどうしの間隔は $`T_\mathrm{k}`$ なので、$`T_\mathrm{k} < T_\mathrm{h}`$ であれば、時計が $`T_\mathrm{h}`$ に達する前に次のパケットで 0 に戻り、行は消えない。$`T_\mathrm{k} \ge T_\mathrm{h}`$ であれば、次のパケットが通る前に時計が $`T_\mathrm{h}`$ に達し、行は消える。

送ったパケットがルータに届く前に失われると（たとえば Wi-Fi の区間で）、時計は戻らない。続けて j 回失われると、ルータに届くパケットの間隔は $`(j + 1) T_\mathrm{k}`$ に延びる。これでも行を保つには $`(j + 1) T_\mathrm{k} < T_\mathrm{h}`$、すなわち

$$
T_\mathrm{k} < \frac{T_\mathrm{h}}{j + 1}
$$

であればよい ∎

たとえば $`T_\mathrm{h}`$ = 60 秒で、2 回続けて失われても行を保つには、$`T_\mathrm{k}`$ < 60 / 3 = 20 秒にする。

```fig
e08_nat_hold
```

キープアライブには電力がかかる。キープアライブを 1 回送るたびに機器が電荷 $`Q_\mathrm{k}`$ を使うとすると、平均電流は 01 章 5 節の式と同じ考え方で $`Q_\mathrm{k} / T_\mathrm{k}`$ だけ増える。例として、1 回に 80 mA を 30 ms 流す（$`Q_\mathrm{k}`$ = 80 mA × 0.03 s = 2.4 mC。仮に置いた代表値）とすると、$`T_\mathrm{k}`$ = 25 秒では 2.4 mC ÷ 25 s = 96 µA、$`T_\mathrm{k}`$ = 110 秒では 21.8 µA だけ平均電流が増える。保持時間が分かれば、間隔を必要なだけ長くできる。分からなければ、安全のために短い間隔を選ぶことになり、その分だけ電池が早く減る。

## 6. IPv6 の場合

IPv6 のアドレスは 128 ビットある（07 章 3 節）。すべての機器にグローバルアドレスを配っても余るので、IPv6 ではふつう NAT を使わず、家庭の中の機器もそれぞれグローバルアドレスを持つ。アドレスの得方も IPv4 と違う。IPv6 では、ルータが定期的にリンクの全員へ、そのリンクのネットワーク部（上位 64 ビットのことが多い）を知らせる。機器は、それに自分で作った下位の部分をつなげて、自分のアドレスを作る。DHCP のようにサーバがアドレスを貸すのではなく、機器が自分でアドレスを決めるこの方式を、**SLAAC**（Stateless Address Autoconfiguration、RFC 4862）という。IPv6 には DHCP の IPv6 版（DHCPv6）もあり、ネットワークによって使い分けられる。リンクの中で MAC アドレスを知るには、ARP の代わりに近隣探索（Neighbor Discovery）という仕組みを使う。名前解決では、A レコードの代わりに AAAA レコードを引く。アドレスの種類と SLAAC の手順は、[Matter シリーズ 03 章 5 節](../matter/03_IPv6の基礎.md#近隣探索-ndp-とアドレス自動設定) が詳しい。

では、IPv6 なら、サーバから機器へ直接接続を始められるか。アドレスの上では届く。しかし家庭のルータの多くは、外から始まる通信を通さない設定で出荷されている。中から外へ出た通信を表に記録しておき、それへの答えだけを通す仕組み（防火壁、ファイアウォールともいう）である。外から始まる接続は、IPv4 の NAT と同じく、表に行が無いので捨てられる。そして、この表の行にも保持時間がある。

```fig

```

したがって、IPv6 でも結論は 5 節と同じで、機器の側から接続を張り、保持時間より短い間隔で通信し続ける。IPv4 と IPv6 の両方が使えるネットワークでは、DNS が A と AAAA の両方を返すことがある。両方を試して先につながった方を使う方法（Happy Eyeballs、RFC 8305）もあるが、小さな機器では、どちらを先に試すかを決めておくだけの実装もある。

## 7. 参加の手順を実装する

ここまでの手順を、機器が実際に行う順に並べ、ファームウェアの状態機械として組み立てる。

まず出発点を決める。リンク層がつながり、フレームを送受信できるようになった状態を**リンクアップ**、つながっていない状態を**リンクダウン**という。Ethernet では、ケーブルがつながり、両端の回路が通信の速さを決め終えたときにリンクアップになる。Wi-Fi では、アクセスポイントへの接続（09 章）が終わったときにリンクアップになる。ケーブルが抜けたり、電波が届かなくなったりすると、リンクダウンになる。

リンクアップから、サーバにつながるまでの段を表にまとめる。各段で答えを待つ期限（05 章 3 節のタイムアウト）と回数は、この節で例として決めた値であり、製品ごとに決める。

| 段 | 機器が送るもの | 次の段へ進む条件 | 期限と再試行（例） | 進めなかったとき |
|---|---|---|---|---|
| DHCP（3 節） | DISCOVER と REQUEST（前に借りたアドレスがあれば REQUEST から） | ACK を受け取る | 送り直しは 3 節の間隔、全体で 30 秒 | 待ってから DHCP をやり直す |
| ゲートウェイの ARP（2 節） | デフォルトゲートウェイの MAC アドレスを尋ねる要求 | 応答を受け取る | 1 秒ごとに 3 回まで | DHCP からやり直す |
| DNS（4 節） | サーバの名前の A レコードの質問 | 答えを受け取る | 2 秒ごとに 2 つの DNS サーバへ交互に 4 回まで。NXDOMAIN ならすぐあきらめる | 待ってから DNS をやり直す |
| 接続 | サーバへの TCP の接続の要求（10 章） | 接続できる | 10 秒 | 待ってから DNS をやり直す |

どの段にいても、リンクダウンになれば接続を閉じてリンクアップを待ち、リースが切れれば DHCP に戻る。「待ってから」の待ち時間は、05 章 5 節の指数バックオフとジッタで、失敗が続くほど長くする。

ゲートウェイの ARP は、DNS の質問を送るときにも TCP/IP スタックが自動で行う。それでも段として分けておくと、DHCP で受け取った設定がいまのリンクに合っているか（ゲートウェイが本当にいるか）を早く確かめられ、どこで止まったかも分かりやすい。ゲートウェイが答えないときに DHCP からやり直すのは、前に借りたアドレスのまま別のネットワークにつながった場合などに、設定が古いことがありうるからである。

この表を状態機械（05 章 1 節）で描くと、次のようになる。

```fig

```

C で書くと次のようになる。届いたイベントを `join_on` に渡すと、状態が遷移し、必要なメッセージが送られる。期限は、ティック（05 章 3 節）を数える `now` と比べて調べる。DHCP・ARP・DNS・TCP の中身は TCP/IP スタックの仕事なので、ここでは**この章で仮に置く関数**（`dhcp_start`・`arp_query_gateway`・`dns_query`・`tcp_connect_server`・`tcp_close`）を呼ぶ。実際の機器では、使う TCP/IP スタックの関数を呼ぶ。待つ時間を返す `backoff_ms` は、05 章 5 節の指数バックオフとジッタである。

```c
enum jst { J_DOWN, J_DHCP, J_ARP, J_DNS, J_TCP, J_UP, J_WAIT };       /* 状態 */
enum jev { E_TICK, E_LINK_UP, E_LINK_DOWN, E_BOUND, E_LEASE_LOST,     /* イベント */
           E_ARP_OK, E_DNS_OK, E_DNS_NXDOMAIN, E_TCP_OK, E_TCP_FAIL };
struct join {
    enum jst st, resume;      /* いまの状態と、待った後にやり直す段 */
    uint32_t deadline;        /* いまの段の期限（ミリ秒を数えるティック） */
    unsigned tries, fails;    /* いまの段で送った回数と、続けて失敗した回数 */
};

/* 段 s に入り、最初の 1 回を送って、その段の期限を決める */
static void enter(struct join *j, enum jst s, uint32_t now)
{
    /* 段ごとの期限 [ms]。並びは enum jst と同じ */
    static const uint32_t limit_ms[] = { 0, 30000, 1000, 2000, 10000, 0, 0 };
    j->st = s; j->tries = 1; j->deadline = now + limit_ms[s];
    if (s == J_DHCP) dhcp_start();
    else if (s == J_ARP) arp_query_gateway();
    else if (s == J_DNS) dns_query(0);
    else if (s == J_TCP) tcp_connect_server();
    else if (s == J_WAIT) j->deadline = now + backoff_ms(j->fails);
}
```

`enter` は、段に入るときに最初の 1 回を送り、その段の期限を決める。イベントを受け取る本体は次のとおりである。

```c
/* この段をあきらめ、待ってからやり直す */
static void give_up(struct join *j, uint32_t now)
{
    j->resume = (j->st == J_DHCP) ? J_DHCP : J_DNS;   /* アドレスがあれば DNS から */
    j->fails++;
    enter(j, J_WAIT, now);
}

void join_on(struct join *j, enum jev e, uint32_t now)
{
    /* リンクダウンとアドレスの喪失は、どの状態からでも同じに扱う */
    if (e == E_LINK_DOWN) { tcp_close(); j->st = J_DOWN; return; }
    if (e == E_LEASE_LOST) { tcp_close(); enter(j, J_DHCP, now); return; }
    int late = (e == E_TICK) && (int32_t)(now - j->deadline) >= 0;   /* 05 章 3 節 */
    switch (j->st) {
    case J_DOWN: if (e == E_LINK_UP) enter(j, J_DHCP, now); break;
    case J_DHCP:
        if (e == E_BOUND) enter(j, J_ARP, now);
        else if (late) give_up(j, now);
        break;
    case J_ARP:                                    /* 1 秒ごとに 3 回まで */
        if (e == E_ARP_OK) enter(j, J_DNS, now);
        else if (late && j->tries < 3) {
            j->tries++; j->deadline = now + 1000; arp_query_gateway();
        } else if (late) enter(j, J_DHCP, now);    /* 設定が古いかもしれない */
        break;
    case J_DNS:                                    /* 2 秒ごと、サーバは交互に */
        if (e == E_DNS_OK) enter(j, J_TCP, now);
        else if (e == E_DNS_NXDOMAIN) give_up(j, now);   /* 繰り返しても直らない */
        else if (late && j->tries < 4) {
            dns_query(j->tries % 2); j->tries++; j->deadline = now + 2000;
        } else if (late) give_up(j, now);
        break;
    case J_TCP:
        if (e == E_TCP_OK) { j->st = J_UP; j->fails = 0; }
        else if (e == E_TCP_FAIL || late) give_up(j, now);
        break;
    case J_UP: if (e == E_TCP_FAIL) give_up(j, now); break;     /* 接続が切れた */
    case J_WAIT: if (late) enter(j, j->resume, now); break;
    }
}
```

リンクダウンとリースの喪失は、状態によらず同じ扱いなので、`switch` の前で処理する。期限の比較は 05 章 3 節の形で書いてあるので、ティックのカウンタが一周しても正しく動く。DNS の段では、送った回数 `tries` の偶奇で 2 つの DNS サーバを交互に使う。リンクダウンの後に遅れて届いた答え（`E_DNS_OK` など）は、`J_DOWN` の `case` が何もしないので無視される。PC の gcc で、正常な流れ、ARP と DNS の期限切れ、NXDOMAIN、リンクダウンとリースの喪失、ティックが一周する場合を、偽の関数とイベントの列を与えて確かめてある。

IP アドレスが変わったときは、それまでの TCP の接続は使えない。リースを延長できずに DISCOVER から借り直すと、別のアドレスになることがあるので、`E_LEASE_LOST` で接続を閉じてから DHCP をやり直している。

### かかる時間は、失われたときの待ち時間で決まる

各段の 1 回の試行は、要求と答えの往復である。1 つのメッセージが途中で失われる確率を p とし、往きと帰りは互いに関係なく失われるとすると、往復が成り立つ確率 q は、往きも帰りも失われない確率 $`q = (1 - p)^2`$ である。往復が成り立つまでに、平均で何回の試行が要るかを求める（回数の上限は考えない）。

**方針**: 1 回目の試行で成り立てば試行は 1 回で終わり、成り立たなければ 1 回を使ったうえで、まだ 1 回も試していないときと同じ状況に戻る。このことから、試行の回数の平均 E を、E 自身を使った式で表して解く。

**導出**: 1 回目の往復は確率 q で成り立ち、そのとき試行の回数は 1 である。確率 1 − q で成り立たず、そのときは 1 回を使ったうえで、最初と同じ状況から平均 E 回かかるので、回数は平均 1 + E である。2 つの場合を確率で重み付けして足すと

$$
E = q \times 1 + (1 - q)(1 + E) = 1 + (1 - q)\,E
$$

となる。右辺の $`(1 - q)E`$ を左辺に移すと $`E - (1 - q)E = qE = 1`$、すなわち $`E = 1/q`$ である ∎

p = 5 % なら q = 0.95² = 0.9025、E = 1/0.9025 ≈ 1.108 で、平均すると 1 つの段で 0.108 回しか送り直さない。しかし、送り直すたびに、その段の再送の間隔だけ時間が足される。LAN の中の往復は数 ms なのに、DHCP では 1 回の送り直しで約 4 秒、ARP では 1 秒、DNS では 2 秒が足される。

```fig
e08_join_time
```

図のように、メッセージが 1 つも失われなければ 0.2 秒もかからない手順が、1 つ失われるだけで数秒に延びる。したがって、接続までの時間は、往復の時間の和ではなく、失われたときの待ち時間の分布で見積もる。平均だけでは、たまに起きる長い待ちが見えないので、95 % の値（100 回のうち 95 回はそれ以内に終わる時間）のような分布の裾の値も見る。

06 章の構成 (b)（AT コマンドで操作する無線モジュール）では、この手順の DHCP から DNS までをモジュールが中で行い、ホストのマイコンには、アドレスを得たことなどが URC（06 章 3 節）で知らされる（たとえば Espressif の ESP-AT では `WIFI GOT IP` という行が届く。命令と通知の名前は製品と版によって違う）。それでも、どの段で止まったかを知り、どこからやり直すかを決める考え方は同じである。

| 項目 | 内容 |
|---|---|
| サブネット・ネットマスク | 上位のネットワーク部が等しいアドレスの集まり。ネットワーク部の長さを、上位を 1 にした 32 ビットの値（ネットマスク）か、ビット数（プレフィックス長、/24）で表す |
| 中か外かの判定 | $`(a \;\mathrm{AND}\; m) = (b \;\mathrm{AND}\; m)`$ なら同じサブネット。AND で残りのビットを 0 にして、ネットワーク部だけを比べる |
| デフォルトゲートウェイ | 外の宛先へのパケットを渡すルータの IP アドレス。自分と同じサブネットになければならない |
| ブロードキャスト・ARP | リンクの全員に届ける送り方。ARP は IP アドレスから MAC アドレスを、ブロードキャストの要求で尋ね、得た組を ARP キャッシュに期限付きで覚える。外の宛先ではゲートウェイの MAC アドレスを聞く |
| DHCP | DISCOVER・OFFER・REQUEST・ACK の 4 つでアドレス・マスク・ゲートウェイ・DNS サーバを借りる。前のアドレスがあれば REQUEST から |
| リースと更新 | 借りる期間 L。T1 = 0.5 L で貸したサーバに、T2 = 0.875 L で全員に延長を求め、L を過ぎたら使うのをやめる |
| DHCP の再送 | 4 秒から倍にして最大 64 秒、各間隔に −1〜+1 秒の乱数（RFC 2131）。k 回目の送信は中心の値 ± (k − 1) 秒 |
| DNS・リゾルバ | 名前からアドレスを調べる仕組み。機器のリゾルバは DNS サーバに 1 往復で尋ねる。質問は 12 バイトのヘッダ + 長さを先に書いたラベルの列 + 型とクラス |
| A・AAAA レコードと TTL | IPv4・IPv6 のアドレスのレコード。DNS の TTL は覚えておいてよい秒数（IP の TTL とは別）。応答なしと NXDOMAIN は分けて扱う |
| プライベートアドレス・NAT | ネットワークの中だけで使うアドレス（RFC 1918）。NAPT は送信元のアドレスとポート番号を書き換えて変換表に記録し、外から始まるパケットは捨てる |
| 保持時間 | 変換表の行が消えるまでの時間。キープアライブの間隔は $`T_\mathrm{k} < T_\mathrm{h} / (j + 1)`$（j 回続けて失われても保つ場合）。平均電流は $`Q_\mathrm{k} / T_\mathrm{k}`$ 増える |
| IPv6 | 機器ごとにグローバルアドレス（SLAAC など）を持てるが、家庭のルータの防火壁が外から始まる接続を通さないので、機器から接続を張る結論は同じ |
| 参加の手順 | リンクアップ → DHCP → ゲートウェイの ARP → DNS → 接続。段ごとに期限と戻る先を決め、リンクダウンとリースの喪失はどの状態からでも扱う |
| かかる時間 | 往復が成り立つ確率 $`q = (1 - p)^2`$、平均の試行回数 $`1/q`$。時間は失われたときの待ち時間で決まるので、分布の裾で見積もる |
