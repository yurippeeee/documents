# 04. 割り込み・DMA・リングバッファ — 取りこぼさずに受け取る

> **この章で扱う問い.**
> 02 章では、UART が 1 本の線の上で 1 バイトを運ぶ仕組みを見た。03 章では、届いたバイトの列をメッセージに区切る方法を見た。この章では、その間をつなぐ部分、つまり UART に届いたバイトを、マイコンのソフトウェアが 1 つも落とさずに受け取り、処理する側へ渡す方法を扱う。
>
> この章では次の 3 つの問いに答える。
>
> 1. UART に届いたバイトは、いつまでに読まなければ失われるのか。ソフトウェアは、どんな方法でそれに間に合わせるのか。
> 2. 割り込みで受け取ったバイトを、普段の処理へ壊さずに渡すにはどうするか。受け渡しのバッファは、どれだけの大きさが要るのか。
> 3. CPU を使わずに受け取る方法（DMA）と、送信が終わったことを知る方法は、どうなっているのか。
>
> 答えの道具は、リングバッファと、それを読み書きする順番の規則、そして「入ってくる速さ × 読み手が止まる時間」の見積もりである。

## 1. 受信レジスタと 3 つの受け取り方

UART の受信回路は、02 章 3 節で見たように、RX の線の立ち下がりで時刻を合わせ、各ビットの中央で値を読む。読んだビットは、1 ビットずつ詰めていく回路（シフトレジスタ）に集められ、ストップビットまで受け取ると、1 バイトがまとめて**受信データレジスタ**に移される。受信データレジスタは、受け取った 1 バイトを、ソフトウェアが読むまで置いておくレジスタである。移したとき、UART は「受信データあり」の印（フラグ）を立てる。ソフトウェアが受信データレジスタを読むと、印は消える（消え方は製品による）。

```fig
e04_rxpath
```

受信データレジスタに 1 バイトが置かれている間も、線の上では次のバイトが届き続け、シフトレジスタに集められていく。次のバイトを受け取り終えたとき、受信データレジスタがまだ読まれていなければ、新しいバイトを移す先がない。この状態を**オーバーラン**という。UART はオーバーランの印を立て、多くの場合は後から届いたバイトを捨てる（どちらのバイトが失われるかは製品による）。どちらにしても 1 バイトが失われる。

送り手が間を空けずに続けて送ると、バイトを受け取り終える時刻は、1 バイトの時間ごとにやってくる。8N1 では 1 バイトは 10 ビット時間で、115200 bps なら、02 章 2 節で求めたとおり 86.8 µs である。したがって、受信データレジスタが 1 バイト分しかない UART では、「受信データあり」の印が立ってから 86.8 µs 以内に読まなければならない。

```fig
e04_overrun
```

受信データレジスタの代わりに、数バイト〜数十バイトをためておける FIFO（先に入れたものから順に取り出す記憶）を持つ UART も多い。これを**ハードウェア FIFO** という。FIFO にためられるバイトの数（深さ）を $`D`$、1 バイトの時間を $`T_\mathrm{B}`$ として、読むまでの猶予を求める。

**方針**: ソフトウェアが FIFO を読んで空にした時刻を 0 とし、次に読むまでの間に何バイト目でオーバーランになるかを数える。

**導出**: 最も厳しいのは、時刻 0 の直後に 1 バイト目を受け取り終える場合である。その時刻を $`\varepsilon`$（正で、いくらでも 0 に近い）とすると、続けて届く $`k`$ バイト目を受け取り終える時刻は $`\varepsilon + (k - 1) T_\mathrm{B}`$ である。FIFO には $`D`$ バイトまで入るので、$`D`$ バイト目までは失われない。$`D + 1`$ バイト目を受け取り終える時刻 $`\varepsilon + D\, T_\mathrm{B}`$ に FIFO が満杯のままなら、オーバーランになる。$`\varepsilon`$ はいくらでも 0 に近くなりうるので、どの場合にもオーバーランを避けるには、前に空にしてから $`D\, T_\mathrm{B}`$ より短い時間のうちに、もう一度読めばよい。$`D = 1`$（受信データレジスタだけ）なら猶予は $`T_\mathrm{B}`$ で、上の 86.8 µs と一致する ∎

具体的な値を並べる（8N1、送り手が続けて送る場合。深さ 16 は例）。

| ボーレート | 1 バイトの時間 $`T_\mathrm{B}`$ | 1 秒に届くバイト数 | 猶予（FIFO なし） | 猶予（深さ 16 の FIFO） |
|---|---|---|---|---|
| 9600 bps | 1.04 ms | 960 | 1.04 ms | 16.7 ms |
| 115200 bps | 86.8 µs | 11520 | 86.8 µs | 1.39 ms |
| 921600 bps | 10.9 µs | 92160 | 10.9 µs | 174 µs |
| 3 Mbps | 3.33 µs | 300000 | 3.33 µs | 53.3 µs |

ソフトウェアがこの猶予の中で読む方法は 3 つある。以下、マイコンが普段実行している処理を「タスク」と呼ぶ。RTOS を使う場合は RTOS のタスク（[OS シリーズ 02 章 2 節](../freertos/02_タスクという抽象.md#タスクとは何か)）、使わない場合は main 関数の中の無限ループがこれにあたる。

- **ポーリング**: タスクが「受信データあり」の印を繰り返し見に行き、立っていれば読む方法である。仕組みは簡単だが、タスクのどの部分を実行していても、猶予より短い間隔で見に行かなければならない。データを待つ間、CPU は印を見続けるので、ほかの仕事ができない。
- **割り込み**: 周辺回路が CPU に合図を送ると、CPU は実行中のプログラムを命令の区切りで一時中断し、あらかじめ決めておいた関数を実行してから、中断した所に戻る。この仕組みを割り込みといい、割り込みで実行される関数を**割り込みハンドラ**（**ISR**、Interrupt Service Routine）という。UART は「受信データあり」で割り込みを出せるので、ISR が届いたバイトを読む。ISR はタスクの途中に割り込んで動き、終わるとタスクに戻る。
- **DMA**（Direct Memory Access）: CPU の代わりに、周辺回路とメモリの間でデータを運ぶ専用の回路（DMA コントローラ）を使う方法である。UART に 1 バイト届くたびに DMA がそれを RAM に運び、CPU は決めた数を運び終えたときなどに、まとめて知らせを受ける（6 節）。

```fig
e04_three
```

CPU が受信に使う時間を比べる。ISR に入ってから出るまでの時間を 1 回 2 µs、DMA の知らせ 1 回の処理を 10 µs とする（どちらも代表値。CPU のクロックと処理の中身で大きく変わる）。DMA は 256 バイトのバッファの半分ごとに知らせを出すとする。

| ボーレート | ポーリング | 割り込み（1 バイトに 1 回） | DMA（128 バイトに 1 回） |
|---|---|---|---|
| 115200 bps | 待つ間ずっと | 11520 回/s × 2 µs = 2.3 % | 90 回/s × 10 µs = 0.09 % |
| 921600 bps | 待つ間ずっと | 92160 回/s × 2 µs = 18 % | 720 回/s × 10 µs = 0.72 % |
| 3 Mbps | 待つ間ずっと | 300000 回/s × 2 µs = 60 % | 2344 回/s × 10 µs = 2.3 % |

遅い速さで、ほかにすることが少ないなら、ポーリングでも足りる（起動直後に更新のデータだけを受け取るプログラムなど）。普通は割り込みを使い、速い速さで長いデータを受け取るときは DMA を使う。2〜5 節で割り込みとそのバッファを、6 節で DMA を見る。

## 2. 割り込みハンドラは短く

ISR が動いている間、タスクは止まっている。それだけでなく、いま動いている ISR より優先度の高くない割り込みも、その ISR が終わるまで待たされる（優先度の仕組みはマイコンによって違う。設定の注意は [OS シリーズ 18 章 3 節](../freertos/18_割り込みとの境界.md#割り込み優先度-最も事故が多い設定)）。割り込みの要求が出てから、その ISR が動き始めるまでの時間を**割り込み遅延**という。割り込み遅延は、次の 3 つの和になる。

- CPU が要求を受け付けて ISR に入るまでの時間。ハードウェアで決まり、数十 MHz の CPU では 1 µs 未満のことが多い（代表値）。
- 割り込みが禁止されている区間（4 節のクリティカルセクションなど）の残りの時間。
- 先に動いている、同じかより高い優先度の ISR の残りの時間。

1 節の結果と合わせると、受信の ISR がオーバーランを起こさない条件は、割り込み遅延の最大値を $`L_\mathrm{max}`$ として

$$
L_\mathrm{max} < D\, T_\mathrm{B}
$$

である（厳密には、ISR が動き始めてから FIFO を読むまでの時間も左辺に足す）。割り込み遅延を延ばすのは、長い ISR と、長く割り込みを禁止する処理である。

例として、受信の ISR が、メッセージの終わりを受け取ったその場でメッセージを解析し、結果を printf で 40 文字のログに出すとする。printf の出力先が 115200 bps の UART で、送り終わるまで待つ作りなら、出力だけで $`40 \times 86.8\ \text{µs} = 3.47`$ ms かかる。その間も受信では 1 バイトずつ届くが、ISR は FIFO を読まない。深さ 16 の FIFO の猶予は 1.39 ms しかないので、17 バイト目から先はオーバーランで失われる。同じ 3.47 ms の間、ほかの周辺回路の割り込みも待たされる。

```fig
e04_latency
```

したがって、ISR では次のことだけをする。

1. 受信データレジスタ（FIFO）を、空になるまで読む。
2. オーバーランやフレーミングエラーの印を読み、数えておく（どう扱うかはタスクで決める）。
3. 読んだバイトを受信バッファに入れる。
4. 受信を待っているタスクに知らせる。

次のことは、ISR ではしない。

- メッセージの解析（03 章の区切りの復号、誤りの検査、コマンドの実行）のように、時間のかかる処理。
- 待つこと。何かが終わるまで繰り返し見に行くループも、RTOS の「待つ」関数も、ISR の中では使わない。ISR が待つと、その間はタスクも、優先度の高くない割り込みも止まる。
- printf などのライブラリの関数。時間がかかるうえ、ISR から呼んでよい作りになっているとは限らない。

```fig
e04_isrjob
```

受信の ISR は、たとえば次のように書ける。`uart_hw_rx_ready()` などの `uart_hw_` で始まる関数と `task_notify_rx()` は、この章で仮に置く関数である。実際のマイコンでは、UART のレジスタを読み書きする。`rxbuf_put(b)` は受信バッファに 1 バイト入れ、満杯なら 0 を返す関数で、中身は 3 節で作る。

```c
static volatile uint32_t rx_err_count, rx_drop_count;   /* 数えるだけ（4 節） */

/* 受信の割り込みハンドラ */
void uart_rx_isr(void)
{
    while (uart_hw_rx_ready()) {             /* FIFO が空になるまで */
        uint32_t err = uart_hw_rx_errors();  /* オーバーランなどの印を読んで消す */
        uint8_t b = uart_hw_read();          /* 読むと FIFO から 1 バイト消える */
        if (err)
            rx_err_count++;                  /* 誤りは数えるだけ（扱いはタスクで） */
        if (!rxbuf_put(b))
            rx_drop_count++;                 /* 受信バッファが満杯: 捨てて数える */
    }
    task_notify_rx();                        /* 受信タスクを起こす（すぐ戻る） */
}
```

`task_notify_rx()` は、RTOS を使うならタスク通知など（[OS シリーズ 14 章 1 節](../freertos/14_タスク通知とイベントグループ.md#タスク通知-tcb-に直接書き込む)）で待っているタスクを起こし、RTOS を使わないなら main のループが見る印を立てる。RTOS の関数を ISR から呼ぶときは、ISR から呼んでよい版（FreeRTOS なら名前が FromISR で終わる関数）を使う。理由は [OS シリーズ 18 章 1 節](../freertos/18_割り込みとの境界.md#なぜ-isr-版-api-が必要なのか) にある。

下の図で、ボーレート、FIFO の深さ、受信の ISR が待たされる最長の時間、ISR が 1 バイトに使う時間を変えると、FIFO にたまるバイトの数の時間変化と、オーバーランで失われるバイト、CPU が受信の ISR に使う時間の割合が表示される。

## 3. リングバッファ

ISR は受け取ったバイトを受信バッファに入れ、タスクは後でまとめて取り出す。受信バッファには、次の 3 つが求められる。

- 届いた順に取り出せること。
- 書き手（ISR）と読み手（タスク）が、互いを待たずに、別々の時刻に読み書きできること。
- 決まった大きさの RAM で、いつまでも使い続けられること。

これを満たすのが**リングバッファ**である。リングバッファは、大きさ $`N`$ の配列を、最後の要素の次が最初の要素に戻る輪のように使う。次に書く位置を**書き込み位置**（**head**）、次に読む位置を**読み出し位置**（**tail**）という。書き手は head の位置に書いて head を 1 つ進め、読み手は tail の位置から読んで tail を 1 つ進める。どちらも配列の最後まで来たら先頭に戻る。tail から head の手前までが、書かれたがまだ読まれていないデータである。

```fig
e04_ring
```

head と tail が同じ位置にあるとき、バッファは**空**（読むものがない）である。ところが、書き手が読み手より $`N`$ 個先まで書いた状態でも、head は一周して tail と同じ位置に来る。この状態を**満杯**（$`N`$ 個入っていて、もう書けない）という。位置だけを見ると、空と満杯の区別がつかない。区別の仕方は 2 つある。

- **1 つ空ける方式**: head と tail を 0〜$`N - 1`$ の位置として持ち、「head の次が tail なら満杯」とする。要素を常に 1 つ空けておくので、入るのは $`N - 1`$ 個である。入っている個数は $`(\mathrm{head} - \mathrm{tail} + N) \bmod N`$ で、$`N`$ はいくつでもよい。
- **増え続ける添字の差で数える方式**: head と tail を「これまでに書いた総数」と「これまでに読んだ総数」として持ち、配列の外に出ても 0 に戻さずに増やし続ける。配列の中の位置は、添字を $`N`$ で割った余りで求める。入っている個数は head − tail で、0 なら空、$`N`$ なら満杯である。$`N`$ 個すべてを使える。

```fig
e04_fullempty
```

2 つ目の方式には、確かめることが 2 つ残る。添字は符号なし整数なので、増やし続けると、いつか最大値を超えて 0 に戻る（一周する）。そのとき head − tail は正しい個数になるのか。また、位置を求める「$`N`$ で割った余り」は、一周の前後で続いているのか。以下、添字を 32 ビットの符号なし整数（C の `uint32_t`）として確かめる。

**方針**: 一周しない本当の通し番号として、書いた総数を $`W`$、読んだ総数を $`R`$ とおく（$`0 \le W - R \le N`$）。変数 head と tail に入っているのは、$`W`$ と $`R`$ を $`2^{32}`$ で割った余りである。C の `uint32_t` どうしの引き算 head − tail が、$`W - R`$ に等しいことを示す。

**導出**: C では、`uint32_t` の計算の結果は $`2^{32}`$ で割った余り（0 以上 $`2^{32}`$ 未満）になる（C の規格による）。$`W`$ と $`R`$ を $`2^{32}`$ で割った商を $`q_W`$・$`q_R`$ とすると

$$
W = q_W \cdot 2^{32} + \mathrm{head}, \qquad R = q_R \cdot 2^{32} + \mathrm{tail} \qquad (0 \le \mathrm{head},\ \mathrm{tail} < 2^{32})
$$

である。左の式から右の式を引き、head − tail について解くと

$$
\mathrm{head} - \mathrm{tail} = (W - R) - (q_W - q_R) \cdot 2^{32}
$$

となる。$`0 \le W - R \le N < 2^{32}`$ なので、$`q_W - q_R`$ は 0 か 1 である（2 以上なら $`W - R`$ が $`2^{32}`$ を超え、負なら $`W < R`$ になる）。場合を分ける。

- $`q_W = q_R`$（head がまだ一周していない）とき: 右辺は $`W - R`$ で、0 以上 $`2^{32}`$ 未満なので、余りをとっても $`W - R`$ のままである。
- $`q_W = q_R + 1`$（head だけが先に一周した）とき: 右辺は $`W - R - 2^{32}`$ で、負の数になる。`uint32_t` の引き算は 0 以上 $`2^{32}`$ 未満の余りを返すので、$`2^{32}`$ が足し戻されて $`W - R`$ になる。

どちらの場合も、head − tail は $`W - R`$、つまり入っている個数に等しい ∎

例: tail = 0xFFFFFFFE（4294967294）のときに 5 バイト書くと、head は 0xFFFFFFFF を超えて 0x00000003 になる。数学の引き算では $`3 - 4294967294 = -4294967291`$ だが、$`2^{32} = 4294967296`$ が足し戻されて 5 になり、入っている 5 バイトと一致する。なお、添字を `uint8_t` や `uint16_t` にすると、C は引き算の前に `int` に広げるので、`(uint8_t)(head - tail)` のように結果を同じ型に戻す。

次に位置である。$`N`$ を 2 のべき乗 $`2^k`$ にすると、$`N`$ で割った余りは下位 $`k`$ ビットを取り出すことと同じなので、`添字 & (N - 1)` で求まる。$`N = 8`$ なら $`N - 1 = `$ `0b0111` で、13 = `0b1101` は `13 & 7` = `0b0101` = 5 となり、13 を 8 で割った余り 5 と一致する。& は 1 命令で済むが、割り算の余りは時間がかかることがある（割り算の命令を持たないマイコンもある。Cortex-M0・M0+ など）。

2 のべき乗にするもう 1 つの理由は、一周の前後で位置が続くことである。$`N = 2^k`$ は $`2^{32}`$ を割り切るので、本当の通し番号 $`W`$ から求めた位置と head から求めた位置は等しい（$`W \bmod N = (q_W \cdot 2^{32} + \mathrm{head}) \bmod N = \mathrm{head} \bmod N`$）。$`N`$ が $`2^{32}`$ を割り切らないと、一周の所で位置が飛ぶ。添字を 8 ビット（256 で一周）にした小さな例を図に示す。

```fig
e04_wrap
```

$`N = 6`$ では、添字 252 と、一周した後の添字 0（本当の通し番号では 256）が、同じ位置 0 を使う。2 つは 4 つしか離れていないので、5 個以上入っていると、書き手がまだ読まれていないデータを上書きする。したがって、増え続ける添字を使う方式では、$`N`$ を 2 のべき乗にする。また、個数 head − tail は 0〜$`N`$ の $`N + 1`$ 通りの値をとるので、添字の型がそれを表せなければならない。`uint32_t` なら問題ないが、8 ビットの添字で $`N = 256`$ にすると、空（0）と満杯（256 が一周して 0）が同じ値になる。8 ビットの添字なら $`N`$ は 128 以下にする。

この方式のリングバッファを C で書く。

```c
#define RB_SIZE 256u                 /* 要素の数。2 のべき乗にする */
#define RB_MASK (RB_SIZE - 1u)       /* 位置 = 添字 & RB_MASK */

struct ring {
    uint8_t  buf[RB_SIZE];
    uint32_t head;                   /* 書き込み位置: これまでに書いた総数 */
    uint32_t tail;                   /* 読み出し位置: これまでに読んだ総数 */
};

/* 入っている個数。添字が一周しても正しい */
static uint32_t ring_count(const struct ring *r)
{
    return r->head - r->tail;
}

/* 書き手: 1 バイト入れる。満杯なら入れずに 0 を返す */
static int ring_put(struct ring *r, uint8_t b)
{
    uint32_t h = r->head;
    if (h - r->tail == RB_SIZE)
        return 0;                    /* 満杯 */
    r->buf[h & RB_MASK] = b;         /* (1) データを書いてから */
    r->head = h + 1u;                /* (2) head を進める */
    return 1;
}

/* 読み手: 1 バイト取り出す。空なら 0 を返す */
static int ring_get(struct ring *r, uint8_t *b)
{
    uint32_t t = r->tail;
    if (r->head == t)
        return 0;                    /* 空 */
    *b = r->buf[t & RB_MASK];        /* (1) データを読んでから */
    r->tail = t + 1u;                /* (2) tail を進める */
    return 1;
}
```

テストでは、添字の初めの値を 0xFFFFFF80 や 0xFFFFFFFE にして一周をまたがせ、普通の配列で作った FIFO と、入れる・取り出すを乱数で数百万回繰り返して比べた。満杯のときは、新しいバイトを入れずに捨てる。ログを残すリングバッファは、満杯なら古いものを上書きする使い方をする（[バイナリ解析シリーズ 12 章 2 節](../binary/12_ログとリングバッファ.md#リングバッファ-巻き戻る記録)）が、受信では、まだ読んでいないデータを上書きすると、メッセージの途中が抜けてしまう。捨てた数を数えておき、5 節の方法で、捨てずに済む大きさにする。

2 節の `rxbuf_put(b)` は、受信用のリングバッファ `rx` に対する `ring_put(&rx, b)` である。`ring_put` と `ring_get` の中の (1) と (2) の順番には意味がある。それを次の節で見る。

## 4. 割り込みとタスクで共有するときの注意

受信用のリングバッファ `rx` は、ISR とタスクが一緒に使う。ISR はタスクの実行の途中、どの 2 つの命令の間にも割り込めるので、タスクが `ring_get` の途中にいるときに、ISR の `ring_put` が実行されることがある。それでも壊れないかを確かめる。

受信用のリングバッファに書くのは ISR だけ、読むのは 1 つのタスクだけである。このように書き手が 1 つ、読み手が 1 つの使い方を **SPSC**（Single Producer, Single Consumer。書き手 1 つ・読み手 1 つ）という。SPSC のリングバッファは、次の 3 つを守れば、割り込みを禁止しなくても壊れない。

1. **1 つの変数を書き換えるのは一方だけにする。** head を書き換えるのは書き手だけ、tail を書き換えるのは読み手だけである。相手の変数は読むだけにする。
2. **head と tail の読み書きを、それぞれ 1 つの命令で行う。** 32 ビットのマイコンでは、アドレスが境界にそろった 32 ビット以下の変数は 1 つの命令で読み書きされ、割り込みは命令と命令の間にしか入らない。したがって相手は、書き換える前か後のどちらかの値を読む。8 ビットのマイコンで 16・32 ビットの添字を使うと、読むのに複数の命令が要り、その間に割り込まれると、上位と下位が別の時点の値になる。
3. **書き手はデータを書いてから head を進め、読み手はデータを読んでから tail を進める。**

3 つ目の規則を守ると、読み手が見る head は、書き終えたデータの位置までしか進んでいない。書き手が見る tail は、読み手がもう使わない位置までしか進んでいない。相手が少し古い値を読んだとしても、書き手は空きを少なめに、読み手はデータを少なめに見るだけで、まだ書いていない位置を読むことも、まだ読んでいない位置に書くこともない。

順番を逆にすると何が起きるかを、満杯の受信バッファで確かめる。図は、$`N = 4`$ のバッファに A B C D が入っている（満杯の）とき、タスクが `ring_get` で 1 バイト取り出す途中に、E を受け取った ISR が割り込む場合の実行の順番である。

```fig
e04_order
```

正しい順番（左）では、ISR がどこで割り込んでも、タスクは A を受け取る。tail が進む前に割り込めば、ISR は満杯と判断して E を捨て（捨てた数を数える）、tail が進んだ後なら、空いた位置 0 に E を書く。逆の順番（右）では、タスクが tail を進めてから A を読むまでの間に割り込まれると、ISR は位置 0 が空いたと判断して E を書き、タスクは A の代わりに E を読む。A は失われ、E は後でもう一度読まれる。割り込みが入りうる 5 か所のうち 1 か所でだけ、しかもバッファが満杯のときだけ起きるので、試験ではめったに見つからない。書き手の順番も同じで、7 節の送信のようにタスクが書き手、ISR が読み手になる場合、タスクが head を進めてからデータを書くと、その間に割り込んだ ISR は、まだ書かれていない位置の古いバイトを送ってしまう。

### volatile — 読み書きを省かせず、順番を守らせる

ここまでは、C の文が、書いた順番どおりに、毎回メモリを読み書きして実行されると考えてきた。ところがコンパイラは、最適化のために、変数の値をレジスタに置いたままにしたり、読み書きの順番を入れ替えたりする。1 つの流れの中では結果が変わらないからである。たとえば、データが来るまで待つ次のループを考える。

```c
while (r->head == r->tail) {
    /* データが来るまで待つ */
}
```

ループの中では head も tail も書き換えていないので、コンパイラは 2 つを最初に 1 回だけ読み、あとはレジスタの値を比べ続けてよいと判断する。gcc 13 で `-O2` を付けて x86-64 向けに翻訳すると、実際にそうなり、ISR が head を進めてもループは終わらない。

**volatile** は、変数に付ける C の型修飾子で、「この変数は、見えている処理の流れの外（ISR やハードウェア）で読み書きされる」ことをコンパイラに伝える。volatile の変数は、ソースに書いた読み書きのたびに実際にメモリを読み書きし、volatile の変数どうしの読み書きの順番は入れ替えられない。リングバッファでは、head と tail だけでなく、データの配列にも volatile を付ける。データの配列が volatile でないと、コンパイラは「データを書く」ことを「head を進める」ことの後に動かしてもよい（C の規格がそれを許している）からである。3 節の構造体を次のように変える。関数はそのままでよい。

```c
struct ring {
    volatile uint8_t  buf[RB_SIZE];  /* データも volatile にして、書く順番をコンパイラに守らせる */
    volatile uint32_t head;          /* 書き手（ISR）だけが書き換える */
    volatile uint32_t tail;          /* 読み手（タスク）だけが書き換える */
};

static struct ring rx;               /* 受信用: ISR が書き、受信タスクが読む */

void rx_poll(void)                   /* 受信タスクから、知らせを受けるたびに呼ぶ */
{
    uint8_t b;
    while (ring_get(&rx, &b))        /* 空になるまで取り出す */
        frame_feed(b);               /* 03 章の復号など、時間のかかる処理はここで */
}
```

2 節の `rx_err_count` と `rx_drop_count` も、ISR だけが書き換え、タスクが読む変数なので、volatile を付けておいた。

volatile には限界が 2 つある。1 つは、読んで・変えて・書き戻す操作を、ひとまとまりにはしないことである。リングバッファの個数を、head と tail の差ではなく 1 つの変数 count で持ち、ISR が `count++`、タスクが `count--` で数えるとする。`count--` は、読む・1 を引く・書き戻すの 3 つの命令になり、その間に ISR の `count++` が入ると、ISR が足した 1 が上書きされて消える。count を volatile にしても防げない。head と tail に分け、それぞれを片方だけが書き換えるのは、この競合を避けるためである。

```fig
e04_count
```

もう 1 つは、CPU の外から見た順番を約束しないことである。同じ CPU の上の ISR とタスクなら、CPU は自分の書き込みを、自分には命令の順番どおりに見せるので、コンパイラの並べ替えを防げば足りる。しかし、マルチコアのマイコンで別のコアがリングバッファの相手になる場合や、DMA のように CPU 以外がメモリを読み書きする場合は、CPU やキャッシュが、書き込みが外から見える順番や時期を変えることがある。そのときは、メモリの読み書きの順番を守らせる命令（メモリバリア。Arm の DMB など）や、キャッシュの操作が要る。キャッシュを持つ Cortex-M7 などでは特に注意が要るので、使うマイコンの資料で確かめる。C11 に対応したコンパイラなら、`<stdatomic.h>` の release と acquire の指定で head と tail を読み書きすると、必要な命令をコンパイラが入れる。RTOS には、この節の考え方で作られた部品が用意されていることも多い（FreeRTOS のストリームバッファ。[OS シリーズ 14 章 7 節](../freertos/14_タスク通知とイベントグループ.md#ストリームバッファとメッセージバッファ)）。

### 書き手が 2 つ以上のとき — クリティカルセクション

SPSC でない使い方では、この節の方法は使えない。たとえば 2 つのタスクが同じ送信バッファに `ring_put` すると、両方が同じ head の値を読み、同じ位置に書いて、head を同じ値に進めることがある。1 バイトが消え、2 つのメッセージが混ざる。このように、共有するデータを読み書きする一連の処理で、途中にほかの処理を割り込ませてはいけない区間を**クリティカルセクション**という。ISR と共有するデータなら、その間だけ割り込みを禁止して作る（上の図の右）。

```c
uint32_t s = irq_save();   /* 割り込みを禁止し、それまでの状態を返す */
/* … 共有するデータを読み書きする（短く） … */
irq_restore(s);            /* それまでの状態に戻す（禁止されていたなら禁止のまま） */
```

`irq_save` と `irq_restore` は、この章で仮に置く関数である（Cortex-M なら、CMSIS の `__get_PRIMASK`・`__disable_irq`・`__set_PRIMASK` で作れる）。禁止する前の状態を保存して戻すのは、すでに割り込みが禁止された所から呼ばれたときに、勝手に許可しないためである。割り込みを禁止している時間は、2 節の割り込み遅延にそのまま加わるので、数 µs で終わる短い処理だけを囲む。タスクどうしで共有するだけなら、RTOS のミューテックスなども使える（[OS シリーズ 19 章 3 節](../freertos/19_排他制御の設計.md#排他の道具と使い分け)）。そもそも、1 つの通信路に書くタスクを 1 つに決め、ほかのタスクはキューで頼む構成にすれば、共有そのものがなくなる（[05 章 2 節](05_状態機械とタイムアウト.md#待ち方-ブロッキング-ノンブロッキング-イベント駆動)）。

## 5. バッファの大きさを決める

リングバッファの大きさ $`N`$ はどう決めればよいか。書き手（ISR）は届く速さで書き、読み手（タスク）は自分の都合で読む。読み手が長く止まると、その間に届いたバイトがたまる。

**方針**: 読み手がバッファを空にした直後から、次に読み始めるまでの間に届くバイトの数の最大を求め、それが $`N`$ 以下になる条件を立てる。

**導出**: 届く速さの最大を $`r`$（バイト/秒）、読み手が止まる最長の時間を $`T_\mathrm{s}`$ とする。読み手は、読み始めたら、たまっていた分をすぐに取り出すとする。読み手が空にした時刻を 0 とすると、時刻 $`T_\mathrm{s}`$ までに届くのは多くとも $`r\,T_\mathrm{s}`$ バイトである。これがすべてバッファに入る条件は

$$
N \ge r\, T_\mathrm{s}
$$

である ∎

**例**: 115200 bps・8N1 で続けて届くなら $`r = 11520`$ バイト/秒である。読み手が最大 20 ms 止まるなら $`r\,T_\mathrm{s} = 11520 \times 0.020 = 230.4`$ バイトなので、231 バイト以上が要る。3 節の方式では $`N`$ を 2 のべき乗にするので、256 とする。

読み手が止まる時間には、優先度の高いほかのタスクが動く時間、読み手自身がメッセージを処理する時間、フラッシュメモリへの書き込みのように CPU が待たされる時間などを含める。見積もりには誤差があるので、余裕を足す。届き方がまとまっている場合（無線モジュールが 1024 バイトを 921600 bps で一度に送ってくるなど）は、$`r`$ にまとまっている間の速さ（92160 バイト/秒）を使う。20 ms 止まるなら 1843 バイト分になるが、1 回のまとまりが 1024 バイトで、次のまとまりまでに読み手が追いつくなら、たまるのは多くとも 1024 バイトである。

大きさで吸収できるのは、一時的な停止だけである。読み手が 1 秒あたりに取り出せるバイト数の平均 $`r_\mathrm{out}`$ が、届くバイト数の平均 $`r_\mathrm{in}`$ より小さいと、バッファの中の量は 1 秒あたり平均 $`r_\mathrm{in} - r_\mathrm{out}`$ ずつ増え続ける。空の状態から満杯になるまでの時間は、およそ $`N / (r_\mathrm{in} - r_\mathrm{out})`$ 秒で、どんな大きさでもいつかはあふれる。たとえば $`r_\mathrm{in} = 11520`$、$`r_\mathrm{out} = 10000`$ バイト/秒なら、256 バイトは 0.17 秒、4096 バイトでも 2.7 秒であふれる。この場合は、読み手を速くするか、送り手を待たせる（02 章 6 節のフロー制御）しかない。フロー制御を使うときは、RTS を無効にするしきい値の上に、02 章 6 節で求めた空きを残す。

## 6. DMA で受け取る

1 節で見たように、DMA は CPU の代わりに、周辺回路とメモリの間でデータを運ぶ。UART の受信に使うときは、DMA コントローラに、読み出し元（UART の受信データレジスタ）、書き込み先（RAM のバッファの先頭）、運ぶバイトの数 $`N`$ を設定する。UART が 1 バイト受け取るたびに DMA に要求が出て、DMA はそのバイトを書き込み先へ運び、書き込み先を 1 つ進め、**残り転送数**（あと何バイト運ぶか）を 1 減らす。CPU は 1 バイトごとには何もしない。

```fig
e04_dma
```

**循環モード**では、残り転送数が 0 になると、DMA は書き込み先をバッファの先頭に、残り転送数を $`N`$ に戻して、運び続ける。バッファは 3 節のリングバッファと同じ形になり、書き手は DMA、DMA が次に書く位置は $`N - \text{残り転送数}`$ である。DMA は止まらないので、どのタイミングでバイトが届いても取りこぼさない。

CPU は、書かれたデータをいつ処理すればよいかを知る必要がある。多くの DMA コントローラは、バッファの半分まで書いたときと、最後まで書いたとき（一周して先頭に戻るとき）に、割り込みを出せる。これを**転送の半分完了**・**全部完了**の割り込みという。半分完了で前半を、全部完了で後半を処理すれば、DMA が一方の半分に書いている間に、CPU はもう一方の半分を処理できる。

しかし、半分がたまるまで知らせは来ない。$`N = 256`$ のバッファの先頭から 10 バイトの短いメッセージが届いても、さらに 118 バイトが届くまで、CPU はそれを知らない。そこで、UART の**アイドルライン検出**を一緒に使う。これは、受信が止まり、RX の線がアイドル（1）のまま 1 文字分（8N1 なら 10 ビット時間。115200 bps で 86.8 µs）続いたことを UART が検出して、割り込みを出す機能である（UART によって名前や、何文字分で知らせるかが違う）。送り手は 1 つのメッセージを続けて送り、メッセージとメッセージの間を空けることが多いので、アイドルラインはメッセージの終わりの目安になる。

```fig
e04_dmatime
```

どの知らせを受けても、CPU がすることは同じである。残り転送数を読んで DMA が次に書く位置 pos を求め、前回処理し終えた位置 last から pos の手前までを処理する。pos が last より小さければ、DMA が一周をまたいだので、last から末尾までと、先頭から pos の手前までの 2 つに分けて処理する。

```fig
e04_dmacirc
```

```c
#define DMA_N 256u                       /* DMA の受信バッファの大きさ */
static uint8_t dma_buf[DMA_N];           /* DMA が循環モードで書き続ける */
static uint32_t dma_last;                /* 前回までに処理し終えた位置 */

/* 半分完了・全部完了・アイドルラインの割り込みから呼ぶ */
void dma_rx_event(void)
{
    uint32_t pos = DMA_N - dma_hw_remaining();   /* DMA が次に書く位置 */
    if (pos >= DMA_N)
        pos = 0;                         /* 残りが 0 と読めたときは先頭として扱う */
    if (pos > dma_last) {                /* 一続きの範囲 */
        rx_deliver(&dma_buf[dma_last], pos - dma_last);
    } else if (pos < dma_last) {         /* 一周をまたぐ: 末尾までと、先頭から */
        rx_deliver(&dma_buf[dma_last], DMA_N - dma_last);
        if (pos > 0)
            rx_deliver(&dma_buf[0], pos);
    }
    dma_last = pos;                      /* pos == dma_last なら新しいデータはない */
}
```

`dma_hw_remaining()`（残り転送数を読む）と `rx_deliver(p, n)`（受け取った範囲を渡す）は、この章で仮に置く関数である。`rx_deliver` は、3 節のリングバッファに写してタスクに知らせてもよいし、03 章の区切りの復号に直接渡してもよい。テストでは、メッセージの長さと知らせの時刻を乱数で変え、知らせの処理を遅らせた場合や、一周の境目で残り転送数が 0 と読める場合も含めて、送ったバイトの列と処理したバイトの列が一致することを確かめた。

循環モードの DMA は、CPU が読み終わるのを待たない。あるバイトは、書かれてから $`N`$ バイト後に、次の周回のバイトで上書きされる。CPU が知らせを受けてから処理を始めるまでの遅れを $`d`$（バイトの時間を単位とする）として、失わない条件を求める。

**方針**: 処理が最も遅くなるバイトについて、書かれてから処理されるまでの時間を求め、それが上書きまでの時間 $`N`$ より短いという条件を立てる。

**導出**: 半分完了・全部完了の知らせは $`N/2`$ バイトごとに来る。ある知らせの直後に書かれたバイトは、次の知らせまで多くとも $`N/2`$ バイトの時間待ち、そこから処理まで $`d`$ 待つ。書かれてから処理されるまでは多くとも $`N/2 + d`$ で、これが $`N`$ より短ければ上書きされる前に処理できる。したがって条件は $`N/2 + d < N`$、すなわち $`d < N/2`$ である ∎

$`N = 256`$ なら、$`N/2 = 128`$ バイトの時間は、115200 bps で $`128 \times 86.8\ \text{µs} = 11.1`$ ms、921600 bps で 1.39 ms である。アイドルラインの知らせは、半分完了・全部完了より早く来ることがあるだけなので、この条件を厳しくはしない。またこの条件が守られていれば、前回の処理から新しく書かれたのは $`N`$ バイト未満なので、`pos == dma_last` は「新しいデータがない」場合に限られる（ちょうど $`N`$ バイト届いた場合と取り違えない）。

DMA で受け取っている間、CPU は眠っていてもよい（01 章 5 節の間欠動作。どの深さの眠りで DMA が動き続けるかは製品による）。データキャッシュを持つマイコン（Cortex-M7 など）では、DMA が RAM に書いた値を、CPU がキャッシュに残った古い値で読むことがある。キャッシュを無効にしてから読む、キャッシュしない領域にバッファを置く、などの対策が要る（使うマイコンの資料で確かめる）。

下の図で、DMA のバッファの大きさ、メッセージの長さと間隔、アイドルライン検出の有無、知らせを処理するまでの遅れを変えると、DMA が書く位置の時間変化と、知らせの種類と時刻、CPU が処理した範囲、メッセージが届いてから処理されるまでの時間が表示される。遅れを $`N/2`$ バイトの時間より長くすると、上書きされて失われるバイトが出る。

## 7. 送信側 — 送信バッファと送信完了

送信の回路は、受信と対になっている。ソフトウェアが送信データレジスタに 1 バイト書くと、UART はそれをシフトレジスタに移し、スタートビットから順に TX の線に出す。シフトレジスタに移した時点で送信データレジスタは空くので、次のバイトを書いてよい。UART はこの様子を 2 つの印で知らせる。

- **送信データレジスタ空**（**TXE**、Transmit data register Empty）: 送信データレジスタが空で、次のバイトを書いてよいことを示す。前のバイトは、まだ線に出ている途中かもしれない。
- **送信完了**（**TC**、Transmission Complete）: 送信データレジスタが空で、シフトレジスタも最後のバイトのストップビットまで線に出し終えたことを示す。

```fig
e04_txpath
```

最後のバイトについて見ると、TXE はそのバイトがシフトレジスタに移ったときに、TC はそのバイトが線から出終わったときに立つ。2 つの間は 1 文字分（115200 bps・8N1 で 86.8 µs）離れている。RS-485 の DE（02 章 5 節）を TXE で無効にすると、最後のバイトはまだ線に出ていないので、途中で切れる。DE は TC で無効にする。UART を止める深い眠りに入る前も同じで、TC を待ってから眠らないと、最後のバイトが切れる。

```fig
e04_txetc
```

タスクが送るバイトを 1 つずつ送信データレジスタに書き、TXE を待ってから次を書くと、115200 bps では 1 バイトに 86.8 µs、40 バイトで 3.47 ms の間、タスクがほかの仕事をできない。そこで、受信と同じくリングバッファを置く。今度は書き手がタスク、読み手が ISR の SPSC である。タスクは送信バッファにバイトを入れ、TXE の割り込みを許可する。TXE の ISR は、送信バッファから 1 バイト取り出して送信データレジスタに書く。送信バッファが空なら、TXE の割り込みを禁止する。TXE は送信データレジスタが空である間ずっと立っているので、禁止しないと ISR が際限なく呼ばれ続ける。RS-485 のように送り終わってからすることがあれば、送信バッファが空になったときに TC の割り込みを許可し、TC の ISR で行う。

```c
static struct ring tx;                       /* タスクが書き、送信の ISR が読む */

/* タスクから呼ぶ: 送信バッファに入れて、送信を始める。入った数を返す */
uint32_t uart_write(const uint8_t *p, uint32_t n)
{
    uint32_t k = 0;
    while (k < n && ring_put(&tx, p[k]))
        k++;                                 /* 満杯なら入った所まで */
    if (k > 0) {
        rs485_de(1);                         /* RS-485 なら送信を有効に（02 章 5 節） */
        uint32_t s = irq_save();             /* 許可のビットは ISR も書き換えるので、 */
        uart_hw_irq(UART_IRQ_TXE, 1);        /* 読んで変えて書き戻す間は割り込みを禁止 */
        irq_restore(s);
    }
    return k;
}

/* 送信の割り込みハンドラ */
void uart_tx_isr(void)
{
    uint8_t b;
    if (uart_hw_txe()) {                     /* 送信データレジスタが空いている */
        if (ring_get(&tx, &b)) {
            uart_hw_write(b);                /* 次のバイトを渡す（送信完了の印は消える） */
        } else {
            uart_hw_irq(UART_IRQ_TXE, 0);    /* 送るものがない: 空の知らせを止め、 */
            uart_hw_irq(UART_IRQ_TC, 1);     /* 最後のバイトが出終わるのを待つ */
        }
    }
    if (uart_hw_tc()) {                      /* 最後のストップビットまで線に出た */
        uart_hw_irq(UART_IRQ_TC, 0);
        rs485_de(0);                         /* RS-485 のドライバを止めて受信に戻す */
    }
}
```

`uart_hw_txe()`・`uart_hw_tc()`（印を読む）、`uart_hw_write()`、`uart_hw_irq()`（割り込みの許可と禁止）、`rs485_de()` は、この章で仮に置く関数である。`uart_tx_isr` は、どの知らせで呼ばれても先に TXE を見る。前の送信の TC の知らせが残っている間にタスクが新しいバイトを入れた場合でも、ISR はまず新しいバイトを送信データレジスタに書く。書くと TC の印は消える（多くの UART でそうなる。消え方は製品による）ので、DE を早く戻すことはない。`uart_write` の中で割り込みを禁止しているのは、割り込みの許可のビットが 1 つのレジスタにまとまっていて、ISR もそれを書き換えるからである。読んで・変えて・書き戻す間に ISR が別のビットを書き換えると、4 節の count と同じく、その変更が消える。許可と禁止を別々のレジスタで行えるマイコンなら、この禁止は要らない。

テストでは、1 ビット時間ずつ進む模擬の UART を作り、`uart_write` の途中のあちこちで ISR を割り込ませても、書いた順にすべてのバイトが線に出ること、ビットが線に出ている間は DE が 1 であること、最後に DE が 0 に戻ることを確かめた。わざと TXE の時点で DE を戻すように書き換えると、テストは「DE が 0 のままビットを出した」ことを検出した。

送信に DMA を使う場合も、DMA の全部完了の知らせは「最後のバイトを送信データレジスタに運び終えた」ことを示すだけで、線から出終わったことではない（多くのマイコンでそうなる）。DE を戻すのも、眠りに入るのも、TC を待ってからにする。

## 8. まとめ

| 項目 | 内容 |
|---|---|
| 受信データレジスタとオーバーラン | 受け取った 1 バイトを置くレジスタ。次のバイトを受け取り終えるまで（115200 bps・8N1 で 86.8 µs）に読まないと、オーバーランで失われる。深さ $`D`$ の FIFO なら猶予は $`D`$ バイト分 |
| 3 つの受け取り方 | ポーリング（印を見に行く）、割り込み（バイトごとに ISR が読む）、DMA（専用の回路が運び、CPU は区切りで知らせを受ける） |
| 割り込みハンドラ | 読む・誤りを数える・バッファに入れる・知らせる、だけにする。割り込み遅延の最大が $`D\,T_\mathrm{B}`$ を超えるとオーバーラン |
| リングバッファ | 配列を輪として使い、書き手は head、読み手は tail を進める。増え続ける添字なら個数は head − tail（$`2^{32}`$ を法として正しい）。$`N`$ は 2 のべき乗、位置は `& (N - 1)` |
| SPSC の規則 | 各変数を書き換えるのは片方だけ。データを書いてから head、データを読んでから tail を進める。head・tail・データの配列に volatile |
| volatile の限界 | 読んで・変えて・書き戻す操作をひとまとまりにしない。ほかのコアや DMA から見た順番も守らない（メモリバリア・キャッシュの操作が要る） |
| クリティカルセクション | 書き手が 2 つ以上なら、短い間だけ割り込みを禁止する（元の状態を保存して戻す）。その時間は割り込み遅延に加わる |
| バッファの大きさ | $`N \ge r\,T_\mathrm{s}`$（入る速さ × 読み手が止まる最長の時間）に余裕を足す。読み手の平均の速さが足りなければ、どの大きさでもあふれる |
| DMA の受信 | 循環モードで回し続け、半分完了・全部完了・アイドルラインの知らせのたびに、前回の位置から $`N - \text{残り転送数}`$ までを処理する。処理の遅れは $`N/2`$ バイトの時間未満 |
| 送信 | 送信バッファ + TXE の割り込み（空なら禁止）。線から出終わったことは TC で知る。RS-485 の DE は TC で戻す |

次章では、こうして受け取ったバイトの列を使い、命令を送って応答を待ち、来なければ送り直す手順を、状態機械とタイムアウトで組み立てる。
