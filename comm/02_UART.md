# 02. UART — 1 本の線でバイトを送る

> **この章で扱う問い.**
> 01 章では、機器の外との通信を、仕事ごとに分けた層の積み重ねとして見た。この章では、いちばん下の層、つまり信号線の上でビットをどう運ぶかを、組み込み機器で最もよく使われる UART で具体的に見る。
>
> この章では次の 3 つの問いに答える。
>
> 1. クロックの線を持たない 1 本の信号線で、1 バイトをどのような形で送るのか。
> 2. 送り手と受け手の時計がわずかにずれていても、なぜ正しく受け取れるのか。どこまでずれてよいのか。
> 3. 信号を遠くまで届けるための電気的な形と、受け手が追いつかないときの止め方は、どうなっているのか。
>
> 答えの道具は、スタートビットで時刻を合わせる仕組みと、読む時刻のずれを数える計算である。

## 1. 並列とシリアル、同期と非同期

1 バイトの 8 ビットを、8 本の線で同時に送る方式を**並列通信**、1 本の線で 1 ビットずつ時間をずらして送る方式を**シリアル通信**という。

```fig
e02_parallel
```

並列通信は 1 度に多くのビットを送れるが、線とコネクタの数が多い。さらに線が長くなると、線ごとに信号の届く時刻が少しずつずれ、どのビットが同じバイトのものかが分からなくなる。機器の外との通信は、ほとんどがシリアル通信である。

シリアル通信では、受け手は「いつ、線の値を読めば次のビットなのか」を知る必要がある。その知り方で 2 つに分かれる。送り手がデータとは別に**クロック**（一定の間隔で 0 と 1 を繰り返す信号）の線を出し、受け手がクロックの変わり目でデータを読む方式を**同期式**という。マイコンとセンサの間でよく使われる SPI や I²C は同期式である。クロックの線を持たず、送り手と受け手が 1 ビットの長さを前もって決めておき、受け手はデータの始まりの印で時刻を合わせる方式を**非同期式**という。

```fig
e02_sync
```

非同期式のシリアル通信を行う、マイコンの周辺回路を **UART**（Universal Asynchronous Receiver/Transmitter）という。この方式の通信そのものも、UART と呼ぶことが多い。UART は、機器どうし、マイコンと無線モジュール（06 章）、マイコンと開発用の PC（ログの出力）をつなぐのに使われる。

UART の配線は次のとおりである。

```fig
e02_wiring
```

送信の線（TX）と受信の線（RX）が別にあるので、両方向に同時に送れる。電圧は GND を基準に測るので、2 つの機器の GND もつなぐ。自分の TX を相手の RX へつなぐ（交差させる）。TX と TX をつないでしまう配線の誤りは、よく起きる失敗である。

## 2. UART のフレーム — スタートビット・データ・パリティ・ストップビット

非同期式では、1 ビットの長さを両者で決めておく。1 ビットを送る時間を**ビット時間**といい、1 秒あたりに送る信号の区切りの数を**ボーレート**という。UART では 1 つの区切りで 1 ビットを送るので、ボーレートはビットレート（bps）と同じ値になる。よく使われるボーレートは 9600、115200 などで、ビット時間はボーレートの逆数である。115200 bps なら、ビット時間は $`1 / 115200 \approx 8.68`$ µs となる。

UART は 1 バイトを、前後に印を付けたまとまりにして送る。このまとまりを、UART の**フレーム**という（03 章では、もっと長いメッセージのまとまりもフレームと呼ぶので、この章では「UART のフレーム」と書く）。文字 'A'（0x41）を送ったときの信号を図に示す。

```fig
e02_frame
```

- 何も送っていない間、線は 1（電圧が高い状態）にしておく。この状態を**アイドル**という。
- **スタートビット**: フレームの始まりの印として、1 ビット時間だけ 0 にする。アイドルの 1 から 0 に変わる所で、受け手は始まりを知る。
- **データビット**: 多くは 8 ビット。**最下位ビット**（**LSB**、いちばん小さい桁 b0）から順に、**最上位ビット**（**MSB**、b7）まで送る。0x41 = 0b0100_0001 は、b0 = 1、b6 = 1 で、ほかは 0 なので、線には 1, 0, 0, 0, 0, 0, 1, 0 の順に出る。
- **パリティビット**（付けない場合もある）: データビットの中の 1 の数を数え、**偶数パリティ**では全体（データとパリティ）の 1 の数が偶数に、**奇数パリティ**では奇数になるように、0 か 1 を付け足す。受け手は 1 の数を数え直し、決まりに合わなければ誤りに気づく。1 ビットだけ反転した誤りは必ず分かるが、2 ビットが同時に反転すると 1 の数の偶奇は変わらないので分からない。
- **ストップビット**: フレームの終わりの印として、1 ビット時間（または 2 ビット時間）だけ 1 にする。これで線がいったん 1 に戻るので、次のフレームのスタートビットで、必ず 1 から 0 への変わり目ができる。

フレームの形は「データビットの数・パリティ・ストップビットの数」で書く。パリティは N（なし）、E（偶数）、O（奇数）である。8N1 は、データ 8 ビット、パリティなし、ストップビット 1 を表し、最もよく使われる。

```fig
e02_formats
```

1 バイトを送るのにかかる時間を求める。8N1 のフレームは、スタートビット 1 + データ 8 + ストップビット 1 = 10 ビット時間である。115200 bps では、1 バイトに $`10 \times 8.68 = 86.8`$ µs かかり、1 秒に送れるバイトの数は $`115200 / 10 = 11520`$ バイトとなる。線の上のビットのうち、データのビットの割合は 8/10 = 80 % である。

パリティとフレームのビット列は、次のように作れる。1 の数の偶奇（パリティ）は、ビットを半分ずつ重ねて XOR をとることを繰り返すと求まる。

```c
/* x の中の 1 のビットの数が奇数なら 1、偶数なら 0 を返す */
static unsigned parity8(uint8_t x)
{
    x ^= x >> 4;    /* 上位 4 ビットを下位 4 ビットに重ねる */
    x ^= x >> 2;
    x ^= x >> 1;
    return x & 1u;
}

enum parity { PARITY_NONE, PARITY_EVEN, PARITY_ODD };

/* 1 バイトを UART のフレームのビット列（線に出す順）にする。
   bits[] に 0/1 を入れ、ビットの数を返す（8N1 なら 10） */
static int uart_frame_bits(uint8_t data, enum parity p, int stop_bits, uint8_t bits[12])
{
    int n = 0;
    bits[n++] = 0;                         /* スタートビット */
    for (int i = 0; i < 8; i++)
        bits[n++] = (data >> i) & 1u;      /* データ: 最下位ビット (LSB) から */
    if (p == PARITY_EVEN)
        bits[n++] = parity8(data);         /* 1 の数を偶数にそろえる */
    else if (p == PARITY_ODD)
        bits[n++] = parity8(data) ^ 1u;    /* 1 の数を奇数にそろえる */
    for (int i = 0; i < stop_bits; i++)
        bits[n++] = 1;                     /* ストップビット */
    return n;
}
```

`parity8` の 3 行は、8 ビットの XOR を 3 回にまとめたものである。1 行目の後、下位 4 ビットの各ビットは、元の b0 と b4、b1 と b5、… の XOR になる。これを 2 回繰り返すと、b0 に 8 ビット全部の XOR、つまり 1 の数の偶奇が残る。実際のマイコンでは、このビット列は UART の回路が作って送るので、ソフトウェアが作るのは、UART の回路を持たない端子で信号を出す場合などに限られる。

## 3. 受信の仕組み — 立ち下がりで合わせ、ビットの中央で読む

受け手は、相手がいつ送り始めるかを知らない。そこで、線がアイドルの 1 から 0 に変わる瞬間（**立ち下がり**）を待ち、それをフレームの始まりとする。受け手も自分の時計で 1 ビット時間を測るが、変わり目の時刻を細かく知るために、1 ビット時間を 16 に分けた細かい時計で線の値を見ている。このように、1 ビット時間あたり何回も線を見ることを**オーバーサンプリング**という（16 倍が多い）。

```fig
e02_sampling
```

立ち下がりを見つけたら、受け手は 8 目盛（半ビット時間）待って、スタートビットの中央でもう一度線を見る。そこで 0 なら本物のスタートビット、1 に戻っていれば短い雑音として読み捨てる。以後は 16 目盛（1 ビット時間）ごとに、各ビットの中央で線を読む。多くの UART は、中央の前後の 3 点を読んで多数決をとり、雑音で 1 点だけが反転しても正しく読めるようにしている（製品による）。

ビットの中央で読むのは、読む時刻が前後どちらに半ビット時間ずれても、同じビットの範囲に収まるからである。次の 4 節で、この余裕を使い切るまでに、どれだけ時計がずれてよいかを求める。

受け手は、最後にストップビットの位置で 1 であることを確かめる。ここが 0 なら、フレームの区切りが合っていない（時計のずれ、雑音、送り手の設定違いなど）ということで、これを**フレーミングエラー**という。パリティが合わない場合を**パリティエラー**という。また、フレームの長さを超えて線が 0 のままのとき、UART はこれを**ブレーク**として知らせる。ブレークは誤りとしてではなく、合図として使われることもある（受け手に、これから送るものの始まりを知らせるなど）。

## 4. 時計のずれはどこまで許されるか

送り手と受け手は、それぞれ自分の時計（水晶発振子、マイコン内蔵の RC 発振回路など）から 1 ビット時間を作る。時計の精度には限りがあり、さらにボーレートは時計の周波数を整数で割って作ることが多いので、両者のビット時間はわずかに違う。受け手が時刻を合わせるのはスタートビットの立ち下がりの 1 回だけなので、ずれはフレームの後ろへ行くほど積み重なる。

```fig
e02_drift
```

図のように、ずれが大きすぎると、受け手はフレームの後ろの方で隣のビットを読んでしまう。どこまでのずれなら、最後のビットまで正しく読めるかを求める。

**方針**: 送り手のビット時間を $`T_\mathrm{t}`$、受け手のビット時間を $`T_\mathrm{r}`$ とし、受け手の相対的な誤差を $`e = (T_\mathrm{r} - T_\mathrm{t}) / T_\mathrm{t}`$ とおく。フレームの先頭（スタートビット）を k = 0 として、k 番目のビットを読む時刻と、そのビットの中央の時刻の差を求め、それが半ビット時間より小さいという条件を立てる。

**導出**: 立ち下がりの時刻を 0 とする。送り手の k 番目のビットは、時刻 $`k T_\mathrm{t}`$ から $`(k+1) T_\mathrm{t}`$ までの間に線に出ていて、その中央は $`(k + \tfrac{1}{2}) T_\mathrm{t}`$ である。受け手は自分の時計で中央を狙うので、k 番目のビットを時刻 $`(k + \tfrac{1}{2}) T_\mathrm{r}`$ に読む。読む時刻と中央の差は

$$
\left(k + \tfrac{1}{2}\right) T_\mathrm{r} - \left(k + \tfrac{1}{2}\right) T_\mathrm{t} = \left(k + \tfrac{1}{2}\right)(T_\mathrm{r} - T_\mathrm{t}) = \left(k + \tfrac{1}{2}\right) e\, T_\mathrm{t}
$$

である（最後の等号は $`T_\mathrm{r} - T_\mathrm{t} = e T_\mathrm{t}`$ を代入した）。読む時刻が k 番目のビットの範囲に入るのは、この差の大きさが半ビット時間 $`\tfrac{1}{2} T_\mathrm{t}`$ より小さいときなので、両辺を $`T_\mathrm{t}`$ で割って

$$
\left| \left(k + \tfrac{1}{2}\right) e \right| < \frac{1}{2}
$$

が条件となる。左辺は k が大きいほど大きいので、最後に読むビットで成り立てば、それより前のすべてのビットで成り立つ。8N1 では最後はストップビットの k = 9 なので、$`|9.5\, e| < 0.5`$、すなわち $`|e| < 1/19 \approx 5.26`$ % となる。

ただし、受け手が立ち下がりに気づくのは、16 に分けた目盛の上なので、本当の立ち下がりより最大 1/16 ビット時間遅れることがある。この遅れの分だけ余裕が減るので、条件は $`|9.5\, e| < \tfrac{1}{2} - \tfrac{1}{16}`$、すなわち $`|e| < 0.4375 / 9.5 \approx 4.61`$ % となる ∎

```fig
e02_offset
```

この $`e`$ は、送り手と受け手の**ビット時間の差**である。送り手が 2 % 速く、受け手が 2 % 遅ければ、$`e`$ は約 4 % になる。つまり 4.61 % は、両側の誤差を合わせた限界である。実際には、信号の立ち上がりと立ち下がりがなまって 0 と 1 の境目がずれることや、多数決のために中央の前後の点を使うこと（さらに 1/16 ビットほど余裕が減る）もある。そこで、片側ずつのボーレートの誤差を ±2 % 程度以下に抑えるのが、一般的な目安である。パリティを付けた 8E1 では最後のビットが k = 10 になるので、限界は $`(0.5 - 1/16) / 10.5 \approx 4.17`$ % と、少し厳しくなる。

### ボーレートを作るときの誤差

マイコンの UART は、周辺回路のクロックの周波数 $`f`$ を分周の値 $`n`$ で割って、オーバーサンプリングの目盛を作る。16 倍のオーバーサンプリングなら、実際のボーレートは $`f / (16 n)`$ である。$`n`$ は整数（または決まった細かさの小数）しか選べないので、$`n = f / (16 \times \text{ボーレート})`$ を丸めた分だけ、ボーレートがずれる。

**例**: $`f`$ = 16 MHz で 115200 bps を作る。$`16 \times 10^6 / (16 \times 115200) = 8.68`$ を丸めて $`n = 9`$ とすると、実際のボーレートは $`16 \times 10^6 / (16 \times 9) = 111111`$ bps で、誤差は −3.55 % となる。片側の目安の ±2 % を超えているので、相手の誤差によっては読み誤る。

```fig
e02_baud
```

誤差を小さくする方法は 3 つある。

- **8 倍のオーバーサンプリングにする**: $`n = 16 \times 10^6 / (8 \times 115200) = 17.36`$ を丸めて 17 とすると、117647 bps で +2.12 % になる（16 倍より細かく分周できるが、受信の雑音への強さは少し下がる）。
- **小数の分周を使う**: 分周の値に 1/16 刻みの小数を使える UART では、$`n = 8.6875`$ として 115108 bps、誤差 −0.08 % にできる。
- **割り切れるクロックを使う**: 14.7456 MHz の水晶を使うと、$`14.7456 \times 10^6 / (16 \times 115200) = 8`$ がちょうど整数になり、誤差は 0 になる。UART のために、このような周波数の水晶が使われることがある。

時計そのものの精度も効く。水晶発振子の誤差は数十 ppm（1 ppm は 100 万分の 1）程度で問題にならないが、マイコン内蔵の RC 発振回路は ±1〜数 % ずれることがあり（代表値。温度でも変わる）、UART に使うときは注意が要る。

分周の値と誤差を求める関数の例を示す（誤差は ppm で返す）。初期化のときにこの誤差を計算し、目安を超える設定を検出できるようにしておくとよい。

```c
/* 分周の値 n = f_clk / (ovs * baud) を四捨五入で整数にし、実際のボーレートの誤差を ppm で返す */
static uint32_t uart_divider(uint32_t f_clk, uint32_t baud, uint32_t ovs, int32_t *err_ppm)
{
    uint32_t n = (f_clk + ovs * baud / 2) / (ovs * baud);   /* 四捨五入 */
    if (n == 0) n = 1;
    double actual = (double)f_clk / ((double)ovs * n);
    *err_ppm = (int32_t)((actual - baud) / baud * 1e6 + (actual >= baud ? 0.5 : -0.5));
    return n;
}
/* uart_divider(16000000, 115200, 16, &e) は 9 を返し、e = -35494（−3.55 %） */
```

## 5. 電気的な形 — TTL レベル・RS-232・RS-485

ここまでは信号を 0 と 1 で考えてきた。実際の線の上では、0 と 1 は電圧で表される。表し方には、主に 3 つがある。

```fig
e02_levels
```

- **TTL レベル**: マイコンの端子の電圧（0 V と 3.3 V など）をそのまま使う。基板の上や、短い線（数 m まで）向きである。
- **RS-232**: 1 を負の電圧（−3〜−15 V）、0 を正の電圧（+3〜+15 V）で表す。論理が反転しているので、マイコンとの間には電圧を変換する IC を置く。1 対 1 の接続で、PC や産業機器のシリアルポートとして長く使われてきた。
- **RS-485**: 2 本の線の電圧の差で 0 と 1 を表す。このような送り方を**差動**という。外から入る雑音は 2 本の線にほぼ同じように乗るので、差をとると打ち消し合い、雑音に強い。受け手は、差がおよそ ±200 mV を超えれば 0 か 1 かを判断できる。どちらの線を A と呼ぶかは製品によって逆のことがあるので、データシートで確かめる。

RS-485 は、1 組の線に複数の機器をつなげる。

```fig
e02_rs485
```

線の両端には、線の特性インピーダンスに合わせた 120 Ω の**終端抵抗**を付け、信号が線の端で反射して戻ってくるのを抑える。低い速さなら 1 km 程度（100 kbps で約 1.2 km）、短い線なら 10 Mbps 程度まで使われる（代表値）。

1 組の線で両方向を受け持つので、同時に送れるのは 1 台だけである。このように、両方向に送れるが同時には一方向だけの方式を**半二重**、UART の TX と RX のように両方向に同時に送れる方式を**全二重**という。RS-485 では、送る機器だけが線を駆動し、ほかの機器は受信だけをする。そのため、マイコンと線の間に置く変換用の IC（**トランシーバ**。01 章のソフトウェアのドライバとは別物）には、送信を有効にする信号 **DE**（Driver Enable）がある。誰がいつ送るかは、上の層のプロトコルで決める（親機が子機を順に呼び、呼ばれた子機だけが答えるなど）。

DE は、送り始める前に有効にし、最後のビットが線から出終わってから無効にする。

```fig
e02_de
```

UART の回路には、「送信データレジスタが空いた」（次のバイトを書いてよい）という知らせと、「送信完了」（最後のビットまで線に出た）という知らせがある。前者で DE を無効にすると、最後のバイトのまだ出ていないビットが線に出ない。後者を待って DE を無効にする。この 2 つの知らせの使い分けは 04 章 7 節で扱う。信号線の電気的な性質（反射・絶縁・保護）は、[組み込み回路シリーズ 20 章](../circuit/20_シリアル物理層.md) が詳しい。

## 6. 流れの制御 — 受け手が追いつかないとき

受け手のマイコンは、届いたバイトをいったん受信用のメモリ（受信バッファ。04 章）にためてから処理する。送り手のほうが速くて、受信バッファがいっぱいになると、その後に届いたバイトは失われる。そこで、受け手が送り手に「待って」と伝える仕組みを使う。これを**フロー制御**という。

```fig
e02_rtscts
```

**ハードウェアフロー制御**では、データの線とは別に 2 本の線を使う。受け手は自分の **RTS**（Request To Send）の出力で「送ってよい」かどうかを示し、その線は送り手の **CTS**（Clear To Send）の入力につながる（TX と RX と同じく交差させる）。受け手は、受信バッファの量が決めたしきい値を超えたら RTS を無効にし、送り手は CTS が無効になったら送るのをやめる。多くの UART は、CTS を見て送信を止める動作を回路だけで行える。

RTS を無効にしても、送り手はすぐには止まらない。送っている途中のバイトと、送り手の UART の中で送信を待っているバイト（送信の FIFO）は届いてしまう。さらに受け手のソフトウェアが RTS を操作する場合は、しきい値を超えてから実際に RTS を無効にするまでの遅れの間にも、バイトは届き続ける。そこで、しきい値は次の分の空きを残して決める。

$$
\text{残す空き} \ge (\text{送り手の送信 FIFO の大きさ} + 1) + \text{1 秒あたりに届くバイトの数} \times \text{RTS を無効にするまでの遅れ}
$$

**例**: 921600 bps・8N1 なら 1 秒に 92160 バイト届くので、遅れが 1 ms あると 92 バイトが届く。送り手の FIFO が 16 バイトなら、残す空きは $`17 + 92 = 109`$ バイト以上になる。

**ソフトウェアフロー制御**では、線を増やさず、データの中に決まった文字を流して知らせる。XOFF（0x13）で「待って」、XON（0x11）で「再開」を表す。線は少なくて済むが、送るデータの中に 0x11 や 0x13 が含まれると区別がつかないので、バイナリのデータには使えない。また、文字が届いて処理されるまでの遅れがある。

フロー制御が要るのは、送り手が速く、まとめて大量に送ってくる場合である。Wi-Fi や BLE の無線モジュール（06 章）は 921600 bps 以上で、ネットワークから届いたデータを一度に送ってくることがあるので、ハードウェアフロー制御を使うことが多い。受信バッファの大きさの決め方は 04 章 5 節で扱う。

## 7. まとめ

| 項目 | 内容 |
|---|---|
| シリアル・非同期 | 1 本の線で 1 ビットずつ送る。クロックの線を持たず、1 ビットの長さを前もって決め、始まりの印で時刻を合わせる |
| UART の配線 | TX を相手の RX へ交差させ、GND を共通にする。両方向に同時に送れる（全二重） |
| ボーレート・ビット時間 | 1 秒あたりの信号の区切りの数（UART では bps と同じ）。ビット時間はその逆数（115200 bps で 8.68 µs） |
| UART のフレーム | スタートビット（0）・データ（LSB から）・パリティ（任意）・ストップビット（1）。8N1 は 10 ビット時間で 1 バイト |
| パリティ | 1 の数の偶奇をそろえる 1 ビット。1 ビットの誤りは分かるが、2 ビットの誤りは分からない |
| 受信の仕組み | 立ち下がりで始まりを知り、16 倍のオーバーサンプリングで各ビットの中央を読む。ストップビットが 0 ならフレーミングエラー |
| 時計のずれの限界 | k 番目のビットを読む時刻のずれは (k + 1/2)e。8N1 では両側の合計で約 4.6 % まで、片側では ±2 % 程度を目安にする |
| ボーレートの誤差 | 周波数の整数の分周で生じる（16 MHz で 115200 bps は −3.55 %）。8 倍のオーバーサンプリング・小数の分周・割り切れるクロックで減らす |
| 電気的な形 | TTL レベル（端子の電圧のまま）、RS-232（正負の電圧、反転）、RS-485（差動・バス・終端抵抗・半二重・DE の制御） |
| フロー制御 | 受け手が送り手を止める仕組み。RTS/CTS の線（ハードウェア）か、XON/XOFF の文字（ソフトウェア）。止まるまでに届く分の空きを残す |

UART は 1 バイトずつしか区切らない。次章では、バイトの列をメッセージの単位に区切る方法と、途中でバイトが壊れたことに気づく方法を見る。
