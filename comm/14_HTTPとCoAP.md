# 14. HTTP と CoAP — 要求と応答のプロトコル

> **この章で扱う問い.**
> 13 章の MQTT では、機器はブローカとの接続を保ち、決めたトピックへメッセージをパブリッシュした。アプリケーション層には、もう 1 つよく使われる形がある。相手に「この値を返してほしい」「この設定を置いてほしい」と頼み、答えを 1 つ受け取る、要求と応答の形である。この章では、その代表である Web の HTTP と、HTTP の考え方を小さな機器と UDP のために作り直した CoAP を扱う。
>
> この章では次の 3 つの問いに答える。
>
> 1. HTTP の要求と応答はどんなバイトの列なのか。受け手は、ヘッダの後に続く本文の終わりをどう知るのか。
> 2. 機器の測定値や設定を、HTTP の要求でどう読み書きするのか。サーバから機器へは、なぜすぐに知らせられないのか。
> 3. UDP の上で動く CoAP は、ヘッダをどう小さくし、失われたメッセージをどう送り直すのか。HTTP・MQTT・CoAP は、何を比べて選ぶのか。
>
> 答えの道具は、03 章の 2 つの区切り方（区切り文字と長さ）、05 章の再送と指数バックオフ、07 章のバイトの数え方である。

## 1. HTTP の要求と応答

温湿度センサの機器が、サーバに置かれた自分の設定（何秒ごとに測るか）を読み出す場面を考える。**HTTP**（Hypertext Transfer Protocol）は、一方が**要求**（リクエスト）を送り、もう一方が要求ごとに**応答**（レスポンス）を 1 つ返す、アプリケーション層のプロトコルである。要求を送る側をクライアント（13 章の MQTT のクライアントと同じく、コネクションを始める側）、応答を返す側をサーバといい、機器はふつうクライアントになる。組み込み機器でよく使われる版の HTTP/1.1 では、要求と応答は、TCP のコネクションの上を文字の列として流れる。サーバは 80 番のポートで待ち、機器は、サーバの名前を名前解決してアドレスを得て、コネクションを張ってから要求を送る。意味の決まりは RFC 9110 に、HTTP/1.1 のバイトの形は RFC 9112 にある。2 進の形で送る HTTP/2・HTTP/3 もあるが、この章では扱わない。

```fig
e14_msg
```

要求の 1 行目（要求行）は、何をしてほしいかを表す**メソッド**、サーバの中のどの情報を対象にするかを表すパス、版を、空白で区切って並べる。メソッドには、GET（読み出す）・POST（データを渡して処理させる）・PUT（置く、置き換える）・DELETE（消す）などがある（使い分けは 3 節）。

2 行目からは「名前: 値」の形の行が続く。この行の並びを、HTTP の**ヘッダ**という。01 章 2 節のヘッダを、文字の行で書いたものである。名前の大文字と小文字は区別しない。HTTP/1.1 の要求には、サーバの名前を書く Host の欄が必ず要る。1 台のサーバ（1 つの IP アドレス）がいくつもの名前のサービスを受け持つことがあり、DNS で調べたアドレスだけでは、どの名前に宛てた要求かが分からないからである。

ヘッダの終わりは、何も書かない行（CR LF の 2 バイトだけ）で表す。ヘッダの行は文字だけからなり、途中に空の行は現れないので、受け手は最初の空行までをヘッダとして読めばよい。空行は、03 章 2 節の区切り文字と同じ働きをしている。

空行の後には、**本文**（ボディ）が続く。設定の値や測定値など、運びたいデータそのものである。本文はどんなバイトでもよく、空行も 0x00 も現れうるので、区切り文字では終わりを示せない。終わりの示し方は 2 節で扱う。図の要求のように、本文の無いメッセージもある。

応答の 1 行目（ステータス行）は、版、**ステータスコード**（結果を表す 3 桁の数）、理由の文字（人が読むための説明。プログラムは使わない）を並べる。ステータスコードは、百の位で 5 つに分類される。機器は、まず百の位を見て、次に何をするかを決める。

```fig
e14_status
```

4xx と 5xx は、どちらも失敗だが、扱いが違う。4xx は要求の側に誤りがある（パスの誤りや、3 節で扱う、機器を確かめるための情報が無い・誤っているなど）ので、同じ要求を送り直しても同じ結果になる。要求を直すまで送り直さない（429 は「要求が多すぎる」という意味で、待ってから送り直す）。5xx はサーバの側の失敗なので、時間をおいて送り直せば成功することがある。ただし、多くの機器が一斉に送り直すと、立ち直りかけたサーバにまた負荷が集まるので、05 章 5 節の指数バックオフとジッタで間隔をあける。サーバが Retry-After の欄で待つ時間を指定してきたら、それに従う。

## 2. 本文の長さを知る — Content-Length とチャンク

TCP はバイトの列を運ぶだけで、送り手が 1 回に書いたまとまりの区切りも、メッセージの終わりも伝えない（07 章 4 節）。受け手が読み出す関数は、その時までに届いた分を返すだけである（11 章 2 節の部分受信）。したがってクライアントは、空行の後の本文がどこで終わるかを、自分で知らなければならない。終わりが分からなければ、本文を受け取り終えたかが分からず、同じコネクションで次の応答を読み始めることもできない。HTTP/1.1 では、本文の終わりを次の 3 つのどれかで示す（RFC 9112）。

```fig
e14_end3
```

- (a) **Content-Length** の欄に、本文のバイト数を 10 進で書く。03 章 4 節の長さフィールドを、文字で書いたものである。受け手は、空行の後をそのバイト数だけ読む。
- (b) `Transfer-Encoding: chunked` の欄を付け、本文を、長さを先に書いたかたまりに分けて送る。この形を**チャンク形式**という（この節の後半で扱う）。
- (c) どちらの欄も無い応答では、サーバがコネクションを閉じるまでが本文になる。途中でコネクションが切れても、受け手には、本文が終わったのか途中で切れたのかが分からない（図の下段）。閉じたコネクションは、次の要求にも使えない。

要求に (a) も (b) も無ければ、その要求に本文は無い。ヘッダだけを返させるメソッド HEAD への応答や、ステータスコードが 1xx・204・304 の応答にも本文は無い。受け手は、Content-Length の値が数字だけからなり、受け取れる大きさ以下であることを確かめる。(a) と (b) の両方がある、または値の違う Content-Length が 2 つあるメッセージは、誤りとして扱う。途中で中継する機器と受け手とで本文の終わりの解釈が分かれると、次の要求の始まりがずれ、攻撃に使われることがあるからである。

要求を組み立てる側は、Content-Length に本文の実際のバイト数を書き、行の終わりをすべて CR LF にする。ヘッダと本文は、1 つのバッファにまとめて送る。別々に送ると、10 章 6 節の Nagle アルゴリズムと遅延 ACK が重なって、応答が遅れることがある。

### 持続的接続 — コネクションを使い続ける

本文の終わりを正確に知る理由は、もう 1 つある。HTTP/1.1 では、応答を受け取った後もコネクションを閉じずに、次の要求に使い続けることを標準にしている。これを**持続的接続**という（keep-alive とも呼ぶが、13 章の MQTT のキープアライブとは別のものである）。要求に `Connection: close` の欄を付けると、その応答の後にコネクションを閉じることを表す。持続的接続では次の応答がすぐ後ろに続くので、(a) か (b) で本文の終わりが分かっていなければならない。使い続けると、どれだけ時間が減るかを数える。

**方針**: TLS（12 章）を使うコネクションで N 回の要求を送るとき、コネクションを毎回張る場合と使い続ける場合で、何往復（RTT）かかるかを数える。計算の時間とデータを送り出す時間は無視する。

**導出**: コネクションを張るのに、TCP の 3 ウェイハンドシェイクで 1 往復、TLS 1.3 のハンドシェイクでもう 1 往復（12 章 3 節）かかり、要求と応答で 1 往復かかる。毎回張ると、1 回の要求ごとに 3 往復で、合計 $`3N`$ 往復である。使い続けると、最初の 2 往復の後は 1 回 1 往復なので、合計 $`N + 2`$ 往復である ∎

```fig
e14_keep
```

RTT が 100 ms で N = 10 なら、毎回張ると 3.0 s、使い続けると 1.2 s である。TLS のハンドシェイクの計算（鍵交換と署名の確認。マイコンでは時間がかかる。12 章 3 節）も、使い続ければ 1 回で済む。ただしサーバは、要求の来ないコネクションを、しばらくすると閉じる（どれだけ待つかはサーバの設定による）。機器は、閉じられていることに、送ろうとして初めて気づくことがある。そのときは、コネクションを張り直して送り直す。応答を受け取る前に切れた要求は、サーバが処理したかどうかが分からないので、送り直してよいかはメソッドによる（3 節）。

### チャンク形式

Content-Length は、本文を送り始める前に全体の長さが分かっていなければ書けない。記録を読み出しながら送るサーバや、ほかから届いた分を中継しながら送るサーバは、全体の長さを知らない。全体を RAM にためてから送れば長さは分かるが、それだけの RAM が要る。閉じて終わりを示せば、持続的接続を使えない。チャンク形式は、本文を、送る時点で長さの分かったかたまり（チャンク）に分け、それぞれの前に長さを書く。

```fig
e14_chunk
```

- 長さの行: チャンクのバイト数を 16 進の文字で書き、CR LF で終える。長さの後に `;` で区切った拡張を書いてもよい（受け手は、意味を知らなければ読み飛ばす）。
- データ: 長さの分のバイト。中身は何でもよく、CR LF を含んでもよい。データの後に CR LF を置く。
- 長さ 0 のチャンクで本文が終わる。その後に、トレーラと呼ぶ「名前: 値」の行を置いてもよく、最後に空行を置く。

図の例では、30 バイトの本文が 45 バイトになった。増えるのは、チャンクごとに長さの桁数 + 4 バイト（CR LF が 2 つ）と、最後の 5 バイト（`0` と CR LF が 2 つ）である。1024 バイトずつのチャンクに分ければ、1 万バイトの本文で 75 バイト（0.75 %）しか増えない。

### 届いた分ずつ読む解析器

機器が受け取る本文は、RAM に収まるとは限らない（22 章のファームウェアの更新では、本文が RAM よりずっと大きい）。そこで、本文を全部ためてから読むのではなく、届いた分ずつ読み、データの部分はすぐに上へ渡す。06 章 3 節の AT コマンドの解析器と同じく、読みかけの状態を構造体に覚えておき、どこで分かれて届いても同じ結果になるように、状態機械として作る。

```fig
e14_ckfsm
```

```c
enum ck_state { CK_SIZE, CK_EXT, CK_LF, CK_DATA, CK_DATA_CR, CK_TRAILER, CK_TRAILER_LINE, CK_DONE, CK_ERR };
struct chunk_rx {
    enum ck_state st, next;   /* st は CK_SIZE（0）で始める。next は LF を読んだ後に移る状態 */
    uint32_t left;            /* 長さの行で読んだ値。データの間は読み残しのバイト数 */
    uint8_t  seen;            /* 長さの行で 16 進の数字を 1 つ以上読んだか */
    void (*on_data)(void *ctx, const uint8_t *p, size_t n);
    void  *ctx;
};
/* s[0..n-1] を読み、使ったバイトの数を返す。本文の終わり（CK_DONE）より後ろのバイトは使わない */
size_t chunk_feed(struct chunk_rx *r, const uint8_t *s, size_t n)
{
    size_t i = 0;
    while (i < n && r->st != CK_DONE && r->st != CK_ERR) {
        if (r->st == CK_DATA) {               /* データ: 長さの分は中身を見ずに渡す */
            size_t k = (n - i < r->left) ? n - i : r->left;
            r->on_data(r->ctx, s + i, k);
            r->left -= (uint32_t)k;
            i += k;
            if (r->left == 0) r->st = CK_DATA_CR;
            continue;
        }
        uint8_t c = s[i++];
        int h = hexval(c);                    /* 16 進の数字なら 0〜15、ほかは -1 */
        switch (r->st) {
        case CK_SIZE:                         /* 16 進の長さ（28 ビットまで） */
            if (h >= 0 && r->left <= 0x0FFFFFFu) { r->left = r->left * 16 + (uint32_t)h; r->seen = 1; }
            else if (!r->seen)                r->st = CK_ERR;
            else if (c == '\r')               { r->next = r->left ? CK_DATA : CK_TRAILER; r->st = CK_LF; }
            else if (c == ';' || c == ' ' || c == '\t') r->st = CK_EXT;
            else                              r->st = CK_ERR;
            break;
        case CK_EXT:          if (c == '\r') { r->next = r->left ? CK_DATA : CK_TRAILER; r->st = CK_LF; } break;
        case CK_LF:           r->st = (c == '\n') ? r->next : CK_ERR; r->seen = 0; break;   /* CR の次は LF */
        case CK_DATA_CR:      if (c == '\r') { r->next = CK_SIZE; r->st = CK_LF; } else r->st = CK_ERR; break;
        case CK_TRAILER:      if (c == '\r') { r->next = CK_DONE; r->st = CK_LF; } else r->st = CK_TRAILER_LINE; break;
        case CK_TRAILER_LINE: if (c == '\r') { r->next = CK_TRAILER; r->st = CK_LF; } break;
        default:              break;
        }
    }
    return i;
}
```

`chunk_feed` は、取り出したデータを `on_data` で知らせる。渡されたバッファの中を指したまま知らせる（写さない）ので、解析器の中にデータ用の配列は要らない。長さは 16 進で 28 ビットまでとし、それを超える長さは誤りにする（大きな値で数があふれて、短い長さに化けるのを防ぐ）。CR の次が LF でないなど、形が規格と違えば `CK_ERR` にして、それ以上読まない。持続的接続では、本文の終わりのすぐ後ろに次の応答が続く。`chunk_feed` は本文の終わり（`CK_DONE`）までに使ったバイトの数を返すので、渡したバイトの残りは、次の応答の解析に回す。`hexval` は 16 進の 1 文字を値にする小さな関数である（省略）。

このコードは、PC の gcc で AddressSanitizer と UndefinedBehaviorSanitizer を付けてテストした。図の例を含む 400 通りの正しい本文（データに CR LF や `0` を含むもの、拡張とトレーラのあるもの、先頭に 0 の付いた長さ、大文字の 16 進）を、まとめて 1 回で渡した場合、1 バイトずつ渡した場合、2 つと 3 つに分けるすべての位置で分けた場合（40 通りの本文で約 10 万通り）、乱数で選んだ 10 万通りの分け方で渡した場合のすべてで、取り出した本文・使ったバイトの数・最後の状態が同じになり、本文が元と一致した。正しい形の 1〜3 バイトを書き換えた入力と乱数の入力（合わせて 3 万個）でも、配列の外を読み書きせず、分け方によらず同じ結果になった。

下の図で、本文とチャンクの大きさ、TCP から受け取る 1 回分の大きさ、壊し方を選ぶと、チャンク形式のバイトの列と、解析器が 1 回分ずつ読んだときの状態、取り出した本文が表示される。

## 3. REST で機器を表す

1 節では、メソッドとパスを例として使った。どのパスに何を置き、どのメソッドで何をするかは、サービスごとに決める。多くのクラウドのサービスは、REST と呼ばれる考え方で決めている。

**REST**（Representational State Transfer）では、サーバが扱うもの（ある機器の最新の測定値、機器の設定、測定値の記録の一覧など）の 1 つ 1 つを**リソース**とし、それぞれに場所を表す文字列を付ける。この文字列を **URL**（Uniform Resource Locator）という。リソースへの操作はメソッドで表し、リソースの中身は本文で運ぶ。どの要求も、それだけで意味が通るように書き、サーバが前の要求を覚えていることを前提にしない。

```fig
e14_url
```

URL は、スキーム（使うプロトコル。http または https）、ホスト名（サーバの名前）、ポート（省略すると http は 80、https は 443）、パス（どのリソースか）、クエリ（`?` の後ろ。読み出す範囲などの条件）からなる（RFC 3986）。要求行にはパスとクエリを書き、ホスト名は Host の欄に書く。

温湿度センサの機器 1 番のリソースを決めた例を示す。本文には、13 章 6 節の JSON を使う。

```fig
e14_rest
```

同じ「設定」というリソースを GET で読み、PUT で置き換える。測定値の記録の一覧には POST で 1 つ足し、サーバは足した記録の URL を Location の欄に入れて、201 で答える。リソースは名詞で表し、操作はメソッドに任せるので、URL の数が増えすぎず、初めて使うサービスでも使い方の見当が付く。

### 送り直してよい要求、よくない要求

応答が届く前にコネクションが切れると、機器には、サーバが要求を処理したかどうかが分からない。05 章 4 節で ACK が失われた場合と同じである。このとき、要求を送り直してよいかはメソッドによる。

```fig
e14_idem
```

GET・PUT・DELETE は、同じ要求を 2 回処理しても、サーバの状態は 1 回処理したときと同じになる。このように、何回行っても結果が 1 回のときと同じになる性質を**冪等**という（15 章 4 節で詳しく扱う）。冪等な要求は、結果が分からなければそのまま送り直してよい。POST は冪等でない。測定値を足す POST を送り直すと、同じ測定値が 2 つ記録されうる。そこで、機器が測定値ごとに番号を付けて本文に入れ、サーバが同じ番号の記録を捨てるようにする（15 章 4 節）。

### HTTPS と、機器を確かめる方法

HTTP のバイトの列は、そのままでは途中で読まれ、書き換えられうる。HTTP を TLS（12 章）の上で送るものを **HTTPS** という。URL のスキームは https、ポートは 443 である。要求と応答のバイトの列は HTTP と同じで、それを TLS のレコードに入れて送る。機器は、サーバの証明書を確かめる（12 章 4 節）。サーバが機器を確かめるには、TLS のクライアント証明書（12 章 5 節）を使うか、機器ごとに発行した合言葉にあたる文字列を Authorization の欄に入れて送る（こうした資格情報の扱いは 15 章 5 節）。

### サーバから機器へは、すぐに知らせられない

HTTP では、要求を送るのはいつもクライアントで、サーバは要求が来るまで何も送れない。機器をサーバにすれば、サーバの側から要求を送れそうに見えるが、NAT の内側の機器には、外から接続を始められない（08 章 5 節）。そこで、サーバから機器へ命令を届けるには、次のどれかを使う。

```fig
e14_push
```

- ポーリング: 機器が決まった間隔 $`T`$ で「命令はあるか」と問い合わせる（`GET /dev/1/cmd`）。04 章 1 節のポーリングと同じく、命令が来ているかどうかに関係なく確かめに行く。
- **WebSocket**（RFC 6455）: Upgrade の欄を付けた GET で始め、サーバが 101 で応じると、その後は同じ TCP のコネクションを、どちらの側からでも小さなメッセージを送れる通り道として使う。サーバは、命令ができたときにすぐ送れる。
- MQTT（13 章）を併用する。命令はブローカから届く。

**方針**: 命令がサーバに届く時刻は、問い合わせの間隔のどこにも同じ確からしさで来る（一様分布）として、届いてから次の問い合わせまでの待ち（遅れ）と、1 日の問い合わせの回数を求める。

**導出**: 問い合わせの時刻を $`0, T, 2T, \ldots`$ とし、命令が時刻 $`u`$（$`0 \le u < T`$）に届いたとする。命令は次の問い合わせ（時刻 $`T`$）で機器に渡るので、待ちは $`T - u`$ である。$`u`$ が $`0`$ から $`T`$ に一様に分布するので、待ちも $`0`$ から $`T`$ に一様に分布し、平均は $`T/2`$、最大は $`T`$ である。1 日の問い合わせは $`86400 / T`$ 回である ∎

$`T`$ = 60 s なら、1 日に 1440 回問い合わせて、平均の遅れは 30 s である。遅れを半分にすると、問い合わせの回数（電力とバイト数）は 2 倍になる。WebSocket と MQTT は、機器の側から張ったコネクションを保ち続けるので、命令はすぐに届く。その代わり、NAT の変換表の行が消えないように、保持時間より短い間隔で何かを送り続ける（08 章 5 節）。機器が HTTP のサーバになるのは、同じネットワークのスマートフォンから Web のページで設定を受け取る場合（09 章 6 節）のように、外のネットワークを通らない使い方が主である。

## 4. CoAP — UDP の上の小さな要求と応答

1〜3 節の HTTP は、文字のヘッダ（数十〜数百バイト）と、TCP のコネクションを前提にしている。数十 KB の RAM で動く機器や、リンク層の 1 つのフレームが 127 バイトしかない IEEE 802.15.4 のリンク（07 章 6 節）には、これは重い。**CoAP**（Constrained Application Protocol、RFC 7252）は、HTTP の考え方（メソッド・URL・ステータスコード・本文の形の指定）をそのまま使い、ヘッダを 2 進の 4 バイトにして、UDP の上で送るプロトコルである。サーバは UDP の 5683 番のポートで待ち、URL のスキームは coap である。UDP は失われたものを送り直さないので、CoAP は確認応答と再送（05 章 4 節の ARQ）を自分で行う。

CoAP では、機器がサーバになり、同じネットワークのゲートウェイなどが要求を送る使い方も多い（NAT を通らないので、外から接続を始められない問題は起きない）。機器がクライアントになって、インターネットの先の CoAP のサーバへ送る使い方もある。以下では、ゲートウェイが機器に温度を問い合わせる `GET /temp` を例にする。

```fig
e14_hdr
```

- 版（2 ビット）: 1。
- 型（2 ビット）: このメッセージに確認応答が要るかどうかを表す。**CON**（Confirmable、0）は ACK を求める。**NON**（Non-confirmable、1）は求めない（失われても再送しない）。**ACK**（Acknowledgement、2）は、CON を受け取ったことを知らせる（05 章 4 節の確認応答）。**RST**（Reset、3）は、受け取ったが処理できない（覚えのない応答が届いたなど）ことを知らせる。
- トークンの長さ（4 ビット）: 後で説明するトークンの、バイト数（0〜8）。
- コード（8 ビット）: 上位 3 ビットの分類と下位 5 ビットの詳細を、c.dd の形で書く。要求では 0.01 GET・0.02 POST・0.03 PUT・0.04 DELETE。応答の分類は HTTP のステータスコードの百の位と同じで、2.05 Content（HTTP の 200 にあたる）、2.04 Changed、4.04 Not Found、5.03 Service Unavailable などがある。
- **メッセージ ID**（16 ビット、ネットワークバイトオーダ）: 送り手がメッセージごとに選ぶ番号。ACK と RST には、答える相手のメッセージのメッセージ ID を書く。重複を見分けるのにも使う（5 節）。
- **トークン**（0〜8 バイト）: クライアントが要求ごとに選び、サーバは応答に同じトークンを付ける。後で見るように、応答が要求への ACK とは別のメッセージで届くことがあるので、メッセージ ID とは別に、要求と応答を結び付ける値が要る。
- **オプション**: HTTP のヘッダの欄にあたる。種類を番号で表す（下の表）。
- 0xFF の後がペイロード（HTTP の本文にあたる）。ペイロードが無ければ 0xFF も付けない。

コードが 0.00 のメッセージは、トークンもオプションも持たない 4 バイトだけの空のメッセージで、ACK や RST に使う。主なオプションを表に示す。

| 番号 | 名前 | 中身 |
|---|---|---|
| 3 | Uri-Host | サーバの名前 |
| 7 | Uri-Port | ポート番号 |
| 11 | Uri-Path | パスの 1 階層分（`dev/1/temp` なら 3 つ並べる） |
| 12 | Content-Format | ペイロードの形の番号（0 = 文字、50 = JSON など） |
| 15 | Uri-Query | クエリの 1 項目 |
| 17 | Accept | 応答で受け取りたい形の番号 |

オプションは、番号の小さい順に並べ、1 つ前のオプションとの番号の差を書く。差と値の長さは、どちらも 4 ビットに収まれば 1 バイトの頭に入り、収まらなければ拡張のバイトを足す。番号を種類として長さと値を並べる点は、03 章 7 節の TLV と同じである。

```fig
e14_opt
```

番号そのものは 0〜65535 まであるが、並べたオプションの番号の差は多くの場合 12 以下なので、ほとんどのオプションは頭の 1 バイトで済む。同じ番号を繰り返すときは、差が 0 になる。`GET /temp` と、その応答のバイトの列を示す。

```fig
e14_get
```

要求は 10 バイト、応答は 11 バイトである。同じことを HTTP で書くと、要求は `GET /temp HTTP/1.1` と Host の欄と空行で 41 バイト、応答は Content-Length の欄だけを付けても 42 バイトになり、その前に TCP のコネクションを張る必要もある。メッセージを組み立てるコードを示す。

```c
struct coap_opt { uint16_t num; const uint8_t *val; uint16_t len; };   /* オプションの番号・値・長さ */
/* 差分または長さ v を、4 ビットの欄の値 *nib と拡張のバイト ext にする。拡張のバイト数を返す */
static size_t coap_ext(uint32_t v, uint8_t *nib, uint8_t ext[2])
{
    if (v < 13)  { *nib = (uint8_t)v; return 0; }
    if (v < 269) { *nib = 13; ext[0] = (uint8_t)(v - 13); return 1; }
    v -= 269; *nib = 14; ext[0] = (uint8_t)(v >> 8); ext[1] = (uint8_t)v; return 2;
}
/* out（cap バイト）にメッセージを組み立て、長さを返す（収まらない・形が誤りなら 0）。
   opt は番号の小さい順に nopt 個。ペイロードが無いときは plen = 0 */
size_t coap_build(uint8_t *out, size_t cap, uint8_t type, uint8_t code, uint16_t mid,
                  const uint8_t *tok, uint8_t tkl, const struct coap_opt *opt, size_t nopt,
                  const uint8_t *pl, size_t plen)
{
    size_t n = 0;
    uint16_t last = 0;                                     /* 1 つ前のオプションの番号 */
    if (type > 3 || tkl > 8 || cap < 4u + tkl) return 0;
    out[n++] = (uint8_t)(0x40 | type << 4 | tkl);          /* 版 1・型・トークンの長さ */
    out[n++] = code;
    out[n++] = (uint8_t)(mid >> 8); out[n++] = (uint8_t)mid;   /* メッセージ ID（ネットワークバイトオーダ） */
    if (tkl) memcpy(out + n, tok, tkl);                    /* 長さ 0 なら tok は NULL でもよい */
    n += tkl;
    for (size_t i = 0; i < nopt; i++) {
        uint8_t dn, ln, de[2], le[2];
        if (opt[i].num < last) return 0;                   /* 番号の順に並んでいない */
        size_t a = coap_ext((uint32_t)(opt[i].num - last), &dn, de);
        size_t b = coap_ext(opt[i].len, &ln, le);
        if (cap - n < 1 + a + b + opt[i].len) return 0;
        out[n++] = (uint8_t)(dn << 4 | ln);                /* 差分 4 ビット・長さ 4 ビット */
        memcpy(out + n, de, a); n += a;
        memcpy(out + n, le, b); n += b;
        if (opt[i].len) memcpy(out + n, opt[i].val, opt[i].len);
        n += opt[i].len; last = opt[i].num;
    }
    if (plen > 0) {
        if (cap - n < 1 + plen) return 0;
        out[n++] = 0xFF;                                   /* ここからペイロード */
        memcpy(out + n, pl, plen); n += plen;
    }
    return n;
}
```

`GET /temp` なら、オプションを `{ 11, "temp", 4 }` の 1 つにし、型 0（CON）・コード 0x01・メッセージ ID 0x7D34・トークン 0x71 で呼ぶと、図の 10 バイトができる。このコードは、図の 2 つの例と、6 節で使う POST のバイトの列を作ることを確かめた。さらに、乱数で作った 2 万個のメッセージ（オプションの差と長さが 13 以上・269 以上になるものを含む）で、規格の形を別に書いた Python の実装が作るバイトの列と一致し、それを解析すると元の値に戻ること、出力先がちょうどの大きさなら同じ結果、1 バイト足りなければ 0 を返して外に書かないことを確かめた（AddressSanitizer と UndefinedBehaviorSanitizer を付けて実行）。

### ピギーバック応答と、別に送る応答

CON の要求を受け取ったサーバは、ACK を返す。すぐに答えられるときは、応答をその ACK に載せて返す。これを**ピギーバック応答**という（piggyback は「背負う」の意味）。図の左である。測定に時間がかかるなどで、すぐに答えられないときは、まず空の ACK を返してクライアントの再送を止め、応答ができたら、新しいメッセージ ID の CON で応答を送る。クライアントはそれに ACK を返す（図の右）。

```fig
e14_piggy
```

別に送る応答は、要求とメッセージ ID が違うので、クライアントはトークンで、どの要求への応答かを知る。NON の要求には、ふつう NON で応答する。

## 5. CoAP の再送 — 指数バックオフの定数

CON を送った側は、ACK が来るまでメッセージの写しを持ち続け、決まった時間がたつと再送する。いつ、何回再送するかを、RFC 7252 は次の定数で決めている（表の値は既定値である。用途に合わせて変えることもできるが、そのときは後で求める時間も変わる）。

| 定数 | 既定値 | 意味 |
|---|---|---|
| ACK_TIMEOUT | 2 s | 最初の待ち時間の基準 |
| ACK_RANDOM_FACTOR | 1.5 | 最初の待ち時間を、ACK_TIMEOUT の何倍までの乱数で選ぶか |
| MAX_RETRANSMIT | 4 | 再送の回数の上限（最初の送信と合わせて 5 回まで送る） |
| NSTART | 1 | 1 つのサーバに対して、同時に応答を待ってよい要求の数 |

送り手は、新しい CON を送るとき、最初の待ち時間 $`T_0`$ を、ACK_TIMEOUT から ACK_TIMEOUT × ACK_RANDOM_FACTOR まで（既定値で 2〜3 s）の一様な乱数で選ぶ。待ち時間が過ぎても ACK が来なければ、再送の回数が MAX_RETRANSMIT より少ない間は、同じメッセージ（同じメッセージ ID）を再送して、待ち時間を 2 倍にする。MAX_RETRANSMIT 回目の再送の後の待ち時間も過ぎたら、諦めてアプリケーションに失敗を知らせる。RST が届いたときも、そこでやめる。05 章 5 節の指数バックオフ（2 倍ずつ）と、最初の値を乱数で選ぶジッタ（同じ時刻に失敗した機器どうしの再送がそろわないようにする）の組み合わせである。待ち時間には上限を置かず、回数で打ち切る。最後の再送と、諦める時刻を求める。

**方針**: k 回目の再送の時刻を、最初の待ち時間 $`T_0`$ の何倍かで表し、$`T_0`$ が最も長い 3 s のときの値を求める。

**導出**: 最初に送った時刻を 0 とする。待ち時間は $`T_0, 2T_0, 4T_0, \ldots`$ と 2 倍ずつ延びるので、k 回目の再送の時刻は k 個の待ち時間の和で、

$$
t_k = T_0 \left(1 + 2 + \cdots + 2^{k-1}\right) = (2^k - 1)\, T_0
$$

である（05 章 5 節と同じ等比数列の和）。最後の再送は k = 4 で $`t_4 = 15 T_0`$、その後の待ち時間 $`2^4 T_0 = 16 T_0`$ が過ぎると諦めるので、諦める時刻は $`15 T_0 + 16 T_0 = 31 T_0`$ である。$`T_0`$ は最大で ACK_TIMEOUT × ACK_RANDOM_FACTOR = 2 × 1.5 = 3 s なので、

$$
t_4 \le 2 \times (2^4 - 1) \times 1.5 = 45\ \text{s}, \qquad 31\, T_0 \le 2 \times (2^5 - 1) \times 1.5 = 93\ \text{s}
$$

となる ∎

RFC 7252 は、この 2 つを MAX_TRANSMIT_SPAN（45 s）と MAX_TRANSMIT_WAIT（93 s）と名付けている。$`T_0`$ が最も短い 2 s のときは、それぞれ 30 s と 62 s である。

```fig
e14_backoff
```

NSTART = 1 なので、クライアントは 1 つのサーバに対して、応答を待っている要求を 1 つしか持てない。サーバが答えなければ、次の要求は、前の要求を諦めるまで（最大 93 s）待たされる。

### 重複を見分ける — メッセージ ID

ACK が失われると、受け手には同じ CON が 2 回以上届く（05 章 4 節の重複）。CoAP の受け手は、受け取った CON の送り手（IP アドレスとポート番号）とメッセージ ID の組を覚えておき、同じ組がもう一度届いたら、要求をもう一度処理せずに、前と同じ ACK（ピギーバック応答なら、同じ応答）を返す。測定値を足す POST が 2 回届いても、記録は 1 つで済む。

```fig
e14_dedup
```

05 章 4 節では、1 ビットの番号で重複を見分けられた。それは、通信路がメッセージの順番を入れ替えないという前提があったからである。UDP のデータグラムは順番が入れ替わり、ずっと遅れて届くこともあるので、CoAP は 16 ビットのメッセージ ID を、しばらく使い回さないことで見分ける。では、受け手はメッセージ ID をどれだけの間覚えておけばよいか。

**方針**: ある CON の写しや、それへの ACK が、ネットワークの中に残りうる最も遅い時刻を求める。RFC 7252 は、データグラムがネットワークを渡るのにかかる時間の上限を MAX_LATENCY = 100 s、受け手が CON を受け取ってから ACK を返すまでの時間の上限を PROCESSING_DELAY = ACK_TIMEOUT = 2 s と置いている。

**導出**: 最後の写しは、最初に送ってから 45 s（MAX_TRANSMIT_SPAN）までに送られ、100 s 以内に届くので、145 s までに届く。受け手は 2 s 以内に ACK を返すので、ACK を送るのは 147 s までで、それが 100 s 以内に届く。したがって、最初に送ってから $`45 + 100 + 2 + 100 = 247`$ s を過ぎると、この交換に関わるメッセージは、ネットワークの中に残っていない ∎

RFC 7252 は、この時間を EXCHANGE_LIFETIME（247 s）と名付けている。受け手は、受け取った CON のメッセージ ID を 247 s 覚えていればよい。送り手は、同じ相手に、同じメッセージ ID を 247 s の間は使わない。メッセージ ID は 16 ビットなので、1 つの相手に送れるメッセージは、247 s に 65536 個まで、平均すると毎秒 $`65536 / 247 \approx 265`$ 個までである。小さな機器が送る量としては、十分に大きい。

### 届く確率

**方針**: 往きと帰りの喪失から、交換が失敗する確率を求める。CON と ACK の 1 回ごとの送信が、それぞれ独立に確率 $`p`$ で失われるとし、5 回の送信がすべて ACK まで届かない確率を求める。

**導出**: 1 回の送信で CON が届く確率は $`1 - p`$、それへの ACK が届く確率も $`1 - p`$ なので、ACK まで届く確率は $`s = (1 - p)^2`$ である。最初の送信と 4 回の再送の 5 回が互いに独立なので、5 回とも届かない確率は $`(1 - s)^5`$ である ∎

$`p`$ = 10 % なら $`s`$ = 0.81 で、失敗する確率は $`0.19^5 \approx 2.5 \times 10^{-4}`$ である。$`p`$ = 30 % なら $`s`$ = 0.49 で、$`0.51^5 \approx 3.5`$ % になる。

### Observe とブロック転送

CoAP には、RFC 7252 の後に加わった仕組みがある。主なものを 2 つ挙げる。

```fig
e14_obsblk
```

**Observe**（RFC 7641）は、サーバから知らせる仕組みである。クライアントが GET に Observe のオプション（番号 6、値 0）を付けて送ると、サーバはクライアントを登録し、リソースが変わるたびに、同じトークンを付けた応答（通知）を送り続ける。通知には増えていく番号（Observe の値）が入っていて、遅れて届いた古い通知を見分けられる。13 章の MQTT のサブスクライブに近い使い方である。ただし、通知は UDP で届くので、NAT を通る場合は、変換表の行が消えないように、クライアントが保持時間より短い間隔で送り続ける必要がある（UDP の保持時間は短いことが多い。08 章 5 節）。

**ブロック転送**（RFC 7959）は、大きなペイロードを分けて運ぶ仕組みである。MTU を超えるデータグラムはフラグメンテーションを起こす（07 章 6 節）。ブロック転送では、ペイロードを 16〜1024 バイト（2 のべき乗）のブロックに分け、1 つのブロックを 1 組の要求と応答で運ぶ。応答を分けるときは Block2（番号 23）、要求を分けるときは Block1（番号 27）のオプションに、ブロックの番号・続きがあるか・ブロックの大きさを入れる。ファームウェアの更新（22 章）のような大きなデータに使う。

CoAP の通信を暗号化するときは、TLS を UDP の上で使えるようにした **DTLS**（Datagram TLS）を使う。URL のスキームは coaps、ポートは 5684 である。DTLS は、ハンドシェイクのメッセージが失われたり順番が入れ替わったりしても進められるように、自分で番号を付けて再送する。使い方の注意は [IoT セキュリティシリーズ 16 章 3 節](../iotsec/16_通信セキュリティ.md#リソース制約への対応) にある。

## 6. 3 つをどう選ぶか

13 章の MQTT と、この章の HTTP・CoAP を比べる。

| | HTTP | MQTT | CoAP |
|---|---|---|---|
| 下の層 | TCP（HTTPS は TLS の上） | TCP（多くは TLS の上） | UDP（coaps は DTLS の上） |
| 形 | 要求と応答 | ブローカを介したパブリッシュとサブスクライブ | 要求と応答（Observe で通知も） |
| ヘッダ | 文字。最小で数十バイト、実際には数百バイトのことも多い | 2 バイト + トピック名など | 4 バイト + トークン + オプション |
| 届くことの確かさ | TCP が再送する | TCP の再送と QoS | CON の再送（NON は再送しない） |
| サーバから機器へ | ポーリングか WebSocket | ブローカから届く（コネクションを保つ） | Observe（変換表の行を保つ） |
| NAT の内側の機器 | 機器から要求を送るだけなら問題ない | 機器から張るので問題ない | 機器から送るなら問題ない。UDP の行の保持時間は短いことが多い |
| 道具 | 最も多い（クラウドの API、ブラウザ、試験の道具） | 多い（ブローカ、クラウドの IoT のサービス） | 少ない（専用の道具や、HTTP との間を取り次ぐゲートウェイが要ることが多い） |

1 回の報告で線の上に出るバイトを、07 章 5 節と同じ数え方（IPv4・Ethernet。プリアンブルと、Ethernet フレームの間の空きを含む）で比べる。データは 07 章と同じ 20 バイトの `{"t":23.5,"h":41.25}`、名前はどれも `dev/1/temp` とする。HTTP の要求は、`POST /dev/1/temp HTTP/1.1`・Host・Content-Length の 3 行と空行の 68 バイトに、データの 20 バイトを足した 88 バイトである。MQTT の PUBLISH（QoS 0）は 34 バイト（07 章 5 節）、CoAP の POST（トークン 1 バイト、Uri-Path 3 つ、Content-Format）は 39 バイトである。

```fig
e14_bytes
```

要求のセグメント・データグラムだけなら、HTTP 166、MQTT 112、CoAP 105 バイトで、HTTP の文字のヘッダが目立つ。届いたことを確かめるまでのやり取りで数えると、応答や確認応答の小さなセグメント・データグラム（詰め物をして 1 つ 84 バイト分）が加わり、HTTP 392、MQTT（QoS 1）282、CoAP（CON）189 バイトになる。HTTP は応答にも文字のヘッダが付くので、差は 2 倍ほどに開いたままである。

1 日に送るバイトでは、別のものが効いてくる。HTTP を報告ごとに張って閉じると、TCP のコネクションを張る 3 つと閉じる 4 つ（10 章）の小さなセグメントで 7 × 84 = 588 バイトが毎回加わり、HTTPS なら TLS のハンドシェイク（楕円曲線の証明書でも 1.6 KB ほど。12 章 3 節）も毎回加わる。一方、MQTT や WebSocket は、データの無い間も、コネクションを保つためにキープアライブを送る。10 分ごとに報告し、下りの命令をすぐ受け取るために 60 s ごとにキープアライブを送る機器では、報告と報告の間の 600 s にキープアライブが 9 回入る。1 日の報告は 86400 ÷ 600 = 144 回なので、キープアライブは 144 × 9 = 1296 回で、1 回の往復（MQTT の 2 バイトのパケットを運ぶセグメント 2 つと、TCP の ACK の 3 つ）が 252 バイトなので、1296 × 252 = 326,592 バイトになる。QoS 1 の報告そのものは 144 × 282 = 40,608 バイトなので、その 8 倍である。保つ間隔は、NAT の保持時間で決まる（08 章 5 節）。

したがって、選び方の目安は次のようになる。

- 機器から時々送るだけで、下りの命令を急がない: HTTP。クラウドのサービスや道具をそのまま使える。コネクションを張る費用は報告ごとにかかるので、報告の間隔が長いほど 1 日の合計は小さくなる（キープアライブの費用は、報告の間隔によらず時間に比例してかかる）。
- 下りの命令をすぐに届けたい、多くの機器を 1 つの仕組みでつなぎたい: MQTT。コネクションを保つ費用を払い、ブローカに配送を任せる。
- RAM が小さく TCP を載せにくい、フレームの小さなリンク（IEEE 802.15.4 など）を通る、同じネットワークの中の機器どうしで問い合わせる: CoAP。インターネットの先のサービスとの間は、ゲートウェイで HTTP や MQTT に取り次ぐことが多い。

下の図で、データの大きさ・名前・報告の間隔・下りの命令の待ち方を変えると、1 回の報告のバイト数と、1 日の合計、下りの命令が届くまでの最大の遅れが、3 つのプロトコルについて表示される。

## 7. まとめ

| 項目 | 内容 |
|---|---|
| HTTP の要求と応答 | 要求行（メソッド・パス・版）またはステータス行、「名前: 値」のヘッダ、空行、本文。ヘッダの終わりは空行（区切り文字）で分かる |
| ステータスコード | 百の位で分類する。4xx は要求を直すまで送り直さない。5xx は指数バックオフとジッタで送り直す |
| 本文の終わり | Content-Length（10 進の長さ）、チャンク形式（16 進の長さ + データ、長さ 0 で終わり）、閉じるまで（途中で切れたかが分からない） |
| 持続的接続 | コネクションを使い続ける。N 回の要求が 3N 往復から N + 2 往復になる（TLS を使う場合）。本文の終わりが正確に分かることが前提 |
| 届いた分ずつ読む | 読みかけの状態を構造体に覚える状態機械にすれば、どこで分かれて届いても同じ結果になり、本文の全体をためる RAM が要らない |
| REST | リソースに URL を付け、GET・PUT・POST・DELETE で操作する。GET・PUT・DELETE は冪等で送り直せる。POST は番号で重複を見分ける |
| サーバから機器へ | HTTP だけではポーリング（遅れは平均 T/2、最大 T）。すぐに届けるには WebSocket か MQTT でコネクションを保つ |
| CoAP | UDP の上の 4 バイトのヘッダ（版・型・トークンの長さ・コード・メッセージ ID）、トークン、差分で番号を書くオプション、0xFF とペイロード |
| CON・NON・ACK・RST | 確認応答を求める・求めない・受け取った・処理できない。すぐ答えられればピギーバック応答、できなければ空の ACK の後に別に送る |
| CoAP の再送 | 最初の待ち時間は 2〜3 s の乱数、再送ごとに 2 倍、4 回まで。最後の再送は 45 s 以内、諦めるのは 93 s 以内。メッセージ ID は 247 s 覚えて重複を見分ける |
| 3 つの選び方 | 時々送るだけなら HTTP、下りをすぐ届けるなら MQTT、小さな機器・小さなフレーム・同じネットワークの中なら CoAP。1 日のバイトは、コネクションを張る・保つ費用で決まることが多い |

次章では、ここまでの層をすべて使い、時刻を合わせ、切れたら再接続し、つながらない間のデータをためておくなど、クラウドとつながり続ける機器の作り方をまとめる。
