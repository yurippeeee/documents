> **この章のゴール.**

## ケース A: 更新に失敗する機器

**状況.** STM32 + MCUboot の機器。OTA 更新後、旧バージョンに戻ってしまう。

**手順.**

1. SWD でフラッシュ全体をダンプ（[04 章](04_ダンプを手に入れる.md)）。2 回読んで一致を確認。SHA-256 を記録（[01 章](01_バイナリ解析とは何か.md#手順-1-証拠を固定する)）
2. `binwalk` とベクタテーブル（[07 章](07_CortexMのイメージ.md#ベクタテーブル-先頭に必ずある表)）でメモリマップを作る。ブートローダ・slot0・slot1・設定領域に分ける
3. slot0 と slot1 の **MCUboot ヘッダ**（[08 章](08_ブートローダとイメージ形式.md)）を読む。バージョンは slot1 のほうが新しい（更新は届いている）
4. 各スロットの**末尾トレーラ**（[08 章](08_ブートローダとイメージ形式.md#tlv-トレーラ-ハッシュと署名)）を読む。slot1 の **image ok がセットされていない**
5. slot1 の **TLV の SHA-256**（[08 章](08_ブートローダとイメージ形式.md#tlv-トレーラ-ハッシュと署名)）を、アプリ本体から計算し直して照合 → 一致（イメージは壊れていない）

**判断.** イメージは正しく、署名も通っている。だが「テスト起動後にアプリが自身を確認（image ok を書く）する処理」が呼ばれていない。
アプリ側の「自己確認」ロジックが動いていないため、ブートローダが「確認されなかった」と判断してロールバックしている。アプリのコードを [16 章](16_逆アセンブルの基礎.md#設定-2-ロードアドレス-base-address)で確認する方向へ。

## ケース B: 設定が化ける

**状況.** EFR32（Zigbee）の機器。ときどき送信出力の設定が異常値になる。

**手順.**

1. Simplicity Commander で NVM3 をダンプ（[10 章](10_NVM3.md#まず公式ツールを試す)）。`commander nvm3 parse` を試す → 一部のキーで「壊れている」警告
2. 手動で NVM3 のページをたどる（[10 章](10_NVM3.md#nvm3-の構造)）。**消去カウンタ**でページの新旧を並べる
3. 問題のキーの**全履歴**を拾う。追記型なので過去の値が残っている
4. 履歴を時系列に並べると、正常値の後に**途中で切れたオブジェクト**があり、その後に異常値
5. 切れたオブジェクトの位置は、あるページの末尾付近

**判断.** 設定書き込みの最中に電源が切れ、オブジェクトが不完全なまま残った。次回の読み出しで、その不完全なオブジェクトを（実装が）誤って有効と解釈し、異常値になった。
対策は書き込みの電源断耐性（[18 章](18_差分と壊れたデータ.md#破損の扱い方)の破損の考え方）。プログラム側の NVM3 の使い方を見直す。

## ケース C: 秘密が漏れていないかの監査

**状況.** 新製品の出荷前セキュリティレビュー。

**手順.**

1. 量産設定のフラッシュをダンプ。まず**読み出し保護が有効か**を確認（[04 章](04_ダンプを手に入れる.md#読み出し保護に当たったとき)）→ 有効だったが、レビューのため保護を外した開発機でダンプ
2. `binwalk -E` で**エントロピーマップ**（[13 章](13_秘密情報の捜索.md#高エントロピー領域を探す-鍵の在りか)・[14 章](14_圧縮と暗号化の見分け.md#エントロピーとは何か)）。高エントロピー区間を列挙
3. 高エントロピー区間を圧縮/暗号/鍵に分類（[14 章](14_圧縮と暗号化の見分け.md)）。ファーム本体は暗号化なし（H≈6、コード）
4. **PEM / DER の証明書と鍵を検索**（[13 章](13_秘密情報の捜索.md#既知の形式で探す-証明書と鍵)）→ サーバの公開鍵と証明書はあるが、秘密鍵はない（正しい）
5. **設定ストレージ（NVS）の全履歴**を検査（[11 章](11_NVS系ストレージ.md)・[13 章](13_秘密情報の捜索.md#設定ストレージの中を見る)）→ 開発中に登録した**テスト用 Wi-Fi パスワードが、削除済みマーカ付きで平文で残存**
6. パターンスキャン（[13 章](13_秘密情報の捜索.md#パターンで探す-トークンと資格情報)）で API キー・トークンを検索 → なし

**判断.** 致命的な鍵漏れはないが、(1) ファーム本体が暗号化されておらず読み出し保護だけが防御、(2) 削除したはずの資格情報が履歴に残る、の 2 点が指摘事項。
対策は PSA 編・IoT セキュリティ編（フラッシュ暗号化、セキュアエレメント、ストレージの適切な消去）。監査は [19 章](19_自動化とパーサ.md#どれを使うか)でスクリプト化し、以後のビルドで自動化。

## ケース D: 素性の分からないファーム

**状況.** 保守対象の古い機器。ソースもビルド環境も失われた `.bin` だけがある。

**手順.**

1. `file` / `strings` / `binwalk`（[02 章](02_道具箱.md#拾う-strings-file-binwalk)）。ELF ではない生バイナリ。文字列に `"FreeRTOS V10.4.3"`、`"USART"`、`"/dev/..."` はなし（ベアメタル/RTOS）
2. 先頭を `xxd -e -g4`（[07 章](07_CortexMのイメージ.md#ベクタテーブル-先頭に必ずある表)）。オフセット 0 が 0x20005000（RAM）、オフセット 4 が 0x08004401（フラッシュ・奇数）→ **Cortex-M イメージ確定**。ロードアドレスは 0x08004000 付近（ブートローダの後ろ）
3. ベクタテーブルの繰り返しアドレスからデフォルトハンドラを特定、割り込み数からチップ系列を推定（[07 章](07_CortexMのイメージ.md#割り込みハンドラの数からチップを推定する)）
4. Ghidra に **ARM Cortex / ロードアドレス 0x08004000 / ベクタテーブル**で読み込む（[16 章](16_逆アセンブルの基礎.md#設定-2-ロードアドレス-base-address)）
5. 文字列 `"FreeRTOS V10.4.3"` を XREF でたどり、スケジューラ初期化とタスク生成を特定（[16 章](16_逆アセンブルの基礎.md#どこから読むか-とっかかりの見つけ方)）。周辺レジスタ 0x40013800（USART1）を触る関数から通信処理を発見
6. 独自の設定チェックサム関数が見つかる。Unicorn でその関数だけ動かし（[17 章](17_動的解析.md#部分エミュレーション-unicorn)）、既知の設定に対する出力を確認 → CRC-16/CCITT と判明

**判断.** ソースなしでも、使用 RTOS・通信周辺・設定形式が復元でき、保守に必要な範囲は把握できた。分かった構造は [19 章](19_自動化とパーサ.md#まず-struct-固定構造)でパーサに残す。


## まとめ — 共通する型

4 ケースに共通する流れ（[01 章](01_バイナリ解析とは何か.md#ワークフロー-ダンプを手にしてからの-5-手順)のワークフローの実践）:

1. **固定**（ダンプの由来とハッシュ）
2. **全体を見る**（エントロピー・文字列・マジック）
3. **地図**（メモリマップ）
4. **対象ごとに解く**（各章の手順。公式ツール → 手動）
5. **判断して記録**（分かったこと・対策・パーサ）

そして繰り返し現れた原則:

- **まず既知の形式と公式ツール**を試す（[01 章](01_バイナリ解析とは何か.md#手順-4-対象ごとに構造を解く)・[02 章](02_道具箱.md#解く-形式-既知の形式の専用ツール)）
- **追記型ストレージには履歴が残る**（[10 章](10_NVM3.md#追記型ストレージから最新値を復元する)〜[12 章](12_ログとリングバッファ.md)）
- **辻褄が合わなければ、まず自分を疑う**（[03 章](03_バイト列を読む基本.md#チェックサムと-crc-を見分ける)・[18 章](18_差分と壊れたデータ.md#壊れたダンプ-まず切り分ける)）
- **静的と動的を往復**する（[16 章](16_逆アセンブルの基礎.md)・[17 章](17_動的解析.md#静的と動的を往復する)）
- **秘密が読めたら、それは設計の問題**（[13 章](13_秘密情報の捜索.md#見つけたらどう判断するか)）
- **解いたら再現できる形に残す**（[19 章](19_自動化とパーサ.md)）

## この章のポイント

- 実際の調査は「**固定 → 全体 → 地図 → 対象ごとに解く → 判断して記録**」の 5 段（[01 章](01_バイナリ解析とは何か.md#手順-4-対象ごとに構造を解く)）の反復
- 更新失敗は **MCUboot のヘッダ・トレーラ・image ok**（[08 章](08_ブートローダとイメージ形式.md)）で段階を特定
- 設定の化けは **NVM3 の履歴と切れたオブジェクト**（[10 章](10_NVM3.md#nvm3-の構造)・[18 章](18_差分と壊れたデータ.md#壊れたダンプ-まず切り分ける)）
- 監査は **エントロピー・鍵/証明書検索・ストレージ履歴**（[13 章](13_秘密情報の捜索.md#高エントロピー領域を探す-鍵の在りか)・[14 章](14_圧縮と暗号化の見分け.md#エントロピーとは何か)）、指摘は対策（PSA / IoT セキュリティ編）へ
- 素性不明のファームは **ベクタテーブル → ロードアドレス → Ghidra → 文字列/周辺から機能**（[07 章](07_CortexMのイメージ.md#ロードアドレスを突き止める)・[16 章](16_逆アセンブルの基礎.md#設定-2-ロードアドレス-base-address)・[17 章](17_動的解析.md)）
- 共通原則: 公式ツール優先、履歴を疑う、自分を疑う、静的動的の往復、読めたら設計の問題、再現可能に残す
