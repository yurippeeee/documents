# 02. 設計書の書き方 — どう作るかと、そう決めた理由を残す

> **この章で扱う問い.**
> [01 章](01_システム仕様書の書き方.md)では、作る物が満たすべきことを、検証できる要求の形でシステム仕様書に書いた。この章では、その要求をどう実現するかを決めて書く設計書（方式設計書と詳細設計書）に、何をどの形で書くかを、電池で動く温湿度ロガー（以下ロガー）の短い例で示す。
>
> この章では次の 3 つの問いに答える。
>
> 1. 仕様書の要求を、どんな部分に分けて受け持たせ、どこまで細かく決めるのか。そのとき、仕様書に無い新しい要求がなぜ生まれるのか。
> 2. 部品の構成、部品とソフトウェアの間のやり取り、時間の上の振る舞い、電池・メモリ・処理時間の見積もりを、どんな図と表で書けば、作る人と試す人が同じものを思い浮かべられるのか。
> 3. 決めたことに加えて、なぜそう決めたかを、どんな形で残すのか。コードを読めば分かることを、なぜ書かないのか。
>
> 答えの道具は、要求と部分の割り当ての表、線の種類と境界を描き分けたブロック図、マスを全部埋めた状態遷移表、状態ごとの電流と時間の割合を積み上げた予算の表、背景・代案・理由を並べた設計判断の記録である。

## 1. 仕様から設計へ — 方式設計・詳細設計と要求の割り当て

### 方式設計と詳細設計

システム仕様書は、ロガーを外から見たときに満たすべきことを決めたが、中をどう作るかは決めていない（[01 章 1 節](01_システム仕様書の書き方.md#文書の階層-要求-仕様-設計-試験)）。中を決める作業は、2 つの段に分けて行う。システムを、ハードウェアの部品とソフトウェアの部分に分け、仕様書の要求のそれぞれをどの部分に受け持たせるかを決めることを**方式設計**という。方式設計で分けた部分の 1 つ 1 つについて、その中を、作る人が迷わずに作れるところまで決めることを**詳細設計**という。方式設計の結果を書くのが方式設計書、詳細設計の結果を書くのが詳細設計書である。方式設計で分けた部分は、それぞれ設計の要素（[01 章 6 節](01_システム仕様書の書き方.md#トレーサビリティと版の管理-要求から試験までをつなぐ)）として ID を付ける。ID は、ハードウェアの部品を `DS-H`、ソフトウェアの部分を `DS-S`、データの形式を `DS-D`、資源の予算を `DS-B` で始め、2 桁の番号を続ける。

記録の件数の要求 SR-F04 が、段を下りるごとにどう細かくなるかを示す。

```fig
e02_levels
```

段を分けるのは、段ごとに確かめてから次へ進むためである。方式設計の段で、すべての要求に受け持つ部分があるかをレビューしておけば、部分ごとの詳細設計を別々の人が同時に進めても、受け持ちの抜けや重なりが後から見つかって作り直すことが減る。方式設計で決めたことは結合試験で、詳細設計で決めたことは単体試験で確かめる（[01 章 1 節](01_システム仕様書の書き方.md#文書の階層-要求-仕様-設計-試験)）。

### 割り当てと派生要求

仕様書の要求の 1 つ 1 つを、それを実現する責任を持つ設計の要素に受け持たせることを**割り当て**という。割り当てを決めると、受け持った要素が満たすべきことを、仕様書の言葉から部品やソフトウェアの言葉に書き直すことになる。このように、割り当てによって設計の要素に生まれる、仕様書には書かれていない要求を**派生要求**という。割り当ての表と、派生要求の例を示す。

```fig
e02_alloc
```

割り当ての表のどの行にも印があれば、受け持つ部分の無い要求は無い。どの列にも印があれば、どの要求にも結び付かない部分は無い（[01 章 6 節](01_システム仕様書の書き方.md#トレーサビリティと版の管理-要求から試験までをつなぐ)のトレーサビリティを、設計の側から見たもの）。電池寿命の SR-W02 のように、ほとんど全部の部分が受け持つ要求は、そのままでは部分ごとの目標にならないので、5 節の電力の予算で部分ごとの電流の上限に分ける。

派生要求は、計算の根拠とともに設計書に書く。書いておかないと、後で部品を替える人が、満たすべき値を知らない。たとえば安い ±50 ppm の水晶に替えると、30 日で最大 130 秒ずれ、SR-P04 の ±60 秒を満たさないことが、システムの試験で初めて分かる。

### 設計書の目次

方式設計書と詳細設計書の目次の型を示す。各章に何をどの形で書くかが、この章の 2〜6 節にあたる。

```fig
e02_toc
```

小さな機器では、2 つを 1 冊にまとめてもよい。ロガーの設計書 LG-DES-001（[04 章](04_実例_設計書.md#文書の情報と設計の入力-仕様書との対応)）は、まとめた例である。

## 2. 構成の設計 — ブロック図とハードウェア・ソフトウェアの分担

### ブロック図

方式設計で分けたハードウェアの部品と、部品の間の電源・信号・バスのつながりを描いた図を**ブロック図**という。同じロガーのブロック図を、悪い例と良い例で並べる。

```fig
e02_block
```

悪い例の図では、図に無いことを、回路を描く人とプログラムを書く人がそれぞれ補うので、補い方が人ごとに割れる。たとえば、電源の線と信号の線が同じ形だと、どの部品の電源を切れるかが読めない。外の相手と境界が無いと、コンテキスト図（[01 章 2 節](01_システム仕様書の書き方.md#システムの境界-コンテキスト図と外部インタフェース)）の外部インタフェースを、どの部品が受け持つのかが決まらない。部品に設計の要素の ID を付けておけば、ブロック図の部品と、1 節の割り当ての表の列を突き合わせられる。悪い例の ⑤ の抜けも、割り当ての表の SR-F13 の行に受け持つ部品（DS-H06）があるのに、図にその線が無いことから見つかる。

### ハードウェアとソフトウェアの分担

ある機能を、回路（ハードウェア）で実現するか、マイコンのプログラム（ソフトウェア）で実現するかを、機能ごとに決めることを、**ハードウェアとソフトウェアの分担**という。比べるのは、反応や制御に要る時間の細かさ、電力、部品の費用と大きさ、後から変えやすいかの 4 つである。ロガーの機能を時間の細かさで並べた地図と、ボタンのチャタリング（押した直後に接点がはね返る現象）を取り除く方法の比較を示す（取り除き方の仕組みは [電源と周辺の制御シリーズ 11 章 2 節](../periph/11_スイッチと外部入力.md#チャタリングを取り除く)）。

```fig
e02_hwsw
```

µs より細かい時間で決まる機能をプログラムで行うと、間に合わないか、その間ほかの処理を止めてしまう。マイコンが眠る間も動き続ける機能（時刻を数える）をプログラムで行うと、マイコンを起こし続けることになり、電池がもたない。そこで、これらは回路かマイコンの周辺の回路に任せる。ms より粗く、後から変える見込みのある機能は、プログラムに任せる。ロガーのボタンは、短押しと長押しを 1 秒と 3 秒で分ける（SR-U01）ので、チャタリングの除去は ms の単位で決まれば足り、ソフトウェアで行う。判定の時間を後で変えるときも、プログラムだけを直せばよい。選ばなかった回路の案と、その理由も書き残す（6 節の設計判断の記録）。

### 部品を選んだ理由

ブロック図の部品は、派生要求を満たすものから選び、選んだ理由を表にして設計書に書く。ロガーの主な部品の例を示す（値はどれも例の値）。

| 設計の要素 | 選んだもの | 選んだ理由（効く要求） | 比べた代案 |
|---|---|---|---|
| DS-H01 マイコン | BLE を内蔵したマイコン（64 MHz、フラッシュ 512 KB、RAM 64 KB、スリープ 2.0 µA） | BLE（SR-I01）を 1 個の部品で受け持ち、部品の費用（SR-C02）と大きさ（SR-C01）を抑える。スリープの電流は、電力の予算で最も大きい項目になる（5 節） | マイコンと BLE のモジュールの 2 個 |
| DS-H03 記録用フラッシュ | SPI の NOR フラッシュ 4 Mbit（512 KiB）、データの保持 20 年 | 記録の記憶 410.6 KiB 以上（SR-F04 の派生要求）。電池を外して 10 年の保持（SR-R01） | FRAM・マイコンの内蔵のフラッシュ（6 節で比べる） |
| DS-H04 時計の水晶 | 32.768 kHz、25 °C で ±20 ppm | ±23.1 ppm 以内（SR-P04 の派生要求） | ±10 ppm の水晶（費用が高い） |

部品が手に入らなくなって替えるときは、この表の「選んだ理由」の列が、次の部品に求める条件になる。

## 3. インタフェースの設計 — 信号・通信・データの形

インタフェースの設計では、部品と部品、ソフトウェアの部分と部分の間で、何をどうやり取りするかを、相手の側を作る人がこの設計書だけで作れるところまで決める。ロガーとアプリの間のデータの形式は、両方の開発者が読むインタフェース仕様書 LG-ICD-001 に書き（[01 章 2 節](01_システム仕様書の書き方.md#システムの境界-コンテキスト図と外部インタフェース)）、設計書には、その文書番号と版を参照として書く。設計書が決めるのは、ロガーの中のインタフェースである。

### ピン割り当て

マイコンのピンの 1 つ 1 つに、どの信号を割り当て、どの向き・論理・電気的な条件で使うかを決めた表を**ピン割り当て**という。

```fig
e02_pins
```

悪い例の表のとおりに作っても、回路とプログラムの両方が「表のとおり」のまま食い違いうる。たとえば、フラッシュの選択の信号（CS）の論理と、リセットの後の状態が書いていないと、マイコンのピンが入力のままのリセットの間に CS が浮き、フラッシュが選ばれたままになりうる（[電源と周辺の制御シリーズ 15 章 1 節](../periph/15_異常に備える.md#リセットの間のピンの状態)）。眠る間の状態が書いていないと、浮いた入力や、電源を切った部品へ流れ込む電流が、5 節の眠りの電流を何倍にもする（[同 7 章 3 節](../periph/07_眠らせ方と起こし方.md#眠る間のピンの状態と漏れ電流)）。

### バスのやり取りとタイミング図

横軸を時間にとり、信号ごとの値の変化と、変化と変化の間の時間の決まりを描いた図を**タイミング図**という。温湿度センサとの I2C の 1 回の測定のやり取りを、設計書に書くタイミング図の例で示す（I2C の仕組みは [電源と周辺の制御シリーズ 8 章 2 節](../periph/08_センサをつなぐ.md#i2c)）。

```fig
e02_i2c
```

設計書には、バスの速さ・相手のアドレス・命令の並びと、待つ時間とその根拠を書く。待ち時間の 5 ms は、4 節の時間割と、5 節の電力と処理時間の予算の入力になる。応答が無いとき（相手が受け取りの合図を返さないとき）の扱いは、6 節の異常時の処理の表に書く。

### データの形式とエンディアン

やり取りしたり保存したりするデータについて、バイトの並び・各欄の意味・単位と倍率・取りうる範囲・範囲の外の値の扱いを決めたものを、**データの形式**という。2 バイト以上の数を、どの順にバイトに並べるかの決まりを**エンディアン**という。小さい桁のバイトを先に置く決まりをリトルエンディアン、大きい桁のバイトを先に置く決まりをビッグエンディアンという（[組み込み通信シリーズ 3 章 6 節](../comm/03_フレーミングと誤り検出.md#数値の並べ方-エンディアンと構造体)）。ロガーの記録 1 件（8 バイト）の形式で示す。

```fig
e02_bytes
```

エンディアンを書いていないと、記録を書く側と読む側（読み出しの処理やアプリ）が、それぞれの思い込みで決める。逆に読まれると、5.12 °C の正しい記録が 0.02 °C になり、下限 2.0 °C を下回ったという、起きていない警報が出る。範囲の外の値を決めていないと、センサが応答しなかった記録と、0.00 °C を測った記録を区別できない。

### API

ソフトウェアを分けた部分の間で、一方が他方に使わせる関数と、その引数と戻り値の意味の決まりを **API** という。記録を受け持つ部分（DS-S02）の API の例を示す。関数を呼んでよい条件と、失敗したときの返し方は、6 節のモジュールの仕様で決める。

| 関数 | 何をするか | 引数 | 戻り値 |
|---|---|---|---|
| `rec_append(r)` | 記録を 1 件、最後に足す | `r`: 記録 1 件（上の図の 8 バイトの形） | `REC_OK`・`REC_FULL`（容量に達して止める設定のとき）・`REC_ERR_FLASH`（書けなかったとき） |
| `rec_count()` | 保存している件数を返す | — | 件数（0〜容量） |
| `rec_read(first, n, buf)` | 最も古い記録を 0 番として、`first` 番から `n` 件を `buf` に読む | 番号・件数・置き場所 | 読んだ件数 |

API が決まっていれば、測定の部分と通信の部分を、記録の部分ができる前から、API だけをまねた偽の記録の部分につないで、別々に作って試せる。

## 4. 振る舞いの設計 — 状態遷移表・シーケンス図・タイミング

### 仕様の動作モードを、中の状態とタスクに分ける

仕様書の主のモード（停止中・記録中・電池切れ）と通信の状態（通信なし・接続の受付中・接続中）は、外から見える状態だけを決めたものである（[01 章 3 節](01_システム仕様書の書き方.md#使われ方と動作モード-ユースケースと状態遷移)。ロガーの仕様書では表 3-2〜3-4。[03 章 3 節](03_実例_システム仕様書.md#動作モード)）。記録中のロガーは、外から見るとずっと記録中だが、中では、次の記録の時刻を待つ・センサの測定の完了を待つ・フラッシュの書き込みの完了を待つ、を繰り返している。設計では、仕様の状態を、中で区別する状態に分ける。

中の状態を変えるきっかけとして、ソフトウェアに届く出来事を**イベント**という。仕様の状態遷移表の列に並べた出来事（長押し・アプリが接続・電池が尽きる など。[01 章 3 節](01_システム仕様書の書き方.md#使われ方と動作モード-ユースケースと状態遷移)）は、中ではイベントの形でソフトウェアに届き、そこへ外からは見えない中だけのイベント（センサの測定の完了・書き込みの完了）が加わる。イベントの多くは割り込みで届く。周辺の部品（タイマ・ピン・通信の回路など）が CPU に今の処理を中断させ、あらかじめ決めておいた関数を実行させる仕組みを**割り込み**という。たとえば記録の時刻は、マイコンの中で眠る間も時刻を数え続ける回路（RTC）が、割り込みで知らせる。OS の上で、ほかの処理と独立に待ったり動いたりする処理の流れを**タスク**という（関数・専用のスタック・OS が管理する情報の 3 つでできている。[OS のシリーズ 2 章 2 節](../freertos/02_タスクという抽象.md#タスクとは何か)）。ロガーの仕様の状態を、中の状態とタスクに分けた例を示す。

```fig

```

仕様で互いに独立に書いた 2 つの状態（記録と通信）を別々のタスクに受け持たせると、それぞれのタスクの状態遷移表は小さいまま保てる。1 つのタスクで両方を受け持つと、状態は組み合わせの数（記録の 4 つ × 通信の 4 つ）だけ要る。

### 中の状態遷移表

記録の流れを受け持つ測定タスクの、中の状態遷移表を示す。イベントは、長押しと記録の流れに関わるものに絞った（アプリからの開始と停止、容量に達した、電池が尽きる、も含めた全部の表は [04 章 4 節](04_実例_設計書.md#ソフトウェアの設計-層-タスク-状態遷移表)）。マスの「→」の後は次の状態で、書いていなければ同じ状態にとどまる。開始の応答（緑を 3 回）と停止の応答（赤を 3 回）は、仕様書の表 3-5 の LED の表示である（[03 章 3 節](03_実例_システム仕様書.md#ボタンと-led)）。

| 状態 ＼ イベント | 長押し | 記録の時刻 | 測定の完了 | 応答なし | 書き込みの完了 |
|---|---|---|---|---|---|
| 停止中 | 記録を始める（RTC を設定し、開始の応答をする）。すぐに 1 件目の測定の命令を送り、5 ms のタイマを掛ける → 測定中。ただし、記録が容量に達していて、止める設定のときは、停止の応答だけをする（表 3-3 の ※） | 起きない（RTC を止めてある） | 起きない（タイマを掛けていない） | 起きない | 起きない |
| 待ち | 記録を止める（RTC を止め、停止の応答をする）→ 停止中 | 測定の命令を送り、5 ms のタイマを掛ける → 測定中 | 起きない | 起きない | 起きない |
| 測定中 | 止める印を立てる | 起きない（記録の間隔は 1 分以上） | 結果を読み、1 件を書き始める → 書き込み中 | 測定異常の印を付けた 1 件を書き始める → 書き込み中 | 起きない |
| 書き込み中 | 止める印を立てる | 起きない | 起きない | 起きない | フラッシュを眠らせる。止める印があれば停止の応答をして → 停止中、無ければ → 待ち |

「起きない」のマスも、起きない理由を書いて埋める。理由が崩れる変更（たとえば記録の間隔を 5 ms より短くできるようにする変更）をしたときに、見直すべきマスが分かるからである。

抜けやすいのは、測定中と書き込み中の長押しのマスである。2 つの状態は 10 分に 6.8 ms（後の時間割）しかないので、長押しがそこに重なるのは約 9 万回に 1 回で、試験ではまず見つからない。マスが空いたまま実装されると、そのイベントは捨てられ、利用者が長押ししても記録が止まらない（SR-F06・SR-U07 を満たさない）。表のマスを全部埋めれば、この組み合わせの扱いが設計の段階で決まる。

### タスクと割り込みの一覧

タスクと割り込みは、名前・起こすもの・優先度・受け持つことを一覧にして書く（例）。BLE の通信の手順を行うソフトウェア（BLE のスタック）は、それ自身のタスクと割り込みを持つので、一覧に入れる。

| 名前 | 種類 | 起こすもの | 優先度 | 受け持つこと |
|---|---|---|---|---|
| RTC の割り込み | 割り込み | 記録の時刻 | — | 測定タスクに知らせるだけ |
| ボタンの割り込み | 割り込み | ボタンのピンの変化 | — | 操作タスクに知らせるだけ |
| BLE のスタック | タスクと割り込み | 無線の出来事 | 最も高い（スタックが決める） | 受付と接続の無線のやり取り |
| 操作タスク | タスク | ボタンの割り込み、5 ms のタイマ、表示のタイマ（30 秒と 2 秒ごと） | 高 | チャタリングの除去、短押しと長押しの判定、LED の表示（表 3-5 の優先順位で 1 つを選ぶ） |
| 通信タスク | タスク | BLE のスタックからの知らせ | 中 | 読み出し・設定のやり取り |
| 測定タスク | タスク | RTC の割り込み、タイマ | 低 | 測定と記録（上の表） |

割り込みの処理は、タスクに知らせるだけにして短くする。割り込みの処理をしている間は、ほかの割り込みとタスクが待たされ、BLE のスタックの時間の決まりを破りうるからである（[OS のシリーズ 18 章 4 節](../freertos/18_割り込みとの境界.md#割り込みハンドラの設計)）。優先度は、周期の短い処理ほど高くした（[同 20 章 4 節](../freertos/20_リアルタイム性の解析.md#レートモノトニック-rm-優先度の付け方)）。

並行に動くタスクと割り込みが同じデータを使う所は、誰が書き、誰が読み、どう守るかを書く。

| 共有するデータ | 書く処理 | 読む処理 | 守り方（例） |
|---|---|---|---|
| 記録と、書き込みの位置 | 測定タスク（`rec_append`） | 通信タスク（`rec_read`） | 記録の部分の中だけに置き、ミューテックス（[OS のシリーズ 12 章 4 節](../freertos/12_セマフォとミューテックス.md#ミューテックス-所有者がいる-ロック)）で一度に 1 つのタスクだけに使わせる |
| 設定（記録の間隔・警報の上限と下限など） | 通信タスク | 測定タスク・操作タスク | 書くのは通信タスクだけ。読む側は、使う前に 1 回まとめて写す |
| ボタンの変化 | ボタンの割り込み | 操作タスク | 割り込みはタスクに知らせるだけで、データを書かない |

書いていないと、2 つのタスクが記録の位置を同時に書き換えて、記録が重なったり抜けたりする（[OS のシリーズ 19 章 1 節](../freertos/19_排他制御の設計.md#レースコンディション)）。

## 5. 資源の予算 — 電力・メモリ・処理時間を見積もって確かめる

電池の電荷・メモリ・CPU の時間のように限りのある資源について、設計の要素ごとの使う量を見積もり、合計が要求から決まる上限に収まることを確かめる表を**予算**という。予算は、部品を買い、プログラムを書く前に立てる。プログラムが入りきらない、電池が足りない、と試作の後に分かると、部品を替えて基板を作り直すことになるからである。

### 電池寿命の式

電流が時間とともに変わるとき、ある長さの時間に流れた電荷を、その時間で割った値を**平均電流**といい、$`\bar I`$ と書く（[電源と周辺の制御シリーズ 1 章 4 節](../periph/01_電源と周辺制御の全体像.md#平均電流を導く)）。電池が、使われる条件（温度・パルスの負荷・自己放電）のもとで機器に渡せると、設計で見込む電荷を**設計で使う容量**といい、$`Q`$ [mAh] と書く。ロガーでは、公称の 220 mAh から、低温・パルスの負荷・自己放電の分を見込んで、$`Q`$ = 180 mAh とした（例の値。見込み方は [同 3 章 5 節](../periph/03_電池を知る.md#容量の内訳)）。

**方針**: 電池寿命 $`L`$ を、設計で使う容量 $`Q`$ を使い切るまでの時間とする。平均電流は、部品ごと・状態ごとの電流を、その状態にいる時間の割合で重み付けして足して求める。

**導出**: 機器の使われ方は、1 日ごとに同じことを繰り返すとする（週に 1 回の出来事は、1 日に 1/7 回とする）。部品 $`p`$ が 1 日のうちに状態 $`k`$（眠り・動作・書き込みなど）にいる時間を $`t_{p,k}`$ [s]、そのときの電流を $`I_{p,k}`$ とする。部品の電流は足し合わさって電池から流れ出るので、1 日に流れ出る電荷は

$$
\sum_p \sum_k I_{p,k}\, t_{p,k}
$$

である。これを 1 日の長さ 86 400 s で割ると平均電流になる。状態にいる時間の割合を $`d_{p,k} = t_{p,k}/86\,400\ \text{s}`$（部品ごとに $`\sum_k d_{p,k} = 1`$）とおくと、

$$
\bar I = \frac{1}{86\,400\ \text{s}} \sum_p \sum_k I_{p,k}\, t_{p,k} = \sum_p \sum_k I_{p,k}\, d_{p,k}
$$

となる。電池は 1 時間あたり $`\bar I \times 1\ \text{h}`$ の電荷を渡すので、$`Q`$ を使い切るまでの時間は

$$
L = \frac{Q}{\bar I}
$$

である。$`Q`$ が mAh、$`\bar I`$ が mA なら $`L`$ の単位は h で、8760 h で割ると年になる ∎

SR-W02 の 1 年以上を満たすには、$`\bar I \le Q/8760\ \text{h} = 180\ \text{mAh}/8760\ \text{h} = 20.5`$ µA が要る。これが電力の予算の上限である。

### 電力の予算

SR-W02 の使い方の条件（記録の間隔 10 分・25 °C・短押しは 1 日に 1 回で、そのたびに受付が 2 分（SR-U06）・読み出しは 1 週間に 1 回で接続 1 分・警報の表示は無い）で、ロガーの電力の予算を立てる（項目は、この節の説明のために絞った例。ロガーの予算は [04 章 5 節](04_実例_設計書.md#資源の見積もり-電池寿命-記録容量-処理時間)）。接続の受付の間、ロガーは接続を受け付けていることを知らせる短い電波を、決まった間隔で送る（アドバタイズ。[組み込み通信シリーズ 17 章 1 節](../comm/17_アドバタイズとスキャン.md#アドバタイズイベント-3-つのチャネルで同じものを送る)）。記録用フラッシュは、書き込みの後、命令で最も電流の小さい眠りの状態（ディープパワーダウン）に入れる。LED は、仕様書の表 3-5 の表示のうち、記録中の表示（30 秒ごとに緑を 1 回）・通信中の表示（受付中と接続中に 2 秒ごとに緑を 1 回）・状態の応答（短押しのたびに緑を 1 回）で点く（[03 章 3 節](03_実例_システム仕様書.md#ボタンと-led)）。仕様書が設計に任せた 1 回の点灯の長さ（表 3-6）は、20 ms とした。

| 部品 | 状態 | 電流 $`I_{p,k}`$ | 1 日の時間 $`t_{p,k}`$ | 時間の割合 $`d_{p,k}`$ | $`I_{p,k}\,d_{p,k}`$ |
|---|---|---|---|---|---|
| マイコン | 眠り（RTC を動かし RAM を保持） | 2.0 µA | 1 日から下の 3 つを引いた時間 | 0.99995 | 2.000 µA |
| マイコン | 動作（測定と記録の処理） | 3.0 mA | 1.1 ms × 144 回 = 0.158 s | 1.83 × 10⁻⁶ | 0.0055 µA |
| マイコン | BLE の送信（受付のアドバタイズ） | 5 mA | 2 ms × 1200 回 = 2.40 s | 2.78 × 10⁻⁵ | 0.139 µA |
| マイコン | BLE の送信（読み出しの接続） | 5 mA | 60 s × 20 % ÷ 7 = 1.71 s | 1.98 × 10⁻⁵ | 0.099 µA |
| 温湿度センサ | 待機 | 0.05 µA | 1 日から測定の時間を引いた時間 | 0.99999 | 0.050 µA |
| 温湿度センサ | 測定 | 0.3 mA | 5 ms × 144 回 = 0.72 s | 8.33 × 10⁻⁶ | 0.0025 µA |
| 記録用フラッシュ | ディープパワーダウン | 0.5 µA | 1 日から下の 2 つを引いた時間 | 0.999999 | 0.500 µA |
| 記録用フラッシュ | 書き込み | 5 mA | 0.7 ms × 144 回 = 0.101 s | 1.17 × 10⁻⁶ | 0.0058 µA |
| 記録用フラッシュ | セクタの消去 | 10 mA | 45 ms × 144 回 ÷ 512 = 0.0127 s | 1.46 × 10⁻⁷ | 0.0015 µA |
| LED | 点灯（記録中の表示） | 2 mA | 20 ms × 2 880 回 = 57.6 s | 6.67 × 10⁻⁴ | 1.333 µA |
| LED | 点灯（通信中の表示） | 2 mA | 20 ms × 64.3 回 = 1.29 s | 1.49 × 10⁻⁵ | 0.030 µA |
| LED | 点灯（状態の応答） | 2 mA | 20 ms × 1 回 = 0.02 s | 2.31 × 10⁻⁷ | 0.0005 µA |
| 合計 $`\bar I`$ | | | | | 4.17 µA |

受付の 2 分は 100 ms ごとにアドバタイズし、1 回に 2 ms 送信するとした。接続の間は、時間の 20 % だけ無線が送受信する（平均 1 mA）とした。セクタ（4 KiB）は 512 件ごとに 1 回消去する。記録中の表示は 1 日に 86 400 s ÷ 30 s = 2 880 回、通信中の表示は (120 s + 60 s ÷ 7) ÷ 2 s = 64.3 回点く。2 つの表示の時が重なって省かれる回（表 3-6）は、多めに見積もるために引かなかった。どれも例の値である。$`L`$ = 180 mAh ÷ 4.17 µA = 43 200 h = 4.9 年で、SR-W02 を満たす。

SR-W02 の条件のうち、警報の表示と電池少の表示は、次のように扱った。警報の表示は、条件で出ないことにしたので（警報の印が付かない上限と下限に設定する）、表に入れない（出続けたときの寿命は下の図の (b)）。電池少の表示は、電池少と判定してから電池切れまでの間だけ、記録中の表示に代わって 30 秒ごとに 2 回（赤と緑を 1 回ずつ）点く（表 3-5・3-6）。その間だけ平均電流が 1.33 µA 増えるが、この期間を 30 日としても、増える電荷は 1.33 µA × 720 h = 0.96 mAh で $`Q`$ の 0.5 % なので、表では省いた（ロガーの見積もりは [04 章 5 節](04_実例_設計書.md#資源の見積もり-電池寿命-記録容量-処理時間)）。

眠りの 3 つ（マイコン・フラッシュ・センサ）で平均電流の 61 %、記録中の表示で 32 % を占め、測定と記録は 0.4 % にすぎない。記録中の表示の点灯 1 回の電荷は 2 mA × 20 ms = 40 µC で、記録 1 回の電荷（表のマイコンの動作・センサの測定・書き込み・消去の 1 回分の和で 9.2 µC）の 4 倍ほどだが、1 日に記録の 20 倍の 2 880 回点くので、1 日の電荷は記録の 87 倍になる。したがって、測定の処理を速くしても寿命はほとんど延びない。寿命は、眠りの電流を決める部品の選び方と眠らせ方、それに 1 年中点く表示の、点灯の長さと電流で決まる。電力の予算から生まれる派生要求は、部品の眠りの電流の上限、「測定の後はフラッシュをディープパワーダウンにする」のような眠らせ方の決まり、LED の 1 回の点灯の長さと電流の上限である。フラッシュを眠らせ忘れる誤りは、プログラムの 1 行で寿命を約 1/7 にするので、時間割（4 節）と状態遷移表に、眠らせる処理を書いておく。

予算の項目を省いてよいかは、1 回の電荷ではなく、1 日の回数を掛けた電荷で決める。[01 章 5 節](01_システム仕様書の書き方.md#使い方の条件)の簡単な模型は、記録 1 回の電荷を 30 µC と大まかに置いたが、記録は 30 µC としても平均電流の 1 % ほどなので、同じ条件の寿命は 4.9 年で、この節の見積もりと変わらない。一方、記録中の表示を、1 回の点灯が短いからと省くと、平均電流は 2.83 µA になり、寿命を 7.3 年と 1.5 倍に見誤る。

### 余裕

上限と見積もりの比を**余裕**という。電力の予算の余裕は、20.5 µA ÷ 4.17 µA = 4.9 倍である。余裕を残すのは、見積もりが外れる理由がいくつもあるからである。時間割の動作の時間はまだ測っていない。部品の電流はデータシートの代表値で、最大値や高い温度での値はもっと大きい（眠りの電流は、温度が上がると増えることが多い）。後から足す機能もある。一方、余裕を大きく取りすぎると、大きな電池や高い部品を選ぶことになる。そこで、どれだけの余裕を目標にするかを、理由とともに予算に書く（この節の最後の表）。

### 処理時間の予算

ある処理を 1 回行うのに CPU を使う時間の、起こりうる最も長い値を**最悪実行時間**という（待つ間に CPU を手放す時間は含めない）。CPU が処理に使われる時間の割合を**利用率**という。周期 $`T_i`$ ごとに起きる処理 $`i`$ の最悪実行時間を $`C_i`$ とすると、利用率は $`U = \sum_i C_i/T_i`$ で見積もれる（[OS のシリーズ 20 章 3 節](../freertos/20_リアルタイム性の解析.md#cpu-利用率)）。処理時間の予算は、最も混む場面で立てる。ロガーでは、アプリへの読み出しの接続の間に、記録の間隔 1 分（SR-F02 の最も短い間隔）の測定が重なり、ボタンも押されている場面である。接続の間、スマートフォンとロガーは、接続の間隔（例の値 15 ms）ごとに短く送り合う。この 1 回を接続イベントという（[組み込み通信シリーズ 18 章 1 節](../comm/18_接続とGATT.md#接続の確立と接続イベント)）。

```fig
e02_cpu
```

利用率が 100 % を超えれば、どう優先度を付けても間に合わない。100 % 以下でも、優先度の付け方によっては締め切りに遅れる。そこで、起きてから終わるまでの最悪の時間（最悪応答時間）を、優先度の高い処理に割り込まれる分を足して求め、締め切りと比べる（[OS のシリーズ 20 章 6 節](../freertos/20_リアルタイム性の解析.md#応答時間解析-正確な判定)）。通信の処理が締め切り（次の接続イベント）に遅れると、その回に送るデータが用意できず、読み出しが遅れる（SR-P05）。最悪実行時間には、データシートの最大値と、実測の最大値に余裕を掛けた値を使う（[同 20 章 8 節](../freertos/20_リアルタイム性の解析.md#wcet-最悪実行時間-をどう求めるか)）。

下の図で、処理ごとの周期と最悪実行時間、センサとフラッシュの待ち方、優先度の順を変えて、時間割・利用率・締め切りに遅れる処理を確かめられる。

### 見積もりと実測

予算の表には、目標の余裕とその理由、見積もり、実測の欄を並べる。実測の欄は、試作と試験の後に埋める（例）。

| 項目 | 上限（どこから） | 目標と理由 | 見積もり | 実測 | 確かめ方 |
|---|---|---|---|---|---|
| 平均電流 | 20.5 µA（SR-W02 と $`Q`$） | 上限の 1/2 以下。部品の電流が代表値で、温度による増え方を見込んでいない | 4.17 µA（余裕 4.9 倍） | （試験の後に書く） | 試験: 眠りの電流と、測定 1 回・点灯 1 回の電荷を測る |
| プログラムの記憶 | 512 KB | 50 % 以下。後で無線の更新を足すと、新しいプログラムを置く同じ大きさの場所が要る | 232 KB（45 %） | （ビルドの後に書く） | 検査: リンカの出力を読む |
| RAM | 64 KB | 70 % 以下。スタックの最も深い所の見積もりは外れやすい | 44 KB（69 %） | （試験の後に書く） | 試験: スタックの使った量を測る |
| 利用率 | 100 % | 70 % 以下（[OS のシリーズ 20 章 9 節](../freertos/20_リアルタイム性の解析.md#実務的な指針)） | 55 % | （試験の後に書く） | 試験: 処理ごとの時間を測る |

見積もりと実測が大きく違う項目は、見積もりの前提（時間割の時間、部品の電流）を直し、予算を立て直す。直した予算は、設計書の版を上げて改訂履歴に書く（[01 章 6 節](01_システム仕様書の書き方.md#トレーサビリティと版の管理-要求から試験までをつなぐ)）。

## 6. 設計判断と詳細設計 — 代案と理由・モジュールの仕様・異常時の処理

### 設計判断の記録

設計の途中で選んだことについて、背景・比べた代案・決めたこと・理由・影響を書き残したものを**設計判断の記録**という。ある設計の問題に対して比べる、互いに違う解き方の候補を**代案**という。理由を書き残すのは、後で設計を変える人が、前の決定が何を前提にしていたかを知るためである。たとえば、LED を見やすくしたい人が、仕様書が設計に任せた 1 回の点灯の長さを 20 ms から 150 ms に延ばすと、5 節の予算で平均電流は 4.17 µA から 13.0 µA になり、寿命は 4.9 年から 1.6 年に縮む。要求はまだ満たすが、余裕は 4.9 倍から 1.6 倍に減り、目標の 2 倍を下回る。「点灯を 20 ms にしたのは、1 年中 30 秒ごとに点く記録中の表示の電荷を抑えて、電池寿命の余裕を残すため」と書いてあれば、変える人はその前提に気づける。

記録を保存する部品を選んだ記録の例を、設計書の形で示す。

| 項目 | 内容 |
|---|---|
| 題 | 設計判断 02（例の番号）: 記録を保存する部品 |
| 背景 | 52 560 件・410.6 KiB（SR-F04）を、電池を外しても 10 年保持し（SR-R01）、記録の間隔 1 分で 5 年使える（SR-R04）記憶が要る |
| 代案 | A: 外付けの NOR フラッシュ（SPI、4 Mbit）／ B: 外付けの FRAM（SPI、4 Mbit）／ C: マイコンの内蔵のフラッシュの空き |
| 決めたこと | A を使う |
| 理由 | C は空きが 280 KB で 410.6 KiB に足りないので、点数を付ける前に外した。A と B を下の図の重み付けの点数で比べ、A が上回った。部品の費用の差（1 台 610 円）が大きい |
| 影響 | 書く前に 4 KiB ごとの消去が要るので、記録の部分に消去の管理を足す（[04 章 3 節](04_実例_設計書.md#インタフェースの設計-センサ-フラッシュ-ble-記録の形式)）。消去の 45 ms を処理時間の予算に入れた（5 節） |
| 関係する要求と設計 | SR-F04・SR-R01・SR-R04・SR-C02、DS-H03・DS-S02 |

代案は、まず要求を満たすかどうかの必須の条件で外し、残った案に、比べる観点ごとの評点（1〜5）を付けて、重み（合計を 100 にそろえる）を掛けて足した点数で比べる。重みは、要求の優先度（[01 章 4 節](01_システム仕様書の書き方.md#要求文の書き方-1-文-1-要求-数値と条件-検証の方法)の要求の属性）から決め、重みも記録に書く。

```fig
e02_trade
```

必須の条件で先に外すのは、点数が高くても要求を満たさない案（C）を選ばないためである。重みは決める人によって変わるので、重みをどれだけ変えると選ぶ案が入れ替わるかも確かめて、記録の理由に書く。ほかの重みをそのままにすると、費用の重みが 20 を下回るか、ソフトウェアの手間の重みが 40 を上回ると、B が A を上回る。

### 詳細設計 — モジュールの仕様

詳細設計で、1 つのまとまった責任を受け持つように分けたソフトウェアの単位を**モジュール**という（方式設計のソフトウェアの部分を、さらに分けたもの。1 つの部分が 1 つのモジュールのこともある）。モジュールの API の関数を呼ぶ前に、呼ぶ側が満たしておく条件を**事前条件**という。関数が正しく戻ったときに成り立つと、モジュールの側が約束する条件を**事後条件**という。記録のモジュールの仕様の例を、詳細設計書の形で示す。

| 項目 | 内容 |
|---|---|
| モジュール | 記録（DS-S02） |
| 責任 | 記録 1 件（8 バイト）を記録用フラッシュに古い順に保存し、番号で読ませる。容量に達したときは、設定に従って最も古い記録から上書きするか、止める（SR-F03〜F05） |
| 持つデータ | 書き込みの位置・最も古い記録の位置・件数（RAM 16 B）、記録用フラッシュの記録の領域 |
| API | `rec_init`・`rec_append`・`rec_count`・`rec_read`（3 節） |
| 事前条件 | `rec_init` が成功していること。`rec_append` は測定タスクだけが呼ぶ。割り込みの処理の中から呼ばない |
| 事後条件 | `REC_OK` で戻ったら、その 1 件は電池を外しても失われない（書いた後に読み返して確かめてから戻る）。件数は 1 増える（上書きのときは変わらない） |
| エラーの返し方 | 戻り値で返す。`REC_ERR_FLASH`: 読み返すと違い、次のページに書き直しても違った。`REC_FULL`: 止める設定で容量に達した。どちらのときも、記録と件数は変えない |
| 資源 | RAM 300 B（ページのバッファ 256 B を含む）。CPU の最悪実行時間 0.4 ms。戻るまでの最悪の時間 46 ms（セクタの消去 45 ms を眠って待つ分を含む） |

```fig
e02_contract
```

コードの手順（変数の使い方、ループの書き方）を設計書に写すと、コードを直すたびに設計書と食い違い、どちらが正しいかが分からなくなる。一方、事前条件・事後条件・理由と、使ってよい資源と時間は、コードを読んでも分からないので、設計書に書かなければどこにも残らない。たとえば「読み返してから戻る」理由が残っていないと、書き込みを速くしたい人が読み返しを消し、書けなかった記録を失っても気づかない作り（SR-F03 を満たさない）に変えてしまう。

### 異常時の処理

部品とソフトウェアに起こりうる異常のそれぞれについて、見つけ方・処置・利用者への見え方を表にして決める。表の行を洗い出すには、部品ごとに起こりうる壊れ方を挙げ、その影響を調べる FMEA（故障モード影響解析）の考え方が参考になる（規格の手順に従う必要のある分野では、その規格を確かめる）。ロガーの例を 3 つ示す（全部の表は [04 章 6 節](04_実例_設計書.md#異常時の設計と試験へのつながり)）。

| 異常 | 見つけ方 | 処置 | 利用者への見え方 | 関係する要求 |
|---|---|---|---|---|
| センサが応答しない | I2C で受け取りの合図が返らないことが 3 回続く | 測定異常の印を付け、温度と湿度の欄を「測れなかった」の値（3 節）にした 1 件を書き、次の記録の時刻にまた測る | アプリの記録の一覧で、その時刻が「測定異常」と見える | SR-F01・SR-F03 |
| フラッシュに書けない | 書いた後に読み返すと違う | 次のページに書き直す。それも違えば `REC_ERR_FLASH` を返し、測定タスクが印を立てる | 次の接続で、アプリに記録の異常として知らせる | SR-F03 |
| ソフトウェアが止まる | ウォッチドッグ（決めた時間のうちに合図が無ければリセットする仕組み）が働く | リセットして起動し直し、記録用フラッシュから書き込みの位置・設定・主のモードを読み直して、止まる前の主のモードの動作に戻る | 記録が 1 件抜けることがある | SR-R03・SR-R05 |

見つけ方が決まっていない異常は、処置のしようがない。処置と見え方が決まっていないと、たとえばセンサが応答しないとき、記録を飛ばすのか、0 を書くのかが実装する人ごとに変わり、アプリが正しく表示できない。壊れ方ごとに、止める機能と続ける機能を決める考え方は [電源と周辺の制御シリーズ 15 章 5 節](../periph/15_異常に備える.md#故障ごとに-止めるものと続けるものを決める) にある。
