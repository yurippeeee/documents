Chapter 13

バイナリプロトコルと設定 — 更新レート・衛星系・省電力

この章で扱う問い. 12 章では、モジュールが出す文字の行（NMEA 0183 の文）を読んだ。多くのモジュールは、値を 2 進のまま並べた形式も持ち、マイコンから命令を受けて、出す文・1 秒に位置を出す回数・受ける衛星系・電流の使い方を変える。この章では、その形式のメッセージを C で組んで解き、設定を送って確かめる。

この章では次の 3 つの問いに答える。

  1. 値を 2 進のまま送る形式は、どんな欄でできていて、受ける側はメッセージの区切りと誤りにどう気づくのか。文字の文と同じ線に混ざっても、なぜ分けられるのか。
  2. 1 秒に位置を出す回数・出す文・通信の速さ・受ける衛星系・動きの見込みを変えると、位置の遅れ・線の負荷・位置のふらつきはどう変わるのか。
  3. 受信機を眠らせると、平均の電流・電池の持ち時間・次の位置が出るまでの時間はどう変わるのか。送った設定が受け入れられ、電源を入れ直しても残ることを、どう確かめるのか。

答えの道具は、同期のバイトと長さの欄で区切る状態機械、バイトの和とその途中の値の和を並べるチェックサム、線が 1 秒に送れるバイトの数と出すバイトの数の比（10 章 4 節）、そして 1 周期の電荷を周期で割った平均の電流である。

この章で学ぶこと. 節ごとに、新しく出てくる用語と、読み終えたときに説明できるようになることを並べる。全部を説明できれば、この章は理解できている（まとめは 7 節）。

1. バイナリの形式 — 見出し・長さ・チェックサム

値を 2 進のまま送る

10 章 4 節の例のモジュール（以下、モジュール）の UART には、文を出す線（TXD）のほかに、マイコンから受ける線（RXD）がある。モジュールは、この線で命令を受けて、出す文や、位置を出す回数などを変える。多くのモジュールは、その命令と、出す値の一部を、文字ではなく 2 進のバイトで送る形式を持っている。値を文字に直さず、2 進の数のまま決まった並びに置いて送るメッセージの形と、そのやりとりの決まりをバイナリプロトコルという。決まりはモジュールの作り手ごとに違う。この章では、広く使われている形式の例として UBX（あるモジュールの作り手が決めた形式）をとり、公開されている資料で確かめられる形だけを使う（細部は、使う製品の資料で確かめる）。同じ値を、12 章の文とバイナリの形で比べる。

バイナリの形では、12 章 5 節で文字から求めた整数を、そのまま送る。文字を数に直す手間も、桁の数の違い（12 章 6 節）も無い。代わりに、人はそのまま読めず、どのバイトが何の値かは、形式の資料を見なければ分からない。

フレームの欄

1 つのメッセージを、始まりの印・長さ・誤りを見つけるための値などで包んだバイトの並びをフレームという（組み込み通信シリーズ 3 章 1 節。2 章 5 節の、航法メッセージの 30 s のフレームとは別のものである）。例の形式のフレームを、次の図に示す。

フレームは、決まった 2 バイト（同期）で始まる。メッセージの大きな分類を表す 1 バイト（クラス）と、その中の種類を表す 1 バイト（ID）を、まとめてクラスと ID という。12 章の文の種類（GGA など）に当たり、例の形式では、航法の結果のクラスが 0x01、命令への応答のクラスが 0x05、設定のクラスが 0x06 である。長さの欄は本体（メッセージの値を並べた部分）のバイトの数で、同期・クラス・ID・長さ・チェックサムは数えない。

2 バイト以上の数を、下位のバイトから先に並べる決まりをリトルエンディアンという（組み込み通信シリーズ 3 章 6 節）。例の形式では、長さの欄も本体の数も、リトルエンディアンで並べる。

フレッチャーのチェックサム

例の形式のチェックサムは 2 バイトで、クラスから本体の終わりまでのバイトから計算する（同期の 2 バイトは入れない）。12 章 3 節と同じく、計算に入るバイトを順に \(a_1, a_2, \ldots, a_n\) と書き、頭から \(k\) 個の和を \(A_k = a_1 + a_2 + \cdots + a_k\) と書く。2 つのバイトは

\[ \mathrm{CK_A} = A_n \bmod 256, \qquad \mathrm{CK_B} = (A_1 + A_2 + \cdots + A_n) \bmod 256 \]

である（\(\bmod 256\) は 256 で割った余りで、8 bit の足し算をあふれたまま続けた値に等しい）。1 つ目はバイトの和（組み込み通信シリーズ 3 章 5 節のチェックサム）、2 つ目は、バイトを 1 つ足すたびの 1 つ目の和を、さらに足した値である。このように、バイトの和と、その途中の値の和の 2 つを並べたチェックサムをフレッチャーのチェックサムという（考えた人の名前による）。

2 つ目の和が何をしているかを確かめる。

方針: \(\mathrm{CK_B}\) の中で、1 つのバイト \(a_i\) が何回足されるかを数え、バイトの位置で重みが変わることを示す。そのうえで、2 つのバイトが入れ替わったときの変化を求める。

導出: \(a_i\) は、\(k \ge i\) の途中の和 \(A_k\) のすべてに入る。そのような \(k\) は \(i\) から \(n\) までの \(n - i + 1\) 通りなので、

\[ \mathrm{CK_B} = \sum_{i=1}^{n}(n - i + 1)\,a_i \bmod 256 \]

である。\(p\) 番目と \(q\) 番目（\(p < q\)）のバイトが入れ替わると、和である \(\mathrm{CK_A}\) は変わらない。\(\mathrm{CK_B}\) の 2 つの項は、\((n - p + 1)a_p + (n - q + 1)a_q\) から \((n - p + 1)a_q + (n - q + 1)a_p\) に変わるので、変化は

\[ (n - p + 1)(a_q - a_p) + (n - q + 1)(a_p - a_q) = (q - p)(a_q - a_p) \]

である ∎

したがって、入れ替わった 2 つのバイトが違う値で、\((q - p)(a_q - a_p)\) が 256 の倍数でなければ、\(\mathrm{CK_B}\) が変わって入れ替わりに気づく。図の (b) の、200 を上位のバイトから並べてしまった誤り（C8 00 → 00 C8）では、変化は 1 × (0 − 200) で、12 章の排他的論理和とバイトの和が見逃す誤りに、\(\mathrm{CK_B}\) が気づく。1 つのバイトだけが化けたときは、バイトの和と同じく \(\mathrm{CK_A}\) が必ず変わる。

2. フレームを組む・解く — C のコード

フレームを組む

送る側は、1 節の欄を並べ、クラスから本体の終わりまでのチェックサムを後ろに付ける（コードは C99）。

#define BIN_SYNC1  0xB5                      /* 同期の 1 バイト目（例の形式） */
#define BIN_SYNC2  0x62                      /* 同期の 2 バイト目 */
#define BIN_MAX    256                       /* 受ける本体の長さの上限（この章で決めた値） */

/* フレッチャーのチェックサム: p[0]〜p[n−1]（クラスから本体の終わりまで）の 2 つの和 */
static void bin_sum(const uint8_t *p, int n, uint8_t ck[2])
{
    uint8_t a = 0, b = 0;                    /* 8 bit の足し算（あふれた分は捨てる） */
    for (int i = 0; i < n; i++) {
        a += p[i];                           /* CK_A: バイトの和 */
        b += a;                              /* CK_B: CK_A の途中の値の和 */
    }
    ck[0] = a;
    ck[1] = b;
}

/* フレームを組む。out には len + 8 バイトの場所が要る。組んだバイトの数を返す */
int bin_build(uint8_t *out, uint8_t cls, uint8_t id, const uint8_t *body, uint16_t len)
{
    out[0] = BIN_SYNC1;
    out[1] = BIN_SYNC2;
    out[2] = cls;
    out[3] = id;
    out[4] = (uint8_t)(len & 0xFF);          /* 長さはリトルエンディアン: 下位のバイトが先 */
    out[5] = (uint8_t)(len >> 8);
    if (len > 0) memcpy(&out[6], body, len);
    bin_sum(&out[2], 4 + len, &out[6 + len]);    /* クラスから本体の終わりまで */
    return 8 + len;
}

文とフレームが同じ線に混ざる

多くのモジュールは、同じ UART に、12 章の文とこの章のフレームを混ぜて出せる（どちらを出すかは設定で選ぶ。3 節）。次の図は、文の後に、命令を受け入れたことを知らせる応答のフレーム（ACK。6 節）が続く例である。

文は、$ からチェックサムまでが 0x20〜0x7E の文字で、最後が CR と LF なので（12 章 1 節）、0xB5 は文の中に現れない。一方、フレームの本体にはどの値も入るので、$（0x24）も同期の B5 62 も現れうる。したがって、受ける側は、フレームの外で 0xB5 を受けたらフレームの頭とし、ほかのバイトは 12 章の状態機械に渡す。フレームの途中のバイトは、何であっても本体として受け、どこで終わるかは長さの欄で決める（組み込み通信シリーズ 3 章 4 節の、長さを先に送る方式）。

1 バイトずつ読む状態機械 — 誤ったら 2 バイト目から探し直す

12 章の状態機械では、$ がどこでも新しい文の頭だった。フレームの途中の B5 は本体の値でありうるので、頭とはみなせない。そのため、長さの欄が化けたり、フレームが途中で切れたりすると、後に続くフレームや文を本体として飲み込み、チェックサムが合わずに捨てるときに、それらも一緒に失う（組み込み通信シリーズ 3 章 4 節）。そこで、同期の 1 バイト目から受けたバイトを全部とっておき、誤りでフレームを捨てたときは、そのフレームの 2 バイト目から受け直す（同じ節の、探し直す位置を戻す対策）。

状態と結果の型を次に示す。状態の名前は、12 章の ST_ と同じプログラムに入れても重ならないように、BS_ で始めた。

enum bin_state  { BS_WAIT, BS_SYNC2, BS_HEAD, BS_BODY };
enum bin_result { BIN_NONE,                  /* フレームの途中（まだ何も起きていない） */
                  BIN_OK,                    /* フレームが 1 つそろい、チェックサムが合った */
                  BIN_ERR_SUM,               /* チェックサムが合わない */
                  BIN_ERR_LONG,              /* 長さの欄が上限を超える */
                  BIN_ERR_SYNC };            /* 同期の 2 バイト目が違う */

struct bin_rx {
    enum bin_state st;                       /* いまの状態 */
    uint8_t raw[BIN_MAX + 8];                /* 同期の 1 バイト目から受けたバイト */
    int n;                                   /* raw にためたバイトの数 */
    uint16_t len;                            /* 長さの欄の値（本体のバイトの数） */
};

状態機械は、1 バイトを受け取って結果を返す関数 bin_feed である。

enum bin_result bin_feed(struct bin_rx *r, uint8_t c)
{
    uint8_t ck[2];
    if (r->st == BS_WAIT) {                  /* 同期の 1 バイト目を待つ間は読み捨てる */
        if (c == BIN_SYNC1) { r->raw[0] = c; r->n = 1; r->st = BS_SYNC2; }
        return BIN_NONE;
    }
    r->raw[r->n++] = c;                      /* 同期の 1 バイト目から、全部ためる */
    switch (r->st) {
    case BS_SYNC2:                           /* 同期の 2 バイト目 */
        if (c != BIN_SYNC2) break;
        r->st = BS_HEAD;
        return BIN_NONE;
    case BS_HEAD:                            /* クラス・ID・長さの 4 バイト */
        if (r->n < 6) return BIN_NONE;
        r->len = (uint16_t)(r->raw[4] | (r->raw[5] << 8));
        if (r->len > BIN_MAX) { r->st = BS_WAIT; return BIN_ERR_LONG; }
        r->st = BS_BODY;
        return BIN_NONE;
    case BS_BODY:                            /* 本体と、チェックサムの 2 バイト */
        if (r->n < 8 + r->len) return BIN_NONE;
        r->st = BS_WAIT;
        bin_sum(&r->raw[2], 4 + r->len, ck);
        return (ck[0] == r->raw[6 + r->len] && ck[1] == r->raw[7 + r->len]) ? BIN_OK : BIN_ERR_SUM;
    default:
        break;
    }
    r->st = BS_WAIT;                         /* 同期の 2 バイト目が違った */
    return BIN_ERR_SYNC;
}

主のループから呼ぶ受信の関数は、12 章 4 節の gnss_poll を置き換えて、文とフレームを分け、捨てたフレームの 2 バイト目からを、まだ読んでいないバイトの前に戻す。nmea_char は、12 章の gnss_poll の繰り返しの中身（1 文字を nmea_feed に渡して結果を使う所）を関数にしたものである。

int  uart_read(void);                        /* 仮に置く関数: 受けたバイト（0〜255）を返す。無ければ −1（12 章と同じ） */
void nmea_char(char c);                      /* 12 章 4 節の gnss_poll の中身（1 文字を nmea_feed に渡して使う） */
void use_frame(const struct bin_rx *r);      /* 仮に置く関数: そろったフレームを使う側へ渡す */

static struct bin_rx bin;                    /* 初めは BS_WAIT（= 0） */
static uint8_t back[BIN_MAX + 8];            /* 探し直すために戻したバイト */
static int nback, iback;
uint32_t n_bad_bin;                          /* 捨てたフレームの数 */

void gnss_poll(void)                         /* 主のループから何度も呼ぶ */
{
    int c;
    while ((c = (iback < nback) ? back[iback++] : uart_read()) >= 0) {
        if (bin.st == BS_WAIT && c != BIN_SYNC1) {   /* フレームの外で、同期のバイトでもない */
            nmea_char((char)c);                       /* 文字の文は 12 章の状態機械へ */
            continue;
        }
        enum bin_result res = bin_feed(&bin, (uint8_t)c);
        if (res == BIN_OK) {
            use_frame(&bin);
        } else if (res != BIN_NONE) {                 /* 捨てたフレームの 2 バイト目からを、 */
            int rest = nback - iback;                 /* まだ読んでいない戻したバイトの前に置く */
            memmove(&back[bin.n - 1], &back[iback], (size_t)rest);
            memcpy(back, &bin.raw[1], (size_t)(bin.n - 1));
            nback = bin.n - 1 + rest;
            iback = 0;
            n_bad_bin++;
        }
    }
}

まだ読んでいない戻したバイトが残るのは、捨てたフレームが戻したバイトの中で始まったときだけなので、戻すバイトは合わせても raw の大きさを超えず、back は raw と同じ大きさで足りる。長さの上限 BIN_MAX は、ためる配列の大きさを決めるほか、文の文字を長さの欄と取り違えたとき（表示できる文字 2 つは 0x2020 = 8224 以上になる）に、すぐ気づくのにも使う。

確かめる

ホストの gcc（C99。メモリの範囲の外の読み書きと未定義の動作を見つける検査を付けた）で、1 節の例のフレームと、壊したフレームを、12 章の nmea_feed と一緒に流して確かめた。

組んだフレームは、Python で計算したバイトと一致した。でたらめに作ったフレームと文の列 3000 本に、書き換え・抜け・入り込みの誤りを 0〜3 個ずつ入れた試験では、誤りに触れていない 14 734 のメッセージのうち、2 バイト目から探し直さないと 318 を失い、探し直すと 1 つも失わなかった（Python に移し替えたコードの結果と、全部の列で一致した）。ただし、長さの欄が化けたフレームは、その長さのバイトが届くまで待つので、出力が途切れている間は、その後ろのメッセージが遅れて渡される（待つ時間に上限を置く対策は組み込み通信シリーズ 3 章 4 節）。

下の図で、送るメッセージと値を選んでフレームを組み、チェックサムの計算を 1 バイトずつ進め、誤りを入れたときに受ける側がどこで気づくかを確かめられる。

3. 設定 — 出力・更新レート・通信速度

設定のメッセージ — 例の形と、版による違い

設定も、2 節のフレームで送る。例の形式の古い版では、設定の項目のまとまりごとにメッセージがあり（クラス 0x06）、本体の並びがメッセージごとに決まっている。1 節の図のフレームは、その 1 つの、位置を求める間隔の設定である。新しい版では、項目ごとに決めた番号（鍵）と値の組を並べる 1 つのメッセージで設定する形に変わった。どのメッセージのどのバイトに何を書くかは、製品と版で違うので、この章の値は例として使う。

出す文を選び、更新レートを決める

受信機が 1 秒に何回、位置を求めて出すかを更新レートといい、\(f_\mathrm{u}\) [Hz] と書く。その逆数 \(T_\mathrm{u} = 1/f_\mathrm{u}\) を、更新の間隔という。1 回に出すバイトの数を \(N_\mathrm{B}\) とすると、データ量は \(D = N_\mathrm{B}f_\mathrm{u}\)、8N1 での負荷率は \(10N_\mathrm{B}f_\mathrm{u}/R_\mathrm{B}\) である（10 章 4 節。\(R_\mathrm{B}\) はボーレート）。出す文とフレームは、種類ごとに、毎回出す・何回かに 1 回出す・出さないを設定で選ぶ。

したがって、更新レートを上げるときは、負荷率が 100 % を超えないように、ボーレートを上げるか、出す文を減らすか、バイナリのフレームに替える。1PPS（10 章 5 節）の周期・幅・どちらの縁を秒の頭にするかも、同じように設定のメッセージで変える製品が多い（使い方は 14 章）。

位置の遅れ

受信機が位置を求めた時刻から、その位置を書いた文（またはフレーム）をマイコンが受け終わるまでの時間を、位置の遅れといい、\(t_\mathrm{d}\) と書く。遅れは、受信機が位置を計算して出し始めるまでの時間 \(t_\mathrm{c}\)（例の値 0.12 s。10 章 5 節の図と同じ）と、その文の最後のバイトまでを送る時間の和である。

負荷率が 100 % を超えると、遅れが回ごとに増えていく。その増え方を求める。

方針: 線が休まず送り続けるとき、\(m\) 回目（0 回目から数える）の出力を送り終える時刻を、それまでに送ったバイトの数から求め、\(m\) 回目の位置を求めた時刻 \(mT_\mathrm{u}\) を引く。

導出: 1 回分を送る時間は \(t_\mathrm{tx} = 10N_\mathrm{B}/R_\mathrm{B}\) で、負荷率 \(10N_\mathrm{B}f_\mathrm{u}/R_\mathrm{B}\) は \(t_\mathrm{tx}/T_\mathrm{u}\) に等しい。負荷率が 1 以下なら \(t_\mathrm{tx} \le T_\mathrm{u}\) で、どの回も次の回の出力が始まる前に送り終わるので、遅れは毎回同じである。負荷率が 1 を超えると、どの回の出力も、送り終わる前に次の回の出力ができるので、線は 0 回目を送り始めた時刻 \(t_\mathrm{c}\) から休まず送り続け、\(m\) 回目は、0〜\(m\) 回目の \(m + 1\) 回分を送り終えた時刻 \(t_\mathrm{c} + (m + 1)t_\mathrm{tx}\) に送り終わる。遅れは

\[ t_\mathrm{c} + (m + 1)t_\mathrm{tx} - mT_\mathrm{u} = t_\mathrm{c} + t_\mathrm{tx} + m\,(t_\mathrm{tx} - T_\mathrm{u}) \]

で、1 回ごとに \(t_\mathrm{tx} - T_\mathrm{u}\) ずつ増える。1 秒には \(f_\mathrm{u}\) 回あるので、1 秒あたりの増え方は \(f_\mathrm{u}(t_\mathrm{tx} - T_\mathrm{u}) = t_\mathrm{tx}/T_\mathrm{u} - 1\)、つまり（負荷率 − 1）秒である ∎

1 回分の中のどの文で測っても、増え方は同じである。例の 11 文を 9600 bit/s・2 Hz で出すと（負荷率 130 %）、遅れは 1 秒に 0.30 s ずつ増える。実際には、モジュールの中の送るためのバッファがあふれた所で、文が捨てられる（製品による）。

使う側は、位置を受けた時刻とは関係なく、そのとき持っている最新の位置を使う。使う位置の古さは、遅れから遅れ + \(T_\mathrm{u}\) までの間を動き、平均すると遅れ + \(T_\mathrm{u}/2\) である。動いている機器では、その間に進んだ距離だけ後ろの位置を使うことになる。位置を求めた時刻（文の時刻の欄）と速度が分かっているので、遅れの分だけ先へ進めて補うこともできる（19 章）。

受信機は、毎回の測った値だけから位置を出すのではなく、前の位置と速度から今の位置を見込み、新しく測った値とならして出す（ならすためのフィルタの中身は 19 章）。どれだけならすかは、機器がどれだけ急に速さと向きを変えうると見込むかで決まる。この見込みを、止まっている・歩く・車・空のような用途の名前で選ぶ設定を、動きのモデル（ダイナミックモデル）という。

5. 省電力 — 連続・周期・必要なときだけ

3 つの方式

位置を毎秒は要らない機器では、受信機を止めておく時間を作って、平均の電流を下げられる。受信機の一部か全部を止める時間を作り、平均の電流を下げる動作の仕方を省電力モードという（設定や命令で選ぶ。呼び方と中身は製品による）。この章では次の 3 つに分けて考え、電流は 10 章の例の値（捕捉中 35 mA・追尾中 25 mA・バックアップ電源だけで 15 µA）を使う。

  • 連続: 追尾を続け、更新レートで位置を出す。
  • 周期的に起きる: 決めた間隔 \(T_\mathrm{u}\) ごとに起きて捕捉し、位置が出たら眠る。
  • 必要なときだけ: マイコンが要るときだけ起こし（起こす入力。10 章 6 節）、それ以外は主の電源を切って、バックアップ電源だけで保つ。

眠らせる・止めるときは、端子のリセットではなく命令で止める（10 章 6 節。例の形式には、受信を止め、保つ情報を書き終えてから止まる命令がある。版による）。1〜10 s ほどの短い周期では、受信機の一部を動かしたまま眠り、起きるたびの捕捉を軽くする方式を持つ製品もある。

平均の電流と電池の持ち時間

1 周期の電流の形から、平均の電流と電池の持ち時間を求める。

方針: 1 周期 \(T_\mathrm{u}\) を、位置が出るまで（捕捉中の電流）・位置が出た後に追尾を続ける間（追尾中の電流）・眠っている間（バックアップの電流）に分け、各区間の電荷（電流 × 時間）を足して周期で割る。次に、エフェメリスを受け直す回の分を足す。

導出: 起きてから位置が出るまでの時間（TTFF）を \(t_\mathrm{acq}\)、その後に追尾を続ける時間を \(t_\mathrm{trk}\)、それぞれの電流を \(I_\mathrm{acq}\)・\(I_\mathrm{trk}\)、眠っている間の電流を \(I_\mathrm{bk}\) とする。1 周期の電荷は

\[ Q_\mathrm{c} = I_\mathrm{acq}t_\mathrm{acq} + I_\mathrm{trk}t_\mathrm{trk} + I_\mathrm{bk}\,(T_\mathrm{u} - t_\mathrm{acq} - t_\mathrm{trk}) \]

で、毎回同じなら、平均の電流は \(I_\mathrm{avg} = Q_\mathrm{c}/T_\mathrm{u}\) である。\(t_\mathrm{acq}\) は、有効なエフェメリスを持っていればホットスタートの \(t_\mathrm{hot}\)、持っていなければウォームスタートの \(t_\mathrm{warm}\) である（5 章 5 節）。エフェメリスは受けてから \(t_\mathrm{eph}\)（2〜4 時間。代表値。10 章 3 節）で使えなくなり、ホットスタートで短く起きるだけでは新しいものを受けない（受けるには 18〜36 s かかる）。そこで、\(T_\mathrm{u} < t_\mathrm{eph}\) なら、\(t_\mathrm{eph}\) の間の \(t_\mathrm{eph}/T_\mathrm{u}\) 回のうち 1 回はウォームスタートで、その回だけ電荷が \(I_\mathrm{acq}(t_\mathrm{warm} - t_\mathrm{hot})\) 多い。\(t_\mathrm{eph}\) の間の電荷を \(t_\mathrm{eph}\) で割ると

\[ I_\mathrm{avg} = \frac{Q_\mathrm{c}}{T_\mathrm{u}} + \frac{I_\mathrm{acq}\,(t_\mathrm{warm} - t_\mathrm{hot})}{t_\mathrm{eph}} \qquad (t_\mathrm{acq} = t_\mathrm{hot}) \]

である（ウォームスタートの回に眠る時間が短くなる分は小さいので無視した）。\(T_\mathrm{u} \ge t_\mathrm{eph}\) なら、毎回ウォームスタートで、\(t_\mathrm{acq} = t_\mathrm{warm}\) とした \(Q_\mathrm{c}/T_\mathrm{u}\) である。容量 \(Q_\mathrm{b}\) の電池からは、1 秒に \(I_\mathrm{avg}\) ずつ電荷が出ていくので、持ち時間は \(t_\mathrm{bat} = Q_\mathrm{b}/I_\mathrm{avg}\) である ∎

例の値（\(t_\mathrm{hot}\) = 2 s・\(t_\mathrm{warm}\) = 30 s・\(t_\mathrm{eph}\) = 2 時間・\(t_\mathrm{trk}\) = 0。電池 2000 mAh は表示の容量で計算した。取り出せる電荷は電流と温度で変わる。電源と周辺の制御シリーズ 3 章 3 節）では、連続の 25 mA で 80 時間、60 s ごとに起きると 1.32 mA で 63 日である。周期を延ばしても、\(t_\mathrm{eph}\) より短い間は、エフェメリスを受け直す分の 0.14 mA より下がらない。\(t_\mathrm{eph}\) より長く眠ると、平均の電流は下がり続けるが、起きるたびに位置が出るまで 30 s 待つ。A-GNSS（5 章 6 節）でエフェメリスを外から受け取れば、受け直す分は要らない（通信の電力は別にかかる）。周期が 2.8 s より短いと、起きるたびの捕捉の電荷のために、連続より電流が大きい（電源と周辺の制御シリーズ 7 章 5 節の損益分岐の眠りの長さと同じ考え方）。位置が出た直後の位置は、追尾を続けた後より誤差が大きいことが多い（受信機による）ので、精度が要るときは \(t_\mathrm{trk}\) を延ばし、その分の電荷を払う。

下の図で、方式・周期・位置が出た後に追尾を続ける時間・エフェメリスの有効な時間・電池の容量を変えて、平均の電流・電池の持ち時間・起きるたびの TTFF を確かめられる。

6. 設定を確かめて保存する

ACK と NAK — 応答を待ち、来なければ送り直す

設定の命令を受けたモジュールは、受け入れたかどうかを応答のメッセージで返す（例の形式では、設定のクラスの命令に返す）。命令を受け入れたことを知らせる応答を ACK（acknowledge）、受け入れなかった（値が範囲の外にある、知らない命令である、など）ことを知らせる応答を NAK（not acknowledge）という。例の形式では、クラス 0x05 の ID 0x01 が ACK、0x00 が NAK で、本体の 2 バイトに、応えた命令のクラスと ID を入れる。命令かその応答が化けて捨てられると、応答は来ない。そこで、待つ時間を決め、過ぎても来なければ同じフレームを送り直し、決めた回数で諦める（組み込み通信シリーズ 5 章 4 節の、1 つずつ送って応答を待つ方式）。

設定の命令は、同じものを 2 回受けても結果が同じなので、送り直してよい（組み込み通信シリーズ 5 章 4 節のような、重なった受信を見分ける番号は要らない）。リセットの命令のように、応答を返さない命令もある。命令の型と、仮に置く関数を次に示す。

#define ACK_CLASS    0x05                    /* 応答のクラス（例の形式） */
#define ACK_ID_ACK   0x01                    /* 受け入れた */
#define ACK_ID_NAK   0x00                    /* 受け入れなかった */
#define CMD_WAIT_MS  1000                    /* 応答を待つ時間 [ms]（例の値） */
#define CMD_TRIES    3                       /* 送る回数の上限（例の値） */

enum cmd_state { CMD_IDLE, CMD_WAIT, CMD_ACK, CMD_NAK, CMD_FAIL };
struct cmd {
    enum cmd_state st;
    uint8_t frame[BIN_MAX + 8];              /* 送ったフレーム（送り直しに使う） */
    int nframe, tries;                       /* フレームのバイトの数・送った回数 */
    uint32_t t_sent;                         /* 最後に送った時刻 [ms] */
};

void uart_write(const uint8_t *p, int n);    /* 仮に置く関数: n バイトを送る */
uint32_t now_ms(void);                       /* 仮に置く関数: 1 ms ごとに 1 増える時刻（一周してよい） */

命令を送る・応答を受ける・時間を見る、の 3 つの関数を示す。

void cmd_send(struct cmd *q, uint8_t cls, uint8_t id, const uint8_t *body, uint16_t len)
{
    q->nframe = bin_build(q->frame, cls, id, body, len);
    uart_write(q->frame, q->nframe);
    q->t_sent = now_ms();
    q->tries = 1;
    q->st = CMD_WAIT;
}

void cmd_on_frame(struct cmd *q, const struct bin_rx *r)    /* use_frame から、フレームごとに呼ぶ */
{
    if (q->st != CMD_WAIT || r->raw[2] != ACK_CLASS || r->len != 2) return;
    if (r->raw[6] != q->frame[2] || r->raw[7] != q->frame[3]) return;   /* ほかの命令への応答 */
    if (r->raw[3] == ACK_ID_ACK) q->st = CMD_ACK;
    else if (r->raw[3] == ACK_ID_NAK) q->st = CMD_NAK;
}

void cmd_tick(struct cmd *q)                 /* 主のループから何度も呼ぶ */
{
    if (q->st != CMD_WAIT || (uint32_t)(now_ms() - q->t_sent) < CMD_WAIT_MS) return;
    if (q->tries >= CMD_TRIES) { q->st = CMD_FAIL; return; }   /* あきらめて知らせる */
    uart_write(q->frame, q->nframe);         /* 応答が無いので、同じフレームを送り直す */
    q->t_sent = now_ms();
    q->tries++;
}

時刻の差を uint32_t で計算するのは、時刻が一周しても待った時間を正しく求めるためである（組み込み通信シリーズ 5 章 3 節）。ホストで、30 ms 後に応答する模擬のモジュールを相手に、図の 4 つの場合と、ほかの命令への ACK が先に届く場合、時刻が途中で一周する場合を確かめた。

読み出して比べる

ACK は、命令を受け入れたことしか表さない。値が意図どおりかは、同じクラスと ID で本体を空にしたフレーム（例の形式の、読み出しの命令）を送り、返ってきた本体を、送った本体と比べて確かめる（図の (a)）。

文とフレームを分ける文は 0x20〜0x7E の文字と CR・LF だけなので、フレームの外の 0xB5 はフレームの頭、ほかは 12 章の状態機械へ
更新レート1 秒に位置を求めて出す回数 \(f_\mathrm{u}\)。負荷率 \(10N_\mathrm{B}f_\mathrm{u}/R_\mathrm{B}\) が 100 % を超えないように、ボーレート・出す文・バイナリを選ぶ
位置の遅れ位置を求めた時刻から、その文を受け終わるまで。\(t_\mathrm{c}\) + 送る時間（例 9600 bit/s で GGA まで 0.20 s）。負荷率が 100 % を超えると 1 秒に（負荷率 − 1）秒ずつ増える。使う位置は平均で遅れ + \(T_\mathrm{u}/2\) だけ古い
通信の速さを変える今の速さで命令 → マイコンも変える → 新しい速さで正しい文が届くことで確かめる。届かなければ速さを順に試す
衛星系増やすと DOP が下がるが、文が長くなり電流も増えやすい。組み合わせは RF フロントエンドの周波数の幅とチャネルの数で限られる
動きのモデル急な動きをどれだけ見込んで位置をならすかを、用途の名前で選ぶ設定。小さく見込むとふらつかないが遅れ、大きく見込むと追いつくがふらつく
省電力モード受信機を止める時間を作って平均の電流を下げる動作。連続・周期的に起きる・必要なときだけ
平均の電流\(I_\mathrm{avg} = Q_\mathrm{c}/T_\mathrm{u} + I_\mathrm{acq}(t_\mathrm{warm} - t_\mathrm{hot})/t_\mathrm{eph}\)、\(t_\mathrm{bat} = Q_\mathrm{b}/I_\mathrm{avg}\)。例で連続 25 mA（80 時間）、60 s ごと 1.32 mA（63 日）、下げ止まり 0.14 mA、損益分岐 2.8 s
ACK・NAK命令を受け入れた／受け入れなかったことを知らせる応答（例: 05 01・05 00、本体は命令のクラスと ID）。待つ時間を過ぎたら送り直し、決めた回数で諦める
確かめて保存する本体を空にして読み出し、送った値と比べる。RAM・バックアップ電源のメモリ・フラッシュのどこに入るかで残り方が違う。起動のたびに読み出して比べ、違えば送り直す
